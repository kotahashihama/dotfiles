# フックが何を強制しているか

`home/.claude/settings.json` に登録したフックの一覧。**実体は `home/.claude/hooks/`。**

**ここに載るのは「形だけで判定できるもの」だけ。** フックはコマンドの文字列とツールの入出力しか見られず、
**会話の状態（明示指示があったか）は見えない**。だから「コミットは指示があるときだけ」のような規約は
フックにできず、ルールの担当のまま残る。

## 一覧

| イベント | 対象 | 何をするか |
| --- | --- | --- |
| `PreToolUse` | `Bash` | **弾く**。下表の 6 種 |
| `PostToolUse` | `Bash` | **警告する**。成功として返ったが出力に失敗の兆候がある |
| `PostToolUse` | `Bash` `Write` `Edit` | **促す**。グローバル資産を編集したら棚卸しへ |
| `SessionStart` | 起動・再開 | **伝える**。dotfiles に未コミットの資産がある（dotfiles 自身のセッションでは黙る） |
| `Stop` | 全部 | **止めさせない**。「よければ着手します」で終えようとしたとき |

## 弾かれるもの

| 形 | なぜ | 代わりに |
| --- | --- | --- |
| 既存ファイルへの `>` | noclobber で黙って失敗し、ループでは前の周回の内容が残る | `>` の代わりに強制上書きの記法 |
| `git add -A` / `git add .` | 設定系ファイルが意識せず混ざる | ファイルを名指し |
| force push | 履歴を書き換える | 人が実行する |
| 環境ファイルを丸ごと読む / 秘匿値らしい変数を出力する | 値が会話に残り、取り消せない | キー名だけ抜く / 存在確認だけする |
| 秘匿値の置き場を読む（シェル履歴・鍵の置き場） | 実際にここから列を抜いて漏れた | `ls` / `test -f` |
| PR の承認・変更要求 | 承認するのはユーザー本人 | コメントとして投稿し、見立ては会話で渡す |

**引用符の中身・ヒアドキュメントの本文・破棄先へのリダイレクトは対象外。** 誤検知で自分の作業が止まるため。

## 弾かれないもの（意図的）

| 操作 | なぜフックにしないか |
| --- | --- |
| コミット / push | 「明示指示があったか」は**会話の状態**で、形からは判定できない |
| ready 化 / レビュー再依頼 | 同上 |
| PR のマージ | 同上 |

これらは `no_auto_commit.md` / `no_auto_ready_pr.md` / `decide_or_ask.md` の担当。

## 直すとき

**実物の入力で 1 回通してから確定する。** 自分で組み立てたペイロードは想定どおりの形なので、
**想定が違っていても全ケース通る**（`verify_before_asserting.md`）。実際に 2 本のフックが、
テストは緑のまま一度も効いていなかった。

- `PostToolUse` の入力フィールド名は、公式ドキュメントの記載と実物が違う。**実物を控えて確かめる**
- Claude に届けるなら `hookSpecificOutput.additionalContext`。ユーザー向けの表示欄とは別
- 作業ツリーは**全セッションで共有**される。状態だけで判定すると他セッションの編集を拾う
- **除去処理は検査ごとに違う。** 片方にだけ掛けると、もう片方が素通りする（実際に踏んだ）
