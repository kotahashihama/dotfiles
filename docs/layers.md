# 3 つの層

このリポジトリが扱うファイルは 3 つの層に分かれる。**どの層に置くかで、公開範囲と復元方法が決まる。**

| 層 | 置き場 | git | zip | 新規マシンでの復元 |
| --- | --- | --- | --- | --- |
| **public** | `home/` | 追跡する | 含めない | `git clone` で入る |
| **private** | `private/` | 追跡しない | 含める | zip を展開して入る |
| **secret** | `~/.secrets/env` | 追跡しない | **含めない** | パスワードマネージャから手で入れる |

リポジトリは GitHub 上で public。**`home/` に置いたものは全世界から読める。**

## 層の選び方

| 問い | 答え | 層 |
| --- | --- | --- |
| 他人に見られて困るか | 困らない | **public** |
| 困るが、機械的に復元したいか | したい | **private** |
| 値そのものが認証情報か | そう | **secret** |

判断に迷ったら **private に倒す**。public から private へ移すのは、一度公開した事実を取り消せないぶん高くつく。

## そもそも管理しないもの

3 層のどれにも入れない。**マシンを乗り換えたら捨てる**もの。

| 種類 | 例 | 理由 |
| --- | --- | --- |
| 会話・実行の記録 | `~/.claude/projects/`、`~/.claude/history.jsonl`、`~/.zsh_history` | 秘匿値が混ざりうるうえ、新マシンで必要にならない |
| キャッシュ・状態 | `~/.claude/{cache,sessions,shell-snapshots}`、`~/.npm`、`~/.cache` | 再生成される。zip が膨らむだけ |
| 揮発性のもの | ソケット、ログ、ロックファイル | 複製しても意味がない |

会話ログ (`~/.claude/projects/<プロジェクト>/<session-id>.jsonl`) は、**Claude とのやり取りが全文そのまま残る**。作業中に画面へ出た値も含まれるため、秘匿値と同じ扱いにする。

`~/.claude` は `PARTIAL_DIRS` により**子要素を明示的にリンクしたものだけ**が管理対象になる。これらは何もしなければ管理外に留まる。

## 公開層への混入を止める

`scripts/git-hooks/pre-commit` が、ステージした公開層のファイルを検査してコミットを止める。`core.hooksPath` はリストア時に設定される。

| 検査 | パターンの置き場 | 理由 |
| --- | --- | --- |
| 認証情報 | フック本体（公開層） | `sk-ant-` 等は一般的な形式で、公開しても情報にならない |
| 非公開の固有名 | `private/.claude/deny-patterns.txt` | **パターン自体が社内固有名**なので公開層に持てない |

社内の呼称・リポジトリ名・GitHub ID が増えたら、パターンを足す。**グローバルの rules / skills は頻繁に書き換わり、複数のセッションが触る。** 規約だけでは取りこぼすので、git の境界で止める。

## secret を独立させる理由

秘匿値を private に置いても git には入らない。それでも分けるのは、**private が丸ごと zip になってクラウドへ上がる**ため。

- zip は暗号化されない。クラウドのアカウントが破られれば中身が読める
- MFA のシード値まで同じ zip に入ると、**2 要素目も一緒に破られる**
- クラウドの版履歴は消えない。**キーを再発行しても古い zip の版が残る**

値を `~/.secrets/env` へ切り出せば、zip に入るのは「その値を参照する設定」だけになる。

## 秘匿値の切り出し方

**設定ファイルに値を直書きせず、変数を参照する。**

```sh
# 悪い例: 値が設定ファイルに残る
alias ssml='curl -d "{\"api_key\": \"a107ad9e-...\"}" ...'

# 良い例: 値は ~/.secrets/env、ここは参照だけ
sesame() {
  curl -d "{\"api_key\": \"$SESAME_API_KEY\"}" ...
}
```

**エイリアスではなく関数にする**のが要点。エイリアスの本体は定義時に展開されるため、`alias ssml` の出力にキーが載る。関数なら実行時に読むので載らない。

変数を増やしたら `scripts/secrets.env.example` にも名前を足す。新規マシンで何を埋めればよいかが、ここだけを見て分かる状態を保つ。

## ~ へのリンクのされ方

`~` 側は実体を持たず、両方の層へリンクを張る。編集はリポジトリ内で完結し、`~` から集め直す工程が要らない。

```
~/.zshrc              -> home/.zshrc
~/.aws                -> private/.aws
~/.zsh_aliases        -> home/.zsh_aliases
~/.zsh_aliases_private -> private/.zsh_aliases_private
```

**両層で同じ名前を使わない。** `link_layer home` の後に `link_layer private` が走るので、名前が衝突すると private 側が public を上書きし、公開エイリアスが読めなくなる。

### 丸ごとリンクしないディレクトリ

`~/.claude` `~/.codex` `~/.cursor` は、管理対象と管理外（セッション・キャッシュ）が同居する。ディレクトリごとリンクすると管理外まで巻き込むため、**子要素を個別にリンクする**。

対象は `scripts/lib.sh` の `PARTIAL_DIRS` で定義する。この 3 つ以外の配下を管理下に置くときは、まずここへ足す。

`~/.claude` 配下は `home/.claude/` に置いたものが自動でリンクされるので、資産の種類が増えてもスクリプトの変更は要らない。

| 資産 | 管理 |
| --- | --- |
| `CLAUDE.md` `rules/` `skills/` `hooks/` `settings.json` `statusline-command.sh` | する |
| `agents/` `output-styles/` | する（現時点では空） |
| `commands/` | **しない**。[skills に統合済み](https://code.claude.com/docs/en/skills)で、新規はすべて `skills/` に置くため空のまま |
