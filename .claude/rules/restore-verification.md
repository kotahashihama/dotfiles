# リストアの変更は、偽の HOME で実測してから確定する

`scripts/restore_dotfiles.sh` は **何も無いマシンで走る**のが本番。既存マシンでは既にリンクや実体があるため、`ln` が黙って失敗して素通りし、**壊れる経路を通らない**。

## 期待する挙動

`scripts/` を変更したら、偽の HOME を作って backup → restore を通しで流す。手順は `/verify-restore` が持つ。

確認するのは次の 4 点。

| 観点 | 見るもの |
| --- | --- |
| **リポジトリが壊れていないか** | `home/` `private/` の実体が残っているか。自己参照リンクになっていないか |
| **リンク先が正しいか** | `~/.zsh_aliases` が public、`~/.zsh_aliases_private` が private を指しているか |
| **部分リンクが効いているか** | `~/.claude` 等が子要素ごとにリンクされているか |
| **秘匿値なしで起動するか** | `~/.secrets/env` が雛形のままでもシェルが立ち上がるか |

## 禁止する挙動

- 既存マシンで動いたことを根拠に「検証済み」とすること
- リンク先の実体を確認せずに `rm -rf` すること。**リンク越しに消すとリポジトリ本体が飛ぶ**
- 既存の実体を無条件に上書きすること。実体があれば退避してから張り直す

## なぜ

- 過去に、先頭ループが `.claude` を丸ごとリンクし、後段の `rm -rf` がリンク越しに**リポジトリの実体を削除する**不具合があった。既存マシンでは `ln` が File exists で失敗して素通りするため、実測するまで表に出なかった
- リストアが走るのは「移行当日、他に手段が無い状況」。**そこで壊れると復旧の足場ごと失う**
- 検証は 1 分で終わる。壊れたときの復旧はその何十倍もかかる
