# ファイルは public と private のどちらかに置く

**旧マシンから新マシンへ何で運ぶか**で 2 つに分かれる（git リポジトリ / 暗号化アーカイブ）。**このリポジトリは GitHub 上で public** なので、`home/` に置いたものは全世界から読める。

区分の定義・選び方・秘匿値の切り出し方は [`docs/placement.md`](../../docs/placement.md) を読むこと。

## 期待する挙動

- ファイルを追加・移動する前に、`docs/placement.md` の判断表でどちらの区分かを決める
- 迷ったら **private に倒す**。後から public へ上げるのは容易、逆は取り返しがつかない
- 秘匿値は設定ファイルへ直書きせず `~/.secrets/env`（実体は `private/.secrets/env`）へ置き、参照だけを残す
- 秘匿値の変数を増やしたら `scripts/secrets.env.example` にも名前を足す
- `~` へ取り込むときは `./scripts/adopt_dotfile.sh {public|private} <path>` を使う。手で `mv` + `ln` しない

## 禁止する挙動

- **`private/` を追跡対象にすること**。`.gitignore` の `/private/` を消す・例外を足すのは、内容を 1 件ずつ確認したうえでの意図的な公開に限る
- 秘匿値を含むファイルを `home/` へ置くこと
- `home/` と `private/` で **同じ名前を使うこと**。private 側が public を上書きし、公開設定が読めなくなる
- コミット前に公開区分の差分を確認せずに済ませること

## 検査は 2 段構え

**`scripts/git-hooks/pre-commit` が強制の担当。** ステージした公開区分のファイルを検査し、認証情報と非公開の固有名を含むコミットを止める。ルールは読み飛ばされうるが、フックは必ず走る。

固有名のパターンは `private/.claude/deny-patterns.txt` に置く。**パターン自体が社内固有名なので公開区分には持てない。** 新しい呼称・リポジトリ名・GitHub ID が出てきたら、ここへ足す。

**`/audit-secrets` が確認の担当。** フックはステージ済みの差分しか見ないので、履歴全体や未ステージの状態を見るときはこちらを使う。

## 履歴に入ってしまったら書き換える

**push 済みでも、履歴から消す。** ユーザーから恒久的な方針として指示を受けている。過去に遡って公開状態が残らないようにする。

**対象は秘匿値と非公開の固有名の両方。** API キー・トークン・秘密鍵が 1 度でもコミットに入ったら、**その時点で書き換える**。「もう消したから」「1 コミットだけだから」は理由にならない——履歴に残っている限り誰でも読める。

1. **公開区分から取り除く**。非公開にすべき内容は `private/` へ移すか、汎用的な表現に置き換える
2. **混入した最初のコミットの直前まで `reset --soft`** し、内容を直したうえでコミットを組み直す
3. 書き換え前の状態を `backup/` 配下のブランチに退避してから実行する
4. `git push --force-with-lease` で反映する
5. **新しい履歴の全 blob を走査**し、消えたことを確認する

**GitHub は force push で切り離したコミットを、しばらく SHA 直指定で配信し続ける。** 完全に消すには Support への GC 依頼が要る。この点は報告に含める。

**秘匿値の場合、書き換えだけでは終わらない。** 履歴から消しても、公開されていた間に読まれた可能性は消えない。**値の再発行が本筋で、履歴の書き換えは二次対応**（`no_secret_values_in_output.md`）。

- **事実は必ず報告する。** 何の値が、いつから、どの範囲に公開されていたか
- **再発行するかはユーザーが決める。** こちらから繰り返し促さない
- 判断を待つ間も、**履歴の書き換えは先に済ませる**。遅らせる理由が無い

## なぜ

- 公開リポジトリは「間違えて置いた」が取り消せない。push した時点で第三者のクローンやキャッシュに残りうる
- private を 1 つの zip に固めてクラウドへ上げる運用のため、**秘匿値を private に置くと卵を 1 つのカゴに入れることになる**。だからカゴ自体に鍵を掛ける
- 置き場のルールが曖昧だと、追加のたびに判断が揺れる。判断表を 1 箇所に置けば、迷いが「表を見る」に変わる
