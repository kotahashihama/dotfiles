# 記録は実測に基づける：場面別の詳細

`rules/base_records_on_measurements.md` から、場面が限られる詳細を移したもの。判定の軸と禁止する挙動は本体にある。

## 速さと待ち時間の測り方

1回の計測は数字として弱い。マシンの負荷・ファイルキャッシュの温まり方・裏で動いている他のプロセスで簡単に上下します。
**3回測って平均を出す。**

| 揃えること | なぜ |
| --- | --- |
| キャッシュを毎回捨てる | 2回目が速いのは、そのツールが速いからではない。タスクランナーだけでなく、各ツール固有のキャッシュも消す |
| 比較対象を交互に測る | まとめて測ると、後に測った側がキャッシュの恩恵を受けます |
| 同じマシン・同じ条件 | 別環境の数字を並べても比較になりません |

ばらつきも見る。3回が大きく散っていたら平均に意味がないので、条件を疑って測り直す。

報告には計測条件を添える。何回測ったか・キャッシュをどう扱ったかが無いと、読み手はその数字を信用できません。

### 待ち時間は、計測器が値を作っていないか先に見る

**自動操作のツールで待ち時間を測ると、そのツールのポーリングと安定判定が数字に混ざります。** 待ち時間の割に CPU が idle なら計測器が待っているだけで、手段を変えると値が変わるなら値は手段から出ています。**ブラウザ内から測る**（ `performance` の指標と `MutationObserver` ）。2回目以降が速いならキャッシュを疑い、初回だけ遅いのか毎回遅いのかを分けて報告する。

## 前と後の並べ方

### 前と後で基準を揃える

片方だけ条件を変えると、差が改善ではなく基準の違いから出ます。揃えるものは、条件の違う実測を並べるときと同じ（本体の「条件の違う実測を並べるなら、条件を列にする」）。

**特に、含める範囲を揃え忘れます。** 前は全体、後は一部で測ってしまう形です。

実際に、CI の分割前を「テストと lint を含むジョブの時間」、分割後を「テストだけの時間」で並べて+5%と書きました。lint を足して揃えると+14%で、3倍近くずれています。

**判定は「前と後で、同じものを数えているか」。** 数えた対象を1語添えると、揃っていないことが自分にも見えます。

### キャッシュで縮めたなら、当たった値と外れた値を並べる

**改善の「後」に、キャッシュが当たった値だけを置かない。** 当たった run は測り直すと一番速く出るので、無意識にそちらを選びます。

上の「速さと待ち時間の測り方」はキャッシュを捨てて測れと定めていますが、それはキャッシュが計測を乱す雑音のときの話です。改善そのものがキャッシュなら、捨てると改善も消えます。キャッシュの有無を条件として列に分けます（本体の「条件の違う実測を並べるなら、条件を列にする」）。

| 列 | 中身 |
| --- | --- |
| 前 | 変更前 |
| 後（当たった） | 入力を変えずに流し直した run |
| 後（外れた） | キャッシュのキーが変わった直後の run |

実際に、CI の改善で build を6分09秒から3分12秒と書いた値は、キャッシュが当たったときだけのものでした。外れた run 3本の平均は6分38秒で、変更前より遅くなっています。同じ表の test の短縮はキャッシュによらないもので、外れても4分53秒でした。列を分けると、どの施策がいつ効くのかが読めます。

**判定は「その短縮は、キャッシュが外れても残るか」。** 残らないなら、外れた値も並べます。

### 並べると、書き手の側の誤りも出る

全行を同じ式で通し直すことになるので、式から出ない数字が浮きます。

実際に、CI の分割数を比べる表へ `| 1 (現状) | 935秒 | 15.9分 | 992秒 |` と書きました。列は「最も重い shard / 待ち時間 / ランナー合計」です。
15.9分は954秒で、935秒（15.6分）にも992秒（16.5分）にも対応しません。手で足した行だけ、どの値からも出ない数字が入っていました。

前後を並べるために全行を1つの式へ通したとき、この行だけ計算が合わずに発覚しています。

**改善の主張は、読み手のためだけではありません。** 検算としても働きます。
