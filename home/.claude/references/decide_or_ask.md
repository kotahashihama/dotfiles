# 自分で決めるか尋ねるか：場面別の詳細

`rules/decide_or_ask.md` から、場面が限られる詳細を移したもの。判定の軸は本体にある。

## 参考作品を挙げられたら

「〇〇っぽく」「〇〇みたいに」は、前提の読み方が割れる典型です。参考作品には、借りられる面がいくつも重なっています。

| 面 | 例 |
| --- | --- |
| 世界観・雰囲気 | 絵柄・語り口・舞台 |
| 選択と結末 | 倒すも倒さないも自由、選んだことが物語に返ってくる |
| 操作の仕組み | 敵の攻撃を避ける、ターン制で戦う |

**作り始める前に、どの面を借りるかを `AskUserQuestion` で確かめる。** 仕組みは作る量が最も多いので、読み違えたときの手戻りが最も大きくなります。

実際に「Undertale っぽく」を操作の仕組みまで借りると読み、弾幕を避ける戦闘を作り込んでから外しました。借りたかったのは、選択の自由と世界観だけでした。

## PR と push の出し方

### PR は、手元の検査の完了を待たずに作る

PR は draft で作るので、最初に読むのはレビュアーではなくユーザーです。型検査・テスト全体・ビルドの結果を待ってから作ると、その間ユーザーは差分も本文も確かめられません。CI が後で同じ検査を回すなら、待つと同じ検査に2回分の時間も使います。これは出す指示を受けている前提の話で、出すかどうかは本体の「取り消せない操作は、指示が一意に読めるときだけ」で決まります。

検査はバックグラウンドで流し、PR を先に作る。本文には結果の出た検査だけを書き、残りは出てから足す。結果は必ず回収し、落ちていたら直す（ `background_heavy_work.md` ）。まだ誰も読んでいない投稿なら、書き換えてよい（ `keep_records_current.md` ）。

**CI が走らない draft でも待たない。** 判定は「同じ検査が後で走るか」ではなく「その PR を最初に読むのが誰か」です。結果が揃っていることを確かめるのは ready にするときで、そこで初めてレビュアーに届きます。

実際に、draft では CI が走らないリポジトリで「CI が無いなら手元で通してから出す」という以前の規定に従い、テスト全体の結果を待って PR の作成を止めました。ユーザーに「はやくつくってよ」と言われています。

### push も、CI が回すテストを手元で待たない

**push した先で CI がテストを回すなら、手元のテスト全体の完了を push の条件にしない。** 待つと同じテストに2回分の時間を使い、その間 PR は古い状態のまま止まります。

| push の前に手元で通す | CI に任せる |
| --- | --- |
| lint と型検査（短く終わり、落ちた場所がそのまま原因の場所になる） | テスト全体とビルド |

push したら CI の結果を回収し、落ちていたら直す（ `keep_records_current.md` の「自分の操作で CI やレビューが走ったら、結果を見るまでが1セット」）。

CI が走らない状態（draft では CI が止まるリポジトリ・CI の無いリポジトリ）には当てはまりません。手元の結果だけが裏付けになるので、バックグラウンドで流して回収します。

実際に、マージの衝突を解いて lint と型検査が通った後も、手元のテスト全体（2,000件超）の完了を待って push を止め、「CI に任せて push しなさいよ」と言われました。

### 後から足せるものは、揃うのを待たずに出す

スクリーンショット・動画は、撮れてから PR を作るものではありません。撮影環境が整わない・強制ログインが通らない等で手間取ると、その完了を PR 作成のブロッカーにしてしまいがちですが、待っている間はレビューも始まりません。

| 先に出す | 後から足す |
| --- | --- |
| PR 本文・実装差分 | スクリーンショット・動画 |
| コミット・push | 撮影用の環境調整・強制ログイン |

添付が無い旨を本文に一言残し、撮れ次第 `gh pr edit` / `gh pr comment` で追加する。撮るかどうかは `/update-pr-description` が、どう撮るかは `/verify-on-local` の `references/capture.md` が持つので、ここが定めるのは出す順序だけ。

**判定は「その添付が無いと、レビュアーが差分を読めないか」。** 読めるなら先に出す。複雑な UI 変更で差分だけでは伝わらないときだけ、撮影を待ってよい。
