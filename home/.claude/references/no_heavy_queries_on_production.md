# 本番の DB に重いクエリを出さないときの手順と実例

`rules/no_heavy_queries_on_production.md` から指す。本番の DB へ流すクエリを書く・渡すときに開く。

本番の DB は利用者の画面と同じものを読み書きしています。重いクエリは画面の応答を遅らせ、流している間はユーザーが止めどきを見張ることになります。

## 先に、DB を使わない手段を探す

知りたいことの多くは、DB を走査しなくても分かります。

| 知りたいこと | 先に使うもの |
| --- | --- |
| 実際に使われているか・どれくらい呼ばれているか | アクセスログ |
| ファイルがあるか・どんな置き場があるか | ストレージの一覧 |
| 値がどんな形で入るか | 書き込む側のコードとスキーマ |
| 件数の見当 | 統計（ `information_schema.TABLES` の行数の見積もり） |

**判定は「その答えに、DB の全行が要るか」。** 実際に使われたものだけを見れば足りるなら、ログで確かめる。

## DB が要るときは、軽く絞る

- 流す前に、対象のテーブルの行数を見る。百万行を超えるなら、そのまま全件を読まない
- インデックスの効く条件・ID の範囲・`LIMIT` で対象を絞る
- 全行の JSON の展開、全行への正規表現、大きなテーブルを `UNION` でつないだ全件の抽出は出さない
- 渡す前に、手元の DB（同じスキーマのもの）で通す。構文の誤りや列名の違いで本番に流し直させない

## どうしても重いクエリが要るなら、前置きしてから渡す

**重いことを先に書いてから、クエリを渡す。** 流すかどうかと、いつ流すかはユーザーが決めます。

| 前置きに書くこと | 例 |
| --- | --- |
| 何行を走査する見込みか | 「約2,000万行を全件読みます」 |
| なぜ避けられないか | 「ログに残らない、ほとんど開かれないファイルまで数えるため」 |
| 流す時間の目安 | 「利用者の少ない時間に」 |

手元の DB で通せなかったなら、通していないことも前置きに書く。

## 禁止する挙動

- 全件を走査するクエリを、DB を使わない手段を探さずに渡すこと
- 重いクエリを、重いと書かずに渡すこと
- 手元で通していないクエリを、通したように渡すこと。失敗するたびに本番で流し直させることになる
- 1本で済まないものを、行数を見ずに1本へまとめること

## なぜ

- 実際に、ファイルの参照を調べるために、2,000万行を超えるテーブルを含む全件の抽出を `UNION` でつないで渡した。試していないクエリが3回続けて失敗し、そのたびに本番で流し直させた。知りたかったことは、アクセスログとストレージの一覧を突き合わせるだけで分かった
- 本番への負荷は取り消せない。遅くなった画面を利用者が見た事実は、クエリを止めても残る

## 例外

- ユーザーが重いクエリであることを承知のうえで、明示的に求めた場合
