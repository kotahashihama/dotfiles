# レビューコメントへの対応：回答の雛形と 👍 の付け方

`rules/responding_to_reviews.md` から移した、場面が限られる細部。判定の軸は本体にある。

## レビューコメントが共有されたら、まず意図を噛み砕き、対応するかどうかをユーザーに尋ねる：テンプレート例

```markdown
## レビューコメントの意図

**指摘対象**: [ファイル:行 / 該当箇所の要約]
**レビュアーが問題視している点**: [噛み砕いた説明 - 1〜2 行]
**提案されている対応**: [噛み砕いた説明 - 1〜2 行]

## 現状のコード

（該当箇所の抜粋または要約）

## 変更案

**案 A**: [具体的にどう変えるか。before/after のコード片があると更に良い]
**案 B**: [別のアプローチがあれば]
（案が 1 個しか自然でなければ「案」1 個で構わない）

## 対応する場合の影響

- 変更範囲: [ファイル・行数の概算]
- トレードオフ: [あれば]
- リスク: [あれば]

## おすすめ

[**対応推奨 / 見送り推奨 / どちらでもよい** のジャッジと、その根拠を 1〜2 行]
[複数案なら、**どの案を推すか** も併記]

**どうしますか？** (追加質問あればどうぞ)
```

## 返信したレビューコメントと、レビュー提出に 👍 を付ける：付ける対象

コミットを伴うコード変更で応え、その返信を投稿したコメントだけに付ける。**両方が揃って初めて付く。**

| コメント | リアクション |
| --- | --- |
| コードを直し、ハッシュを返信した | 付ける |
| コードを直したが、まだ返信していない | 付けない |
| 非対応と判断し、理由を返信した | 付けない。理由が伝わらないと誤解になる |
| `[ask]` の質問 | 付けない。答えになっていない |
| PR 説明・タイトルなど、コミットを伴わない記述の指摘 | 付けない。差分で確かめられない |

人間レビューでは返信自体が明示指示制です。指示が出るまでは返信も 👍 も行わず、会話の対応表で報告するに留める。

「読んだ」の意味では使わない。付いていること自体が「直っている」の印になるので、対応していないものに付けると、レビュアーが差分を確認せずに閉じてしまう。

## 返信したレビューコメントと、レビュー提出に 👍 を付ける：レビュー提出には、謝意として付ける

**個々の指摘と、レビュー提出（本文のあるもの）は意味が違います。**

| 対象 | 👍 の意味 | 付ける条件 |
| --- | --- | --- |
| 個々の指摘 | その指摘に応えた | コードを直し、返信もした |
| レビュー提出の本文 | 見てもらったことへの謝意 | 返信を投稿した回。指摘の可否は問わない |

謝意なので、非対応の指摘しか無かった回でも付ける。逆に本文が空の提出には付けない。インラインを束ねる入れ物で、読む文章が無い。

REST にエンドポイントが無いので GraphQL を使う（ `/reactions` は issue コメントとインラインコメントにしかない）。`PullRequestReview` は `Reactable` を実装しているので `addReaction` が通る。

## 返信したレビューコメントと、レビュー提出に 👍 を付ける：付け方

コマンドと対象ごとの経路は `/resolve-human-reviews` の手順7と `/resolve-ai-reviews` が持つ。

## 返信したレビューコメントと、レビュー提出に 👍 を付ける：なぜ

- **リアクションもレビュアーへ向けた発信です。** 返信を控えている相手に 👍 だけ届くと、こちらが何を発信してよいと判断したのかが揺れる。同じ許可のもとで動かすほうが事故が少ない
- 👍 だけでは、どう直したかを辿れない。「対応済み」に見えるのに差分への手がかりが無く、レビュアーは結局全件を開くことになる。ハッシュの返信とセットで初めて一覧として機能する
- 逆に返信があるコメントでは、どれが片付いたかを一覧で見て分かる状態になる

## 返信したレビューコメントと、レビュー提出に 👍 を付ける：例外

- ユーザーが「リアクションは不要」と明示した場合
- ユーザーが「リアクションだけ付けて」と明示した場合（返信が無くても付ける）
- リアクションが運用として使われていないリポジトリ（既存 PR を見て判断する）
