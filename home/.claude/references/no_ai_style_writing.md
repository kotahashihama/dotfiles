# AI が書いたと分かる文章を出さない：場面別の詳細

`rules/no_ai_style_writing.md` から、場面が限られる詳細を移したもの。判定の軸は本体が持つ。

## 文章の点検の詳細

### 順序の理由

**1から順に当てます。** 段落と論証を先に直してから、言い回しを直します。言い回しを先に整えても、あとで段落を組み替えるとやり直しになります。

**2のあとに、1の2節だけを当て直します。** 2は問いかけや短い言い切りで緩急を作るので、1が抑えている修辞の問いや決め台詞の段落が混ざることがあります。4は言い回しを見ますが、1の演出の基準は持っていません。見直すのは2で足した文だけで、段落は組み替えないので上の順序と食い違いません。

**4の書き直しは、2と3の結果を崩すものを採りません。** `/yomiyasu:yomiyasu` は、短い主題・主語・目的語のあとの読点を外し、箇条書きのラベルを文へ入れて1文にします。そのため、2で付けた拍（短文で立て、長めの文で流し、短文で止める）や箇条書きで作った間が均され、3で残した読点が外れることがあります。4のあとで直し直さず、4の書き直しを取捨選択する段で落とすのは、4の点検の記録のあとに本文を1字でも変えると、4を回し直すことになるためです（ `/yomiyasu:yomiyasu` の規定）。回し直すとまた寄せられ、往復になります。この取捨選択は2つのスキルの規定を読んで決めたもので、記事で実際に均されたかはまだ確かめていません。

**`/yomiyasu:yomiyasu` とユーザーの表記の規約が食い違うときは、規約を優先します。** 英字と日本語のあいだの空白は、`/yomiyasu:yomiyasu` が残す書式なので食い違いません（ `~/.claude/references/japanese_notation.md` ）。また `/yomiyasu:yomiyasu` の README は似たスキルを無効にするよう勧めていますが、ここでは1〜3のあとに重ねて使います。

### 短いものも通す

実際に、1つの PR へ `[fyi]` 20件と補足コメントを1件ずつ投稿し、コードコメントも直しましたが、どれも通していませんでした。1件ずつは3〜5行で、例外に当てはまって見えたためです。

### 2を報告に当てる範囲

**2は、読み物には全部、報告には一部だけ当てます。** このスキルは冒頭で答えの出ていない問いを作って読み進めさせる形で、一言目で答える規約（ `concise_first_then_detail.md` ）と逆を向きます。そのため、報告では冒頭の作りに関わる部分を当てません。

| 文章 | 当てる部分 |
| --- | --- |
| 読み物（記事・本の章・長めの解説文。読み進めてもらうこと自体が目的） | 全部 |
| 報告（PR 本文・課題管理ツールのコメント・調査や完了の報告） | 「緩みと駄文の見分け方」の話題テスト（文章そのものを語るだけの文を、扱う対象についての文に替えるか削る）と、密な表や列挙のあとに要点を1行で置くことだけ。冒頭で答えを伏せる・問いを後半まで開けておく・当事者の声で迷いを書く、は当てない |
| 会話の応答 | 当てない |

実際に、調査結果を書いた課題の memo に一部だけ当てたところ、「この memo は出どころで節を分けている」のような前置きが「数字の出どころは4つあり、節ごとに分けてある」になり、4行×7列の順位表のあとに観点をまたいで上位に入る構成を1行で足せました。冒頭の結論はそのまま残っています。

### 5（文脈の無い読み手）の回し方

**書き手は自分の文脈で補って読むので、指す先が決まらない語や定義していない呼び名に自分では気づけません。** 1〜4はどれも書き手が当てる点検なので、ここだけ書き手の事情を知らない読み手に読ませます。読み手への指示と、読み手が拾う8つの型（指す先が決まらない語・定義していない呼び名・前の段落の言い直し・読み飛ばしても困らない文など）は tsuzuri のものを借ります。

**tsuzuri の記録は作らない。** 記録は tsuzuri で書くときに1文ごとの執筆意図を残すフォルダ（ `<文書>.tsuzuri/` ）です。読み手への指示を組み立てる tsuzuri のコマンド `cold` は記録を入力に取りますが、1〜4で仕上げた文章には記録がありません。指示のひな形を直接埋めます。

1. ひな形は tsuzuri の `skills/tsuzuri/references/cold-reader-prompt.md` にある（プラグインの置き場は `~/.claude/plugins/cache/` の下で、バージョンごとにフォルダが分かれるので最新のものを使う）。ファイルの途中に1行だけある区切りの行 `---` から下だけを使う
2. `{{READER}}` にはその文章の読み手を1〜2行で書く。読み手の決め方は `github_writing.md` の「読みやすさの基準も、読み手で変わる」の表に従う（PR 本文ならその機能を知らないエンジニア、課題管理ツールの `[fyi]` なら非エンジニアやその課題を初めて読む人）。ほかの文書から指されて開かれる文書なら、どこから開いたかも読み手に書く。書かないと、開く前に読んだはずの定義まで「分からない」と拾われる
3. `{{TEXT}}` には本文を1文ずつ `[s0001]` の形の ID を付けて並べる。見出し・表・コードブロックは `[b0001]` を付けて1行にまとめる。段落の区切りは空行で残す
4. 埋めた指示だけを `general-purpose` のサブエージェント1体に渡す。会話の経緯・元にしたファイル・前のバージョン・直した箇所は渡さない。1つでも渡すと、読み手が書き手の文脈で補って読む
5. 返ってきた指摘を1件ずつ、直すか、直さない根拠を名指しするかに分ける。根拠の名指し方は tsuzuri の `skills/tsuzuri/references/cold-read.md` の「修正しないときの根拠」に従う。型8（知らなくても困らない）は「その文章を読んだ人が次に何をするか」と照らして判定する
6. 直した文が4つ以上か、段落を外した・動かしたときだけ、新しい読み手でもう1回回す。3回目は回さない

**直したら1〜4の結果を確かめ直す。** 直した文だけに1〜3を当て、4は yomiyasu に同梱の `yomiyasu_check.py` の `run` と `verify` を回し直します（ `run` が残す結果のファイルは検査した本文のハッシュを持ち、`verify` は今の本文がそれと一致するかを確かめるため）。

**読み手の直し案に本文に無い事実が入っていたら、確かめてから採る。** 読み手は書き手の事情を知らないので、推測で事実を埋めることがあります。

### いつ通すか

書いている途中では回さず、書き終えてから回します。複数あるときはまとめて1回で通します。

**出したあとで書き直したら、そのたびに通します。** 一度通した文でも語句だけの修正でも例外にしません。書き直しは文体や段落まで動きやすく、「語句だけ」に見えた修正がそうでないことがあります。

実際に、課題へ投稿したコメントのアノテーションを替えて敬体から常体へ書き換えたとき、「語句を直すだけ」と扱って通さずに出しました。通し直すと、指す先が決まらない語が3か所と息継ぎの読点が残っていました。

**投稿する文章は投稿の直前に通します。** 1件ずつ投稿していく作業では「書き終えた」時点が来ないので、まだ通していない分をためてから1回で通し、そのあとで投稿します。

**コミットする文書も同じで、コミットの直前に通します。** スクラッチパッドで書いて API でそのままコミットする経路では、エディタで書き終えた区切りが来ません。

実際に、別のリポジトリの規約文書（ルール2本と `docs/` の2本）をこの経路でコミットし、4本とも通していませんでした。規約文書を「設定」として扱い、読み物と見なしていなかったためです。

`require-writing-review.sh` が、そのターンに書いた `.md` を、その後で `/yomiyasu:yomiyasu` に通していなければ差し戻します。拾うのは Write / Edit と、Bash のリダイレクト・`sed -i`・`tee`・`--body-file` で書いた分です。スクリプトの中で書いた分は拾えないので、本節が受け持ちます。

bee で投稿する文章（課題の本文やコメント）は、コマンドの引数や標準入力で渡るので、上のフックでは見えません。投稿は取り消せないため、`require-review-before-post.sh` が投稿の直前に止めます。本文は `.md` に書いて点検を通し、その中身を渡します。

**急ぎは点検を飛ばす理由になりません。** どうしても先に出すなら、出す時点で未点検だと会話で伝え、点検したあとで直します。直し方は `~/.claude/references/keep_records_current.md` の「まだ誰も読んでいない投稿は、書き換える」に従います。

実際に、急ぎの不具合対応で PR 本文と課題へのコメントを点検せずに投稿し、尋ねられるまで言いませんでした。後から通すと、常体の混在・指す先が決まらない語・結論を言い切った見出しが見つかっています。

`/yomiyasu:yomiyasu` の書き直しは取捨選択します。専門用語を平易な語へ置き換える提案や、断定を弱める提案が混ざるので、`/japanese-tech-writing`・`plain_language_explanation.md`・`base_records_on_measurements.md` を優先します。
