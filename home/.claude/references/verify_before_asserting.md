# 断定する前に一次情報で裏を取る：場面別の詳細

`rules/verify_before_asserting.md` から、場面が限られる詳細を移したもの。判定の軸は本体が持つ。

## 文書と実装を突き合わせるとき

### 文書と実装が合っていても、あるべき形かは別に確かめる

**文書（仕様・表・PR 本文）と実装を突き合わせるときは、合っているかだけでなく、どちらがあるべき形かを、それを決めた方針に照らして決める。** 合っているかだけを見ると、食い違ったときは片方へ寄せて終わり、合ったときは両方が同じように誤っていても素通りします。

| 見る箇所 | 問い |
| --- | --- |
| 食い違った箇所 | 方針を満たすのは文書か実装か。満たさない側を直す |
| 合っている箇所 | 両方とも方針を満たしているか |

方針は、その文書を作るときに置いた決め方です（「今の画面でそのファイルを見ている人だけが開ける」など）。方針が何を基準にしているかを読み、その基準のほうを開いて確かめる。画面を基準にした方針なら、API の判定ではなく、画面にその操作があるかを見ます。

**判定は「その記述と実装のどちらが、決めた方針を満たしているか」。**

実際に、ファイルを開ける人の表と、各ブランチの判定の実装を突き合わせたことがあります。食い違いを表の書き換えで揃えようとして、「整合性が取れているだけではなく、あるべき形である必要がある」と言われました。方針に照らし直すと、5か所とも正しいのは実装で、誤っていたのは表の書き方です。そのうち1か所はテンプレートの添付を開く API が無いことの正否で、画面に開くリンクがあるかを見るまで決まりませんでした。

## 妙に見える実装を直す前に

### 妙に見える実装は、直す前に変更の経緯を遡る

**周りと食い違う実装を見つけたら、直す前に、そうなった経緯を過去の PR とコミットで確かめる。** 1つだけ項目名が違う、似た処理と1か所だけ形が違う、といった実装には、わざとそうした理由があることも、別の場所で既に直されていることもあります。経緯を見ずに直すと、理由を消すか、既にある修正と別の形で同じ行を直すことになります。

**判定は「その実装がなぜその形なのかを、経緯から説明できるか」。** 説明できないまま直さない。

遡り方の手順（ `git blame` ・ `git log --follow` ・ PR の本文と議論の引き方）は `/pstack:why` の「Establish the Code Anchor」にある。ただし、それは作業中のブランチで今の行を触ったコミットをたどる手順なので、次の3つは自分で足す。

| 足すこと | 拾えるもの |
| --- | --- |
| 食い違っている語で変更を探す（ `git log -S <語>` ） | 今の行を触っていないが、同じ語を足したり消したりしたコミット |
| main 以外の長く続くブランチ（release・hotfix）も同じ行を引く（ `git grep <語> origin/release` ） | 片方のブランチだけで直され、もう片方へ戻っていない修正 |
| 関わる語で PR を検索する（ `gh search prs --repo OWNER/REPO <語>` ）。その行を触っていない PR の本文とコメントも読む | 別の PR で調べて書き残した原因・範囲（「このずれは1か所だけ」など） |

実際に、公開の API の添付だけが項目名を `title` ではなく `name` で返していて、`name` から `title` へ写す形で直して PR に出しました。後から経緯を遡ると、v2 へ移したときの取り違えで、release のブランチでは数か月前に hotfix で直されていました（SQL の組み立てで `title` にする形）。main には戻っておらず、直し方が違うまま release へ載せると同じ行がぶつかるので、release と同じ形に直し直しています。
