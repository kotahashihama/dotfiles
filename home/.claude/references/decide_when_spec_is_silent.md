# 仕様が書かれていないところに出くわしたとき：判定の軸と記録のしかた

`rules/decide_when_spec_is_silent.md` から開く。仕様の無い箇所を見つけたときに読む。

仕様書・規約・契約のどれにも書かれていない箇所に出くわしたら、**既存の実装がどちらへ倒しているかを数えて**、その形に着地してください。

**「妥当だと思った」では検証できません。** 自分の理屈で決めると、後から誰も確かめられない判断が残ります。既存の倒し方は数えられるので、根拠として渡せます。

## まず、本当に書かれていないかを確かめる

**「仕様が無い」と感じた時点では、隣を読んでいません。** 探す先は3つあります。

| 見る先 | 例 |
| --- | --- |
| 逆向きの操作 | 作る側が決まっていれば、消す側は自由ではない |
| 同じリソースの別の操作 | 一括版と単体版、管理者向けと利用者向け |
| 旧実装の相当箇所 | 移植であれば、そこが仕様の出どころ |

実際に、ある復元処理の仕様が書かれていないと判断して実装を2度ひっくり返しました。逆向きの削除処理には明記があり、しかも「旧実装の相当箇所」と書かれていました。片側が決まっていたので、消す案は最初から採れませんでした。

**片側が決まっているなら、それは制約です。** 書かれていないのは残りの半分だけです。

## 尋ねる側と着地する側の境界

「書かれていない」はたいてい「読み方が割れる」に見えます。ここを分けないと `decide_or_ask.md` と正反対の指示になります。

| 決め方 | 対象 |
| --- | --- |
| 尋ねる | 方針・粒度・公開範囲・取り消せない操作（ `decide_or_ask.md` ） |
| 擦り合わせる | 他のリポジトリと共有する契約（ `implement_from_contract_inward_out.md` ） |
| 着地する | 実装の細部で、契約にも規約にも書かれていないもの |

**判定は「その判断が外へ出るか」。** 出るなら尋ねるか擦り合わせる。内側で閉じるなら着地する。

## 3つの軸で判定する

1つ目を既定にします。残り2つは既存の倒し方が見つからないときに使います。

| 軸 | 問い | 強さ |
| --- | --- | --- |
| 既存の倒し方 | 同じ状況を扱う既存のコードは、どちらへ倒しているか。数える | 強い |
| 壊れたときの代償 | 誤ったとき、どちらが安いか。黙って通すか、止めるか | 中 |
| 後から変えられるか | 保存される値か、実行中だけの値か | 中 |

**数えるのは実装の分岐です。** 並び順・命名・コメントは書き換えられるので根拠になりません（ `verify_before_asserting.md` ）。

同じ処理の前例が無くても、パターンの段では見つかります。実際に、復元処理そのものの前例は旧実装に無かったものの、同じ値を状態遷移に追随させる形が2箇所にありました。そこに乗せることで、独自の判断を持ち込まずに済みました。

**自分の差分を数に入れないでください。** 同じ作業ツリーでは区別が付きません（ `verify_the_check_worked.md` ）。

数えた結果が割れたらそれは判断材料になりません。同じファイル・同じディレクトリの流儀に合わせ、指摘の根拠にはしない。

数え方を添えないと受け取った側が別の数を出します。実際に同じ対象を3通りの手順で数えて22対15・22対25・22対22になり、多数派が入れ替わりました。

この軸が使えるのは、機械的に集計できる判定だけです。命名やコメントの流儀では同じ手が使えません。

## 着地したら、仕様書へ書く

**書かないと、次に触る人が同じ判断をやり直します。** 判断そのものより、判断が書かれていないことが問題でした。

- 決めた形を、その API・機能の仕様書へ足す
- どちらへ倒したかだけでなく、倒さなかった側も書く（対象にしない値・触らない経路）
- 経緯は書かない。成果物に指示や検討の過程を残さない（ `no_instruction_echo_in_output.md` ）

その文書が規約本体なら、尋ねてから足します（ `ask_before_editing_claude_assets.md` ）。同じ `docs/` の下に、API の振る舞いを書いた仕様書と、次に触る人が従う規約が混在していることがあります。判定はあちらと同じで、「その変更を知らないまま次のセッションが始まったとき、挙動が変わって見えるか」です。

**自分が書いた節を、その判断の根拠として引かないでください。** 循環します。根拠になるのは、既存の倒し方と隣の仕様です。

### テストを先に書くなら、期待の根拠を課題に残す

**テストの期待を決めた時点で、仕様の無い箇所の判断は済んでいます。** 実装はその期待に合わせるだけなので、期待が誤っていれば、テストが通っても誤りは残ります。後から確かめられるよう、課題へ `[memo]` で次の3つを残す。

| 残すもの | 書き方 |
| --- | --- |
| 決め方の方針と、その方針を選んだ理由 | 採らなかった案と、採らなかった理由も添える |
| 方針を当てはめた箇所ごとの根拠 | 箇所・決めたこと・根拠を1行ずつ並べる |
| 期待が正しいと言える確かめ方 | 期待値と実装の値の突き合わせと、変更前の実装でテストを流したときの結果 |

**変更前の実装に、今のテストを流す。** 落ちたテストが、動きを変えた箇所の一覧になります。1件ずつ、意図した変更か、それに伴って決めた動きかに分ける。通ったテストは、変更前と同じ動きを固定していることになります。

上の「経緯は書かない」は仕様書の話で、こちらは判断の記録です。仕様書には決めた形を、課題には決めた理由を置きます。

実際に、権限の判定を直す2本の PR で、仕様の無い箇所をテストの期待で決めて進めました。根拠を課題へ残す段で、宣言どおりに判定を効かせた結果、管理者がメニューから開けていた画面から締め出されていたと分かっています。テストは宣言の値をそのまま期待にしていたので、通っていました。

## 仕様が書いてある形から外れたら、課題と PR の両方に残す

**仕様が無い箇所の逆で、仕様（課題の本文・依頼書・設計書）が決めている形から、正当な理由で外れて実装したときも、そのずれを残します。** 課題を読む人と PR を読む人は別なので、両方に残す。片方だけだと、もう片方を読む人は設計と違うことに気づけません。

| 残す先 | 形 |
| --- | --- |
| 課題 | コメント。他人が起票した課題の本文は書き換えない（ `verify_before_asserting.md` ） |
| PR | 本文のテンプレートにある節（補足など）に、違う点を表で並べる。節は増やさない。各行から課題側の記録へリンクする |

1点ごとに、仕様の形・実装した形・理由の3つを書く。理由は「仕様どおりだと何が壊れるか」で書き、測った数字があれば添えます（「名前に `..` を含むファイルが2,842件ある」）。アノテーションは `[fyi]` に限りません（ `github_writing.md` ）。

外れた時点で課題へ書き、PR を作るか更新するときに載せる。後でまとめようとすると、どれが仕様と違うのかを数え直すことになります。

**課題のコメントは、外れた点ごとに積まず、意味のまとまりごとに1件へまとめる。** 同じ時期に見つかった外れた点は、1件の表に並べます。分けるのは、読み手や判断する人が違うときだけです（実装で外れた点と、運用で決めてほしい点など）。

投稿したあとに外れた点が増えたら、元のコメントを直すか新しいコメントに書くかは、`keep_records_current.md` の「書いて間もないなら、元のコメントを直す」で決めます。

実際に、1つの課題で外れた点を見つけるたびにコメントを足し、取り下げた案とその取り下げも含めて5件になりました。ユーザーに「なるべくまとめてほしい」と言われています。

**外れる理由を事実で示せないなら、外れずに仕様どおりに作るか、作る前に尋ねる**（ `decide_or_ask.md` ）。好みや作りやすさは理由になりません。

実際に、ある課題の作業で仕様と違う形を4つ選び、課題にはコメントを残したのに PR には書いていませんでした。ユーザーに「PR にももちろん残してね」と言われてから足しています。

## 禁止する挙動

- **隣を読まずに「仕様が無い」と判断すること**。逆向きの操作・別の操作・旧実装の相当箇所を先に見る
- 自分の理屈だけで妥当さを決めること。既存の倒し方を数える
- 並び順・命名・コメントを根拠にすること。書き換えられるものは根拠にならない
- **外へ出る判断を、着地で済ませること**。方針・粒度・公開範囲は尋ねる（ `decide_or_ask.md` ）
- 他のリポジトリと共有する契約を、片方で決めること（ `implement_from_contract_inward_out.md` ）
- 着地した形を仕様書へ書かないこと。次に同じ判断をやり直すことになる
- 自分が書いた仕様を、その判断の根拠として引くこと。循環する
- テストを先に書いて仕様の無い箇所を決めたのに、期待の根拠を課題へ残さないこと。テストが通っても、期待が正しいかは誰も確かめられない
- 仕様と違う形で作って、課題と PR のどちらか、または両方に残さないこと
- 同じ時期に見つかった外れた点を、1点ずつ別のコメントに書くこと。意味のまとまりごとに1件へまとめる
- 仕様から外れる理由を「〜のため変更」だけで済ませること。仕様どおりだと何が壊れるかを書く

## なぜ

- 仕様が無い箇所は必ず出る。**そこで止まると進まず、独自に決めると検証できない判断が残る**
- 既存の倒し方は数えられる。根拠として渡せるので、レビューでも次のセッションでも同じ結論に辿り着ける
- 片側の仕様は残りの半分を縛る。読まずに決めると、決まっていることと矛盾する形へ着地する
- 着地した判断は、書かなければ次に触る人には「仕様が無い」ままに見える。同じ往復が繰り返される

## 例外

- ユーザーが方針を明示した場合はそれに従う
- 試作・検証目的で、捨てる前提のコードを書く場合
