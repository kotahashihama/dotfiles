# そのプロジェクトに入っているバージョンで書く

コードを書くときは、**そのプロジェクトに実際にインストールされている**言語・ライブラリのバージョンを確かめ、**そのバージョンが備える API と文法を使って**ください。
これは全プロジェクト共通の規約です。

**既定の書き方は、学習した時点の分布に引きずられます。** 広く使われていた古い書き方のほうが手に馴染んでいるので、放っておくと**入っているバージョンより古い書き方**になる。逆に、記憶で新しい機能を使うと**まだ入っていない**ことがある。どちらも確かめれば防げます。

## 書く前に確かめる

**記憶で判断しない。** バージョンは上がるので、前回見た値も古くなります。

| 見るもの | なぜ |
| --- | --- |
| **ロックファイル** | **入っているのはこちら**。宣言側の範囲指定（`^1.2.0`）は実際の値ではない |
| 言語のバージョン指定 | `go.mod` の `go` 行、`.node-version`、`mise.toml`、`.python-version` 等 |
| **実際に解決される値** | 迷ったら引く（`npm ls <pkg>` / `go list -m <mod>` / `pip show <pkg>`） |

**宣言とロックが食い違うことがあります。** 範囲指定は「許す幅」であって「入っている値」ではないので、**ロック側を正とする**。

## 何を使うか

| 場面 | 選ぶもの |
| --- | --- |
| **そのバージョンで使える新しい API・文法がある** | **読みやすく / 安全になるなら使う**（下記） |
| 記憶にある書き方が、そのバージョンには**まだ無い** | 使わない。ビルドか実行時に落ちる |
| そのバージョンで**非推奨**になっている | 新規では使わない。理由をコメントに残す必要は無い |

**「動くから」で古い書き方を選ばない。** 新しい API は、たいてい**古い書き方が踏んでいた罠を塞ぐため**に入っています。使わないと、その罠を自分で避け続けることになる。

### 新しさ自体は理由にならない

**判断の軸は「読みやすくなるか」「間違えにくくなるか」の 2 つだけ。** 入っているバージョンを確かめるのは、**選択肢を落とさないため**であって、新しい順に選ぶためではありません。

| 使う | 使わない |
| --- | --- |
| 手書きしていた処理が**言語機能で置き換わる** | 同じことを**書き方だけ変えて**表現する |
| **型で防げるようになった**（実行時チェックが要らなくなる） | 読み手が**仕様を引かないと読めない**書き方 |
| 定型の記述が減り、**意図が前に出る** | そのプロジェクトで**まだ 1 度も使われていない**構文を、1 箇所だけに持ち込む |

**迷ったら使わない。** 読みにくくなった分は、次にそのコードを読む人が毎回払います。

## 周囲のコードと食い違うとき

**既定は周囲に合わせること。** ただし**周囲が古いのは、書かれた時点で使えなかったからであることが多い**——それは新規のコードまで古く書く理由にはなりません。

| 状況 | どうするか |
| --- | --- |
| **新しく足す箇所** | **新しい書き方でよい** |
| 既存を触る箇所 | **そのファイル・その関数の中では流儀を混ぜない**。周囲に合わせる |
| 既存を一括で置き換えたい | **別のコミットに分ける**。機能の変更と混ぜると差分が読めなくなる |

**1 つの差分の中で流儀が割れているのが最も読みにくい。** 迷ったら周囲に合わせ、置き換えは独立させる。

## 禁止する挙動

- **入っているバージョンを確かめずに書くこと**。既定の書き方が古い側へ寄る
- **宣言側の範囲指定を「入っているバージョン」として扱うこと**。正はロックファイル
- 記憶を頼りに「このバージョンなら使えるはず」と書くこと（`verify_before_asserting.md`）
- **1 つの差分の中で新旧の流儀を混ぜること**。置き換えるなら独立したコミットで
- 一括置換をユーザーに諮らずに始めること。**新規を新しく書くのと、既存を書き換えるのは別の作業**
- **新しいという理由だけで使うこと**。読みやすさか安全性が上がらないなら、選ぶ理由が無い

## なぜ

- **書き手の既定は、そのプロジェクトの現在とは無関係に決まっている。** 確かめない限り、選んだ書き方が古いか新しいかすら分からない
- 新しい API は**古い書き方の失敗を踏まえて**入る。使わないという判断は、その失敗を引き受けるという判断になる
- 一方、記憶で先走ると**ビルドが通らない**。同じ「確かめない」ことから、正反対の 2 種類の事故が出る
- ただし**新しさは目的ではない**。確かめるのは選択肢を落とさないためで、読みにくくなるなら選ばない。読みにくさは、次に読む人が毎回払う
- 流儀が割れた差分は、レビュアーに「これはどちらが正しいのか」を考えさせる。**判断の負担が差分の外に漏れる**

## 例外

- ユーザーが「既存に合わせて」と明示した場合
- そのリポジトリの規約が書き方を固定している場合（そちらが優先）
- 使い捨ての検証コード

## 関連

- `verify_before_asserting.md`（断定の前に裏を取る）: あちらは**書く文章**の裏取り、本ルールは**書くコード**が前提とするバージョンの裏取り。「確かめずに書かない」という点で同じ
- `implement_from_contract_inward_out.md`（契約を先に決めて内側から積む）: あちらは**作る順序**、本ルールは**何を使って書くか**
- `code_comment_why_and_what.md`（コメントの書き方）: 新しい API を選んだ理由は、**非自明なときだけ** WHY として書く
