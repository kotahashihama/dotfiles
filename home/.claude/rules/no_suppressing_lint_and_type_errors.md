# lint と型のエラーを抑制して回避しない

`@ts-expect-error` / `@ts-ignore` / `eslint-disable` / `biome-ignore` / `as any` のような、**検査を黙らせて先に進む手段**を使わないでください。
これは全プロジェクト共通の規約です。

**どうしても必要なときは、`AskUserQuestion` で尋ねてから使う。** 自分の判断で入れない。

## エラーは直す対象で、消す対象ではない

検査が出すエラーは、**そのコードが抱えている問題を指している信号**です。抑制すると信号だけが消え、問題は残ります。

| 抑制すると | |
| --- | --- |
| **問題が見えなくなる** | 次に読む人は「検討済みで許容された」と受け取り、疑わなくなる |
| **周りへ伝染する** | 1 つ入ると 2 つ目の敷居が下がる |
| **本当の原因が分からないまま残る** | 抑制は原因の調査を打ち切る行為でもある |

## 抑制したくなったら、まずエラーの全文を読む

**型エラーは長いので、先頭だけ読んで「ライブラリの型定義が悪い」と判断しがちです。** ところが原因は末尾に書かれていることがあります。

TypeScript は `Type 'X' is not assignable to type 'Y'` を出したあと、**どのプロパティで食い違ったか**を字下げして続けます。この最後の数行に、実際に直せる原因があります。

```
error TS2322: Type '{ ...300 個のプロパティ... }' is not assignable to type 'Base'.
  Types of property 'defaultValue' are incompatible.        ← ここが原因
    Type 'string | number | readonly string[] | undefined' is not assignable to ...
```

**出力が truncate されているなら外す。** `tsc --noErrorTruncation` で全文が出ます。実際に、この 1 行を読むまで「ライブラリと React の非互換で直せない」と判断していたものが、**型定義から 1 つのプロパティを除くだけで解決**しました。

## 直し方を探す順序

**上から順に試し、下へ行くほど最後の手段になる。**

| 順 | 手段 | 例 |
| --- | --- | --- |
| 1 | **エラーの全文を読み、名指しされた原因を直す** | 衝突しているプロパティを型から除く |
| 2 | **型が絞れる形へ書き換える** | union を変数に取り出さず、判別可能なプロパティで直接分岐する |
| 3 | **ジェネリックや型引数の指定を型定義と突き合わせる** | 二重に渡していた型引数を正す |
| 4 | **ライブラリの新しい版で解決していないか確かめる** | 型定義の修正が入っていることがある |
| 5 | **理由を明記した型アサーション** | プロジェクトの規約が許す範囲で |
| 6 | **抑制コメント** | **`AskUserQuestion` で承認を得てから** |

**5 と 6 の間には段差があります。** アサーションは「この型で正しいと判断した」の表明ですが、抑制は「検査そのものを止める」ので、意味が違います。

## 尋ねるときに示すもの

`AskUserQuestion` には、**なぜ 1〜4 で解決しなかったか**を添える。

- エラーの原因（全文の末尾で名指しされた箇所）
- 試した手段と、それぞれが通らなかった理由
- 抑制する場合に**いつ外せるか**（ライブラリの追従待ち、等）

## 禁止する挙動

- **承認を得ずに抑制コメントを入れること**
- **エラーの全文を読まずに「直せない」と判断すること**。原因は末尾に書かれている
- **`as any` で型を捨てること**。アサーションが要るなら、具体的な型へ寄せる
- 抑制コメントに**理由を書かないこと**（承認を得た場合も、なぜ必要かと外せる条件を残す）
- 抑制を**一時しのぎのつもりで入れて、そのままにすること**

## なぜ

- 検査を入れる目的は**問題を早く見つけること**で、抑制はその目的を局所的に取り消す。**入れた検査を自分で無効化するなら、最初から検査しないのと変わらない**
- 型エラーは**周辺の推論を巻き込んで 1 件に見える**ことがある。1 つ抑制すると別のエラーが露出し、抑制を重ねることになる
- 抑制は**判断の記録が残らない**。「調べたが直せなかった」のか「調べていない」のかが、後から区別できない

## 例外

- ユーザーが `AskUserQuestion` で承認した場合（**その 1 箇所だけ**。他へ広げない）
- ユーザーが「ここは抑制していい」と明示した場合
- 生成されたコードや外部から取り込んだコードで、こちらが直す対象でない場合

## 関連

- `decide_or_ask.md`（自分で決めるか尋ねるか）: **尋ねる形は `AskUserQuestion`**。本ルールはその適用場面の 1 つ
- `verify_before_asserting.md`（断定の前に裏を取る）: 「直せない」も断定にあたる。**エラーの全文を読むまでは裏を取っていない**
- `write_for_installed_versions.md`（入っているバージョンで書く）: 手段 4 の根拠。型定義は版で変わる
