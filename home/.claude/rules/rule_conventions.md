# グローバルルールの書き方と整理

`~/.claude/rules/` に置くルールの追加・編集・整理の規約です。
これは全プロジェクト共通の規約です。

## プロジェクトルールとの違い

同じ「ルール」でも、置き場所によって性質が変わります。**プロジェクト側の書き方をそのまま持ち込まないでください。**

| | グローバル (`~/.claude/rules/`) | プロジェクト (`.claude/rules/`) |
| --- | --- | --- |
| ロード | **常に全文** | `paths` にマッチしたときだけ |
| 構成 | **1 層**（ルールに直接書く） | 2 層（ルールは入口、`docs/` が本体） |
| 内容 | 振る舞いの規約（コミット・レビュー・報告の仕方） | コードの規約（命名・配置・実装パターン） |
| 命名 | スネークケース (`no_auto_commit.md`) | ケバブケース (`data-fetching.md`) |

命名の型は 3 つある。**どれでもよいが、ファイル名だけで何の規約か分かること**を優先する。

| 型 | 使うとき | 例 |
| --- | --- | --- |
| `no_` 始まり | 禁止が主題 | `no_auto_commit` / `no_agent_coordination_in_pr` |
| 動詞始まり | 「〜せよ」が主題 | `verify_before_asserting` / `summarize_after_each_task` |
| 名詞句 | 書式・スタイルそのものが主題 | `karma_commit_style` / `plain_language_explanation` |

**改名は相互参照の追随コストが高い。** `## 関連` で参照し合っているので、型を揃えるためだけの改名は避ける。

`paths` は**プロジェクト内のファイルパス**にしかマッチしません。`~/.claude/skills/**` のようなプロジェクト外のパスは絞り込めないので、グローバルルールに `paths` は使いません。

## 期待する挙動

- **新設する前に `ls ~/.claude/rules/` で近い主題を見る。** 理由は `verify_before_asserting.md`（「無い」を語で判定しない）
- **節を足す前に `grep '^## '` で章立てを出す。** 章順の規約を知っていても、既存の並びを見ないと挿入先を誤る
- **1 ファイル 1 主題**にする。複数の主題が混ざったら分割し、`## 関連` で相互に参照する
- **常時ロードされることを意識して量を絞る**。判断に必要な情報（何を守るか・なぜか・例外）は残し、言い換えの反復と前置きを削る
- 章立ては次を基本にする。ただし**内容に即して変えてよい**

  ```
  # タイトル
  <1〜3 行の説明>
  これは全プロジェクト共通の規約です。

  ## 期待する挙動
  ## 禁止する挙動
  ## なぜ
  ## 例外
  ## 関連
  ```

- **見出し名は内容に合わせる**。文体の規約なら `## 期待するスタイル`、PR 説明の規約なら `## 期待する記述` でよい。機械的に `## 期待する挙動` へ揃えない
- **禁止が主題のルール（`no_` 始まり）は、禁止をタイトルとリード文で明示する**。`## 禁止する挙動` を節として置くなら `## 期待する挙動` より先。ただし 1 行で言える禁止に節を立てる必要はない
- `## なぜ` は必ず書く。理由が分かると、規約が想定していない場面でも判断できる
- **`## 関連` で相互に繋ぐ**。近い主題のルールが複数あるとき、どれが何を担うかを 1 行で示すと、読み手が両方を踏まえて判断できる

## 整理の契機

**このディレクトリに手を入れるときが、棚卸しのタイミングです。** 定期的に見直す必要はありません。次のどれかに当たったら、そのつど整理する。次の指示を待たず、提案まで出す。

| 契機 | 見直すこと |
| --- | --- |
| **ルールを追加・変更・削除した** | ディレクトリ全体。手を入れるたびに再編成する |
| **ルールを守れなかった／守らなかったと気づいた** | **そのルール自体**。逸脱はルール側の欠陥を示す信号 |
| **既定の挙動が変わったと分かった** | 埋めていた穴が塞がっていないか |
| **スキルや `CLAUDE.md` に汎用の規定を見つけた** | **ルールへ引き上げられないか**（下記） |
| **auto memory に書いた／書こうとした** | **ルールと重複していないか**、そして**実行時に効く場所へ落ちているか**（下記） |
| **失敗した／指摘を受けた** | その失敗を防ぐ規定が**どこに要るか**。メモリで足りるか、ルールやスキルの手順が要るか |

**1 行直しただけでも契機になります。** そのルールを読み返した時点で、隣に同じ主題が無いか・既定と重なっていないかが見えるためです。

守れなかったときに問うのは「次から気をつける」ではなく、**なぜ守られなかったか**。書き方が曖昧なのか、置き場所が悪いのか、そもそも不要なのか。原因に応じて書き直す・移す・消すのいずれかを選ぶ。**同じ逸脱が繰り返されるルールは、内容ではなく形に問題がある。**

### 学んだことを、どこに置くか

**失敗から学んだとき、メモリへ書いて終わりにしない。** メモリは読まれるが、**作業中に辿るのは手順のほう**なので、次に同じスキルを打てば同じ失敗をします。

置き場は「**次に同じ場面へ来たとき、何を見ているか**」で決める。

| 学んだこと | 置き場 |
| --- | --- |
| そのリポジトリ固有の事実（設計の前提・落とし穴） | **メモリ** |
| どのリポジトリでも効く振る舞いの規約 | **ルール** |
| **特定の作業中に必ず踏む判断** | **そのスキルの手順** |

**1 つに決めきらなくてよい。** 事実はメモリ、判断の基準はルール、実行時の手順はスキル——同じ学びが 3 か所に分かれることがあります。ただし**同じ文を 3 回書かない**。片方だけ古くなります。

**「メモリに書いた」で止まったかを疑う。** 失敗の再発を防げるのは、**その場面で開くもの**に書いたときだけです。

### 置き場をまたぐ整理

**良い規定が 1 つのスキルにだけ書かれていると、そのスキルを呼んだときしか効きません。** 汎用のものを見つけたらルールへ引き上げる。

| 元の場所 | 引き上げる判断 |
| --- | --- |
| `skills/*/SKILL.md` | **その作業に固有か**を見る。固有でないならルールへ移す |
| `CLAUDE.md` | 「〜せよ」と読めるならルールへ。前提の記述ならそのまま |
| **auto memory** | **どのリポジトリでも効く好みならルールへ。移したら元は消す**（下記） |

引き上げたあとは、**元を消さずに「土台はルール」と参照を張る**。スキル側には固有の事情（ツールのレンダリング挙動、テンプレの構成）が残るので、丸ごと移すと失われる。

**ルールが土台、スキルが上乗せ。** 両方に同じことを書かず、差分だけを持たせる。

#### 逆方向も見る——ルールにあるのに、手順に落ちていない

**引き上げだけでは片手落ちです。** ルールに書いてあっても、**そのとき呼ぶスキルの手順に無ければ実行時に落ちます**。ルールは読まれても、作業中に辿るのは手順のほうだからです。

| 症状 | 直し方 |
| --- | --- |
| ルールが求める作業が、対応するスキルの**手順に無い** | 手順として節を足す |
| スキルが**「〜してよい」「必要なら」**で書いている | ルールが求めているなら**手順へ格上げする** |
| スキルの `## 例外` に、ルールの本則が入っている | 例外から出す |

**「〜してよい」は最も見つけにくい形です。** 書いてあるので抜けに見えず、実際には毎回やらない理由になります。

**スキルとルールは、どちらを触っても対で見る。** ルールを足したら「これを実行するスキルの手順に入っているか」、スキルを直したら「土台のルールと食い違っていないか」を確かめる。

### auto memory との境界

auto memory（`~/.claude/projects/<project>/memory/`）は**自分が書く学習ノート**で、ルールは**ユーザーが承認した規約**です。`MEMORY.md` の索引は毎セッション読み込まれるので、**ルールと同じことを書けば同じ規約が 2 回ロードされます**。

| | ルール | auto memory |
| --- | --- | --- |
| 書き手 | ユーザーの承認を経て自分が書く | **自分が判断して書く** |
| 効く範囲 | **全リポジトリ** | そのリポジトリだけ |
| 内容 | 汎用の振る舞いの規約 | **そのリポジトリ固有の事実**（設計の前提・落とし穴・進行中の作業） |

**汎用の好みをメモリに書かない。** ルールへ引き上げてよいか尋ね、ルールにしたらメモリからは消す。**ここはスキルと違い「元を残して参照を張る」をしない**——どちらも常時ロードされるので、両方に残すと二重に読み込まれたうえ片方だけ古くなる。

**逆に、リポジトリ固有の事実をルールへ書かない。** それはメモリか、そのリポジトリの `.claude/rules/` の担当です。

**残すと判断したら、なぜ残すのかを 1 行添える。** ルールと主題が近いメモリは、次に整理する人が同じ判定をやり直します。**ルールに無い判定軸を名指しで書く**——「ユーザー指示由来も対象」「理由語で判定する」のように、どこが覆われていないかを示す。

**照合するのは主題ではなく判定軸。** 主題が同じでも、そのメモリだけが持つ判定の手順があれば別物です。原文を開かずに「近いから重複」と決めない。

## 分割・マージ・削除

見るのは次の 3 つ。

| 操作 | いつ | 何をする |
| --- | --- | --- |
| **分割** | 1 ファイルに主題が 2 つ以上ある | 主題ごとに分け、`## 関連` で繋ぐ |
| **マージ** | 同じ主題が複数ファイルに散っている | 1 つに寄せ、残りを消す。**近い主題を新設するより既存へ足す** |
| **削除** | そのルールが無くても挙動が変わらない | 消す。判断に迷うものは残し、**なぜ残すのかを 1 行添える** |

### 削除の判断

グローバルルールには、**Claude Code の既定の挙動が足りない部分を埋めているもの**があります。アップデートで既定に取り込まれたら、その時点で消す。

既定に入ったかは、ツールの説明文・実際に外して試す・リリースノートで確かめる。**裏を取れないまま「もう既定に入った」と断定しない**（`verify_before_asserting.md`）。

既定より**厳しい**運用を求めるルール、既定が不安定で明文化しておくと守られやすいルールは残してよい。その旨を本文に書く。

## 禁止する挙動

- **手を入れたルールだけ直して終えること**。追加でも 1 行の修正でも、分割・マージ・削除の見直しまでが 1 セット
- **逸脱を「次から気をつける」で閉じること**。守られなかったルールは、書き方・置き場所・要否のどれかを見直す
- 既定の挙動と同じことを書いたルールを新設すること
- 「念のため」で重複したルールを残し続けること
- `paths` frontmatter を書くこと（プロジェクト外のパスには効かない）
- 既存ルールと重なる内容を新しいファイルに書くこと。**既存を直すか、`## 関連` で繋ぐ**
- プロジェクト固有の事情（ディレクトリ構成・使用ライブラリ）を書くこと。それは**そのリポジトリの `.claude/rules/`** に置く
- 見出しを揃えるためだけに、内容と合わない名前へ変えること

## なぜ

- グローバルルールは**毎セッション全文が展開される**。量がそのままコンテキストのコストになる
- 振る舞いの規約は「守らせる」より「なぜそうするかを共有する」ほうが効く。想定外の場面でも判断がぶれない
- 置き場所を間違えると効かない。プロジェクト固有の規約をグローバルに置くと、関係ないリポジトリでも展開される
- **足すだけだと必ず増える。** 整理を編集とセットにしないと、本当に効かせたいルールが量に埋もれる
- 定期的な棚卸しは要らない。**触ったときに見れば足りる**うえ、触っていない期間に見直しても得るものが少ない
- 穴埋めのルールは、穴が塞がった時点で役目を終える。残す理由が「消す手間」だけなら消す

## 例外

- ユーザーが特定の書式を明示した場合はそれに従う

## 関連

- `align_skill_md_format.md`（グローバルスキルの書き方と整理）: ルールとスキルで置き場所が違う。**常に効かせたいものはルール、呼ばれたときだけ効くものはスキル**。整理の考え方は共通
- `concise_first_then_detail.md`（簡潔に書く）: ルール本文にも同じ基準を適用する
- `verify_before_asserting.md`（断定の前に裏を取る）: 「既定に入った」も裏取りの対象
- `ask_before_editing_claude_assets.md`（尋ねてから手を入れる）: **手を入れてよいかの判断**を規定する。本ルールは手を入れると決まった後の書き方と整理
