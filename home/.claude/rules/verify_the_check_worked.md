# 検査が成立していたかを、結果より先に疑う

**返ってきたものを結果とみなす前に、その検査が動いていたかを確かめて**ください。壊れた実行の出力は一次情報ではありません。
これは全プロジェクト共通の規約です。

**空でない結果が返ってきても、正しい結果とは限りません。** 探し方が壊れていた・読み方を誤った・検証の条件が実物と違った——いずれも**それらしい出力が返る**ので、確かめる動機が湧きません。

## 踏み方は 3 つに分かれる

**実測したつもりで、何も測れていないことがあります。** 実行結果は一次情報ですが、**壊れた実行の結果は一次情報ではありません**。

**踏み方は 3 つに分かれ、直し方も違います。** どれも根は「返ってきたものを結果とみなした」ですが、
**疑う先が違うので、混ぜると直せません**。

| 何が返ったか | 疑うもの | 直し方 |
| --- | --- | --- |
| 空だった / 件数が想定より少ない | **探し方** | **別の経路でもう一度数える** |
| 成功・緑・正常系のメッセージ | **読み方** | **件数と実体を見る** |
| テストが全部通った | **検証の条件** | **実物の入力で 1 回通す** |

**1 行目は想定があるときしか発動しません。** 初めて調べることでは「少ない」を判定できず、
**実際に気づけた 9 件のうち、想定と照合できたのは 1 件だけ**でした。残りは「結果の中身を開いた」
「実物を流した」「他者に指摘された」で気づいています。

**だから想定の有無に関わらず、次の 2 つを既定にする。**

- **その数を根拠に断定するなら、数える経路を 2 つ持つ**
- **成功表示で止めず、結果の中身と実体を開く**

### 探し方が壊れていないか

**「空の結果」を「該当なし」と読まない。** 空が返る経路は 2 つあり、**出力を見るだけでは区別できません**。

| 経路 | 例 |
| --- | --- |
| 探し方が正しく、本当に該当が無い | 違反が無いので `grep` が何も返さない |
| **探し方が壊れていて、何も探せていない** | パターンやパスが誤っている / 変数が空で引数が渡っていない / 参照が手元に無く `stderr` に出た警告をパイプで捨てている |

区別するには、**結果ではなくやり方のほうを先に確かめる**。次のどれかで足ります。

- **必ず当たるはずの入力**で試し、ちゃんと当たることを見る
- **別の方法で数え直す**（件数を出す経路を 2 つ持つ）
- **`stderr` を捨てていないか**見る
- **書いたなら読み返す**。書き込み・置換・復元は、**書いた先を読んで**反映されたか確かめる（上書きが拒否された・置換が空振りしたときも、後続の出力があるので成功したように見える）

**探索範囲が全体を覆っているかを確かめる。** 結果が非空でも、**見ていない場所があれば答えは違います**。同じものが 2 か所以上に置ける仕様（`skills` と `commands`、プロジェクトと個人環境）で特に起きる。**無いことを示すには、置ける場所を列挙してから数える。**

**リンク越しのディレクトリは `grep -r` で辿れない。** `~/.claude/` 配下は**ディレクトリ 1 つずつがシンボリックリンク**になっており、親を見てもリンクだと分かりません（`~/.claude` も `~/.claude/skills` も実ディレクトリです）。そこへ `grep -r` を掛けると、**リンクの下だけが黙って落ちます**。

**`-R` を当てにしない。** `grep` の実体はセッションによって変わります。Claude Code のシェルは `grep` を関数で覆っており、**発動していれば ugrep、していなければ素の `/usr/bin/grep`**。ところが**どちらも `--version` は `BSD grep, GNU compatible` を返す**ので、応答からは判別できません。

**リンクを `-R` で辿るかは実体で変わります**（実測: ugrep は 9 件、`/usr/bin/grep` は 0 件）。どちらでも通るのは次の 2 通り。

```bash
grep -rl '<語>' ~/.claude/skills/*/                              # 末尾 / でリンクを解決させる
grep -rl '<語>' home/.claude/skills/ private/.claude/skills/     # 実体を直接
```

**実体を確かめたいときは、BSD grep が持たないオプションで叩く**（`grep -P '\d' <file>` が `invalid option` なら素の BSD grep）。ただし**判別してから使い分けるより、上の 2 通りで書くほうが速い**。

**0 件が出たら、まず探せていたかを確かめる。** 同時に**必ず当たるはずの語**でも数えると、探索が効いているかが分かります。

**「無い」を語で判定しない。** 場所を全部見ていても、**同じ主題が別の言葉で書かれていれば当たりません**。「規約が無い」「その処理は存在しない」のように**不在を断定するとき**は、語ではなく主題で確かめる——一覧を出して目で見る（`ls`）、対象の型や定義から参照を辿る、思いつく限りの言い換えで引き直す。**1 語で引いて空だったことは、無いことの根拠になりません。**

**検査を作るときは、語の列挙より文字種や属性で見る。** 列挙した検査は**一覧から漏れたものを構造的に見逃し**、しかも通った側は結果に出ないので漏れに気づけません。実際に、公開してよいかを走査する検査が 0 件を返しましたが、**一覧に無い綴りが 2 箇所ありました**。

**「この語が入っていたら」ではなく「この文字種が隣り合っていたら」で書く。** 表記の検査なら助数詞を並べるより `[0-9] [ぁ-んァ-ヶ一-龠]` のような文字クラスの組で拾える。**列挙が避けられないなら、その一覧が主張の広さに足りているかを見る**——「その種の語が無い」を示すのに語の一覧で引くのは、循環しています。

### 返ってきたものを読み違えていないか

**既存ファイルへ書き出すときは `>` ではなく `>|` を使う。** シェルが上書きを拒む設定（zsh の `noclobber` 等）だと `>` は黙って失敗します。**空振りで済むとは限りません**——ループの中なら**前の周回で書いた内容がそのまま残り**、後続のコマンドはそれを読んで実行します。取得した 1 件を全件へ書き込む、といった破壊になる。

**成功を前提に後続を繋がない。** `&&` の前が黙って失敗すると**後続ごと消え**、期待した出力が出ないまま別の出力だけが並ぶので「実行したつもり」になります。**出力は末尾だけでなく、期待した行が出ているかで確かめる。**

**成功表示を「検査された」証拠にしない。** 検査ツールの多くは**対象 0 件でも成功を返します**。フックや CI が緑でも、除外設定に阻まれて 1 件も見ていないことがある。**`Checked N files` / `tests N` のような件数まで見る。**

空の出力より見つけにくい形です。空なら「何も出ていない」と気づけますが、**こちらは `✔️` が出ている**ので、確かめる動機そのものが湧きません。「動かした結果」ではなく「**何件に対して動いたか**」を見る癖にしておく。

**「見つかった」も検算する。** 空振りは「何も出ていない」と気づけますが、**誤検出は結果が出ているので手が止まりません**。件数を根拠にするなら、**必ず当たらない入力**でも試し、0 件が返ることを見る。

### `wc -l` が数えているのは「行」であって「件」ではない

**数える経路が正しくても、数える対象を取り違えると誤ります。** しかも**それらしい数が返る**ので、空振りと違って手が止まりません。

| 対象 | `wc -l` が返すもの | 正しい数え方 |
| --- | --- | --- |
| **JSON を出すコマンド** | **整形出力の行数** | `jq length` / `json.load` して `len()` |
| **設定ファイル** | コメントと空行を含む全行 | `grep -cv '^\s*#\|^\s*$'` |
| 複数行にまたがる項目 | 項目数ではなく行数 | 区切りで数える |

実際に、`carapace --list \| wc -l` で 5916 と報告しましたが**実体は 653**（JSON の行数を数えていた）、`deny-patterns.txt` を 28 件と報告しましたが**実体は 17 件**（コメントと空行込み）でした。**どちらも妥当に見える数字だったので、指摘されるまで気づいていません。**

**件数を根拠にするなら、出力形式を先に見る。** 先頭の数行を出せば、JSON か 1 行 1 件かは一目で分かります。

**見出しを行頭一致で拾うと、コードブロックの中まで数えます。** `grep '^## '` は、**サンプルとして埋め込んだ見出し**も節として拾います。実際に、サブエージェントへ渡すプロンプト内の `## レビュー条件` を節と読み、「節番号が割れている」と誤報しかけました。

```bash
awk '/^```/ { b = !b; next } !b && /^## / { print FILENAME ":" FNR ": " $0 }' <file>
```

**成立する範囲は、対のフェンスで開閉するものだけ。** ネストしたフェンス（4 バックティックの中に 3 バックティック）とインデントのコードブロックは拾えません。**構造を数えたら、原文を開いて確かめる。**

**日本語を含む行を `sort` / `uniq` で数えない。** macOS の `uniq -d` は**マルチバイトを含む行で、相異なる行を重複として報告します**（`LC_ALL` を UTF-8 にしても変わらない）。実際に、すべて 1 回ずつしか無い見出しを重複 3 件と誤報しました。**行番号付きで一覧を出して目で見る**（`grep -nE '^#{2,3} '`）ほうが確実です。

**変更の前後を比べるときは、派生物も一緒に戻す。** `git stash` や `git checkout` が戻すのは**ソースだけ**で、ビルド成果物（`dist`・生成コード・生成したモック）は古いまま残ります。参照が成果物側を向いていると（`package.json` の `exports` が `dist` を指す等）、ソースだけ戻した状態は**どちらの版でもありません**——存在しない組み合わせを測ることになる。

**前後で数が動いたら、まずその差が測り方から出ていないかを疑う。** 戻した側でも生成し直してから比べる。

### 検証の条件が実物と合っているか

**入力や対象を自分で選んだなら、実物で 1 回通す。** 組み立てた入力は**自分の想定どおりの形**で、
自分の対象は**自分が試した条件**です。どちらも、想定が違っていても全ケース通ります。

**「自分で作った入力」は最も気づきにくい形です。** 出力が空なら気づけますが、こちらは**テストが全部通ります**。

フック・パーサー・API のモック・テストの固定値——**入力の形を自分で決められるものは全部これに当たります**。実際に、`PostToolUse` フックを 13 ケースで通して登録しましたが、**実物のフィールド名が違っていた**ため一度も検出が走っていませんでした。ドキュメントの記載と実際の入力が食い違っており、**手元のテストはドキュメントの側に揃えていた**。

**確かめ方は 1 つ。実物を 1 回流し、入力そのものを控えて見る。** 形が合っていることを確かめてから、残りは組み立てた入力で回してよい。

**人から受け取った手順も同じです。** 渡した側は自分の対象でしか試していないので、**自分の対象で 1 回走らせてから使う**（`notify_related_repo_sessions.md` の「手順を渡すときは、成立する範囲まで添える」）。

**受け取るのが判定なら、基準ごと読み替える。** 手順は走らせれば合うか分かりますが、**判定は結果だけ渡ってくるので、どの基準で出したかが見えません**。

| 受け取るもの | 確かめ方 |
| --- | --- |
| **手順** | 自分の対象で 1 回走らせる |
| **判定・重要度・可否** | **その基準が自分の体系と同じかを見る**。同じ語でも定義が違う |

実際に、委譲先スキルの判定表で `must` とされたものを、そのままリポジトリの `[must]`（かならず変更して）として投稿し、取り下げました。**語は一致していましたが、基準は別物**でした。

**同じ語ほど危ういです。** 語が違えば読み替えますが、一致していると**そのまま通してしまいます**。

### 通ったのは「動かさない検査」かもしれない

**ビルド・型・lint・テストは、どれも動かさずに確かめるものです。** 全部通っても、**起動したら落ちる**ことがあります——
依存の初期化順、実行時にしか読まれない設定、バンドル後にだけ現れる解決の失敗は、静的な検査を通り抜けます。

**依存やツールのバージョンを上げたときは特に効きます。** 型が合っていることと、その版が実行時に期待どおり振る舞うことは別です。

| 対象 | 一度は確かめる |
| --- | --- |
| Web アプリ | 起動して **HTTP で叩き、応答を見る** |
| ライブラリ | 取り込む側から import して、代表的な関数を 1 つ動かす |
| CLI | `--version` か、最小のサブコマンドを実行する |

**動かせなかったなら、そう書く。** 環境変数が無い等で起動できないことはあります。**黙って飛ばして「動作確認済み」と報告しない。**

### 速さを測るなら、3 回測って平均を取る

**1 回の計測は数字として弱い。** マシンの負荷・ファイルキャッシュの温まり方・裏で動いている他のプロセスで簡単に上下します。
**3 回測って平均を出す。**

| 揃えること | なぜ |
| --- | --- |
| **キャッシュを毎回捨てる** | 2 回目が速いのは、そのツールが速いからではない。**タスクランナーだけでなく、各ツール固有のキャッシュも消す** |
| **比較対象を交互に測る** | まとめて測ると、**後に測った側がキャッシュの恩恵を受けます** |
| **同じマシン・同じ条件** | 別環境の数字を並べても比較になりません |

**ばらつきも見る。** 3 回が大きく散っていたら平均に意味がないので、条件を疑って測り直す。

**報告には計測条件を添える。** 何回測ったか・キャッシュをどう扱ったかが無いと、読み手はその数字を信用できません。

## 禁止する挙動

- **空の出力を「該当なし」として報告すること**。探し方が正しかったことを先に確かめる
- **1 語で引いて空だったことを、無いことの根拠にすること**。不在の断定は主題で確かめる
- **語を並べて作った検査の結果を、不在の根拠にすること**。一覧から漏れたものは結果に出ないので、漏れ自体に気づけない
- **成功表示だけを根拠に「検査した」と書くこと**。件数を見る
- **`wc -l` の結果を件数として報告すること**。JSON なら整形の行数、設定ファイルならコメント込みの行数になる
- **ソースだけ戻して前後を比べること**。ビルド成果物が古いままだと、存在しない状態を測ることになる
- **自分で組み立てた入力だけでテストを通して、動くと判断すること**。実物と形が違っていても全ケース通る
- **静的な検査が通ったことを「動く」と報告すること**。起動時の失敗は出ない
- **1 回だけ測った数字を性能の根拠にすること**。3 回測って平均を取り、キャッシュを毎回捨てる
- コマンドが**成功したことを確かめずに**、その結果を根拠に使うこと
- **既存ファイルへ `>` で書き出すこと**。拒まれても後続は走り、古い内容で上書きしうる

## なぜ

- **空振りは気づけるが、誤検出は手が止まらない。** 0 件なら疑いますが、それらしい数字が返ると検算する動機が湧かない
- 壊れた検査は**「該当なし」と同じ出力**を返す。**出力からは区別できない**ので、やり方の側を確かめるしかない
- 検査の成功表示は「対象 0 件」でも出る。**何件に対して動いたか**を見ないと、検査したことにならない

## 例外

- ユーザーが「裏取り不要」と明示した場合
- 使い捨ての確認（結果を根拠に何も書かない場合）
