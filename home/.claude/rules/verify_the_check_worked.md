# 検査が成立していたかを、結果より先に疑う

**返ってきたものを結果とみなす前に、その検査が動いていたかを確かめて**ください。壊れた実行の出力は一次情報ではありません。
これは全プロジェクト共通の規約です。

**空でない結果が返ってきても、正しい結果とは限りません。** 探し方が壊れていた・読み方を誤った・検証の条件が実物と違った。いずれも**それらしい出力が返る**ので、確かめる動機が湧きません。

## 踏み方は3つに分かれる

**実測したつもりで、何も測れていないことがあります。** 実行結果は一次情報ですが、**壊れた実行の結果は一次情報ではありません**。

**踏み方は3つに分かれ、直し方も違います。** どれも根は「返ってきたものを結果とみなした」ですが、
**疑う先が違うので、混ぜると直せません**。

| 何が返ったか | 疑うもの | 直し方 |
| --- | --- | --- |
| 空だった / 件数が想定より少ない | **探し方** | **別の経路でもう一度数える** |
| 成功・緑・正常系のメッセージ | **読み方** | **件数と実体を見る** |
| テストが全部通った | **検証の条件** | **実物の入力で1回通す** |

**1行目は想定があるときしか発動しません。** 初めて調べることでは「少ない」を判定できず、
**実際に気づけた9件のうち、想定と照合できたのは1件だけ**でした。残りは「結果の中身を開いた」
「実物を流した」「他者に指摘された」で気づいています。

**だから想定の有無に関わらず、次の2つを既定にする。**

- **その数を根拠に断定するなら、数える経路を2つ持つ**
- **成功表示で止めず、結果の中身と実体を開く**

### 探し方が壊れていないか

**「空の結果」を「該当なし」と読まない。** 空が返る経路は2つあり、**出力を見るだけでは区別できません**。

| 経路 | 例 |
| --- | --- |
| 探し方が正しく、本当に該当が無い | 違反が無いので `grep` が何も返さない |
| **探し方が壊れていて、何も探せていない** | パターンやパスが誤っている / 変数が空で引数が渡っていない / 参照が手元に無く `stderr` に出た警告をパイプで捨てている |

区別するには、**結果ではなくやり方のほうを先に確かめる**。次のどれかで足ります。

- **必ず当たるはずの入力**で試し、ちゃんと当たることを見る
- **別の方法で数え直す**（件数を出す経路を2つ持つ）
- **`stderr` を捨てていないか**見る
- **書いたなら読み返す**。書き込み・置換・復元は、**書いた先を読んで**反映されたか確かめる（上書きが拒否された・置換が空振りしたときも、後続の出力があるので成功したように見える）

**探索範囲が全体を覆っているかを確かめる。** 結果が非空でも、**見ていない場所があれば答えは違います**。同じものが2か所以上に置ける仕様（ `skills` と `commands`、プロジェクトと個人環境）で特に起きる。**置ける場所を列挙してから数える。**

**不在を示すときだけではありません。一覧・件数・棚卸しを出すときも同じです。** こちらのほうが漏らしやすい。**列挙しているとき、自分では「無いことを示している」と思っていない**ので、確かめる動機が湧きません。しかも結果は非空なので、空振りのようには見えません。

| 出すもの | 先にやること |
| --- | --- |
| 「〜は無い」 | 置ける場所を列挙する |
| **「〜は N 件」「内訳はこう」** | **同じく列挙する。件数より先に置き場を確かめる** |

実際に、`migrates/` の下が `schema` と `seeder` に分かれているリポジトリで、`schema/` だけを走査して件数を報告しました。**同じ日に2回踏み、渡した相手も同じ穴に落ちています**（件数だけ伝えてパスを添えなかったため）。

**リンク越しのディレクトリは `grep -r` で辿れない。** `~/.claude/` 配下は**ディレクトリ1つずつがシンボリックリンク**になっており、親を見てもリンクだと分かりません（ `~/.claude` も `~/.claude/skills` も実ディレクトリです）。そこへ `grep -r` を掛けると、**リンクの下だけが黙って落ちます**。

**`-R` を当てにしない。** `grep` の実体はセッションによって変わります。Claude Code のシェルは `grep` を関数で覆っており、**発動していれば ugrep、していなければ素の `/usr/bin/grep`**。ところが**どちらも `--version` は `BSD grep, GNU compatible` を返す**ので、応答からは判別できません。

**リンクを `-R` で辿るかは実体で変わります**（実測: ugrep は9件、`/usr/bin/grep` は0件）。どちらでも通るのは次の2通り。

```bash
grep -rl '<語>' ~/.claude/skills/*/                              # 末尾 / でリンクを解決させる
grep -rl '<語>' home/.claude/skills/ private/.claude/skills/     # 実体を直接
```

**実体を確かめたいときは、BSD grep が持たないオプションで叩く**（ `grep -P '\d' <file>` が `invalid option` なら素の BSD grep）。ただし**判別してから使い分けるより、上の2通りで書くほうが速い**。

**0件が出たら、まず探せていたかを確かめる。** 同時に**必ず当たるはずの語**でも数えると、探索が効いているかが分かります。

**「無い」を語で判定しない。** 場所を全部見ていても、**同じ主題が別の言葉で書かれていれば当たりません**。「規約が無い」「その処理は存在しない」のように**不在を断定するとき**は、語ではなく主題で確かめる。一覧を出して目で見る（ `ls` ）、対象の型や定義から参照を辿る、思いつく限りの言い換えで引き直す。**1語で引いて空だったことは、無いことの根拠になりません。**

**検査を作るときは、語の列挙より文字種や属性で見る。** 列挙した検査は**一覧から漏れたものを構造的に見逃し**、しかも通った側は結果に出ないので漏れに気づけません。実際に、公開してよいかを走査する検査が0件を返しましたが、**一覧に無い綴りが2箇所ありました**。

**「この語が入っていたら」ではなく「この文字種が隣り合っていたら」で書く。** 表記の検査なら助数詞を並べるより `[0-9] [ぁ-んァ-ヶ一-龠]` のような文字クラスの組で拾える。**列挙が避けられないなら、その一覧が主張の広さに足りているかを見る**。「その種の語が無い」を示すのに語の一覧で引くのは、循環しています。

#### 一時的に壊して確かめたら、戻したことを確かめてから離れる

**検査が効いているかを見る最も確実な方法は、わざと違反を入れて落ちることを見ることです。** ただし**その改変が残ると、次に読む人には正しいコードに見えます**。

**同じ作業ツリーを別のセッションが使っているなら、残骸はそのまま相手のブランチへ混ざります。** 自分のブランチへ戻す前提でいると、**相手がコミットするまで誰も気づきません**。

| 順 | やること |
| --- | --- |
| 1 | 改変を入れて、**検査が落ちることを見る** |
| 2 | 戻す |
| 3 | **戻ったことを確かめる**（ `git status` が clean か、`grep` で0件か） |

**3を飛ばさない。** 復元のコマンドは黙って失敗します。実際に `cp` が上書き確認で止まり、**`not overwritten` と出ているのに次のコマンドへ進んで**残骸が残りました（ `\cp -f` を使う）。

**戻し方は、そのとき未コミットの変更が何本あるかで変わります。**

| 状況 | 戻し方 |
| --- | --- |
| **壊した分だけが未コミット** | **`git checkout -- <path>`**。退避と書き戻しの両方が要る形より、失敗する箇所が少ない |
| **他にも未コミットの変更がある** | **壊す前にコピーして控え、`\cp -f` で戻す** |

**2つ目を取り違えると、直したばかりの変更ごと消えます。** `git checkout` は HEAD へ戻すので、**壊した分と直した分を区別しません**。

実際に1日で4回踏みました。いずれも「検査用に壊した分」と「その検査で見つけた修正」が同時に未コミットで、`git checkout` が両方を消しています。**戻した後に検査が通っても、それは修正が消えたからでした。**

**判定は「壊す前に `git status` へ何行あるか」。** 1行でないなら控える。

### 数えた対象に、自分の差分が入っていないか

**「既存の流儀に合わせる」と判断するとき、その「既存」が自分の差分でないかを確かめる。** 同じ作業ツリーでは区別が付きません。

実際に、テストの並列化が1件あるのを「既存」と読んで根拠にしましたが、**その1件は自分が同じ変更で足したもの**でした。
探索範囲は正しく、件数も正しく返っています。**見ていた時点だけが違った。**

| 数えるもの | 見る先 |
| --- | --- |
| **既存の流儀・多数派** | **base 側**（ `git show BASE:PATH` ） |
| 変更後の状態 | 作業ツリー |

**「repo に何件あるか」も同じ。** 提示された案のうち片方を選ぶとき、**多数派を数えずに選ぶと、唯一その形でない状態を作ります**。
どちらも「既存」を主観で判定しており、数えれば分かることを数えていません。

**判定は「その数に自分が寄与しているか」。** 寄与しているなら、それは既存ではありません。

**数を渡すときは、どう数えたかを1語添える。** 上は自分が数えるときの話で、渡すときは別の面です。受け取る側は自分の手元で数え直すので、**数え方が違えば別の数が出ます**。

| 数え方 | 書き方 |
| --- | --- |
| コミット済みの状態から | 「HEAD から」 |
| 直前の作業ツリーから | 「編集前から」 |
| 自分の変更を除いて | 「base 側で」 |
| **1000で割るか1024で割るか** | **「MB」か「MiB」を明示**（ `du -h` の `M` は MiB） |

実際に1日で3回、起点を書かずに数を渡して食い違わせました（索引の件数・落とした読点の数・ファイルの行数）。**どれも数えた手順は正しく、見ていた時点だけが違っています。**

### 返ってきたものを読み違えていないか

**既存ファイルへ書き出すときは `>` ではなく `>|` を使う。** シェルが上書きを拒む設定（zsh の `noclobber` 等）だと `>` は黙って失敗します。**空振りで済むとは限りません**。ループの中なら**前の周回で書いた内容がそのまま残り**、後続のコマンドはそれを読んで実行します。取得した1件を全件へ書き込む、といった破壊になる。

**成功を前提に後続を繋がない。** `&&` の前が黙って失敗すると**後続ごと消え**、期待した出力が出ないまま別の出力だけが並ぶので「実行したつもり」になります。**出力は末尾だけでなく、期待した行が出ているかで確かめる。**

**パイプを挟んだら `$?` は最後のコマンドの終了コードです。** `cmd | tail` の後で読むと `tail` の値を拾い、`cmd` が落ちていても0が返ります。**確かめたつもりで別のものを見る**形なので、成功表示を疑う癖では防げません。パイプを外すか、`${PIPESTATUS[0]}` か `set -o pipefail` を使う。

**`cd` が失敗しても後続は走ります。** 別名（zoxide 等）が `cd` を覆っていると `no match found` を出しながら次へ進み、**別のディレクトリで実行されます**。`cd <path> || exit 1` で繋ぐ。

**成功表示を「検査された」証拠にしない。** 検査ツールの多くは**対象0件でも成功を返します**。フックや CI が緑でも、除外設定に阻まれて1件も見ていないことがある。**`Checked N files` / `tests N` のような件数まで見る。**

空の出力より見つけにくい形です。空なら「何も出ていない」と気づけますが、**こちらは `✔️` が出ている**ので、確かめる動機そのものが湧きません。「動かした結果」ではなく「**何件に対して動いたか**」を見る癖にしておく。

**「見つかった」も検算する。** 空振りは「何も出ていない」と気づけますが、**誤検出は結果が出ているので手が止まりません**。件数を根拠にするなら、**必ず当たらない入力**でも試し、0件が返ることを見る。

### 主張を確かめるなら、偽なら落ちる例を選ぶ

**成り立つ側の例だけを流すと、必ず追認になります。** 反証しに行ったつもりでも、入力を自分で選べる限り、主張が通る例を作ってしまいます。

| 確かめること | 用意する入力 |
| --- | --- |
| 検査が効くか | 必ず当たる入力 |
| 検査が過剰でないか | 必ず当たらない入力 |
| **主張が正しいか** | **その主張が偽なら落ちる入力** |

実際に「日本語の文章では塊で取れる」を3例で確かめ、**3例とも共通文字がゼロ**だったため全部通りました。共通文字がある例を1つ入れれば偽と分かります。

**「どちらでも通る例」を何回流しても、確かめたことになりません。**

### `wc -l` が数えているのは「行」であって「件」ではない

**数える経路が正しくても、数える対象を取り違えると誤ります。** しかも**それらしい数が返る**ので、空振りと違って手が止まりません。

| 対象 | `wc -l` が返すもの | 正しい数え方 |
| --- | --- | --- |
| **JSON を出すコマンド** | **整形出力の行数** | `jq length` / `json.load` して `len()` |
| **設定ファイル** | コメントと空行を含む全行 | `grep -cv '^\s*#\|^\s*$'` |
| 複数行にまたがる項目 | 項目数ではなく行数 | 区切りで数える |
| **同じ語を複数回出すツールの出力** | **出現数（対象数の倍数）** | **対象の識別子で数える** |

実際に、`carapace --list \| wc -l` で5916と報告しましたが**実体は653**（JSON の行数を数えていた）、`deny-patterns.txt` を28件と報告しましたが**実体は17件**（コメントと空行込み）でした。**どちらも妥当に見える数字だったので、指摘されるまで気づいていません。**

実際に `suiko` の検出を `grep -o … | wc -l` で数えて8本としましたが、実体は4本です。**1ファイルにつき、カテゴリ別の内訳と警告行の2回出ます。** **倍になった数字も妥当に見える**ので、内訳を並べるまで気づきません。

**`diff | grep '^[+-][^+-]'` は Markdown の箇条書きを落とします。** `- ` で始まる行は diff で `--` になるので、`---` ヘッダを除くつもりのパターンが**本文を弾きます**。差分が空で返ったら、`wc -l` で生の行数を見る。

**件数を根拠にするなら、出力形式を先に見る。** 先頭の数行を出せば、JSON か1行1件かは一目で分かります。

**見出しを行頭一致で拾うと、コードブロックの中まで数えます。** `grep '^## '` は、**サンプルとして埋め込んだ見出し**も節として拾います。実際に、サブエージェントへ渡すプロンプト内の `## レビュー条件` を節と読み、「節番号が割れている」と誤報しかけました。

```bash
awk '/^```/ { b = !b; next } !b && /^## / { print FILENAME ":" FNR ": " $0 }' <file>
```

**成立する範囲は、対のフェンスで開閉するものだけ。** ネストしたフェンス（4バックティックの中に3バックティック）とインデントのコードブロックは拾えません。**構造を数えたら、原文を開いて確かめる。**

**日本語を含む行を `sort` / `uniq` で数えない。** macOS の `uniq -d` は**マルチバイトを含む行で、相異なる行を重複として報告します**（ `LC_ALL` を UTF-8にしても変わらない）。実際に、すべて1回ずつしか無い見出しを重複3件と誤報しました。**行番号付きで一覧を出して目で見る**（ `grep -nE '^#{2,3} '` ）ほうが確実です。

**変更の前後を比べるときは、派生物も一緒に戻す。** `git stash` や `git checkout` が戻すのは**ソースだけ**で、ビルド成果物（ `dist`・生成コード・生成したモック）は古いまま残ります。参照が成果物側を向いていると（ `package.json` の `exports` が `dist` を指す等）、ソースだけ戻した状態は**どちらの版でもありません**。存在しない組み合わせを測ることになる。

**前後で数が動いたら、まずその差が測り方から出ていないかを疑う。** 戻した側でも生成し直してから比べる。

### 検証の条件が実物と合っているか

**入力や対象を自分で選んだなら、実物で1回通す。** 組み立てた入力は**自分の想定どおりの形**で、
自分の対象は**自分が試した条件**です。どちらも、想定が違っていても全ケース通ります。

**「自分で作った入力」は最も気づきにくい形です。** 出力が空なら気づけますが、こちらは**テストが全部通ります**。

フック・パーサー・API のモック・テストの固定値。**入力の形を自分で決められるものは全部これに当たります**。実際に、`PostToolUse` フックを13ケースで通して登録しましたが、**実物のフィールド名が違っていた**ため一度も検出が走っていませんでした。ドキュメントの記載と実際の入力が食い違っており、**手元のテストはドキュメントの側に揃えていた**。

**確かめ方は1つ。実物を1回流し、入力そのものを控えて見る。** 形が合っていることを確かめてから、残りは組み立てた入力で回してよい。

**人から受け取った手順も同じです。** 渡した側は自分の対象でしか試していないので、**自分の対象で1回走らせてから使う**（ `notify_related_repo_sessions.md` の「手順を渡すときは、成立する範囲まで添える」）。

**受け取るのが判定なら、基準ごと読み替える。** 手順は走らせれば合うか分かりますが、**判定は結果だけ渡ってくるので、どの基準で出したかが見えません**。

| 受け取るもの | 確かめ方 |
| --- | --- |
| **手順** | 自分の対象で1回走らせる |
| **判定・重要度・可否** | **その基準が自分の体系と同じかを見る**。同じ語でも定義が違う |

実際に、委譲先スキルの判定表で `must` とされたものを、そのままリポジトリの `[must]` （かならず変更して）として投稿し、取り下げました。**語は一致していましたが、基準は別物**でした。

**同じ語ほど危ういです。** 語が違えば読み替えますが、一致していると**そのまま通してしまいます**。

### 通ったのは「動かさない検査」かもしれない

**ビルド・型・lint・テストは、どれも動かさずに確かめるものです。** 全部通っても、**起動したら落ちる**ことがあります。
依存の初期化順、実行時にしか読まれない設定、バンドル後にだけ現れる解決の失敗は、静的な検査を通り抜けます。

**依存やツールのバージョンを上げたときは特に効きます。** 型が合っていることと、その版が実行時に期待どおり振る舞うことは別です。

| 対象 | 一度は確かめる |
| --- | --- |
| Web アプリ | 起動して **HTTP で叩き、応答を見る** |
| ライブラリ | 取り込む側から import して、代表的な関数を1つ動かす |
| CLI | `--version` か、最小のサブコマンドを実行する |

**動かせなかったなら、そう書く。** 環境変数が無い等で起動できないことはあります。**黙って飛ばして「動作確認済み」と報告しない。**

### 速さを測るなら、3回測って平均を取る

**1回の計測は数字として弱い。** マシンの負荷・ファイルキャッシュの温まり方・裏で動いている他のプロセスで簡単に上下します。
**3回測って平均を出す。**

| 揃えること | なぜ |
| --- | --- |
| **キャッシュを毎回捨てる** | 2回目が速いのは、そのツールが速いからではない。**タスクランナーだけでなく、各ツール固有のキャッシュも消す** |
| **比較対象を交互に測る** | まとめて測ると、**後に測った側がキャッシュの恩恵を受けます** |
| **同じマシン・同じ条件** | 別環境の数字を並べても比較になりません |

**ばらつきも見る。** 3回が大きく散っていたら平均に意味がないので、条件を疑って測り直す。

**報告には計測条件を添える。** 何回測ったか・キャッシュをどう扱ったかが無いと、読み手はその数字を信用できません。

#### 待ち時間は、計測器が値を作っていないか先に見る

**自動操作のツールで待ち時間を測ると、そのツールの都合が数字に混ざります。** 「要素が見えるまで待つ」系の API はポーリング周期と安定判定を挟むので、**画面が出た後もしばらく返りません**。

| 症状 | 疑うもの |
| --- | --- |
| **待ち時間の割に CPU が idle** | 計測器が待っているだけ。アプリは終わっている |
| **手段を変えると値が変わる** | 値は現象ではなく手段から出ている |
| **プロファイルの上位が計測器の関数** | 自分自身を測っている |

**ブラウザ内から測る。** `performance` の指標と `MutationObserver` なら外側のポーリングが混ざりません。**画面がいつ変わったか**を、画面自身に答えさせる。

実際に、同じ操作を6通りの手段で測って毎回違う値が出ました。原因はすべて手段の側で、**現象は1つも変わっていません**。

**2回目以降が速いならキャッシュを疑う。** アプリ側のキャッシュ（ルーターの保持など）は「同じ操作を繰り返す」形の計測で必ず効きます。**初回だけ遅いのか毎回遅いのか**は別の事実なので、分けて報告する。

## 禁止する挙動

- **空の出力を「該当なし」として報告すること**。探し方が正しかったことを先に確かめる
- **1語で引いて空だったことを、無いことの根拠にすること**。不在の断定は主題で確かめる
- **語を並べて作った検査の結果を、不在の根拠にすること**。一覧から漏れたものは結果に出ないので、漏れ自体に気づけない
- **一覧・件数・内訳を、置き場を列挙する前に出すこと**。不在の断定と同じ確認が要る。**結果が非空なので空振りに見えず、確かめる動機が湧かない**
- **成功表示だけを根拠に「検査した」と書くこと**。件数を見る
- **主張を、それが成り立つ側の例だけで確かめること**。偽なら落ちる入力を1つ入れる
- **「既存の流儀」を、自分の差分を含んだ状態で数えること**。base 側を見る。同じ作業ツリーでは自分が足した分と区別が付かない
- **数を渡すときに、どこを起点に数えたかを書かないこと**。受け取る側は手元で数え直すので、起点が違えば別の数になる
- **`wc -l` の結果を件数として報告すること**。JSON なら整形の行数、設定ファイルならコメント込みの行数になる
- **ソースだけ戻して前後を比べること**。ビルド成果物が古いままだと、存在しない状態を測ることになる
- **自分で組み立てた入力だけでテストを通して、動くと判断すること**。実物と形が違っていても全ケース通る
- **静的な検査が通ったことを「動く」と報告すること**。起動時の失敗は出ない
- **1回だけ測った数字を性能の根拠にすること**。3回測って平均を取り、キャッシュを毎回捨てる
- **自動操作ツールの待ち時間を、そのまま体感時間として報告すること**。ポーリング周期が値を作る。ブラウザ内から測る
- コマンドが**成功したことを確かめずに**、その結果を根拠に使うこと
- **既存ファイルへ `>` で書き出すこと**。拒まれても後続は走り、古い内容で上書きしうる

## なぜ

- **空振りは気づけるが、誤検出は手が止まらない。** 0件なら疑いますが、それらしい数字が返ると検算する動機が湧かない
- 壊れた検査は**「該当なし」と同じ出力**を返す。**出力からは区別できない**ので、やり方の側を確かめるしかない
- 検査の成功表示は「対象0件」でも出る。**何件に対して動いたか**を見ないと、検査したことにならない

## 例外

- ユーザーが「裏取り不要」と明示した場合
- 使い捨ての確認（結果を根拠に何も書かない場合）
