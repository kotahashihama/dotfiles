# 検査が成立していたかを、結果より先に疑う

返ってきたものを結果とみなす前に、**その検査が動いていたかを確かめて**ください。壊れた実行の出力は一次情報ではありません。
これは全プロジェクト共通の規約です。

壊れた検査も、それらしい出力を返します。空でない結果や成功表示が返っても、正しいとは限りません。

## 踏み方は3つあり、疑う先が違う

| 何が返ったか | 疑うもの | 直し方 |
| --- | --- | --- |
| 空だった / 件数が想定より少ない | 探し方 | 別の経路でもう一度数える |
| 成功・緑・正常系のメッセージ | 読み方 | 件数と実体を見る |
| テストが全部通った | 検証の条件 | 実物の入力で1回通す |

想定と照らせるのは1行目だけです。初めて調べることでは「少ない」を判定できないので、想定の有無に関わらず次の2つを既定にします。

- その数を根拠に断定するなら、**数える経路を2つ持つ**
- 成功表示で止めず、結果の中身と実体を開く

2つの経路が食い違ったら、両方を同じ入力へ突き合わせる。片方の出力から他方の挙動を説明しない。一致しても、それは「その入力が差の出る条件を通らなかった」ことしか意味しません。**同じ走査エンジンを共有する2つ**（ `grep -c` と `grep -o` ）は、弱点も共有するので対照になりません。

## 探し方が壊れていないか

**「空の結果」を「該当なし」と読まない。** 探し方が壊れていても空が返ります。やり方の側を次のどれかで確かめる。

- 必ず当たるはずの入力で試す
- 別の方法で数え直す
- `stderr` を捨てていないか見る
- 書き込み・置換・復元のあとは、書いた先を読んで反映を確かめる

**置き場を列挙してから数える。** 同じものが2か所以上に置ける仕様（skills と commands、プロジェクトと個人環境）では、見ていない場所があれば答えが違います。不在の断定だけでなく、一覧・件数・内訳を出すときも同じです。結果が非空なので、漏れに気づけません。

**シンボリックリンクは再帰の走査から落ちる。** `~/.claude/` 配下はディレクトリ1つずつがリンクです。`grep -R` が辿るかは `grep` の実体（ugrep か BSD grep）で変わり、`--version` では見分けられないので、どちらでも通る書き方にする。

```bash
grep -rl '<語>' ~/.claude/skills/*/                              # 末尾 / でリンクを解決させる
grep -rl '<語>' home/.claude/skills/ private/.claude/skills/     # 実体を直接
```

リンクのファイルは `-r` を付けずに渡すか、`readlink -f` で実体に変えてから渡す。ディレクトリと混ぜると `-r` が要り、ファイルだけが黙って落ちます。Python の `glob('**')` と `rglob` もリンクを辿らないので、段を明示するか `recurse_symlinks=True` （3.13以降）を使う。

**陽性対照は、0件を報告してよいかの条件として先に置く。** 0件を見た後では「念のため」を挟む動機が湧きません。対照は使い回さず、その回の中でスクラッチパッドに作って使い切る。消えた対照や中身の変わった対照は、本命と同じ0件を返すからです。

**「無い」を1語で判定しない。** 同じ主題が別の言葉で書かれていれば当たりません。不在は主題で確かめる（一覧を目で見る、定義から参照を辿る、言い換えで引き直す）。検査を作るときも、語の一覧より文字種や属性で書く。一覧から漏れたものは結果に出ないので、漏れ自体に気づけません。

### 壊して確かめたら、戻ったことを確かめてから離れる

わざと違反を入れて検査が落ちるのを見るのは確実な方法ですが、残骸は次に読む人に正しいコードとして見えます。作業ツリーを共有する別のセッションのブランチにも混ざります。

1. 改変を入れて、検査が落ちることを見る
2. 戻す
3. **戻ったことを確かめる**（ `git status` が clean か、`grep` で0件か）。復元のコマンドは黙って失敗する（ `cp` の上書き確認で止まる等。`\cp -f` を使う）

戻し方は、壊す前の `git status` の行数で決める。壊した分だけなら `git checkout -- <path>` （ステージ済みなら `git checkout HEAD -- <path>` ）。他にも未コミットの変更があるなら、壊す前にコピーして控え、`\cp -f` で戻す。`git checkout` は壊した分と直した分を区別しないので、直したばかりの変更ごと消えます。

## 数えた対象に、自分の差分や他の作業ツリーが入っていないか

**「既存の流儀」は base 側で数える**（ `git show BASE:PATH` ）。同じ作業ツリーでは、自分が足した分と既存の分を区別できません。判定は「その数に自分が寄与しているか」。

リポジトリの中に `.claude/worktrees/` があると、`grep -r` は別のブランチのチェックアウトまで数えます。**「このリポジトリに何件あるか」は `git grep` で数える**（ `grep -r` なら `--exclude-dir=worktrees` ）。

**数を渡すときは、起点と対象を1語添える**（「HEAD から」「base 側で」「この2ファイルで」「MiB で」）。受け取る側は手元で数え直すので、数え方が違えば別の数が出ます。

## 調べた対象が、origin に対して古くないか

長く動いているブランチでは、調べている間に base が進みます。古い base で調べると、正しい指摘に対して逆向きの修正をします。`git fetch` して `git rev-list --count HEAD..origin/<base>` を見て、差があれば `git show origin/<base>:<path>` で読む。HEAD は動かさない（ `notify_related_repo_sessions.md` ）。

## 返ってきたものを読み違えていないか

- 既存ファイルへの書き出しは `>|`。`>` は noclobber で黙って失敗し、ループでは前の周回の内容が残る
- 成功を前提に `&&` で後続を繋がない。期待した行が出ているかで確かめる
- パイプの後の `$?` は最後のコマンドの値。`${PIPESTATUS[0]}` （zsh は `${pipestatus[1]}` ）か `set -o pipefail` を使う。**バックグラウンドの完了通知の終了コードも同じ**なので、集計行の件数で判定する
- 完了通知が来ても出力ファイルが無いことがある。存在を先に見て、無ければ前景で流し直す
- `cd` が失敗しても後続は走る。`cd <path> || exit 1` で繋ぐ
- **成功表示を「検査された」証拠にしない。** 対象0件でも成功を返すツールは多い。`Checked N files` のような件数まで見る
- 「見つかった」も検算する。必ず当たらない入力で0件が返ることを見る
- コマンドの形を見る仕組み（フック）は、変数展開で渡した中身を検査できない。弾かれた理由が中身と合わないときは渡し方を疑う
- ヒアドキュメントに私用領域の文字（ `U+E000` 〜 `U+F8FF` ）を実体で書くと空になる。エスケープで書く

## 入力は、偽なら落ちるものを選ぶ

成り立つ側の例だけを流すと、必ず追認になります。

| 確かめること | 用意する入力 |
| --- | --- |
| 検査が効くか | 必ず当たる入力 |
| 検査が過剰でないか | 必ず当たらない入力 |
| 主張が正しいか | その主張が偽なら落ちる入力 |
| 壊れているかもしれない部分 | **その部分を通る入力**（深い階層・リンクの下・境目の両側） |

必ず当たる入力でも、疑っている条件を通らなければ対照になりません。区切り文字（バッククォート・引用符・括弧）を含む検査は、拾うべき入力と拾ってはいけない入力の両方を並べる。片方への対策がもう片方を招きます。

## 数える単位を取り違えない

数える経路が正しくても、数える対象を取り違えると誤ります。しかもそれらしい数が返るので、手が止まりません。

| 対象 | 誤りやすい数え方 | 正しい数え方 |
| --- | --- | --- |
| JSON を出すコマンド | `wc -l` （整形の行数） | `jq length` |
| 設定ファイル | `wc -l` （コメント・空行込み） | `grep -cv '^\s*#\|^\s*$'` |
| 同じ語を複数回出すツールの出力 | 出現数 | 対象の識別子で数える |
| `git diff --stat` | 追加行数と読む（実際は追加＋削除） | `--numstat` |
| Markdown の見出し | `grep '^## '` （コードブロックの中も拾う） | フェンスを除いてから数える |
| 日本語を含む行 | `sort` / `uniq` （別の行を重複と報告する） | 行番号付きで一覧を出して見る |

`diff | grep '^[+-][^+-]'` は箇条書きの行を落とします。件数を根拠にするなら、先頭の数行で出力の形式を見てから数える。変更の前後を比べるときは、ビルド成果物などの派生物も一緒に戻す。前後で数が動いたら、まず測り方から差が出ていないかを疑う。

## 自分で切った出力から集計しない

`head` / `tail` / `sed -n` で切った出力は、完全な一覧と見分けが付きません。切るのと根拠にするのは別のターンになるので、切ったことを思い出せません。

- **切るなら、総数を隣に出す**（ `… | head` と `… | wc -l` を並べる）。判定は「この一覧に総数が添えられているか」
- `grep` のパターンで失敗を数えない。形の違う失敗（build エラー・panic）が落ちる。失敗の有無は終了コードか集計行で見る

## 検証の条件が実物と合っているか

**入力を自分で組み立てたなら、実物で1回通す。** 組み立てた入力は想定どおりの形なので、想定が違っていても全ケース通ります。フックの入力・パーサー・API のモック・テストの固定値が当たります。実物を1回流して入力そのものを控え、形が合っていることを確かめてから、残りを組み立てた入力で回す。

自分が文書へ書いた手順も同じで、読み返すだけでは穴が見えません。書いた形のまま実行する。判定は「書いた形と試した形が同じか」。

画面の操作や管理画面の設定のように実物で流せない手順は、**成立する条件を実装から読む**（その表示が出る条件、操作が反映される契機）。判定は「相手の手元で止まる箇所があるか」。

人から受け取った手順は、自分の対象で1回走らせてから使う。受け取ったのが判定（重要度・可否）なら、**基準が自分の体系と同じかを見る**。同じ語でも定義が違うことがあり、語が一致していると素通りします。

## 動かさない検査しか通っていないかもしれない

ビルド・型・lint・テストが全部通っても、起動したら落ちることがあります。依存やツールのバージョンを上げたときは特に、一度は動かす（Web アプリは HTTP で叩く、ライブラリは取り込む側から1つ呼ぶ、CLI は最小のサブコマンドを実行する）。**動かせなかったなら、そう書く。**

## 禁止する挙動

- 空の出力を「該当なし」として報告すること。探し方が正しかったことを先に確かめる
- 置き場を列挙する前に、不在・一覧・件数を出すこと
- 語で引いて空だったことを、無いことの根拠にすること
- 自分で切った出力から、件数や有無を結論すること
- 成功表示やバックグラウンドの完了通知の終了コードを、成否の根拠にすること
- 主張を、それが成り立つ側の例だけで確かめること
- 「既存の流儀」を、自分の差分を含んだ状態で数えること
- 数を渡すときに、起点と対象を書かないこと
- 自分で組み立てた入力だけでテストを通して、動くと判断すること
- 静的な検査が通ったことを「動く」と報告すること
- 既存ファイルへ `>` で書き出すこと

## なぜ

- 空振りは気づけるが、それらしい数字が返ると検算する動機が湧かない
- 壊れた検査は「該当なし」と同じ出力を返すので、出力からは区別できない。やり方の側を確かめるしかない
- 成功表示は対象0件でも出る。何件に対して動いたかを見ないと、検査したことにならない

## 例外

- ユーザーが「裏取り不要」と明示した場合
- 使い捨ての確認（結果を根拠に何も書かない場合）
