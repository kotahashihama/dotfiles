# レビュー依頼は明示指示があるときだけ

**レビュアーへ通知が飛ぶ操作**は、ユーザーから明示的に指示されたときだけ実行してください。draft の PR を ready for review にすることも、一度レビューを受けた PR へ**再依頼を出すこと**も含みます。
これは全プロジェクト共通の規約です。

## 対象

| 操作 | 例 |
| --- | --- |
| **ready 化** | `gh pr ready` |
| **レビューの再依頼** | `gh pr edit --add-reviewer`、`POST .../requested_reviewers` |
| **ready 化した PR を draft へ戻す** | `gh pr ready --undo` |

**再依頼が見落とされやすい。** レビュアーがレビューを提出すると request が消えるため、`reviewRequests` が空になります。これを「依頼が漏れている」と読んで補完したくなりますが、**提出済みという正常な状態**です。

## 禁止する挙動

- 点検・テスト・AI レビューが揃ったからといって、自分の判断で ready 化・再依頼を実行すること
- 「人間レビューに出せる状態にして」「仕上げて」といった**曖昧な依頼を指示と解釈する**こと。準備を整えることと、レビューを開始することは別
- **レビュー指摘への対応が終わったことを、再依頼の根拠にすること**。直したら見てもらう、は自然に見えるが、いつ見てもらうかはユーザーが決める
- `reviewRequests` が空なのを**依頼漏れとみなして補うこと**
- ready 化した PR を、指示なく draft へ戻すこと（戻す操作も同じく外向き）

## 期待する挙動

- 準備が整ったら**状態を報告して次の指示を待つ**。「ready にしますか」「再依頼しますか」とも聞かない
- ユーザーが「ready にして」「レビュー出して」「再依頼して」等と明示したときにだけ実行する
- レビュー対応が終わったら、**対応表を会話で報告するまで**が責務（`/resolve-human-reviews`）

## なぜ

- **レビュアーへ通知が飛ぶ。** 取り消しても通知は戻らず、相手の時間を奪ったことは元に戻らない
- **再依頼は「もう一度見てほしい」という要求**で、ready 化より強い。相手は前回との差分を読み直すことになる
- CI の構成によっては ready 化が新しいワークフローを起動する。承認待ちで止まる設定なら、**ユーザーにしか解消できない状態**を作ってしまう
- いつレビューを依頼するかは、他のレビュー状況・リリース計画・依存 PR のマージ順を見て決めるもの。**判断材料をすべて持っているのはユーザー**

## 例外

- ユーザーが「ready にして」「再依頼して」と明示した場合
- ユーザーがそのセッション内で「以降はレビュー依頼まで任せる」と委譲を明示した場合
- **PR 作成時に reviewer を指定すること**は対象外（PR 作成の手順に含まれる）。本ルールが規定するのは、**一度依頼した後の再依頼**

## 関連

- `no_auto_commit.md`（コミット・プッシュは明示指示のみ）: どちらも**外部に出るアクションを自己判断で実行しない**という同じ趣旨。あちらは履歴、こちらはレビュー依頼
- `no_auto_reply_human_review_comments.md`（人間コメントへ返信しない）: **レビュアーへ働きかける操作を勝手にしない**という点で同じ。あちらは返信と Resolve、こちらは依頼
- `use_ship_pr_for_pr_creation.md`（PR 作成は ship-pr から）: **`/ship-pr` は AI レビューまで回しても draft のまま止まる**。本ルールがその後の状態変更を規定する
