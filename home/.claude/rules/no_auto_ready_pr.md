# PR の ready 化は明示指示があるときだけ

draft の PR を ready for review にするのは、**ユーザーから明示的に指示されたときだけ**にしてください。
これは全プロジェクト共通の規約です。

## 禁止する挙動

- 点検・テスト・AI レビューが揃ったからといって、自分の判断で `gh pr ready` を実行すること
- 「人間レビューに出せる状態にして」「仕上げて」といった**曖昧な依頼を ready 化の指示と解釈する**こと。準備を整えることと、レビューを開始することは別
- ready 化した PR を、指示なく draft へ戻すこと（戻す操作も同じく外向き）

## 期待する挙動

- PR は draft のまま完成させ、**「ready にしますか」とも聞かず**、状態を報告して次の指示を待つ
- ユーザーが「ready にして」「レビュー出して」等と明示したときにだけ実行する

## なぜ

- ready 化は**レビュアーへ通知が飛ぶ**。取り消しても通知は戻らず、相手の時間を奪ったことは元に戻らない
- CI の構成によっては ready 化が新しいワークフローを起動する。承認待ちで止まる設定なら、**ユーザーにしか解消できない状態**を作ってしまう
- いつレビューを依頼するかは、他のレビュー状況・リリース計画・依存 PR のマージ順を見て決めるもの。**判断材料をすべて持っているのはユーザー**

## 例外

- ユーザーが「ready にして」と明示した場合
- ユーザーがそのセッション内で「以降は ready 化まで任せる」と委譲を明示した場合

## 関連

- `no_auto_commit.md`（コミット・プッシュは明示指示のみ）: どちらも**外部に出るアクションを自己判断で実行しない**という同じ趣旨。あちらは履歴、こちらはレビュー依頼
- `/create-pr` スキルは PR を必ず draft で作成する。本ルールはその後の状態変更を規定する
