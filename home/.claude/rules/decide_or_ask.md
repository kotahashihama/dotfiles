# 自分で決めるか、ユーザーに尋ねるか

**取り消せることは自分で決めて進め、取り消せないこととユーザーの領分は尋ねてください。**
これは全プロジェクト共通の規約です。

## 判断軸

| 尋ねる | 自分で決める |
| --- | --- |
| **取り消せない**（外部へ出る・履歴が残る・通知が飛ぶ） | 取り消せる（作業ツリー・ローカル・下書き） |
| **ユーザーの領分**（方針・粒度・優先度・公開範囲） | 手段の選択（実装の書き方・調査の順序・道具立て） |
| **前提の読み方が割れる**（どちらでも筋が通る） | 前提が 1 通りに決まる |
| **やり直しのコストが確認より高い** | やり直しても安い |

**迷ったら「間違えたとき、取り消せるか」で決める。** 取り消せないなら尋ねる。

## 取り消せない操作は、指示が一意に読めるときだけ

**「指示があった」と読めた時点で、判断軸を通ったことにしない。** 取り消せない操作では、**その読みが 1 通りか**まで見る。

日本語は主語を落とすので、**宣言と指示が同じ形になります**。

| 読みが割れる | 一意に読める |
| --- | --- |
| 「マージします」「やっておきます」 | 「マージして」「やっといて」 |
| 「そろそろ出そうか」 | 「出して」 |
| 直前の話題への相槌 | 操作を名指しした依頼 |

左の列は**自分でやるという宣言**のことがあります。代行してほしいなら依頼の形で来るので、**宣言とも読めるなら実行しない**。

割れたら `AskUserQuestion` で「こちらでやりますか」を聞く。**聞き返しは 1 往復だが、外部へ出た操作は戻せない。**

## 尋ねるときの形

**`AskUserQuestion` ツールを使う。** 文章の中に確認文を混ぜると見逃される。選択式の UI で出せば、尋ねていることが一目で分かる。

判断材料は揃えてから聞く。「どうしますか」だけでは、ユーザーが状況を組み立て直すことになる。

| 要素 | 入れ方 |
| --- | --- |
| 何を決めたいか | `question`（1 文で、疑問符で終える） |
| 選択肢 | `options` の `label`（1〜5 語）。自然な案が複数あるなら並べる |
| それぞれの影響 | 各 `description`。トレードオフを 1〜2 行 |
| **推奨** | 推す案を**先頭**に置き、`label` に「(推奨)」を付ける |

**本文側には背景と根拠を書く。** ツールは判断そのものを受け取る場で、経緯を説明する場ではない。

**選択肢が 2 つ以上あるときは必ずツールを使う。** 「進めてよろしいですか」のような可否確認も、`はい / いいえ` の 2 択として出す。

**「提案」のつもりでも、選択肢を並べた時点で尋ねている。** 「どうしますか」と書いていなくても、案を 2 つ以上示せばユーザーは判断を求められたと受け取ります。**表に並べて終わらせない**。そのままツールで出す。判定は書き方（疑問文かどうか）ではなく、**ユーザーが選ばないと次に進めないか**で行う。

改善案・代替案・恒久対策の提示は、この形になりやすい。本文には背景と根拠だけを置き、案そのものは選択肢へ移す。

## 止まりうる操作は、他の処理と同じ呼び出しに入れない

**承認待ちや検査で止まると、その呼び出しは丸ごと実行されません。** 同じ呼び出しに前処理を入れていると、**前処理まで走らない**まま止まります。

```bash
# ❌ push が止まると、ブランチの付け替えも実行されない
git checkout -B feat/x && git push --force-with-lease

# ✅ 先に状態を整えてから、止まりうる操作だけを単独で出す
git checkout -B feat/x
git push --force-with-lease
```

**止まった側は分かりますが、走らなかった側は分かりません。** 実際に、付け替えが実行されないまま detached HEAD が残り、その後の push が `Everything up-to-date` を返して**成功に見えて何も起きていない**状態になりました。

対象は**承認が要る操作**（`no_auto_commit.md` / `no_auto_ready_pr.md`）と、**検査で弾かれうる操作**（フックが形で止めるもの）。どちらも**単独で出す**。

## 尋ねないほうがよい場面

**確認そのものが判断領域への侵入になる**ことがある。

- ユーザーが受け身に徹すると決めている領域（人間レビューへの返信要否など）は、**聞かずに待つ**
- 一度委譲された判断を、次の機会に聞き直す（「毎回聞かなくていい」と言われた領域）
- 手段の選択を丸投げする。**推奨を持たずに選ばせない**

## 禁止する挙動

- 取り消せない操作を、確認なしに実行すること
- **宣言とも読める発言を、取り消せない操作の根拠にすること**。「〜します」は自分でやる宣言かもしれない
- **確認を口実に手を止めること**。取り消せる範囲は進めながら聞く
- 選択肢だけ並べて**推奨を出さない**こと。判断コストをユーザーへ全部渡すことになる
- **文章の末尾に確認文を書いて済ませること**。読み飛ばされ、こちらは待ち続けることになる
- 一度の承認を、範囲を広げて使い回すこと（`no_auto_commit.md`）
- **止まりうる操作を、他の処理と同じ呼び出しに入れること**。止まると前処理まで走らず、中途半端な状態が残る

## なぜ

- 取り消せない操作は、間違えると**相手の時間や履歴を奪う**。確認 1 往復のほうが安い
- 一方、取り消せることまで聞くと**作業が止まる**。ユーザーは判断のために呼ばれ続けることになる
- 判断軸が無いと、個別の禁止事項を列挙し続けることになる。**軸があれば、書かれていない場面でも決められる**

## 例外

- ユーザーが「以降は任せる」と委譲を明示した領域は、そのセッション内では自分で決める
- 緊急に止めるべき事象（データ破壊が進行中など）は、止めてから報告する

## 関連

本ルールは判断軸を示す。**個別の場面はそれぞれのルールが規定する。**

- `no_unnecessary_pausing.md`（確認が要らないなら止まらない）: 本ルールが**尋ねるべき場面**を定め、あちらが**尋ねるべきでない場面**を定める。表裏で 1 組
- `no_operating_on_others_prs.md`（他人の PR は触らない）: **他人の PR への操作はすべて「取り消せない」側**。本ルールの判断軸を、誰の成果物かという面から絞る
- `no_auto_commit.md` / `no_auto_ready_pr.md`: 取り消せない操作の代表例
- `no_auto_reply_human_review_comments.md`: 「聞かずに待つ」側の代表例
- `explain_review_comment_first.md`: 尋ねるときの形を、レビュー対応の文脈で具体化したもの
- `ask_before_editing_claude_assets.md`（設定は尋ねてから）: ユーザーの領分にあたる例。**必ず `AskUserQuestion` で出す**という強い形を定める
- `treat_user_suggestions_as_proposals.md`（ユーザーの案には賛否を返す）: **向きが逆で対になる**。本ルールは**取り消せない操作で、指示と読めるかを厳しく見る**。あちらは**軽い変更で、指示と読みすぎない**
