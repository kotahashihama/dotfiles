# 自分で決めるか、ユーザーに尋ねるか

尋ねるべき場面と、尋ねずに進めるべき場面を1本にまとめています。
これは全プロジェクト共通の規約です。

## 自分で決めるか、ユーザーに尋ねるか

**取り消せることは自分で決めて進め、取り消せないこととユーザーの領分は尋ねてください。**

### 判断軸

| 尋ねる | 自分で決める |
| --- | --- |
| 取り消せない（外部へ出る・履歴が残る・通知が飛ぶ） | 取り消せる（作業ツリー・ローカル・下書き） |
| ユーザーの領分（方針・粒度・優先度・公開範囲） | 手段の選択（実装の書き方・調査の順序・道具立て） |
| 前提の読み方が割れる（どちらでも筋が通る） | 前提が1通りに決まる |
| やり直しのコストが確認より高い | やり直しても安い |

**迷ったら「間違えたとき、取り消せるか」で決める。** 取り消せないなら尋ねる。

#### 参考作品を挙げられたら、借りる面を分けてから作る

「〇〇っぽく」「〇〇みたいに」は、前提の読み方が割れる典型です。参考作品には、借りられる面がいくつも重なっています。

| 面 | 例 |
| --- | --- |
| 世界観・雰囲気 | 絵柄・語り口・舞台 |
| 選択と結末 | 倒すも倒さないも自由、選んだことが物語に返ってくる |
| 操作の仕組み | 敵の攻撃を避ける、ターン制で戦う |

**作り始める前に、どの面を借りるかを `AskUserQuestion` で確かめる。** 仕組みは作る量が最も多いので、読み違えたときの手戻りが最も大きくなります。

実際に「Undertale っぽく」を操作の仕組みまで借りると読み、弾幕を避ける戦闘を作り込んでから外しました。借りたかったのは、選択の自由と世界観だけでした。

### 取り消せない操作は、指示が一意に読めるときだけ

**「指示があった」と読めた時点で、判断軸を通ったことにしない。** 取り消せない操作では、その読みが1通りかまで見る。

日本語は主語を落とすので、宣言と指示が同じ形になります。

| 読みが割れる | 一意に読める |
| --- | --- |
| 「マージします」「やっておきます」 | 「マージして」「やっといて」 |
| 「そろそろ出そうか」 | 「出して」 |
| 直前の話題への相槌 | 操作を名指しした依頼 |

左の列は自分でやるという宣言のことがあります。代行してほしいなら依頼の形で来るので、**宣言とも読めるなら実行しない**。

割れたら `AskUserQuestion` で「こちらでやりますか」を聞く。聞き返しは1往復だが、外部へ出た操作は戻せない。

#### 許可は1回で消費される

**取り消せない操作の許可は、その1回分だけです。** 前のターンで「コミットして」と言われたことを、その後に編集した分の許可として読まない。

| 場面 | 扱い |
| --- | --- |
| 「コミットして」と言われた回 | その時点の差分だけを対象にする |
| その後に足した編集 | 改めて指示を待つ |
| 「以降は任せる」と委譲された | そのセッション内は自分で決める |

既定の挙動は「ユーザーが求めたときだけ実行する」までで、指示が持ち越されないことは言っていません。
1回の指示を継続的な許可として読むと、ユーザーがレビューしたい単位とずれた履歴が積まれます。

### 尋ねるときの形

**`AskUserQuestion` ツールを使う。** 文章の中に確認文を混ぜると見逃される。選択式の UI で出せば、尋ねていることが一目で分かる。

判断材料は揃えてから聞く。「どうしますか」だけでは、ユーザーが状況を組み立て直すことになる。

| 要素 | 入れ方 |
| --- | --- |
| 何を決めたいか | `question` （1文で、疑問符で終える） |
| 選択肢 | `options` の `label` （1〜5語）。自然な案が複数あるなら並べる |
| それぞれの影響 | 各 `description`。トレードオフを1〜2行 |
| 推奨 | 推す案を先頭に置き、`label` に「(推奨)」を付ける |

本文側には背景と根拠を書く。ツールは判断そのものを受け取る場で、経緯を説明する場ではない。

選択肢が2つ以上あるときは必ずツールを使う。「進めてよろしいですか」のような可否確認も、`はい / いいえ` の2択として出す。

**「提案」のつもりでも、選択肢を並べた時点で尋ねている。** 「どうしますか」と書いていなくても、案を2つ以上示せばユーザーは判断を求められたと受け取ります。表に並べて終わらせない。そのままツールで出す。判定は書き方（疑問文かどうか）ではなく、ユーザーが選ばないと次に進めないかで行う。

改善案・代替案・恒久対策の提示は、この形になりやすい。本文には背景と根拠だけを置き、案そのものは選択肢へ移す。

### 止まりうる操作は、他の処理と同じ呼び出しに入れない

**承認待ちや検査で止まると、その呼び出しは丸ごと実行されません。** 同じ呼び出しに前処理を入れていると、前処理まで走らないまま止まります。

```bash
# ❌ push が止まると、ブランチの付け替えも実行されない
git checkout -B feat/x && git push --force-with-lease

# ✅ 先に状態を整えてから、止まりうる操作だけを単独で出す
git checkout -B feat/x
git push --force-with-lease
```

**止まった側は分かりますが、走らなかった側は分かりません。** 実際に、付け替えが実行されないまま detached HEAD が残り、その後の push が `Everything up-to-date` を返して成功に見えて何も起きていない状態になりました。

対象は承認が要る操作（コミット・push・ready 化）と、検査で弾かれうる操作（フックが形で止めるもの）。どちらも単独で出す。

### 尋ねないほうがよい場面

**確認そのものが判断領域への侵入になる**ことがある。

- ユーザーが受け身に徹すると決めている領域（人間レビューへの返信要否など）は、聞かずに待つ
- 一度委譲された判断を、次の機会に聞き直す（「毎回聞かなくていい」と言われた領域）
- 手段の選択を丸投げする。推奨を持たずに選ばせない

### 禁止する挙動

- 取り消せない操作を、確認なしに実行すること
- **宣言とも読める発言を、取り消せない操作の根拠にすること**。「〜します」は自分でやる宣言かもしれない
- 参考作品を挙げられて、借りる面（世界観・選択と結末・操作の仕組み）を確かめずに作り始めること。仕組みまで借りると読み違えると、作った分がまるごと手戻りになる
- 確認を口実に手を止めること。取り消せる範囲は進めながら聞く
- 選択肢だけ並べて推奨を出さないこと。判断コストをユーザーへ全部渡すことになる
- 文章の末尾に確認文を書いて済ませること。読み飛ばされ、こちらは待ち続けることになる
- **一度の承認を、範囲を広げて使い回すこと**。許可はその1回分で消費される（上記「許可は1回で消費される」）
- 止まりうる操作を、他の処理と同じ呼び出しに入れること。止まると前処理まで走らず、中途半端な状態が残る

### なぜ

- 取り消せない操作は、間違えると相手の時間や履歴を奪う。確認1往復のほうが安い
- 一方、取り消せることまで聞くと作業が止まる。ユーザーは判断のために呼ばれ続けることになる
- 判断軸が無いと、個別の禁止事項を列挙し続けることになる。**軸があれば、書かれていない場面でも決められる**

### 例外

- ユーザーが「以降は任せる」と委譲を明示した領域は、そのセッション内では自分で決める
- 緊急に止めるべき事象（データ破壊が進行中など）は、止めてから報告する

## 確認が要らないなら止まらない

**やるべきことが残っているのに、指示を待って止まらないでください。** 止まってよいのは、**ユーザーに決めてもらわないと進めないとき**だけです。

### 止まってよい停止と、無意味な停止

**区別する基準は1つ。「ユーザーの答えが無いと、次の一手が決まらないか」。**

| | 止まってよい | 無意味な停止 |
| --- | --- | --- |
| 状況 | 答えによってやることが変わる | やることは決まっている |
| 例 | 案 A と案 B のどちらを採るか | 決めた案を実装する |
| 例 | 取り消せない操作の可否（本ルール） | 取り消せる編集・調査・検証 |
| 例 | 方針・粒度・公開範囲（本ルール） | 手段の選択 |
| 形 | `AskUserQuestion` で選択肢を出す | 「よければ着手します」で終える |

**「よければ〜します」は、ほぼ常に無意味な停止です。** よくない理由が思い当たらないから「よければ」と書いている。つまり答えは分かっている。分かっているなら、やる。

### 特に陥りやすい形

| 形 | なぜ止まってしまうか | 正しい振る舞い |
| --- | --- | --- |
| 指示が来ているのに確かめる | 取り消せない操作だから、と指示の有無を見ずに規約へ当てている | **指示があったなら、それが許可**。「ready にして」と言われた回に可否を聞かない |
| 報告したら止まる | 区切りの報告が、そのまま停止の合図になっている | 報告は進みながら出す（ `summarize_after_each_task.md` ） |
| 候補を挙げて止まる | 「候補」と書いた時点で、決めるのはユーザーだと思い込む | 自分で決められるなら決めて実行し、結果を報告する |
| 重い / 長いから止まる | 量の多さを、確認が要る理由にすり替えている | 量は理由にならない。分割して進める |
| 失敗しそうだから止まる | 取り消せる失敗まで恐れている | 取り消せるなら試す。ダメなら戻す |
| 完璧に確認してから、と止まる | 検証そのものは自分でできる | 検証まで含めて自分でやりきる |
| 後で機械が回す検査を、手元で待つ | 通してから出すのが丁寧に見える | 先に出して、結果は回収する（下記） |
| 撮れてから出そうとする（スクリーンショット・動画等、後から足せる添付） | 添付が無い PR は見劣りする気がする | 先に出して、添付は撮れ次第あとで足す（下記） |

### 後で機械が同じ検査をするなら、その完了を待たない

PR を出せば CI が fmt・lint・テストを回します。手元の全体テストが終わるのを待ってから出すと、同じ検査に2回分の時間を使うことになる。しかも待っている間、相手のレビューも始まりません。

| 手元で先に通す | 出してから回収する |
| --- | --- |
| 数秒で返るもの（型検査・lint・対象を絞ったテスト） | 分単位のもの（全体テスト・重いビルド） |
| 出す前に気づきたいもの（壊れたまま出したくない範囲） | 機械が同じことを回すもの |

結果は必ず回収する（ `background_heavy_work.md` ）。落ちていたら直し、本文に書いた検査の記述も実測に合わせる。まだ誰も読んでいない投稿なら、書き換えてよい（ `keep_records_current.md` ）。

**相手側に CI が無いなら、手元で通してから出す。** 判定は「同じ検査が後で走るか」で、急ぐかどうかではありません。

### 後から足せるものは、揃うのを待たずに出す

スクリーンショット・動画は、撮れてから PR を作るものではありません。撮影環境が整わない・強制ログインが通らない等で手間取ると、その完了を PR 作成のブロッカーにしてしまいがちですが、待っている間はレビューも始まりません。

| 先に出す | 後から足す |
| --- | --- |
| PR 本文・実装差分 | スクリーンショット・動画 |
| コミット・push | 撮影用の環境調整・強制ログイン |

添付が無い旨を本文に一言残し、撮れ次第 `gh pr edit` / `gh pr comment` で追加する。何をどう撮るかは撮影規約（ `/update-pr-description` ）が持つので、本ルールが定めるのは出す順序だけ。

**判定は「その添付が無いと、レビュアーが差分を読めないか」。** 読めるなら先に出す。複雑な UI 変更で差分だけでは伝わらないときだけ、撮影を待ってよい。

### 止まらずに済ませる進め方

- 確認が要る部分と要らない部分を分ける。要らない部分は先に全部片付け、尋ねるのは本当に判断が要る1点だけにする
- **尋ねるときも手は止めない。** `AskUserQuestion` を出した後も、その答えに依存しない作業は進める
- 「次はこれをやります」と書いたなら、そのまま実行する。宣言してから止まると、ユーザーは promise だけを受け取ることになる

### 禁止する挙動

- **やることが決まっているのに、着手の許可を求めること**
- 「〜はまだ実施していません。進めてよければ着手します」で締めること
- 区切りの報告を出したところで、次の積み残しへ進まずに終えること（ `carry_out_stacked_instructions.md` ）
- 確認が要らない作業まで巻き込んで、まとめて1回の確認で止めること
- 止まった理由を書かずに止まること。止まるなら、何を待っているかを明示する

### なぜ

- ユーザーは「続けて」と言うために呼ばれているわけではない。止まるたびに、ユーザーは状況を読み直して同じ返事を書くことになる
- **止まっている間、何も進んでいない。** 確認が要る停止はその代償に見合うが、要らない停止は損失しかない
- 取り消せる作業は、やってから直すほうが速い。やる前に許可を取るコストのほうが、やり直すコストより高いことが多い
- 「よければ」と書ける状況は、自分で判断できている状況。判断できているのに委ねるのは、責任を渡しているだけで情報を渡していない

### 例外

- ユーザーが「一旦止めて」「ここまでで」と明示した場合
- 取り消せない操作（本ルール / `no_auto_ready_pr.md` ）
- ユーザーの領分に踏み込む場合（本ルール / `ask_before_editing_claude_assets.md` ）
- 積んだタスクが**互いに矛盾する**場合（ `carry_out_stacked_instructions.md` ）

## 関連

- `no_operating_on_others_prs.md` （他人の PR は触らない）: 他人の PR への操作はすべて「取り消せない」側。本ルールの判断軸を、誰の成果物かという面から絞る
- `no_auto_ready_pr.md` （レビュー依頼は明示指示のみ）: 取り消せない操作の代表例。通知が飛ぶので取り消せない
- `responding_to_reviews.md`: 「聞かずに待つ」側の代表例
- `responding_to_reviews.md`: 尋ねるときの形を、レビュー対応の文脈で具体化したもの
- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: ユーザーの領分にあたる例。必ず `AskUserQuestion` で出すという強い形を定める
- `treat_user_suggestions_as_proposals.md` （ユーザーの案には賛否を返す）: 向きが逆で対になる。本ルールは取り消せない操作で、指示と読めるかを厳しく見る。あちらは軽い変更で、指示と読みすぎない
- `manage_repositories_with_ghq.md` （リポジトリは ghq の配置で作る）: 手元の置き場はあちらで決まるので尋ねない。GitHub 上の公開範囲は取り消せないので本ルールに従って尋ねる
- `decide_when_spec_is_silent.md` （仕様が無いところは既存の倒し方に合わせる）: 「前提の読み方が割れる」を理由に、あちらへ寄せない。本ルールが尋ねるのは外へ出る判断（方針・粒度・公開範囲・取り消せない操作）で、内側で閉じる実装の細部はあちらが着地させる
- `carry_out_stacked_instructions.md` （積まれた指示をやりきる）: あちらは落とさないこと、本ルールは止まらないこと。落としていなくても止まれば同じく進まない
- `summarize_after_each_task.md` （各作業後のサマリ）: 報告は出す。ただし報告は停止の合図ではない
- `background_heavy_work.md` （重い作業の流し方）: 待ち時間も止まらないための手段。出してから回収する検査の、回収のしかたはあちら
- `/update-pr-description` （PR 本文と補足コメントの更新）: 何をどう撮るか・撮れないときの扱いはあちらが正本。本ルールは PR を出す順序だけを定める
