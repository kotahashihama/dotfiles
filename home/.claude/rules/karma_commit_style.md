# コミットメッセージは Karma スタイルで書く

`git commit` のメッセージは Karma (Conventional Commits 系) スタイルで書いてください。
これは全プロジェクト共通の規約です。

## フォーマット

```
<type>(<scope>): <subject>

<body>

<footer>
```

- 1行目（subject 行）は `type(scope): 要約` の形。`scope` は省略可（ `type: 要約` ）。
- subject は日本語の体言止め（名詞・サ変動詞の語幹で終える）で書く。「〜を追加」「〜を削除」「〜を修正」「〜の分離」のように名詞止めにし、「〜した」「〜する」のような動詞終止形・命令形にはしない。
- 末尾にピリオドや句点は付けない。目安50文字程度。
- **チケット番号を subject に入れない**（ `fix: [PROJ-123]〜` の形にしない）。番号は PR のタイトルと本文が持つ。どの PR に付けるかは下記
- 本文が必要なら1行空けて `body` に Why（なぜこの変更をしたか）を書く。何をしたかは差分が持つので書き写さない。コードの How・テストの What・コードコメントの Why not との分担は `code_comments.md` の「置き場ごとに、書くものを1つに決める」。
- `Co-Authored-By` や `BREAKING CHANGE:` 等のトレーラーは `footer` に置く。

**PR に課題の番号を付けるかの判定と、課題の側へ発見の経緯を残す書き方は `~/.claude/references/karma_commit_style.md` の「PR に番号を付けるか」にある。** PR を作る・本文を直すときに開く。

## 生成者のトレーラー

Claude が作ったコミットには、`footer` に次の1行を置く。

```
Co-Authored-By: Claude Code <noreply@anthropic.com>
```

**モデル名は書かない。** `Claude Opus 5` のように書くと、リリースのたびに古くなる。書き手はいずれも Claude Code なので、クライアント名に統一する（ `github_note_generated_by_claude.md` が GitHub 上の文章に対して定めているのと同じ理由）。

**これはコミットを作るすべての経路に適用する。** `/commit-push` だけでなく、レビュー対応やコンフリクト解消の途中で作るコミットも対象。

## type 一覧

- `feat`: 新機能・スキーマ追加など機能面の追加
- `fix`: バグ修正
- `refactor`: 挙動を変えないコード/定義の改善・整理
- `perf`: パフォーマンス改善
- `docs`: ドキュメントのみ
- `style`: フォーマット・空白等、コードの意味を変えない変更
- `test`: テストの追加・修正
- `build` / `ci`: ビルド設定・CI の変更
- `chore`: その他（依存更新、雑務など）

**`feat` と `refactor` は「その時点で実際の動作が変わるか」で分ける。** 部品に能力（引数・指定・検証）を足しても、それを使う呼び出しがまだ無ければ、画面や API の動作は変わらないので `refactor` です。動作が変わるのは、その能力を使い始める変更のほうで、そちらが `feat` になります。

実際に、署名付き URL の部品へ期限とバケットを指定できる引数を足した PR を、部品の振る舞いが増えるとして `feat` にし、「能力を追加するまでで、実際の動作が変わっていないならリファクタ」と指摘を受けました。

**ルール・スキルは「振る舞いが変わるか」で分ける。** 毎セッション読まれて判断を変えるので `feat`、`README` や `docs/` の説明だけなら `docs`。

**ファイルの拡張子で判定しない。** ルールも `docs/` の説明も `.md` なので、拡張子では分かれない。

## scope

- 変更の対象領域を表す短い識別子（例: `csv_import`, `auth`, `jobs` ）。
- `type(scope):` プレフィックスは英小文字で書き、subject 本体は日本語の体言止めで書く。

## 例

体言止め（名詞止め）で統一する。

```
feat(csv_import): 実行者・エラー列の追加と取込オプションの分離
fix(auth): トークン期限切れ時に 401 を返す修正
refactor(csv_import): 未リリースのためデータ移行処理を削除
chore: 依存パッケージの更新
```

**既存のコミットのメッセージを書き換えるときは、`~/.claude/references/karma_commit_style.md` の「既存メッセージの書き換え」を読む。** そちらには、ツリーを変えずにメッセージだけを差し替える手順と、レビューが始まった PR では書き換えないという規定がある。

## なぜ

- type/scope が揃うと履歴を検索しやすくなり、changelog を自動で生成でき、レビューで意図をつかみやすくなる。
- subject の粒度と語調が統一され、PR・リリースノートの整形コストが下がる。
- **チケット番号はコミット単位では重複する。** PR のタイトルと本文が紐づけを持つので、subject に置くと本題が右へ寄るだけになる

## 例外

- プロジェクト固有の規約が文書として書かれている場合は、そちらを優先する（CONTRIBUTING・リポジトリの規約ドキュメント）。ただしチケット番号は入れない（上記）
  - **`git log` の傾向は文書に当たらない。** 直近が同じ形でも、それは誰かがそう書いただけで、従うべき規約とは限らない
  - 文書が見つからず、履歴の形に合わせるか迷ったらユーザーへ尋ねる。書式はユーザーが管理したい領分（ `decide_or_ask.md` ）
- マージコミット等、ツール生成のメッセージはこの限りではない。
- 本ルールはコミットメッセージの書式に関するもので、いつコミットするかは `decide_or_ask.md` が優先する。

## 関連

- `github_writing.md` （GitHub へ投稿する文章の書き方）: 句点を落とす点は同じだが、あちらは PR 本文・コメントが対象。本ルールは commit subject の1行だけ。課題へ残すコメントの `[fyi]` の書式もあちら
- `write_for_installed_versions.md` （入っているバージョンで書く）: どちらも周囲に合わせるかを判断する。あちらはコードの書き方、本ルールはメッセージの書式。傾向を規約と読まない点は共通
- `/create-pr` / `/update-pr-description` （PR の作成と本文の更新）: 「PR に番号を付けるか」の判定は本ルールが持つ。あちらは Backlog 節への貼り方と、課題へ発見の経緯を残す手順を持つ
- `explain_from_observables.md` （観測できるものから始める）: 受入基準に入らない変更の扱いが近い。本ルールは PR 単位（番号を付けるか）、あちらは1本の本文の中で課題に要る変更と付随した変更を書き分ける
- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: 別 PR にするかの判断はあちら。本ルールはその PR へ番号を付けるかを定める
