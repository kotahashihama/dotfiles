# コミットメッセージは Karma スタイルで書く

`git commit` のメッセージは **Karma (Conventional Commits 系) スタイル**で書いてください。
これは全プロジェクト共通の規約です。

## フォーマット

```
<type>(<scope>): <subject>

<body>

<footer>
```

- 1行目（subject 行）は `type(scope): 要約` の形。`scope` は省略可（ `type: 要約` ）。
- subject は **日本語の体言止め（名詞・サ変動詞の語幹で終える）** で書く。「〜を追加」「〜を削除」「〜を修正」「〜の分離」のように名詞止めにし、「〜した」「〜する」のような動詞終止形・命令形にはしない。
- 末尾にピリオドや句点は付けない。目安50文字程度。
- **チケット番号を subject に入れない**（ `fix: [PROJ-123]〜` の形にしない）。番号は**PR のタイトルと本文**が持つ。**どの PR に付けるかは下記**
- 本文が必要なら1行空けて `body` に「なぜ・何を」を書く。
- `Co-Authored-By` や `BREAKING CHANGE:` 等のトレーラーは `footer` に置く。

## PR に番号を付けるか

**判定は「その課題から辿れてほしいか」。** 課題を開いた人がその PR を見たとき、なぜ並んでいるのか分かる関係かで決める。

| 付ける | 付けない |
| --- | --- |
| その課題を全部解決する | どの課題とも関係が無い（独立したリファクタ・雑務） |
| その課題を一部解決する（分割した1本目） | **同じファイルを触っただけ・話題に出ただけ** |
| **その課題の調査中に見つけた別件**（閉じる条件には入らない） | |

**3つ目を「関係があれば付ける」へ広げない。** 付けるのは**調査の起点がその課題だったとき**だけ。ここを緩めると全部に付く形へ流れる。

**閉じる条件に入らないものを付けるときは、そうと分かるように書く。** タイトルだけ見ると課題を解決する PR に見えるので、本文へ1行残す（「この課題を閉じる PR ではありません」）。

**課題の側にも発見の経緯を残す。** 課題に並ぶのは PR のタイトルと URL だけで、`[PROJ-123]` が付いた PR が5本あっても、どれが課題を進めるものかは読めない。`[fyi]` のコメントへ3つ書く。

| 書くこと | 例 |
| --- | --- |
| 何が起きていたか | 表示名が空になり、7箇所で段階の名前が出ない |
| どう見つけたか | この課題を調べる過程で、BE と FE が持つ一覧の件数が食い違った |
| その課題との関係 | 閉じる条件には入らないが、別の PR が入れた保険が1件減る |

**末尾に `対応 PR: <URL>` を明示行として置く。** 本文中に言及があっても、末尾に独立した行が無いと、経緯コメントの中のどれが対応 PR か探すことになる。

手順は `/create-pr` と `/update-pr-description` が持つ。

## 生成者のトレーラー

Claude が作ったコミットには、`footer` に次の1行を置く。

```
Co-Authored-By: Claude Code <noreply@anthropic.com>
```

**モデル名は書かない。** `Claude Opus 5` のように書くと、リリースのたびに古くなる。書き手はいずれも Claude Code なので、クライアント名に統一する（ `github_note_generated_by_claude.md` が GitHub 上の文章に対して定めているのと同じ理由）。

**これはコミットを作るすべての経路に適用する。** `/cp` だけでなく、レビュー対応やコンフリクト解消の途中で作るコミットも対象。

## type 一覧

- `feat`: 新機能・スキーマ追加など機能面の追加
- `fix`: バグ修正
- `refactor`: 挙動を変えないコード/定義の改善・整理
- `perf`: パフォーマンス改善
- `docs`: ドキュメントのみ
- `style`: フォーマット・空白等、コードの意味を変えない変更
- `test`: テストの追加・修正
- `build` / `ci`: ビルド設定・CI の変更
- `chore`: その他（依存更新、雑務など）

**ルール・スキルは「振る舞いが変わるか」で分ける。** 毎セッション読まれて判断を変えるので `feat`、`README` や `docs/` の説明だけなら `docs`。

**ファイルの拡張子で判定しない。** ルールも `docs/` の説明も `.md` なので、拡張子では分かれない。

## scope

- 変更の対象領域を表す短い識別子（例: `csv_import`, `auth`, `jobs` ）。
- `type(scope):` プレフィックスは英小文字で書き、subject 本体は日本語の体言止めで書く。

## 例

体言止め（名詞止め）で統一する。

```
feat(csv_import): 実行者・エラー列の追加と取込オプションの分離
fix(auth): トークン期限切れ時に 401 を返す修正
refactor(csv_import): 未リリースのためデータ移行処理を削除
chore: 依存パッケージの更新
```

## 既存メッセージの書き換え

- 既存コミットを Karma スタイルへ直す指示があれば、**ツリー（変更内容）は一切変えずメッセージだけ**書き換える。
- `git rebase -i` が使えない環境では「ベースへ `reset --hard` → 各コミットを `cherry-pick` → 直後に `commit --amend` でメッセージ差し替え」で再構築し、`git diff <backup> HEAD` がゼロであることを確認する。
- 共有ブランチの履歴書き換え後の push は `--force-with-lease` を使う。
- **他の人のレビューが始まった PR では実行しない**（ `no_rebase_under_human_review.md` ）。メッセージだけの書き換えでもコミットの同一性は失われる。

## なぜ

- type/scope が揃うと履歴の検索性・自動 changelog 生成・レビュー時の意図把握が容易になる。
- subject の粒度と語調が統一され、PR・リリースノートの整形コストが下がる。
- **チケット番号はコミット単位では重複する。** PR のタイトルと本文が紐づけを持つので、subject に置くと本題が右へ寄るだけになる

## 例外

- プロジェクト固有の規約が**文書として書かれている**場合は、そちらを優先する（CONTRIBUTING・リポジトリの規約ドキュメント）。**ただしチケット番号は入れない**（上記）
  - **`git log` の傾向は文書に当たらない。** 直近が同じ形でも、それは誰かがそう書いただけで、従うべき規約とは限らない
  - 文書が見つからず、履歴の形に合わせるか迷ったら**ユーザーへ尋ねる**。書式はユーザーが管理したい領分（ `decide_or_ask.md` ）
- マージコミット等、ツール生成のメッセージはこの限りではない。
- 本ルールはコミット**メッセージの書式**に関するもので、いつコミットするかは `decide_or_ask.md` が優先する。

## 関連

- `github_one_sentence_per_line.md` （GitHub へ書く日本語の改行と句点）: 句点を落とす点は同じだが、**あちらは PR 本文・コメントが対象**。本ルールは commit subject の1行だけ
- `write_for_installed_versions.md` （入っているバージョンで書く）: どちらも**周囲に合わせるかを判断する**。あちらは**コードの書き方**、本ルールは**メッセージの書式**。**傾向を規約と読まない**点は共通
- `/create-pr` / `/update-pr-description` （PR の作成と本文の更新）: **「PR に番号を付けるか」の判定は本ルールが持つ**。あちらは Backlog 節への貼り方と、課題へ発見の経緯を残す手順を持つ
- `github_rich_formatting.md` （投稿する文章の記号）: **課題へ残すコメントの `[fyi]` の書式はあちら**
