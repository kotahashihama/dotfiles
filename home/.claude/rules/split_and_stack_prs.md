# 大きい変更はブランチを分け、gh stack でスタック化する

1 つの PR に収まらない規模の変更は、**着手前にブランチを分けて**スタックにしてください。分けたブランチで PR を作るとき（base が `main` 以外になるとき）は、`gh stack` で GitHub 上のスタックとしてリンクします。
これは全プロジェクト共通の規約です。

## ブランチ名

`<type>/<slug>` の形で、**slug は kebab-case**（`feat/talent-work-history-v1-passthrough`）。type はコミットの `<type>` と同じ語彙を使う（`karma_commit_style.md`）。

**アンダースコア繋ぎにしない。** 個人の好みではなく**チームの慣習に合わせる**もので、一覧に並んだとき自分のブランチだけ表記が違うと目に付きます。

**既に push 済み・PR 化済みのブランチは直さない。** 改名すると PR を作り直すことになり、**レビューコメントと履歴が失われます**。次に切るブランチから揃えれば足ります。

**迷ったら実際のブランチ名を見る。** リポジトリごとに慣習が違うことがあります。

```bash
gh pr list --state merged --limit 20 --json headRefName -q '.[].headRefName'
```

## 分割の判断

**着手前に「1 PR で収まるか」を見積もる。** 収まらないなら最初から分ける。

| 兆候 | 対応 |
| --- | --- |
| **目的が 2 つ以上ある**（リファクタ + 機能追加） | 目的ごとに分ける。混ざるとレビュアーが「なぜこの変更が要るか」を判断できない |
| **独立してマージできる塊がある** | 先に出せるものを下段へ。上段が長引いても下段は進む |
| 書いているうちに**変更ファイルが増え続けている** | 途中でも下段を切り出す。**後から分けるより、書きながら分けるほうが安い** |
| レビュアーが 1 回で読み切れない量になった | 分ける。指摘が 1 PR に集中すると、どれがどの変更への指摘か追えなくなる |
| **既に複数の PR を出した後で、依存関係が読み取れないと気づいた** | **後からスタック化する**（下記）。分け直しは要らない |

判断に迷ったら**分ける側に倒す**。スタックなら下段から順にレビューが進むので、分けすぎても損は小さい。逆に 1 本へ詰め込むと、**レビューが止まったとき全部が止まる**。

## 期待する挙動

1. **下段から順にブランチを adopt する**（ローカル操作。GitHub には影響しない）

   ```bash
   gh stack init <下段ブランチ> <上段ブランチ>
   ```

   既存ブランチはそのまま取り込まれる。`--base` でトランクを指定できる（既定はデフォルトブランチ）。

2. **GitHub 上のスタックへリンクする**

   ```bash
   gh stack submit --auto
   ```

   push・PR の base 更新・スタックの作成をまとめて行う。**既に PR があるブランチは新規作成されず、base とリンクだけが更新される**（本文・draft 状態は変わらない）。

- `gh stack view` で現在の並びを確認できる
- 下段の変更を上段へ伝播するときは `gh stack rebase`、リモートと揃えるときは `gh stack sync`
  - **上段に他の人のレビューが付いていたら `gh stack rebase` を使わない**。上段の履歴まで書き換わる（`no_rebase_under_human_review.md`）。その PR だけ `git merge` で取り込む
- PR 本文にも**どのブランチの上に積んでいるか**を 1 行書く。スタック表示に気づかないレビュアーがいる

### 下段の履歴を書き換えると、上段の差分が壊れる

**base の位置は正しいまま、差分だけが壊れます。** 履歴の系統が切れて GitHub が差分を計算し直せなくなるので、
**下段の内容まで上段の差分に含まれて表示**されます。実測では 17 ファイル・+183/-183 の PR が
58 ファイル・+3165/-623 になりました。

**原因は squash マージに限りません。** 下段の履歴が入れ替わる操作はすべて該当します。

| 下段でやること | 上段 | 避けられるか |
| --- | --- | --- |
| **force push** | 壊れる | **避けられる**（やらなければ起きない） |
| **rebase** | 壊れる | **避けられる**（同上） |
| **squash マージ** | 壊れる | **避けられない**（下段をマージするのは通常の運用） |
| 通常のマージ・追加のコミット | 壊れない | — |

**squash が絡まなくても起きます。** force push だけで同じ症状が出ることを実測しています。

**ただし squash だけは性質が違います。** 他の 2 つは「やらない」で回避できますが、**squash マージのリポジトリでは、
下段をマージした時点で必ず通る道**です。スタックを積むなら、**上段を作り直す前提で計画する**。

**復旧は履歴ベースの手段では通りません。** `git merge` は衝突が大量に出て、片側を採ると主題か修正の
どちらかが消える。`cherry-pick` は選別基準が立たない。3 点比較（`A...B`）は merge-base が遡りすぎて
下段の内容を拾う。**ツリー同士を直接比較して作り直す**のが唯一通った手段です。

**作り直すとき、下段で入った修正を打ち消すファイルは除外する。** 上段はその修正を知らないので、
差分に巻き戻しが混ざります。

### 既に PR が出ている群を、後からスタック化する

**分け直しは要りません。** PR 番号を下段から順に並べるだけで、GitHub 上のスタックだけを作れます。

```bash
gh stack link <下段のPR> <次のPR> ... <上段のPR>
```

`link` は**ローカルの追跡を伴わない**ので、`init` の adopt も `submit` の push も起きません。**PR 本文・draft 状態・レビューコメントは一切変わりません。**

**鎖にマージ済みの PR が混ざっていると `gh stack unstack` は失敗します。** 並びを組み直したいときは unstack を経由せず、`link` で残った PR だけを張り直す。

## 禁止する挙動

- **1 本の PR に詰め込んでから分割を考えること**。コミットを跨いだ切り出しは差分の整合を取るコストが高い
- `gh pr create --base <下段>` だけで済ませること。**PR の base は正しくなるが、GitHub 上のスタックにはならない**ので、レビュアーが依存関係を辿れない
- スタック化のために既存 PR を閉じて作り直すこと。`gh stack submit` も `gh stack link` も既存 PR をそのままリンクできる
- **下段の履歴を書き換えて、上段をそのままにすること**。base は正しく見えるが差分が壊れており、レビュアーには下段の内容まで混ざって見える
- **依存関係のある PR 群を、スタックにせず放置すること**。レビュアーはどれから読むべきか分からず、番号順に開いて上段から読み始める
- `gh stack submit --open` を安易に付けること。**新規・既存の PR がまとめて ready になる**。draft のまま置きたいなら付けない

## なぜ

- レビュアーが読める量には限りがある。**大きい PR はレビューが雑になるか、着手されずに滞留する**
- 分けておくと下段だけ先にマージできる。1 本だと上段の議論が終わるまで全部が止まる
- GitHub のスタック表示があると、**どの PR から読めばよいか**と**どれがマージ待ちか**が一目で分かる
- 下段がマージされたときの base 付け替えを GitHub 側が面倒を見てくれる。手動運用だと付け替え忘れで差分が膨らむ

## 例外

- `gh stack` 拡張が入っていない環境では `--base` の指定に留め、PR 本文で依存関係を明示する（`gh extension install github/gh-stack` で導入できる）
- 1 本しかブランチが無いときは不要
