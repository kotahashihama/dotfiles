# 課題の中はスタック PR で分け、下段の履歴を書き換えたら上段を作り直す

課題より細かく分けたいときは、課題を増やさずスタック PR で分けてください（下記）。
スタックした PR で下段の履歴が入れ替わると（force push・rebase・squash マージ）、上段の差分が壊れます。警告は出ず、気づけるのは差分の行数が跳ねたときだけです。下段を書き換えたら上段を作り直してください。上段に他の人のレビューが付いているなら、作り直さず `git merge` で取り込みます（ `no_rebase_under_human_review.md` ）。
これは全プロジェクト共通の規約です。

## 課題より細かく分けるなら、課題を増やさずスタック PR で分ける

**1つの課題を PR 1本で出すには大きいときは、課題を分割せず、同じ課題の下でスタック PR に分ける。** ダウンロードとアップロードで出す時期が違う、DB の変更を待つ部分がある、といった実装の区切りがこれに当たります。

課題は受け入れの単位で、受入基準と QA の手順が課題に付いています。実装の区切りで課題を割ると、それらが子課題ごとに割れ、どこまで終われば閉じてよいかが分かりにくくなります。区切りは PR の側で持ちます。

スタックの各 PR にも、その課題の番号を付けます（ `~/.claude/references/karma_commit_style.md` の「PR に番号を付けるか」）。課題そのものを分けるのは、受け入れや QA を別々に行う理由があるときだけです。

**PR を積む・下段を書き換える・`gh stack` を使うときは、`~/.claude/references/split_and_stack_prs.md` を読む。** 壊れ方の実測、`gh stack link` に既存のスタックの一部だけを渡したときの事故、禁止する挙動はそちらにある。作り直しの手順は `/rebase-stack` が持つ。

### 中心の対応は、手順ごとに PR を分ける

**作業が手順（段階）に分かれているなら、中心の対応は少なくとも手順ごとに PR を分け、1本の PR に別の手順の変更を混ぜない。** 混ぜると、その手順だけを先に出したり戻したりできなくなります。同じ手順の中は、意味の粒度やレビューのしやすさで分けてよいですが、できるだけまとめます。

実際に、後の手順の PR が、共通で使うために前の手順のテストの補助関数の名前を付け替えていました。前の手順の PR で最初から共通の名前にして直しています。

後片付けと、全部の手順がそろってからでないと手を付けられない細かい対応は例外です。手順をまたいで1本にまとめ、スタックの後ろに積んでよい。なんでも手順ごとに分けると、PR が多くなりすぎるためです。

**マージしない、動作確認のためだけの PR をスタックに混ぜない。** スタックに入ると、上段をマージするのにその PR まで要ることになります。

## 関連

- `report_formatting.md` （報告に貼る識別子の書式）: スタックを報告するときも PR 番号を直接列挙する
- `no_rebase_under_human_review.md` （レビュー中は履歴を書き換えない）: スタックの取り込み方を上段のレビュー状況で切り替える。一度でも merge したブランチは rebase しない。マージコミットが平坦化され、衝突の解決ごと消える
- `verify_merge_with_checks.md` （マージは検査を通すまで終わっていない）: 本ルールは取り込む前の依存判定、あちらは取り込んだ後の検証
- `/update-pr-description` （PR 本文の組み立て）: 分けた後、説明の書き方を揃えるのはあちら。本ルールは分ける判断とマージ順を扱う
- `/rebase-stack` （スタックへ伝播する）: 実行手段
- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: 分ける前に、その変更を入れるかどうかはあちらが決める。入れると決めたものが大きいときに、課題ではなくスタック PR で分けるのが本ルール
- `~/.claude/references/karma_commit_style.md` （PR に番号を付けるか）: スタックの各 PR に課題の番号を付けるかの判定はあちら
- pstack の `principle-sequence-verifiable-units` （確かめられる単位に切って積む）: 分け方と積み方の考え方。本ルールは下段の履歴が変わったときの作り直し
