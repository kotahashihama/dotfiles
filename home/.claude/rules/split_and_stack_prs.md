# 下段の履歴を書き換えたら、上段を作り直す

スタックした PR で**下段の履歴が入れ替わると、上段の差分が壊れます**。警告は出ません。base の位置は正しいままなので GitHub の表示は普通に見え、気づけるのは差分の行数が跳ねているのを見たときだけです。
これは全プロジェクト共通の規約です。

### 下段の履歴を書き換えると、上段の差分が壊れる

**base の位置は正しいまま、差分だけが壊れます。** 履歴の系統が切れて GitHub が差分を計算し直せなくなるので、
下段の内容まで上段の差分に含まれて表示されます。実測では17ファイル・+183/-183の PR が
58ファイル・+3165/-623になりました。

ただしファイル数は当てになりません。上の例でファイル数が動いたのは、上下段が別のファイルを
触っていたからです。同じファイルを2段で直していると、ファイル数は動かず行数だけが変わります。
別の実測では5ファイル・+218/-25の上段が、5ファイルのまま+509/-16になりました。控えるのは行数のほう。

原因は squash マージに限りません。下段の履歴が入れ替わる操作はすべて該当します。

| 下段でやること | 上段 | 避けられるか |
| --- | --- | --- |
| force push | 壊れる | 避けられる（やらなければ起きない） |
| rebase | 壊れる | 避けられる（同上） |
| squash マージ | 壊れる | 避けられない（下段をマージするのは通常の運用） |
| 通常のマージ・追加のコミット | 壊れない | — |

squash が絡まなくても起きます。force push だけで同じ症状が出ることを実測しています。

ただし squash だけは性質が違います。他の2つは「やらない」で回避できますが、squash マージのリポジトリでは、
下段をマージした時点で必ず通る道です。スタックを積むなら、**上段を作り直す前提で計画する**。

上段の作り直し方（通らなかった手段と、通った手段）は `/rebase-stack` の「上段の差分が壊れたら作り直す」が持ちます。

**上段に他の人のレビューが付いているなら、作り直さない。** `git merge` で取り込み、衝突は手で解きます（ `no_rebase_under_human_review.md` ）。作り直すと force push になり、レビューコメントが outdated になるためです。作り直すのは、レビューが付いていない上段だけです。

## 禁止する挙動

- 1本の PR に詰め込んでから分割を考えること。コミットを跨いだ切り出しは差分の整合を取るコストが高い
- 触るファイルが重ならないことを、分割の理由にすること。それはマージ順の判定材料であって、分割の可否とは別
- `gh pr create --base <下段>` だけで済ませること。PR の base は正しくなるが、GitHub 上のスタックにはならないので、レビュアーが依存関係を辿れない
- スタック化のために既存 PR を閉じて作り直すこと。`gh stack submit` も `gh stack link` も既存 PR をそのままリンクできる
- **下段の履歴を書き換えて、上段をそのままにすること**。base は正しく見えるが差分が壊れており、レビュアーには下段の内容まで混ざって見える
- 依存関係のある PR 群を、スタックにせず放置すること。レビュアーはどれから読むべきか分からず、番号順に開いて上段から読み始める
- `gh stack submit --open` を安易に付けること。新規・既存の PR がまとめて ready になる。draft のまま置きたいなら付けない
- **上段に他の人のレビューが付いているのに `gh stack rebase` を使うこと**。上段の履歴まで書き換わる（ `no_rebase_under_human_review.md` ）

## なぜ

- レビュアーが読める量には限りがある。大きい PR はレビューが雑になるか、着手されずに滞留する
- 分けておくと下段だけ先にマージできる。1本だと上段の議論が終わるまで全部が止まる
- GitHub のスタック表示があると、どの PR から読めばよいかとどれがマージ待ちかが一目で分かる
- 下段がマージされたときの base 付け替えを GitHub 側が面倒を見てくれる。手動運用だと付け替え忘れで差分が膨らむ
- **squash マージのリポジトリでは、下段をマージした時点で必ず通る道**。避けられないので、上段を作り直す前提で計画する
- 壊れたことは差分の行数でしか分からない。17ファイル・+183/-183が58ファイル・+3165/-623になった実測がある

## 例外

- `gh stack` 拡張が入っていない環境では `--base` の指定に留め、PR 本文で依存関係を明示する（ `gh extension install github/gh-stack` で導入できる）
- 1本しかブランチが無いときは不要

## 関連

- `report_formatting.md` （報告に貼る識別子の書式）: スタックを報告するときも PR 番号を直接列挙する
- `no_rebase_under_human_review.md` （レビュー中は履歴を書き換えない）: スタックの取り込み方を、上段のレビュー状況で切り替える。一度でも merge したブランチは rebase しない。マージコミットが平坦化され、衝突の解決ごと消える
- `verify_merge_with_checks.md` （マージは検査を通すまで終わっていない）: 本ルールは取り込む前の依存判定、あちらは取り込んだ後の検証
- `/update-pr-description` （PR 本文の組み立て）: 分けた後、説明の書き方を揃えるのはあちら。本ルールは分ける判断とマージ順を扱う
- `/rebase-stack` （スタックへ伝播する）: 実行手段
- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: 分ける前に、その変更を入れるかどうかはあちらが決める
