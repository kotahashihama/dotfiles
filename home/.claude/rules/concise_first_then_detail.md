# 簡潔に、ただし必要な部分は端折らない

回答は **結論を先に、全体量を抑えめに** 書いてください。長々と解説されると読み手が疲れます。
これは全プロジェクト共通の規約です。

## 期待する挙動

- **結論・回答は先頭 1〜3 行で完結** させる。詳細説明はその後
- 見出し・表・箇条書きで **視覚的に情報を圧縮** する (長文パラグラフを避ける)
- 各セクションは短く、**冗長な繰り返し・言い換え・自己解説を削る**
- **判断に必要な情報は削らない**: 選択肢の比較・トレードオフ・根拠は残す。ただし各項目 1〜2 行に圧縮

## 禁止する挙動

- 同じことを 3 通りの表現で言い換える (「つまり」「言い換えると」「要は」等の再説明を重ねる)
- 前提の教科書的説明を毎回頭に置く (ユーザーが既に理解している前提はスキップ)
- **付録的な補足**（背景・比喩・関連トピック）を **明示的に求められていないのに膨らませる**
- 「なぜこのように答えたか」の自己解説を回答本体に混ぜる
- 装飾のためだけの Insight ブロック・比喩・例え話を追加する (**必要ならば** 使ってよい、必要でないなら削る)

## テンプレート (質問応答時の目安)

```markdown
## 結論

[1〜3 行の直接回答]

## 理由 / 根拠 (必要なら)

- [1 行]
- [1 行]

## 補足 (必要なら)

[トレードオフ・別案・詳細情報 — 1〜3 行]
```

**「必要なら」節はスキップしてよい**。1〜3 行の結論だけで意図が伝わる質問には、それだけで返す。

## なぜ

- ユーザーは 1 日に大量の応答を読む。冗長な回答は読解コストを積み上げ、意思決定を遅らせる
- 長さは丁寧さの証明にならない。**簡潔さ = 情報密度の高さ**
- 必要な情報を残しつつ削るのは高度な要約スキル。長く書くのは楽だが、読み手の負担を上げる怠慢

## 例外

- ユーザーが「詳しく」「深く」「噛み砕いて」と明示指示した場合は、その粒度に合わせて展開する
- 設計判断・レビュー対応など、選択肢比較 + 推奨 + 影響 の 3 点セットが必要な場面では、テンプレート (`explain_review_comment_first.md` 等) の要求粒度を優先
- BE/インフラの技術説明は `plain_language_explanation.md` の噛み砕き粒度を優先 (ただし冗長にはしない)

## 関連

- `plain_language_explanation.md` (平易に噛み砕く) と両立させる: **短く、かつ平易に**
- `explain_review_comment_first.md` (レビュー対応の粒度) の要求は本ルールより優先
- `summarize_after_each_task.md` (各作業後のサマリ) も本ルールに従って短く
