# 簡潔に、ただし必要な部分は端折らない

回答は **結論を先に、全体量を抑えめに** 書いてください。長々と解説されると読み手が疲れます。
これは全プロジェクト共通の規約です。

## 期待する挙動

- **質問には一言目で答える**（下記）。詳細説明はその後
- 見出し・表・箇条書きで **視覚的に情報を圧縮** する (長文パラグラフを避ける)
- 各セクションは短く、**冗長な繰り返し・言い換え・自己解説を削る**
- **判断に必要な情報は削らない**。選択肢の比較・トレードオフ・根拠は残す。ただし各項目1〜2行に圧縮
- **文と文は接続詞で繋ぐ**（「そのため」「一方」「ただし」）。断片を並べただけだと、読み手が関係を組み立て直すことになる
- **量が増えたら畳むか、切り出す**。長い散文を最後まで読ませない

## 質問には、一言目で答える

**相手が知りたいことへの答えを、応答の最初に置く。** 理由・根拠・補足はその後に続ける。

| 相手が知りたいこと | 一言目 |
| --- | --- |
| できるか・そうであるか | **はい / いいえ**。条件付きなら「はい、ただし〜」 |
| **自分の理解が合っているか** | **その理解は正しい / 違う**。一部だけ違うなら、どこが違うか |
| **自分の案がよいか**（可否を問う形で来ることが多い） | **賛成 / 反対**。「できます」だけで終えない（ `treat_user_suggestions_as_proposals.md` ） |
| 値・名前・場所・件数 | 答えそのもの |
| 理由 | 理由を1文で |

**語尾・疑問符・文の形では判定しない。** 相手が何を知りたくて送ってきたかで決める。同じ理解の確認でも、要約だけを送ってくる、自分の説明を貼って「合ってる？」と添える、疑問符の無い言い切りで書く、と形はまちまちです。**語尾の一覧で判定すると、一覧に無い形を落とします。**

**指示や別の質問に混ざっていても拾う。** 特に理解の確認は、答えないと相手は自分の理解が合っていたのか分からないまま次へ進みます。1つのメッセージに複数あれば、1つずつ答える。

```
❌ ## 結論
   削除してから作り直す作りが、不具合の原因そのものです。…   ← 「この案が合理的か？」への応答
✅ はい。
   同じ組み合わせの行は1件しか作れないので、…
```

**見出しや前置きから書き始めない。** 「先頭1〜3行」のような幅のある基準だと、見出しの下に何を書いても満たせてしまい、答えが一言目から外れます。実際に「合理的か？」への応答を `## 結論` から書き始め、「はい」を言わないまま理由を並べて指摘を受けました。

**一言目は、調べ終えてから書く。** 裏取りが要る問いでは裏取りが先です（下記「例外」）。一言目を急ぐと、調べる前に「いいえ」と書いて撤回する形になります。

## 禁止する挙動

- **質問への応答を、答え以外（見出し・前置き・背景）から書き始めること**
- **自分の理解を確かめる文を、正誤を返さずに流すこと**。形を問わず、指示に混ざっていても答える
- **質問かどうかを、語尾や疑問符で判定すること**。相手が何を知りたいかで決める
- 同じことを3通りの表現で言い換える (「つまり」「言い換えると」「要は」等の再説明を重ねる)
- 前提の教科書的説明を毎回頭に置く (ユーザーが既に理解している前提はスキップ)
- **付録的な補足**（背景・比喩・関連トピック）を **明示的に求められていないのに膨らませる**
- 「なぜこのように答えたか」の自己解説を回答本体に混ぜる
- 装飾のためだけの Insight ブロック・比喩・例え話を追加する (**必要ならば** 使ってよい、必要でないなら削る)
- **差分や一覧を見れば分かることを散文で書き写す**。説明が要るのは「なぜそうしたか」と「何に注意すべきか」
- 網羅のために項目を並べること。**該当なしは1行で足りる**

**書き終えたら削る前提で読み返す。** 網羅と丁寧さに寄って必ず膨らむので、次の型を名指しで探して落とす。

| 型 | 例 |
| --- | --- |
| 言い換えの反復 | 同じことを「つまり」「言い換えると」で2度書く |
| 過程の説明 | 検討の経緯・試した順序・一度覆した判断。**最終方針だけでよい** |
| 残す理由の断り書き | 「〜のため残しておきます」「参考までに記載します」。**残すなら黙って残す** |
| 丁寧さの水増し | 「〜という点にご注意ください」「〜と考えております」 |
| 自明な補足 | 「テストも通しています」だけの行。**事実の直後に置く「つまりこう読める」の1文**（「Figma にコメントがある。**そのデザインの位置で読める**」） |
| **会話の写し** | 受け取った内容を「**太字の一言。** 補足」の形で並べる。**会話ログを読んでいるように見える** |

**噛み砕くのは1行で足りる。** 用語や挙動をそのまま置かず「何を指すか / 結果どうなるか」を一言添える。ただし結論を噛み砕き直して2度言うと、短さと読みやすさを同時に失う（ `plain_language_explanation.md` ）。

## 畳み方

同じ観点が並ぶなら**表**、構造・関係・流れなら **Mermaid**。どちらも散文より速く読める。

| 使うもの | いつ |
| --- | --- |
| **表** | 同じ観点の項目が3件以上（選択肢と理由、変更点と影響、対応と結果） |
| **Mermaid** | 列挙からは読み取れない構造・関係・流れ（ `flowchart` / `sequenceDiagram` / `erDiagram` ） |
| **前と後の対比** | **`flowchart` の `subgraph` を2つ**。**別のブロックに分ける**（同じブロックだと横並びになり、上下が決まらない） |

**同じ情報を2つの形式で持たない。** 表に書いたことを散文で繰り返さない。図を置くなら、置く順は**図（全体像）→ 表（項目ごと）**。

### 描いた図は4つの軸で判定する

**1つずつ直すと巡回します。** ある軸で改善して別の軸を悪くする形が続き、実際に**5回作り直しました**。

| 軸 | 問い |
| --- | --- |
| **正確さ** | 矢印が1つの意味だけを持っているか。「参照」と「止める」を同じ線で描いていないか |
| **差の見えやすさ** | 前と後の差が**図だけで**読めるか |
| **主題との一致** | 本文が主張していることを軸にしているか。消えるのが作業なら、**状態ではなく作業**を描く |
| **本文との重複** | **本文の表や散文が既に持っていないか**。図を足したら、重なった散文を削る |

**4つ目が最後に残ります。** 主題へ寄せると、本文が同じことを書いている箇所へ近づくためです。

**他の案と比べて選ばない。** 読み手は図を1つだけ見るので、**単独で読めるか**で判定する。

**描画結果を見る**（ `recheck_after_every_revision.md` の3周目）。構文が通っても、意図した見え方になるとは限りません。

**読み手が見る描画器で確かめる。** 会話へ出す図は TUI が Unicode で描くので、そちらへ流す。

```bash
printf '<ソース>' | node ~/.claude/plugins/cache/claude-code-mermaid/claude-code-mermaid/*/scripts/claude-code-mermaid.mjs
```

**貼り先がブラウザなら、そちらでも描く。** 描画器が違えば崩れ方も違うので、**通した側の結果しか保証できません**。

```bash
npx -y -p @mermaid-js/mermaid-cli mmdc -i diagram.mmd -o diagram.svg
```

**SVG から数えるときは、定義と使用を分ける。** `crossEnd` や `edge-thickness-thick` は `defs` と CSS にも出るので、単純に数えると多く出ます（実測で0本のものが2件と出た）。`marker-end=` や `class=` で絞るか、**ソースの `==>` を数える**。

**1列目に長い値を置かない。** ファイルパスや長い識別子を先頭列に置くと、残りの列が潰れて読めなくなる。短くできないなら表をやめて箇条書きにする。

## 切り出す

**本文に置くのは軸だけ**。判断に迷ったら「**それが無いと読み始められないか**」で決める。

| | 本文 | 別の場所 |
| --- | --- | --- |
| 置くもの | 結論・主要な判断・影響範囲・注意点 | 全文の引用・調査ログ・採らなかった案の詳細 |
| 読み手 | **全員が読む** | 必要な人だけ開く |

切り出したら**本文からリンクを貼り**、同じ情報を両方に持たない。

## テンプレート (質問応答時の目安)

```markdown
[一言目の答え。はい / いいえ / 答えそのもの]
[補う 1〜2 行]

## 理由 / 根拠 (必要なら)

- [1 行]
- [1 行]

## 補足 (必要なら)

[トレードオフ・別案・詳細情報 — 1〜3 行]
```

**「必要なら」節はスキップしてよい**。一言目の答えだけで意図が伝わる質問には、それだけで返す。

## なぜ

- ユーザーは1日に大量の応答を読む。冗長な回答は読解コストを積み上げ、意思決定を遅らせる
- 長さは丁寧さの証明にならない。**簡潔さ = 情報密度の高さ**
- 必要な情報を残しつつ削るのは高度な要約スキル。長く書くのは楽だが、読み手の負担を上げる怠慢

## 例外

- ユーザーが「詳しく」「深く」「噛み砕いて」と明示指示した場合は、その粒度に合わせて展開する
- **裏取りが要る問いでは、裏取りが先** (`verify_before_asserting.md`)。本ルールの「結論を先に」は、**結論が出てからの話**
- 設計判断・レビュー対応など、選択肢比較 + 推奨 + 影響 の3点セットが必要な場面では、テンプレート (`explain_review_comment_first.md` 等) の要求粒度を優先
- BE/インフラの技術説明は `plain_language_explanation.md` の噛み砕き粒度を優先 (ただし冗長にはしない)

## 関連

- `focus_insights_on_judgment.md` （洞察は判断材料に絞る）: 本ルールが禁じる「装飾のための Insight」の**線引き**をあちらが定める
- `no_ai_slop.md` （量を出さない）: 本ルールは**どう畳むか**、あちらは**そもそも足さない**。畳む前に、足す必要があったかを問う
- `no_ai_style_writing.md` （AI が書いたと分かる文体で書かない）: あちらは**表現**。短く畳んでも、演出や実況が残れば読まれない
- `plain_language_explanation.md` (平易に噛み砕く) と両立させる: **短く、かつ平易に**
- `explain_review_comment_first.md` (レビュー対応の粒度) の要求は本ルールより優先
- `verify_before_asserting.md` （断定の前に裏を取る）: **裏取りが要る問いでは、裏取りが先**。調べながら書くと、本ルールの「結論を先に」が**未検証の見立てを結論の位置へ置く**形に化ける
- `summarize_after_each_task.md` (各作業後のサマリ) も本ルールに従って短く
- `/format-github-post` （投稿する文章の畳み方）: **表と Mermaid の使い分けは本ルールが持つ**。あちらは GitHub でしか使えない手段（Alert / `<details>` / 脚注）を足す
- `report_formatting.md` （報告に貼る識別子の書式）: **会話へ Mermaid を出すときのフェンスの書式はあちら**。本ルールは使うかどうかを定める
- `create-pr` / `update-pr-description` スキル: 本ルールを土台に、**PR 固有の事情**（GitHub のレンダリング挙動、テンプレの節構成、補足コメントへの切り出し）を上乗せする
- `explain_from_observables.md` （観測できるものから始める）: 本ルールは**量と順序**、あちらは**何を手がかりに書くか**。**結論を先に置いても、それが抽象語なら伝わらない**
- `treat_user_suggestions_as_proposals.md` （ユーザーの案には賛否を返す）: **どちらも形ではなく中身で判定する**。相手が出したのが案なら、一言目は可否ではなく**賛否**になり、その返し方はあちらが持つ
