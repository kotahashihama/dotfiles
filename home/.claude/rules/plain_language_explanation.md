# 技術説明は噛み砕いて（特に BE / インフラ）

技術的な概念を説明するときは、**噛み砕いた平易な説明**を心がけてください。
これは全プロジェクト共通の好みです。

## 期待するスタイル

- **身近な例え**を添える（例: Go の埋め込みを「箱にラベルを貼って持つ」vs「中身を直接くっつける」で対比する、など）
- **用語 → 意味の対応**を明示する（専門用語をそのまま置かず「〜とは〜」と一段噛み砕く）
- **Before / After・対比構造**で違いを見せる（今の構造 → 提案の構造、旧 → 新、など）
- 結論・要点を先に述べ、そのあと噛み砕いた詳細を続ける

## 領域ごとの粒度

**どの領域でも噛み砕く。** 違うのは**どこまで開くか**であって、開くかどうかではない。

| 領域 | 粒度 | 開き方 |
| --- | --- | --- |
| **バックエンド / インフラ** | **深く開く** | 用語そのものを「〜とは〜」で一段開く。例え・対比を添える（ミドルウェア、DB、マイグレーション、パーサー、ネットワーク、ビルド/CI、コンテナ等） |
| **フロントエンド** | **一段浅く開く** | 一般的な用語はそのまま置く。**そのコード固有の仕掛けと、なぜその形かは開く** |

**フロントエンドで開かなくてよいもの**: 一般的な言語機能・ライブラリの用語（hydration、メモ化、Server Component）。強みの領域なので、教科書的な説明は要らない。

**フロントエンドでも開くもの**: そのリポジトリ固有の呼び名、実装が採った方針とその理由、素直に書くとどこが困るか。**用語を知っていることと、初見のコードの意図が読めることは別。**

**「聞かれたら答える」では遅い。** 読み手は分からないことに気づいてから尋ねるので、**分からないまま読み進める分**が落ちる。強みの領域でも、こちらから開く。

**領域ではなく、言語・ツール単位で見る。** 同じバックエンドでも、慣れている言語と初めての言語では要る粒度が違う。個別の習熟度は `CLAUDE.md` が持つ。

## 業界で通っている語を使う

**訳語を自分で選ばない。** 日本の IT で定着している言い方があるなら、それを使います。

| 使わない | 使う | 場面 |
| --- | --- | --- |
| 段 | **フェーズ** | 処理の区切り |
| 索引 | **インデックス** | DB の索引 |
| 引き金 | **トリガー** | 起点になるもの |
| 待ち行列 | **キュー** | SQS・ジョブキュー |
| 覚え書き | **メモ** | — |
| 対応表 | **マッピング** | キーから値を引く定義 |
| 綴りの誤り | **typo** | コードの書き間違い |
| 選択肢 | **union** | 型が取りうる値の集合 |
| 既定の〜 | **default の〜** | **コードの分岐・値**（振る舞いの規約では「既定」のまま） |

**判定は「その現場で口に出すか」。** 会話で「インデックスが効いてない」と言うなら、書くときも同じ語にする。

**コードの話では英語のまま使うことが多い。** `typo` `default` `union` を日本語へ訳すと、意味は通っても現場の言い方から離れます。**訳すほうが丁寧だと感じたときほど疑う。**

**同じ語でも場面で変わります。** 「索引」は DB では使いませんが、**目次の意味なら自然**（ `MEMORY.md` の索引）。機械的に置き換えず、その場面で通っている側を選ぶ。

**カタカナが常に正しいわけでもありません。** 「更新経路」「実行時間」「走査」のように漢語で定着しているものはそのまま。**定着している側を選ぶ**のが規約で、カタカナに寄せるのが規約ではありません。

**読み手が引っかかると、そこで読むのが止まります。** 意味が伝わるかどうかではなく、**流れが切れるかどうか**の問題です。

## 用語は略さず、正式な名前で書く

**同じ文書の中で2回目だから略す、をしない。** 読み手はどこから読み始めるか分からず、略した先が何を指すかは書き手にしか見えていません。

```
❌ 履歴1行が2.60ms、詳細1行が0.354ms
✅ 変更履歴1行が2.60ms、変更内容1行が0.354ms
```

**別の実体が同じ語になるときは、特に危ない。**

| 実体 | 呼び方 |
| --- | --- |
| `accounts` | **アカウント** |
| `sub_accounts` | **子アカウント** |

**「アカウント」とだけ書くと、どちらの話か決まりません。** 片方しか出てこない文書でも、読み手はもう片方を知っています。

**正式な名前は推測せず、定義の側から採る。** テーブルなら `COMMENT`、型なら doc コメント。`sub_account_change_details` を「変更詳細」と呼んでいたところ、実際の定義は**子アカウント変更内容**でした。

## 長い修飾語を先に置く

**同じ語に修飾語が2つ以上かかるなら、長いものから並べます。** 短いほうを先に置くと、読み手は係り先を保留したまま長い句を読むことになります。

```
❌ 新しい、履歴の行数が増えると遅くなる経路
✅ 履歴の行数が増えると遅くなる、新しい経路
```

**引っかかる場所が減るだけで、意味は変わりません。** 読点を足して支えたくなったら、順序を疑う。

**順序の目的は、かかる語と受ける語を近づけることです。** 長さで決まらないときは、**離れている組を先に寄せる**。

## 読み手がユーザーとは限らない

**GitHub へ書く文章は、領域に関わらず「その機能を知らないエンジニア」に合わせる。** PR 説明・コメント・レビュー返信の読み手はユーザーではないので、**前節の領域ごとの粒度は持ち込みません**。FE の PR だからと一段浅くしない。**ユーザーが FE に強いことは、レビュアーがその機能を知っていることを意味しない**。

**1機能を1人が担当する体制では、レビュアーは必ず別の文脈から来ます。** 設計の議論に同席しておらず、その領域のコードも読んでいない。**書き手だけが持っている前提を書き出さないと、差分の意味が伝わりません。**

| | 読み手 | 揃える先 |
| --- | --- | --- |
| 会話での説明 | ユーザー | **本人の習熟度**（FE は一段浅く、BE / インフラは深く） |
| **PR 説明・コメント** | **別チーム・別領域のレビュアー** | **その機能を知らない前提** |

書き手は実装したばかりで**何が自明でないかが見えなくなっています**。次の3つが落ちやすい。

- **内部の呼び名**。型名・サービス名・SQL ファイル名は、初めて見る人には意味を持たない
- **前提**。「この経路はドメインモデルを経由せず直接書き込む」のような背景は、差分からは読み取れない
- **判断の分かれ目**。「なぜ A ではなく B か」は、詳しい人ほど自明として省く

**ただし噛み砕きすぎない。** レビュアーはエンジニアなので、一般的な技術用語まで開く必要はありません。開くのは**そのリポジトリ固有の語彙**です。

## なぜ

- **ユーザーはフルスタックエンジニアで、強みはフロントエンド**。BE / インフラも担当するが、前提知識の厚みに差があり、それがそのまま理解の差になる。
- 専門用語の羅列より「例え＋用語の噛み砕き＋対比」のほうが理解が速い、と本人が明言している。
- 特に BE/インフラは抽象度が高く、身近な例えがないと伝わりにくい。
- 理由が「好み」ではなく**強みの偏り**だと分かれば、書かれていない領域でも粒度を判断できる。担当範囲かどうかではなく、**慣れているかどうか**で決める。
- **ここまでの根拠はすべて読み手がユーザーである場合のもの。** GitHub へ書く文章の読み手は別人なので、**ユーザーの習熟度は判断材料にならない**。FE の PR を浅くしてよい理由がどこにも無い
- **強みの領域でも、初見の実装は別**。用語の習熟が高いほど「読めば分かる」と見なされやすいが、**そのコードが何を避けてその形になったか**は書かれていなければ伝わらない。開く対象が用語から設計判断へ移るだけで、開く必要は消えない。
- **PR は1人1機能の体制で読まれる。** レビュアーは設計の議論に同席しておらず、その領域のコードも読んでいない。**書き手にとっての自明が、読み手にとっての空白になる**

## 例外

- ユーザーが明示的に「詳細不要」「専門的でよい」と指示した場合はそれに従う。
- ユーザーが「手短に」「結論だけ」と求めた場合は簡潔さを優先し、噛み砕きは最小限に。

## 関連

- `focus_insights_on_judgment.md` （洞察は判断材料に絞る）: あちらは**説明の選び方と長さ**。本ルールは**用語の粒度**。両立させる
- `concise_first_then_detail.md` （簡潔に）: **短く、かつ平易に**の両立。全体量は抑えつつ、説明する概念は噛み砕く。噛み砕きを理由に長くしない
- `/create-pr` / `/update-pr-description`: GitHub へ書く文章での具体化。本ルールが土台で、スキルは PR 固有の事情（テンプレの節構成・表と図の使い方）を上乗せする
- `explain_from_observables.md` （観測できるものから始める）: 本ルールは**用語の粒度**（どこまで開くか）、あちらは**構成**（何から書くか）。用語を開いても、抽象から書き始めれば読み手は像を結べない
- `no_ai_style_writing.md` （AI が書いたと分かる文体で書かない）: あちらは**書き癖**（演出・実況・読点）、本ルールは**読み手が引っかかる箇所**。名詞で積まず動詞で書くのはあちら
