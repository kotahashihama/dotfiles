# データ値と識別子はインラインコードで囲む

文章の中にそのシステムに存在する値や名前を書くときは、バッククォートで囲んでください。
会話・PR 説明・レビューコメント・課題管理ツールのコメント・ドキュメント、こちらが書くものすべてが対象です。
これは全プロジェクト共通の規約です。

## 判定は「読み手がそのまま打つか、貼るか」

| 囲む | 囲まない |
| --- | --- |
| 値・ID・変数名・テーブル名・列名・パス・コマンド（ `12` `user_id` `/settings` `task test` ） | 数量・件数（3ファイル / 21秒）。単位と詰める |
| API が受け取る値（ `owner` ）、入力した値（打ち込んだ語、選択肢から選んだ値の `公開中` ） | 画面のラベル・ボタン・メニュー・欄の名前・見出し（「オーナー」「保存する」は鉤括弧） |

**同じ語でも、値か表示かで変わります。** API へ送る `owner` は囲み、画面に出ている「オーナー」は鉤括弧で示す。

**画面に出ていても、登録したデータなら値です。** 利用者や自分が入力した企業名・商品名・ラベル名・人名は、行ごとに違う値なので囲む（ `サンプル株式会社` とその ID の `12345` ）。人そのものへの言及（「山田さんに聞く」）は囲まない。

**入力した値は、選択肢から選んだものでも囲む。** 判定は「その語が操作する場所か、入力した中身か」。絞り込みで選んだ `公開中` や並び順で選んだ `新しい順` は入力した中身なので囲む。欄の名前（「公開設定」）、押したボタン（「検索する」）、開いたメニュー（「設定」）は操作する場所なので鉤括弧にする。画面に出た表示を引くときも鉤括弧にする（「絞り込み： 公開中」）。

実際に、QA の結果報告で打ち込んだ語はインラインコード、選んだ値は鉤括弧で書き、同じ表の中で書き方が割れていると指摘を受けました。選択肢はコードで決まっているので鉤括弧、と分けていたためです。読み手にとってはどちらもそのまま入れる値です。

表のセルでも同じです。実際に、課題へ残した確認報告で、検証用に作った企業名と ID を表のセルに素のまま書き、指摘を受けました。

## GitHub では、自動で解釈される記法だけ囲まない

**囲むとリンクになりません。** `POST /markdown` （ `mode: gfm` ）で5種とも実測した。

| 記法 | 裸 | 囲む |
| --- | --- | --- |
| `@ユーザー名` | メンションになる | ならない。通知が飛ばない |
| `#123` / `owner/repo#123` | 参照になる | ならない |
| 生の URL | リンクになる | ならない |
| コミット SHA（短縮形も含む） | コミットへのリンクになる | ならない |

**短縮した SHA も裸で書く。** PR 本文で「先頭 `89c676db4` 」のように囲んで書き、リンクにならないと指摘を受けました。実測では7桁以上ならそのリポジトリのコミットへのリンクになり（表示は7桁に縮む）、6桁ではなりませんでした。`git log --oneline` の9桁をそのまま書けば足ります。

会話への報告では逆に囲む（ `report_formatting.md` ）。クリックできないので値として示すほうが役に立つ。ただし URL は囲まない。ターミナルは裸の URL をリンクにするので、囲むとクリックできなくなります。

## なぜ

- 値と地の文の境界が無いと、どこまでが値か読み手が決められない。囲まない数字は助数詞にも年号にも見える
- 等幅で表示されるので、`l` と `1`、`0` と `O` の取り違えが減る
- 読み手はその値をそのまま貼る。囲めばコピーの単位が揃う

## 例外

- 引用・ログの原文（原文を書き換えない）
- ユーザーが書式を指定した場合

## 関連

- `no_space_between_number_and_unit.md` （数値と単位の空白）: 囲んだ後の前後の空白はあちら（ `### インラインコードの前後は空ける` ）。本ルールは囲むかどうかを決める。URL と課題キーをリンクにするのもあちらで、リンクにした課題キーは囲まない
- `github_writing.md` （他リポジトリの PR / issue）: 囲まない側の代表。あちらが前提として置く「パス・コマンド・識別子は囲むのが正しい」の本体が本ルール
- `report_formatting.md` （報告に貼る識別子の書式）: 会話と GitHub で扱いが逆になる。あちらは会話への報告が対象
- `code_comments.md` （コードコメントに何を書くか）: コードコメントでは issue を `owner/repo#123` ではなく URL で書く（あちらの「外部の資料は、URL を単独の行に書く」）。GitHub で囲まないという本ルールの話は、コードコメントには起きない
