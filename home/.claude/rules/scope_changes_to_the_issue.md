# 課題に紐づく作業では、その課題を直接解決しない変更を極力入れない

課題票に紐づけて出す変更は、**その課題を直接解決するもの**へ寄せてください。付随して避けられないものと、入れないほうが不自然になるものだけ一緒に対応します。
これは全プロジェクト共通の規約です。

**見る単位は PR 全体です。** 1本ずつでは小さくても、その課題に紐づく PR を通すと積み上がります。

## 3つの問いで決める

上から順に問い、**1つでも「はい」なら入れてよい**。どれも「いいえ」なら外す。

| 問い | 例 |
| --- | --- |
| それが無いと課題が直らないか | 直す対象そのもの、直ったことを確かめるテスト |
| 触った箇所から波及して避けられないか | 変えたインターフェースの呼び出し側・モック・仕様書の該当節 |
| 入れないと、残りが食い違ったままになるか | 同じ判定の片側だけ直して経路ごとに挙動が割れる、doc が実装と合わなくなる |

**「ついでだから安い」は理由になりません。** レビュアーは課題が直るかを確かめに来ているので、関係の無い差分はその確認を薄めます。

最も混ざりやすいのはレビュー対応です。指摘を直すのは依頼の範囲ですが、そこから波及した改善（エラー種別・命名・書式・設定）は別の判断になります（ `ask_before_editing_claude_assets.md` の「レビュー対応は最も広がりやすい経路」）。

## 外したものの行き先

**外すことと、捨てることは別です。**

| 見つけたもの | 行き先 |
| --- | --- |
| その課題の調査中に見つけた別の不具合 | 別の PR（課題との紐づけ方は `karma_commit_style.md` ） |
| 規約違反・改善の余地 | 課題を立てるか、会話で報告する |
| どちらとも言えない | 入れずに報告する。入れるかはユーザーが決める |

## 禁止する挙動

- **課題を直接解決しない変更を、同じ PR へ混ぜること**
- 「付随」「不自然」を感覚で広げること。上の3つの問いに当てて決める
- レビュー指摘から波及した改善を、指摘への対応として一緒に入れること
- 外したものを黙って捨てること。行き先を決めて報告する

## なぜ

- レビュアーは課題が直るかを確かめに来ている。関係の無い差分はその確認を薄め、読む量だけ増やす
- 混ざった変更は**戻せない**。課題の修正を revert したいとき、無関係な改善まで一緒に戻る
- 「ついで」は際限が無い。触ったファイルに改善の余地は必ずあるので、線を引かないと差分が膨らみ続ける

## 例外

- ユーザーが「ついでに直して」と明示した場合
- **機械が自動で直すもの**（フォーマッタ・lint の自動修正）。ステージした時点で入るので避けられない
- 課題そのものが整理・リファクタである場合

## 関連

- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: 依頼の範囲から波及するものを勝手に入れないという同じ形。あちらは設定ファイル、本ルールは変更全般
- `explain_from_observables.md` （観測できるものから始める）: あちらは入れると決めた付随の変更をどう書くか、本ルールは**そもそも入れるかどうか**
- `split_and_stack_prs.md` （分けて積む）: 入れると決めたものが大きいなら分ける
- `karma_commit_style.md` （PR に番号を付けるか）: 別 PR にしたものを課題へ紐づける判定はあちら
- `no_unnecessary_pausing.md` （確認が要らないなら止まらない）: 外したものを報告するのは停止ではない
