# 投稿する文章の末尾に生成者表示を添える

Claude がユーザーに代わって投稿・更新する文章には、**末尾に生成者表示を添えて**ください。
これは全プロジェクト共通の規約です。

主な投稿先は GitHub で、そこでは Note アノテーションを使います。課題管理ツールのコメントやチャットへ書くときも付けますが、形が変わります（下記「Alert が使えない投稿先では引用だけ残す」）。

**ただし課題管理ツールの課題の本文には付けません**（下記「課題管理ツールの課題の本文には付けない」）。

## 対象

Claude がユーザーに代わって書き込むテキスト全般。

- PR 説明（新規作成・更新のいずれも）
- PR コメント（issue comment）
- レビューコメントへの返信（inline reply）
- issue の本文・コメント
- Discussion の投稿
- 課題管理ツールのコメント（**課題の本文は対象外**。下記「課題管理ツールの課題の本文には付けない」）
- チャットへの投稿

## 形式

本文の末尾に空行を1行挟み、以下のブロックを置く。

```
<本文>

> [!NOTE]
> このコメントは Claude Code を使って作成されています。
```

- PR 説明の場合は主語を変える: `この PR 説明は Claude Code を使って作成されています。`
- モデル名（Opus / Sonnet 等）ではなくクライアント名 `Claude Code` を使う。モデル名は起動ごとに揺れるが、書き手はいずれも Claude Code なので統一する
- **「で作成」ではなく「を使って作成」**。「で」だと道具が主語になり、Claude Code が単独で書いたように読める。実際はユーザーが渡した文脈と指示を元に組み立てたもので、内容の責任もユーザー側にある。道具として書けば、レビュアーは疑問をユーザーへ投げればよいと分かる
- **必ず末尾**に置く。冒頭に置くと読み手が本文本体に辿り着くまでにメタ情報を読まされる
- 既存の投稿に旧フォーマットの生成者表示があれば、この Note ブロック1つに正規化する

## Alert が使えない投稿先では、引用だけ残す

`> [!NOTE]` は GitHub の拡張です。他のツールでは `[!NOTE]` が文字として出ます。

| 投稿先 | 形 |
| --- | --- |
| GitHub | `> [!NOTE]` と `> <定型文>` の2行 |
| Markdown が使える他のツール | `> <定型文>` の1行（ `[!NOTE]` だけ落とす） |
| Markdown が使えない | 素のまま1行 |

**`>` は落とさない。** 本文と切り離す働きはこちらが担っており、行末の句点を残す根拠にもなっています（ `github_writing.md` の検査が `>` 始まりを対象外にしている）。素のテキストにすると、定型文の句点が本文の違反として拾われます。

記法は投稿先ごとに確かめる。記憶で決めない（ `verify_before_asserting.md` ）。
引き方はツールごとに違います。Backlog ならプロジェクトの `textFormattingRule` が `markdown` か独自記法かを返しますが、他のツールでは別の引き方になります。

## 期待する挙動

- `gh pr comment` / `gh pr edit --body` / `gh api ... /replies` 等で投稿する前に、本文末尾へ Note ブロックを足したか確認する
- ハッシュだけを返す短い返信でも省略しない。Note はブロッククォートで本文と改行分離されるため、**1行目からのハッシュ機械抽出を妨げない**
- 既存投稿を更新するときも、Note が末尾に残っているかを確認する（本文を差し替えて消してしまわない）

## 禁止する挙動

- Note を付けずに GitHub へ投稿すること
- **GitHub 以外へ投稿するときに生成者表示を省くこと**。書式を検査するフックは `gh` コマンドの本文しか見ないので、MCP や API 経由の投稿は素通りする
- `>` を落として素のテキストにすること。本文と切り離す働きを担っており、行末の句点を残す根拠にもなっている
- 本文の冒頭や中間に置くこと
- `Claude Opus 5` のようなモデル名を書くこと
- 「AI が書きました」等の独自文言に置き換えること（文言は上記で固定）

## なぜ

- 人間のレビュアーが**書き手を判別できる**ようにするため。人が書いた文章と混ざると、指摘の重みや確認の仕方を読み手が判断できない
- 文言とクライアント名を固定することで、**投稿の出どころが機械的に追える**（後から一括検索・集計ができる）
- 末尾固定にすることで、レビュアーは本文本体を先に読める

## 例外

**既定は「付ける」。** 外すのは、その投稿がユーザー本人の言葉として出るときだけ。

| 場面 | Note |
| --- | --- |
| Claude が投稿するもの全般（PR 説明・補足コメント・bot への返信・人間レビューへの返信） | 付ける |
| 課題管理ツールの課題の本文（新規起票・本文の更新のいずれも） | 付けない（下記） |
| 自分たちが管理していないリポジトリへの投稿（OSS への PR・issue・コメント） | 付けない（下記） |
| ユーザーが文面を指定して「これをそのまま投稿して」と指示した | 付けない |
| ユーザーが「Note は不要」と明示した | 付けない |

人間のレビューコメントへの返信も付けます。かつては「宛先が個人なので、生成者表示が挟まると誰と話しているのか曖昧になる」として外していましたが、文言を「を使って作成」に改めた時点でその懸念は消えました。道具として書けば、話している相手はユーザーのままです。

外すのは**ユーザーが文面を指定したときだけ**。そのときは Claude が組み立てていないので、生成者表示が事実に合いません。

そもそも対象外のもの。

- `git commit` のメッセージ・PR タイトル（こちらは `Co-Authored-By` トレーラーが役割を担う）
- コマンドコメント（ `/ai-review` 等、ワークフローが本文を検知するもの）。Note を足すと検知が壊れる（ `github_writing.md` ）

### 課題管理ツールの課題の本文には付けない

同じツールでも、課題の本文とコメントで扱いが違います。

| 投稿先 | Note |
| --- | --- |
| 課題の本文 | 付けない |
| 課題へのコメント | 付ける |

課題の本文は、その課題で何をするかの定義です。読み手（実装する人・品質保証の担当・報告者）が要るのは作業の内容だけで、誰が文章を組み立てたかは判断を変えません。

コメントは発言なので付けます。調査の結果・判断の根拠・経緯は、書き手によって扱いが変わります。

**判定は「その文章が発言か、定義か」。** 発言なら付ける、定義なら付けない。

課題の子チケットをまとめて起票するときに効きます。14件の本文へ同じ1行が並び、どの課題を開いても作業の内容の前に同じ文が入ります。

### 自分たちが管理していないリポジトリには付けない

外部のリポジトリでは、書式は相手のプロジェクトのものです。Note はこちらの運用（誰が書いたかを後から機械的に追える状態を保つこと）のために付けるもので、相手のリポジトリにはその運用がありません。読み手が知りたいのは変更の中身だけで、道具の開示は求められていません。

**判定は「そのリポジトリの運用をこちらが決めているか」。** 決めているなら付ける、そうでないなら付けない。社内のリポジトリは、他チームのものでも付ける側です。

**外すのは Note だけで、`Co-Authored-By` トレーラーは外部でも付けます。** あちらは共同作業者の表記として広く使われている書式なので、相手のリポジトリでも読み方が決まっています（ `karma_commit_style.md` ）。

## 関連

- `responding_to_reviews.md` （レビューコメントへの対応）: 投稿してよいかと、返信の後の 👍 はあちら。本ルールは投稿すると決まった後の書式
- `github_writing.md` （GitHub へ投稿する文章の書き方）: コマンドコメントの節が本ルールの適用外を定める（宛先が機械のコメントには Note を付けない）。あちらは GitHub のみで本文の書き方を定め、本ルールは投稿先全般の末尾の Note を定める。Note の定型文はあちらの対象外。**開示の場所は本ルールが持つ**。帰属の節は本文中の言い回しを扱い、Note で足りている開示を本文で重ねないことを定める
- `/create-pr` / `/update-pr-description` / `/review-pr` / `/resolve-ai-reviews` / `/resolve-human-reviews` の各スキルにも同じ規定がある。本ルールはスキル経由でない自然文依頼の経路を含めて横断的に適用する
- `/format-github-post` （投稿する文章の畳み方）: 本ルールが `NOTE` を占有している。他の Alert と混ざらないよう、あちらが用途を分ける
