# 重い作業はバックグラウンド化するか、並列で流す

テスト・ビルド・lint・CI 待ちのように**数十秒以上かかる処理**は、前景で待たずに `run_in_background` で流してください。待っている間は他の作業を進めます。
これは全プロジェクト共通の規約です。

## 期待する挙動

- バックグラウンド化する。全体テスト・ビルド・lint・型チェック・依存インストール・CI 完了待ち・大きなマイグレーション
- 並列で出す。依存関係のないツール呼び出しは1メッセージにまとめて発行する（調べ物と別の調べ物、複数ファイルの Read、複数 PR への `gh` 問い合わせ）
- 待ち時間を埋める。バックグラウンドに投げたら、結果に依存しない作業（別ファイルの編集、コミット文の用意、他タスクの調査、届いたメッセージへの返信）へ進む
- **結果は必ず回収する**。完了通知を受けたら出力を読み、失敗していれば対処する。投げっぱなしにしない
- **完了通知を待つために `sleep` を挟まない**。通知は自動で届く。`sleep` は待ち時間を埋めないどころか、その間ツールを1つ占有して他の作業もできなくする

## 待っている間に「できることが無い」と判断しない

**待つ処理が塞いでいるのは、たいてい1つの資源だけです。** build が作業ツリーの成果物を使っているならブランチは切り替えられませんが、読むことも書くことも止まっていません。

「進められない」と感じたら、先に塞がっているものを名指しする。そのうえで、それを使わない作業を探す。

| 塞がっているもの | まだできること |
| --- | --- |
| 作業ツリー（build・テストが走っている） | 次に書くテストやコードを scratchpad に下書きする / 別のブランチの差分や周辺コードを `git show <ref>:<path>` で読む |
| 次の一手の判断材料（結果が要る） | 結果に依らない側の準備（PR 本文の組み立て・コミット文・既存 PR の本文の更新） |
| 他セッションやユーザーの返事 | 返事で変わらない範囲の作業、届いた連絡への返信・照会 |

**途中経過を報告してターンを終えない。** 報告は進みながら出すもので、報告したことは手を止める理由になりません（ `decide_or_ask.md` の「確認が要らないなら止まらない」）。止まってよいのは、どの資源も塞がっていて、表のどの行にも作業が残っていないときだけです。

実際に、build を待つ間に途中経過の表を出してターンを終える形を1つのセッションで3回以上繰り返し、そのたびにユーザーから「待ってる間にもできることはきっとある」と言われました。どの回も、次の対象のテストの下書きと差分の読み取りが残っていました。

## コミット時に重いフックが走る場合

`git commit` が pre-commit フックで全テストを同期実行するリポジトリでは、**コミット自体が数分ブロックする**。この場合は検証を前倒しする。

1. 変更に関係するテスト・lint をバックグラウンドで流し、結果を確認する
2. 通っていることを確認してから、フックを飛ばしてコミットする

フックを飛ばすのは、**そのフックが持つ検査を全部自分で済ませた場合に限る**。テストだけ通しても、同じフックが秘匿値の走査や書式の検査を持っていれば、それも一緒に外れる。検証せずに飛ばすのは単なる手抜きになる。

## 推敲を複数まとめて回すときの出し方

`/agy-review` は1回あたり20〜40秒かかります。対象が増えるほど待ちますが、並列度を上げると失敗します。

実測（同じ3ファイル。並列3本だけ2回測った）。

| 呼び出し方 | ファイル数 | 実時間 | 落ちた呼び出し |
| --- | --- | --- | --- |
| 1回の呼び出しにまとめる | 3 | 44秒 | 0本 |
| 並列2本 | 2 | 32秒 | 0本 |
| 並列3本 | 3 | 36秒 / 49秒 | 2回とも1本 |

**まず1回の呼び出しにまとめます。** 複数ファイルを渡せて、出力は元の見出しごとに分かれて返るので、ファイル数に比例して待たされません。

まとめきれない量なら、分けて並列2本までにします。3本以上はクォータ（429）と容量（503）に当たり、2回とも1本が落ちました。どちらもモデル側の混み具合から出るので、こちらの書き方では避けられません。

バックグラウンドで流し、待つあいだは別の作業へ進みます（上記）。

**落ちても本文が返っていることがあります。** 終了コードが0以外だと `--out` は書かれませんが、stderr の JSON にある `response` には、指摘と修正後全文が入っていました（2回とも）。捨てる前に開いてください。

## 前景で待ってよいもの

- 1秒程度で返るもの（ `git status`、単一ファイルの `grep`、`gh pr view` ）
- **次の一手がその結果で決まる**もの（分岐の判断材料。ただし他に進められる作業があるなら、それを先に片付ける）
- 対話が必要なもの（バックグラウンドでは入力を返せない）

## 禁止する挙動

- 全体テストや CI 完了待ちを前景で回し、何もせずに待つこと
- **待っている間に途中経過を報告して、ターンを終えること**。塞がっている資源を名指しし、それを使わない作業へ進む（上記「待っている間に『できることが無い』と判断しない」）
- **バックグラウンド化したうえで `sleep` / ポーリングで前景を塞ぐこと**。重い処理を投げた事実は、待ってよい理由にならない。ユーザーからは前景が止まって見える
- 独立した調査を1つずつ直列に投げること（1メッセージに複数まとめる）
- バックグラウンドに投げた結果を確認しないまま次へ進むこと
- 結果待ちの間に「終わりました」と報告すること（完了通知は自分で書くものではない）
- **`/agy-review` を3本以上同時に出すこと**。まとめられるならまとめる。実測で2回とも1本落ちた
- 落ちた `/agy-review` の出力を、見ずに捨てること。終了コードが0以外でも本文が返っていることがある

## なぜ

- ユーザーの体感時間は**エージェントが止まって見える時間**で決まる。テストの実行時間そのものは変えられないが、その裏で別の作業が進んでいれば全体は縮む
- 前景で長時間ブロックすると、ユーザーからは**固まっているのか動いているのか判別できない**
- 直列に投げた独立処理は、単純に所要時間が足し算になる。並列なら最も遅い1本で済む

## 例外

- ユーザーが「順番に見たい」「1つずつ確認して」と明示した場合
- バックグラウンド実行が使えない環境では、前景で実行してよい（その場合も独立処理の並列化は行う）

## 関連

- `concise_first_then_detail.md` （簡潔に）: バックグラウンドの結果報告も要点だけに絞る
- `summarize_after_each_task.md` （各作業後のサマリ）: 回収した結果は作業サマリに含める
- `decide_or_ask.md` （確認が要らないなら止まらない）: あちらは許可を待って止まる形、本ルールは結果を待って止まる形。どちらも報告は停止の合図ではない
- `verify_the_check_worked.md` （検査が成立していたかを疑う）: **回収した結果が成立しているか**を扱う。空の出力や、`&&` の前段が黙って失敗した結果を根拠にしない。**完了通知の終了コードも同じ**で、パイプを挟むとパイプ末尾の値が返る
- `verify_before_asserting.md` （断定の前に裏を取る）: 回収した結果を断定として書く前の裏取り
