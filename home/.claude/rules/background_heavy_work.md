# 重い作業はバックグラウンド化するか、並列で流す

テスト・ビルド・lint・CI 待ちのように**数十秒以上かかる処理**は、前景で待たずに `run_in_background` で流してください。待っている間は他の作業を進めます。
これは全プロジェクト共通の規約です。

## 期待する挙動

- **バックグラウンド化する**。全体テスト・ビルド・lint・型チェック・依存インストール・CI 完了待ち・大きなマイグレーション
- **並列で出す**。依存関係のないツール呼び出しは**1メッセージにまとめて**発行する（調べ物と別の調べ物、複数ファイルの Read、複数 PR への `gh` 問い合わせ）
- **待ち時間を埋める**。バックグラウンドに投げたら、結果に依存しない作業（別ファイルの編集、コミット文の用意、他タスクの調査、届いたメッセージへの返信）へ進む
- **結果は必ず回収する**。完了通知を受けたら出力を読み、失敗していれば対処する。投げっぱなしにしない
- **完了通知を待つために `sleep` を挟まない**。通知は自動で届く。`sleep` は待ち時間を埋めないどころか、**その間ツールを1つ占有して他の作業もできなくする**

## コミット時に重いフックが走る場合

`git commit` が pre-commit フックで全テストを同期実行するリポジトリでは、**コミット自体が数分ブロックする**。この場合は検証を前倒しする。

1. 変更に関係するテスト・lint をバックグラウンドで流し、結果を確認する
2. 通っていることを確認してから、フックを飛ばしてコミットする

フックを飛ばすのは**同じ検証を自分で済ませた場合に限る**。検証せずに飛ばすのは単なる手抜きになる。

## 前景で待ってよいもの

- 1秒程度で返るもの（ `git status`、単一ファイルの `grep`、`gh pr view` ）
- **次の一手がその結果で決まる**もの（分岐の判断材料。ただし他に進められる作業があるなら、それを先に片付ける）
- 対話が必要なもの（バックグラウンドでは入力を返せない）

## 禁止する挙動

- 全体テストや CI 完了待ちを前景で回し、**何もせずに待つ**こと
- **バックグラウンド化したうえで `sleep` / ポーリングで前景を塞ぐこと**。重い処理を投げた事実は、待ってよい理由にならない。ユーザーからは前景が止まって見える
- 独立した調査を1つずつ直列に投げること（1メッセージに複数まとめる）
- バックグラウンドに投げた結果を確認しないまま次へ進むこと
- 結果待ちの間に「終わりました」と報告すること（**完了通知は自分で書くものではない**）

## なぜ

- ユーザーの体感時間は**エージェントが止まって見える時間**で決まる。テストの実行時間そのものは変えられないが、その裏で別の作業が進んでいれば全体は縮む
- 前景で長時間ブロックすると、ユーザーからは**固まっているのか動いているのか判別できない**
- 直列に投げた独立処理は、単純に所要時間が足し算になる。並列なら最も遅い1本で済む

## 例外

- ユーザーが「順番に見たい」「1つずつ確認して」と明示した場合
- バックグラウンド実行が使えない環境では、前景で実行してよい（その場合も独立処理の並列化は行う）

## 関連

- `concise_first_then_detail.md` （簡潔に）: バックグラウンドの結果報告も要点だけに絞る
- `summarize_after_each_task.md` （各作業後のサマリ）: 回収した結果は作業サマリに含める
- `verify_the_check_worked.md` （検査が成立していたかを疑う）: **回収した結果が成立しているか**を扱う。空の出力や、`&&` の前段が黙って失敗した結果を根拠にしない。**完了通知の終了コードも同じ**で、パイプを挟むとパイプ末尾の値が返る
- `verify_before_asserting.md` （断定の前に裏を取る）: 回収した結果を断定として書く前の裏取り
