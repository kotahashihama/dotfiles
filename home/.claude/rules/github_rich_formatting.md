# 投稿する文章では、伝わる形を選んで書く

PR 本文・コメント・レビュー返信・課題管理ツールのコメントでは、**散文で書くと長くなるものを別の形へ畳んで**ください。
これは全プロジェクト共通の規約です。

**手段の選び方は `/format-github-post` が持ちます**（表・Mermaid・Alert・`<details>`・脚注・パーマリンク・別コメント）。**PR 本文やコメントを書き始めたら、そちらを開く。**

**アノテーションだけは本ルールが持ちます。** 投稿先を問わず要るうえ、**フックもスキルも通らない経路がある**ためです。課題管理ツールへは MCP 経由で投稿するので `lint-github-body.sh` （ `Bash` の `gh` しか見ない）が走らず、**どのスキルの手順にも入りません**。

## アノテーションで、相手に求めることを示す

レビューで使う `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` は、**受け取った側が何をすべきか**を1行目で示す記号です。

| 記号 | 相手に求めること |
| --- | --- |
| `[must]` | 直してほしい |
| `[imo]` | 検討してほしい |
| `[nits]` | 気が向けば直してほしい |
| `[ask]` | 答えてほしい |
| **`[fyi]`** | **読むだけでよい** |

**自分の PR へ補足を置くときは `[fyi]`。** 調査の結果・移行の事情・判断の根拠は、**対応も返信も求めていない**ので `[fyi]` が合います。

```
[fyi]
<本文>
```

**1行目に置き、次の行から本文を書く**（間に空行は入れない）。

**`[memo]` は使わない。** メモは**自分のために残すもの**で、GitHub に書くものは**読む人のためにあります**。
自分用の記録はメモリや手元のノートへ置く。

**課題管理ツールのコメントでも同じ記号を使います。** ただし使うのは **`[fyi]` だけ**です。

課題のコメントを読んで誰かがコードを直すことはないので、`[must]` / `[imo]` / `[nits]` は出てきません。
**`[ask]` も使いません。** 質問はチャットで直接聞くほうが早く、課題のコメントには残らないためです。

## 禁止する挙動

- **ハッシュだけの返信に何かを足すこと**。1行目からハッシュを機械抽出できる形を壊す
- **GitHub のコメントへ `[memo]` と書くこと**。メモは自分用で、**読む人のために書くなら `[fyi]`**
- **投稿先がスキルやフックの外だからと、畳まずに散文で出すこと**。判断軸は投稿先で変わらない

## なぜ

- **レビュアーは差分を読むために来ており、本文を読むのは前段**。前段が長いほど、本題に入るまでの負担が増える
- アノテーションは**1行目で相手の次の行動を決める**。記号を誤ると、対応が要らないものに対応させる
- 強調も記号も**相対的**にしか働かない。全部を強調すると、何も強調していないのと同じになる

## 例外

- ユーザーが形式を指定した場合
- **コマンドコメント**は本文をコマンド1行に保つ（ `github_command_comments.md` ）

## 関連

- `/format-github-post` （投稿する文章の畳み方）: **手段の選び方はあちら**。本ルールはアノテーションと、あちらが読まれない経路の注意を持つ
- `concise_first_then_detail.md` （簡潔に）: **表と Mermaid の使い分けはあちら**
- `github_note_generated_by_claude.md` （生成者表示）: **`NOTE` を占有している**
- `github_one_sentence_per_line.md` （1文ごとに改行）: あちらは**文の表記**、本ルールは**記号の使い方**
- `write_invariant_why_in_code.md` （不変の WHY だけコードに残す）: **移ろう文脈の行き先が `[fyi]`**。本ルールがその書式を定める
- `report_formatting.md` （報告に貼る識別子の書式）: **`path:line` の扱いが逆になる**。会話ではクリックできるので使い、GitHub では差分が動くので使わない
