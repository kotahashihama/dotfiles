# GitHub では、伝わる形を選んで書く

PR 本文・コメント・レビュー返信では、**散文で書くと長くなるものを別の形へ畳んで**ください。GitHub が解釈する記法は、どれも**読む負担を下げるため**にあります。
これは全プロジェクト共通の規約です。

**増やすためではなく、減らすために使う。** 飾りとして足すと、本当に見てほしいものが埋もれます。

## 手段の選び方

| 手段 | 使う場面 | 詳細 |
| --- | --- | --- |
| **表** | 同じ観点の項目が3件以上 | `concise_first_then_detail.md` |
| **Mermaid** | 列挙から読み取れない構造・関係・流れ | 同上 |
| **Alert** | **読み飛ばすと事故る1〜2点** | 下記 |
| **`<details>`** | **その場で開ける形で長い実体を置く** | 下記 |
| **脚注** | **本筋から外れる1行の補足** | 下記 |
| **パーマリンク** | **コードの特定の行を指す** | 下記 |
| **別コメント** | 本文と独立に参照される情報のかたまり | `/create-pr` / `/update-pr-description` |

## 投稿先で変わるのは量、判断軸は同じ

**本文だけの話ではありません。** 補足コメントもレビュー返信も、散文だと長くなるなら畳む。

| 投稿先 | 効きやすい手段 | 注意 |
| --- | --- | --- |
| PR 本文 | 全部 | Alert は1〜2個 |
| **補足コメント** | **`<details>`**・表・パーマリンク | 長い実体を置く場所なので `<details>` が最も効く |
| **レビュー返信（非対応の理由）** | **表**・Mermaid・パーマリンク | 観点が3つ（指摘 / 現状 / 判断）並ぶなら表 |
| **ハッシュだけの返信** | **何も足さない** | 1行目からハッシュを機械抽出できる形を壊さない |
| コマンドコメント | **何も足さない** | 本文がコマンド1行でないと起動しない |

**返信でこそパーマリンクが効きます。** 「その行は今こうなっている」を示すのに `path:line` を書くと、**相手が開いたときには差分が動いていることがあります**。

**Alert の1〜2個は本文の話。** コメントや返信は短いので、**そもそも1個で足ります**。返信に2個並ぶなら、それは返信ではなく別コメントか本文の役目です。

**短さは免罪符になりません。** 返信3行に表を付けるのは過剰で、散文のままが正解です。

## アノテーションで、相手に求めることを示す

レビューで使う `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` は、**受け取った側が何をすべきか**を1行目で示す記号です。

| 記号 | 相手に求めること |
| --- | --- |
| `[must]` | 直してほしい |
| `[imo]` | 検討してほしい |
| `[nits]` | 気が向けば直してほしい |
| `[ask]` | 答えてほしい |
| **`[fyi]`** | **読むだけでよい** |

**自分の PR へ補足を置くときは `[fyi]`。** 調査の結果・移行の事情・判断の根拠は、**対応も返信も求めていない**ので `[fyi]` が合います。

```
[fyi]
<本文>
```

**1行目に置き、次の行から本文を書く**（間に空行は入れない）。

**`[memo]` は使わない。** メモは**自分のために残すもの**で、GitHub に書くものは**読む人のためにあります**。
自分用の記録はメモリや手元のノートへ置く。

## Alert は3種だけ使う

GitHub には5種ありますが、**使うのは3種**に絞ります。選択肢が多いと毎回迷い、迷った末に強い方を選びがちになります。

| 種類 | 使う場面 |
| --- | --- |
| `NOTE` | **生成者表示に占有されている**（ `github_note_generated_by_claude.md` ）。他の用途に使わない |
| `IMPORTANT` | **知らないと動かせない・順序を誤ると壊れる**（マージ順、DB の再生成、前提の設定） |
| `WARNING` | **既存の挙動が壊れうる**（この経路だけ並行更新に弱い、この条件で値が落ちる） |

`TIP` は PR に書く場面が無く、`CAUTION` は `WARNING` と役割が重なるので使いません。

**本文には1〜2個。生成者表示の `NOTE` は数えません。** GitHub 自身が「1記事あたり1〜2個」としており、生成者表示は**末尾の固定節よりさらに後ろ**にあるので、本文の Alert と注意を奪い合っていません。**連続して置かない**のは GitHub の指示どおり守ります。

**順序を逆にしないでください。** 先に**「読み飛ばすと事故るか」で選び**、その結果が2個を超えたときに畳み方を見直す。**上限から逆算して落とすと、大事なほうが散文へ戻ります**。実際に「手元で DB を初期化しないとテストが落ちる」と「この経路はロックを取るので後から来た更新が待つ」の2点が競合し、後者を落とす判断をして戻した例があります。

**3つ目の候補が出たら、それを信号として扱う。** たいてい次のどちらかです。

- **3つ目は警告ではなく説明**（読み飛ばしても事故らない）
- **本文が構造化できていない**。同じ主題の危険が分かれているなら1つに束ねるか、表に畳む

**Alert は他の要素の中へネストできません。** 表のセル・箇条書きの中には置けないので、置くなら独立した位置に。

## `<details>` と別コメントを使い分ける

どちらも「本文を汚さずに詳細を置く」手段なので、**基準を持たないと毎回迷います**。

| | `<details>` | 別コメント |
| --- | --- | --- |
| 置く場所 | **その情報が要る節の直下** | 本文の外 |
| 読み手 | **その節を読んでいる人が、その場で開く** | 必要になった人が探して開く |
| 例 | テスト出力の抜粋、失敗したときのログ、SQL の全文 | API 契約の全文、調査ログ、他リポジトリ向けの申し送り |

**`<summary>` には中身が分かる名前を付ける。** 「詳細」では開くまで判断できません。

**畳んだ中身にも本文と同じ基準を当てる。** 畳めば何を書いてもよいことにはなりません。

## コードの行を指すときはパーマリンクを使う

`path:line` は**行がずれた瞬間に別の行を指します**。レビュー中は差分が動くので、書いた側が正しくても読む側には違う行が見えます。

**パーマリンクはコミットに固定されるので腐りません。** GitHub 上でファイルを開き、行番号をクリックして `y` を押すと、コミットハッシュを含む URL になります。

```
https://github.com/OWNER/REPO/blob/<commit>/path/to/file.go#L42-L48
```

同一リポジトリのパーマリンクは、**GitHub がコード片として展開して表示します**。引用を貼らずに済むので、その場で読める。

`path:line` を書いてよいのは、**差分の中で位置が自明なとき**（インラインコメントの中で同じファイルを指す等）だけ。

## 自動クローズのキーワードを書かない

`Closes #123` / `Fixes #123` / `Resolves #123` は、**マージした瞬間に対象を閉じます**。

**閉じる時機は自分で決める。** 依存する変更が別 PR に残っている、リリースまで開けておきたい、複数 PR で1つの課題を分けている。いずれも**マージ＝完了ではありません**。

参照するだけなら `#123` と書けば足ります（ `github_cross_repo_reference.md` ）。リンクは張られ、閉じません。

## 脚注は着地位置に注意する

**GitHub は脚注を描画結果の末尾へ集めます。** PR 本文では**生成者表示より後ろ**に出るので、テンプレの節構成とは無関係の位置に着地します。

そのため、**節の中で読まれる必要がある補足には使わない**。使うのは、読み飛ばしても本筋が通る1行だけです。

括弧書きで済むなら括弧書きにする。**脚注は読み手に往復させる**ので、1行の補足に見合わないことが多い。

## 禁止する挙動

- **`Closes` / `Fixes` / `Resolves` を書くこと**。マージした瞬間に対象が閉じる。閉じる時機は自分で決める
- **本文に Alert を3つ以上置くこと**。GitHub 自身が1〜2個に制限している（生成者表示の `NOTE` は数えない）
- **ハッシュだけの返信に何かを足すこと**。1行目からハッシュを機械抽出できる形を壊す
- **上限から逆算して落とすこと**。先に「読み飛ばすと事故るか」で選ぶ。**数を守って大事なほうを散文へ戻すのは逆**
- **Alert を表のセルや箇条書きの中へ入れること**。ネストできず、記法として壊れる
- **`<summary>` を「詳細」で済ませること**。開くまで中身が判断できない
- **GitHub のコメントへ `[memo]` と書くこと**。メモは自分用で、**読む人のために書くなら `[fyi]`**
- **差分が動く箇所を `path:line` で指すこと**。行がずれると別の行を指す

## なぜ

- **レビュアーは差分を読むために来ており、本文を読むのは前段**。前段が長いほど、本題に入るまでの負担が増える
- 記法はどれも**読む順序を作る**もの。Alert は「先に読め」、`<details>` は「後で読め」、脚注は「読まなくてよい」を意味する。**意味と合わない使い方をすると、読み手の判断を狂わせる**
- 強調は**相対的**にしか働かない。全部を強調すると、何も強調していないのと同じになる

## 例外

- ユーザーが形式を指定した場合
- **コマンドコメント**は本文をコマンド1行に保つ（ `github_command_comments.md` ）

## 関連

- `concise_first_then_detail.md` （簡潔に）: **表と Mermaid の使い分けはあちら**。本ルールは GitHub でしか使えない手段を足す
- `github_note_generated_by_claude.md` （生成者表示）: **`NOTE` を占有している**。他の Alert と混ざらないよう、用途を分ける
- `github_cross_repo_reference.md` （他リポジトリの参照）: **`#123` は参照するだけで閉じない**。閉じるキーワードを避ける根拠はあちらと対で読む
- `github_one_sentence_per_line.md` （1文ごとに改行）: あちらは**文の表記**、本ルールは**構造の選び方**
- `write_invariant_why_in_code.md` （不変の WHY だけコードに残す）: **移ろう文脈の行き先が `[fyi]`**。本ルールがその書式を定める
- `report_formatting.md` （報告に貼る識別子の書式）: **`path:line` の扱いが逆になる**。会話ではクリックできるので使い、GitHub では差分が動くので使わない
- `/create-pr` / `/update-pr-description` / `/review-pr` / `/resolve-ai-reviews` / `/resolve-human-reviews`: 本ルールが土台で、各スキルは投稿先固有の事情を上乗せする
