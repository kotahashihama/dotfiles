# 説明は、読み手が観測できるものから始める

会話・PR 説明・PR のコメント・レビュー返信・報告のいずれでも、**読み手が自分で像を結べる形**から書き始めてください。
これは全プロジェクト共通の規約です。

**結論を先に置いても伝わらないことがあります。** 結論が抽象語でできていると、読み手はまず言葉の意味を組み立てることになる。順序は正しいのに読めない、という形で失敗します。

## 3つの手がかり

| 手がかり | やること | 効き方 |
| --- | --- | --- |
| 観測できるものから始める | 画面の見え方・エラー文・失敗した操作を先に置く | 読み手が自分の経験と結びつけられる |
| 誰が何を決めるかを先に置く | 登場人物が2つ以上あるなら役割を明示する | 「なぜ食い違うのか」が説明不要になる |
| 抽象語を実例に接地する | 型名・状態名には実際の値を1つ添える | 定義文より速い |

**実例は1つで足ります。** 「担当者が `山田 太郎 → 佐藤 花子` 」の1行があれば、その項目が何を持つかの説明は要りません。

## 通常と問題は、同じ形式で並べる

差を散文で述べると、読み手が両方を頭の中で組み立てて引き算することになります。**同じ列に並べれば、差だけが目に入る。**

| 状況 | 画面に出るもの |
| --- | --- |
| 通常 | 山田 太郎 → 佐藤 花子 |
| 食い違い | (未設定) → (未設定) |

## 前後を比べるなら、軸は時期ではなく事象で書く

**「7月」「いま」と書くと、読み手は7月に何があったかを別に知っている必要があります。** 比較の軸が文の外にあるためです。

```
❌ 7月は65.6万レコードが3分29秒で通っていたのに、いまは47.5万レコードが落ちる
✅ 実装前は65.6万レコードが3分29秒でインポート処理されていたのに対し、
   実装後は47.5万レコードのインポートでジョブが落ちる状態になった
```

| 書かない | 書く |
| --- | --- |
| 7月 / 先週 / 前回 | 実装前 / 導入前 / 移行前 |
| いま / 現在 | 実装後 / 導入後 |

日付が要るなら、事象と併記する（「実装前（2026-07）」）。日付だけにしない。

## 語を読んで、指すものが1つに決まるか

書き手は指す先を知っているので、決まらないことに気づけません。実装した直後は、どれが初出かも分かりません。

| 決まらない語 | 例 | 直し方 |
| --- | --- | --- |
| 動詞 | 通る / 落ちる / 飛ぶ / 切り替わる | 何がどうなるかまで書く（「切り替わる」→「星の表示が切り替わる」） |
| 名前 | 初めて出す画面・hook・状態の呼び名 | それが何かを1行添える（「削除の確認ダイアログ」→「星を押すと出る削除の確認ダイアログ」） |
| 内部の呼び名 | 行 / レコード / 図のノードID / スタックの位置 | 画面に出るもので書く（「行」→「項目のカード」） |
| 参照 | 同じく / 同様に / 上記 / この / その / あちら / 両方 | 直前に指す先が無ければ書く。あるなら残してよい |

**判定は「その1行だけを読んだ人が、指すものを決められるか」。**

**表のセルと見出しで最も落ちます。** 短く書こうとして主語・対象・参照先が消えるためです。セルは独立して読まれるので、隣のセルを指せません。

節の冒頭も同じ理由で落ちます。概要では直前に対象が出ているので決まりますが、節をまたぐと参照先が消えます。「両方の経路を実測しました」を節の1行目に置いて、何と何かが決まらなかった例があります。

語を狩らないでください。`この` と `その` は日本語で最も使う指示語で、直前に指す先があれば残してよい。問われているのは唐突さで、語そのものではありません。

```
❌ | 保存・解除 | 一覧と詳細の星は切り替わる | 同じく切り替わる |
✅ | 保存・解除 | 一覧と詳細の星の表示は切り替わる | 一覧と詳細の星の表示が切り替わる |
```

後の節で説明しても届きません。読み手は詰まった位置で読むのをやめます。

表の例は一覧ではありません。同じ形は次々に出てきます（「走る」「回る」「叩く」「撃つ」）。語で覚えると、一覧に無いものを構造的に見逃します。

業界で通っている言い方は残します（ `plain_language_explanation.md` ）。「テストが落ちる」「lint が通る」は、その現場で1つに決まる語です。

対象が直前にあれば省いてよい。表の列や、同じ文で対象を出した後は繰り返さない。

## 症状を書いたら、それが起きる条件まで書く

書き手は経路を知っているので範囲を書かなくても文が成立します。読み手は自分のケースに当てはまるか判断できません。

```
❌ 追加した直後に外しても件数が減らない
✅ 保存した直後に外すと件数が減らない（一括でも単一でも起きる）
```

**判定は「読み手が自分のケースに当てはまるか、本文だけで決められるか」。** 決められないなら条件が抜けています。

| 抜けやすい条件 | 例 |
| --- | --- |
| 操作の経路 | 一括か単一か、どの画面から入ったか |
| 直前の状態 | 詳細を開いた後かどうか、初回かどうか |
| 対象の種類 | 既定の項目だけか、追加した項目も含むか |

条件が2通り以上あるなら表にする。1行で書こうとすると必ずどちらかが不正確になります。

「起きる」と書いたなら起きない条件も確かめる。全部で起きるのか一部だけなのかは書き手にも実測しないと分かりません。

## 課題票に紐づくなら、課題票の記述から繋ぐ

課題票は報告者の言葉で書かれています。**課題票の言葉から入り、課題 → 原因 → 直し方 → 原因が取り除かれる理由の筋で、マージすると直ることを示す。** 付随した変更は筋と分け、受入基準に要る変更がどれかも示す。対象は PR 本文に限らず、課題へのコメントや完了報告も同じです。

PR 本文での組み立て方（流れの各段・記述ごとの対応表・付随した変更の書き分け）は `/update-pr-description` の `references/body.md` が持ちます。

## 複数の PR に分けたなら、どこから入っても全体へ着けるようにする

**判定は「どの1本を開いた読み手も、全体へ着けるか」。** 隣の PR としか繋がっていないと、2本先が見えません。マージ順は「どれを先に入れるか」で、全体像（なぜこの本数なのか）とは別です。置き方は `/update-pr-description` の `references/multi-pr.md` が持ちます。

## 禁止する挙動

- 内部の呼び名から書き始めること。型名・関数名・フラグ名は、読み手の観測と結びついていない
- **その1行だけでは指すものが決まらない語を置くこと**。動詞（通る・切り替わる）・初出の名前・内部の呼び名（行・ノードID）・参照（同じく）の4つ。表のセルと見出しで最も落ちる
- 抽象語のまま最後まで説明すること。実例が1つあれば足りる
- 前後の比較を時期で書くこと。「7月 / いま」は、読み手が7月に何があったかを知っている前提になる
- 登場人物の役割を省くこと。「A と B が食い違う」は、A と B を誰が決めるかを知らないと理解できない
- 症状を書いて、それが起きる条件を書かないこと。読み手は自分のケースに当てはまるか判断できない
- 差を散文で述べること。並べれば済む
- **課題票に紐づく変更を、直したことだけで説明すること**。冒頭は課題 → 原因 → 直し方 → 原因が取り除かれる理由の筋でマージすると直ることを示し、記述ごとの対応は補足に置く
- 原因と直し方を並べて、なぜ症状が消えるかを書かないこと。書き手には因果が見えているので、並べただけで繋がったつもりになる
- 原因を処理の説明だけで書き、報告の言葉との対応を流れに入れないこと。報告者の操作から順に、どこで何が出て、それが課題票のどの記述かを示す
- 課題の解決に要る変更と、付随した変更を同じ重みで並べること。どれが課題を直すのか読めない。付随した変更は筋の後ろに分け、解決する状態を添える
- 複数の変更が要る課題を、単体の限界の断りから書き始めること。「この2本で直る」を先に言う
- 複数の PR に分けたまま、どの1本からも全体へ着けない状態にすること。隣としか繋がっていないと、2本先が見えない
- 「結論は先に書いた」で済ませること。抽象的な結論は、先に置いても像を結ばない

## なぜ

- **結論ファーストは順序の規約で、何を手がかりに書くかは別の軸。** 順序を守っても、結論が抽象語なら読み手は2度読むことになる
- 書き手は実装した直後で、内部の呼び名が身についている。その語彙は読み手と共有されていない
- 具体例は短い。定義を積むより、実例1つのほうが速くて正確

## 例外

- 読み手が同じ実装を触っている場面（相手セッションへの連絡など）では、内部の呼び名で通じることがある
- ユーザーが「結論だけ」「手短に」と求めた場合

## 関連

- `concise_first_then_detail.md` （簡潔に）: あちらは量と順序、本ルールは何を手がかりに書くか。**結論を先に置いても、抽象なら伝わらない**
- `plain_language_explanation.md` （噛み砕いた説明）: あちらは用語の粒度（どこまで開くか）、本ルールは構成（何から書くか）
- `focus_insights_on_judgment.md` （洞察は判断材料に絞る）: あちらは何を選ぶか、本ルールは選んだものをどう書くか
- `no_ai_style_writing.md` （AI が書いたと分かる文章を出さない）: 「量を出さない」の節とは具体性の面で重なる。本ルールは構成、あちらは1文ごとの判定。文体の節は名詞で積まず動詞へ開き、本ルールは開いた動詞を具体にする。向きは同じで段が違う
- `base_records_on_measurements.md` （記録は実測に基づける）: どちらも「条件を書く」を求めるが対象が違う。あちらは測った数字につく条件（オプション・キャッシュ・版）、本ルールは症状が起きる条件（一括か単一か）
- `code_comments.md` （コメントは WHY に熱量を）: 本ルールの対象はコードコメントを含まない。「指すものが1つに決まるか」をコードコメントへ当てるのはあちら
- `verify_before_asserting.md` （断定の前に裏を取る）: どちらも課題票の記述を扱うが向きが違う。あちらは記述を鵜呑みにしない（裏取り）、本ルールは記述と修正を繋ぐ（説明）
- `/create-pr` / `/update-pr-description`: PR での具体化。本ルールが土台。課題の一覧表の形（列名・置く PR）はあちら
- `karma_commit_style.md` （PR に番号を付けるか）: 受入基準に入らない変更の扱いが近い。あちらは PR 単位（閉じる条件に入らない別件）、本ルールは1本の本文の中での書き分け
- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: あちらはそもそも入れるかどうか、本ルールは入れると決めた付随の変更をどう書くか
