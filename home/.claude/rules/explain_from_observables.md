# 説明は、読み手が観測できるものから始める

会話・PR 説明・コメント・レビュー返信・報告のいずれでも、**読み手が自分で像を結べる形**から書き始めてください。
これは全プロジェクト共通の規約です。

**結論を先に置いても伝わらないことがあります。** 結論が抽象語でできていると、読み手はまず言葉の意味を組み立てることになる。順序は正しいのに読めない、という形で失敗します。

## 3つの手がかり

| 手がかり | やること | 効き方 |
| --- | --- | --- |
| **観測できるものから始める** | 画面の見え方・エラー文・失敗した操作を先に置く | 読み手が自分の経験と結びつけられる |
| **誰が何を決めるかを先に置く** | 登場人物が2つ以上あるなら役割を明示する | **「なぜ食い違うのか」が説明不要になる** |
| **抽象語を実例に接地する** | 型名・状態名には実際の値を1つ添える | 定義文より速い |

**実例は1つで足ります。** 「担当者が `山田 太郎 → 佐藤 花子` 」の1行があれば、その項目が何を持つかの説明は要りません。

## 通常と問題は、同じ形式で並べる

差を散文で述べると、読み手が両方を頭の中で組み立てて引き算することになります。**同じ列に並べれば、差だけが目に入る。**

| 状況 | 画面に出るもの |
| --- | --- |
| 通常 | 山田 太郎 → 佐藤 花子 |
| **食い違い** | **(未設定) → (未設定)** |

## 前後を比べるなら、軸は時期ではなく事象で書く

**「7月」「いま」と書くと、読み手は7月に何があったかを別に知っている必要があります。** 比較の軸が文の外にあるためです。

```
❌ 7月は65.6万レコードが3分29秒で通っていたのに、いまは47.5万レコードが落ちる
✅ 実装前は65.6万レコードが3分29秒でインポート処理されていたのに対し、
   実装後は47.5万レコードのインポートでジョブが落ちる状態になった
```

| 書かない | 書く |
| --- | --- |
| 7月 / 先週 / 前回 | **実装前 / 導入前 / 移行前** |
| いま / 現在 | **実装後 / 導入後** |

**日付が要るなら、事象と併記する**（「実装前（2026-07）」）。日付だけにしない。

## 状態を表す語は、1つに決まるところまで開く

**判定は「その語を読んで、何が起きたか1つに決まるか」。** 決まらないなら開きます。

| 書かない | 書く |
| --- | --- |
| 通る | **インポート処理される** |
| 落ちる | **ジョブが落ちる** |
| 動く / 効く | 何がどう動くか |

**表の3行は例で、判定の一覧ではありません。** 同じ形は次々に出てきます（「飛ぶ」「走る」「回る」「叩く」）。**語で覚えると、一覧に無いものを構造的に見逃します**。

**主語があっても決まらないことがあります。** 「削除が飛ぶ」は主語（削除）を持っていますが**何の削除かは決まりません**。「グループから項目を外す API が呼ばれる」まで書くと決まります。

**日本語は主語を落とせるので、落としたことに書き手が気づきません。** ただし主語を補うのは最低限で、**そこから1つに決まるかまで見る**。

**対象が直前にあれば省いてよい。** 表の列や、同じ文で対象を出した後は繰り返さない。

**業界で通っている言い方は残します**（ `plain_language_explanation.md` ）。「テストが落ちる」「lint が通る」は、その現場で1つに決まる語です。

## 初めて出す名前には、それが何かを添える

**書き手は全部を既知として書きます。** 実装した直後は、どれが初出かも分からなくなっています。

| 落ちやすい名前 | 添えること |
| --- | --- |
| **画面・ダイアログ** | **いつ出るか**（「星を押すと出る、グループから外す確認」） |
| **hook・関数・状態** | **何をするか**（「保存の成否を受けて表示中の画面を取り直す hook」） |
| **図のノードID・スタックの位置** | **そもそも使わない。** 描画されるラベルと PR 番号で指す |

**添えるのは1行。** 定義を書くのではなく、**その名前が指すものを読み手が思い浮かべられる**ところまで。

**後の節で説明しても届きません。** 読み手は初出の位置で詰まり、そこで読むのをやめます。

**見出しと表のセルで最も落ちます。** 短く書こうとして説明が消えるためです。「削除の確認ダイアログは、今のところどこからも開きません」は初出でそれが何か決まらず、「星を押すと出る削除の確認ダイアログは、今のところどこからも開きません」なら決まります。

**主語が落ちているだけなら、この節の対象ではありません**（「状態を表す語は、1つに決まるところまで開く」）。**名前は出したが、それが何かを言っていない**のがこちらです。

**判定は「この行だけを読んだ人が、その名前の指すものを決められるか」。**

## 症状を書いたら、それが起きる条件まで書く

**書き手は経路を知っているので範囲を書かなくても文が成立します。** 読み手は自分のケースに当てはまるか判断できません。

```
❌ 追加した直後に外しても件数が減らない
✅ 保存した直後に外すと件数が減らない（一括でも単一でも起きる）
```

**判定は「読み手が自分のケースに当てはまるか、本文だけで決められるか」。** 決められないなら条件が抜けています。

| 抜けやすい条件 | 例 |
| --- | --- |
| **操作の経路** | 一括か単一か、どの画面から入ったか |
| **直前の状態** | 詳細を開いた後かどうか、初回かどうか |
| **対象の種類** | 既定の項目だけか、追加した項目も含むか |

**条件が2通り以上あるなら表にする。** 1行で書こうとすると**必ずどちらかが不正確になります**。

**「起きる」と書いたなら起きない条件も確かめる。** 全部で起きるのか一部だけなのかは**書き手にも実測しないと分かりません**。

## 禁止する挙動

- **内部の呼び名から書き始めること**。型名・関数名・フラグ名は、読み手の観測と結びついていない
- **抽象語のまま最後まで説明すること**。実例が1つあれば足りる
- **前後の比較を時期で書くこと**。「7月 / いま」は、読み手が7月に何があったかを知っている前提になる
- **初めて出す名前を、説明なしで置くこと**。書き手には全部が既知なので、**初出かどうかも見えていない**
- **図のノードIDやスタックの位置で指すこと**。どちらも書き手にしか見えない座標で、読み手の画面には出ない
- **状態を表す語を、1つに決まらないまま置くこと**。「通る」「落ちる」「飛ぶ」はどれも、何がどうなったかを書くまで決まらない
- **登場人物の役割を省くこと**。「A と B が食い違う」は、**A と B を誰が決めるかを知らないと理解できない**
- **症状を書いて、それが起きる条件を書かないこと**。読み手は自分のケースに当てはまるか判断できない
- **差を散文で述べること**。並べれば済む
- **「結論は先に書いた」で済ませること**。抽象的な結論は、先に置いても像を結ばない

## なぜ

- **結論ファーストは順序の規約で、何を手がかりに書くかは別の軸。** 順序を守っても、結論が抽象語なら読み手は2度読むことになる
- 書き手は実装した直後で、**内部の呼び名が身についている**。その語彙は読み手と共有されていない
- 具体例は短い。**定義を積むより、実例1つのほうが速くて正確**

## 例外

- 読み手が同じ実装を触っている場面（相手セッションへの連絡など）では、内部の呼び名で通じることがある
- ユーザーが「結論だけ」「手短に」と求めた場合

## 関連

- `concise_first_then_detail.md` （簡潔に）: あちらは**量と順序**、本ルールは**何を手がかりに書くか**。**結論を先に置いても、抽象なら伝わらない**
- `plain_language_explanation.md` （噛み砕いた説明）: あちらは**用語の粒度**（どこまで開くか）、本ルールは**構成**（何から書くか）
- `focus_insights_on_judgment.md` （洞察は判断材料に絞る）: あちらは**何を選ぶか**、本ルールは**選んだものをどう書くか**
- `no_ai_slop.md` （量を出さない）: **具体性**の面で重なる。本ルールは構成、あちらは1文ごとの判定
- `no_ai_style_writing.md` （AI が書いたと分かる文体で書かない）: あちらは**名詞で積まず動詞へ開く**、本ルールは**開いた動詞を具体にする**。向きは同じで段が違う
- `base_records_on_measurements.md` （記録は実測に基づける）: **どちらも「条件を書く」を求めるが対象が違う**。あちらは**測った数字**につく条件（オプション・キャッシュ・版）、本ルールは**症状**が起きる条件（一括か単一か）
- `/create-pr` / `/update-pr-description`: PR での具体化。本ルールが土台
