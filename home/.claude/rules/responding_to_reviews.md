# レビューコメントへの対応

PR に付いたレビューコメントを共有されたとき、どう咀嚼し、何を返し、何をしないかをまとめています。
これは全プロジェクト共通の規約です。

## レビューコメントが共有されたら、まず意図を噛み砕き、対応するかどうかをユーザーに尋ねる

ユーザーから「〜にコメントがついた」「〜というレビューが来た」等の形で
**PR/コードレビューコメント（人間・bot 問わず）が共有された場合**、
すぐに修正実装に走らず、以下の手順を踏んでください。


### 期待する挙動

1. 意図の咀嚼: レビュアーが何を問題視しているか、どういう改善を提案しているかを
   簡潔かつ噛み砕いた表現で説明する
2. 現状コードの確認: 必要なら該当箇所を読み、指摘が現状のコードにどう当てはまるかを対応させて示す
3. 具体的な変更案の提示: 対応する場合にどう変更するかの具体案を必ず提示する。
   自然な選択肢が複数ある場合は候補を複数並べて比較できる形で出す
   (例: 案 A シンプル削除 / 案 B 実態に沿った書き換え / 案 C 別関数へ切り出し 等)
4. 影響の整理: 変更範囲 (ファイル数・行数の概算)・トレードオフ・リスクを短くまとめる
5. **対応の推奨判断を添える**: 「対応した方が良い/しない方が良い/どちらでもよい」の
   おすすめを、根拠と一緒に一言で示す (例: 「規約違反なので対応推奨」「見送りでよい理由: …」)。
   複数案の場合はどの案を推すかも併記する
6. ユーザーに対応可否を尋ねる: 「対応しますか？」「案 A/B どちらにしますか？」等の
   形で明示的にジャッジを仰ぐ
7. 追加質問への応答: ユーザーから追加質問があれば答える。この段階で複数往復してよい
8. **明示的な GO を得てから実装着手**: ユーザーが「対応して」「GO」「進めて」等の承認を出すまで、
   コード編集や設定変更は始めない

### 禁止する挙動

- コメントが共有された直後にいきなり `Edit` / `Write` に飛ぶ
- 「実装します」「対応します」と宣言してユーザーの返答を待たずに走る
- 意図の説明をスキップして「では〜を消せば OK ですね」と結論だけで実装に入る
- 「明らかに正論だから対応する」と自己判断で進める（レビュアーが正論でもユーザーが別方針を選ぶ余地はある）
- 対応後にサマリだけ添える形（事後承諾のパターン）
- **変更案を提示せずに「対応しますか？」だけ聞く**（ユーザーがどう変わるかを想像しないと判断できない状態にしない）
- **対応の推奨判断を添えずに「どうしますか？」と丸投げする**（判断コストをユーザーに全部押し付けない）

### 例外

- ユーザーが「このコメントに対応して」「〜を修正して」等、明示的に対応指示付きで共有した場合
  はそのまま実装してよい (意図確認の段は不要)。以降の手順は、人間のコメントなら
  `/resolve-human-reviews`、bot なら `/resolve-ai-reviews` が担う
- `/resolve-ai-reviews` / `/resolve-human-reviews` スキル実行中は、そのスキルの手順
  (文脈照合と、判断に迷う場合のユーザー確認) に従う。本ルールと矛盾しない
- ユーザーが「即対応 OK」「毎回聞かなくていい」等、判断委譲を明示した会話の中では、
  それ以降そのセッション内は自律対応してよい

### なぜ

- レビュアーの指摘が「正論に見える」からといって、そのプロジェクト・その PR の文脈で
  正しいとは限らない（過去の合意事項・スコープ・トレードオフで見送る判断はよくある）
- 対応可否・対応方針の最終判断はユーザーの領分。エージェントが先読みして走ると、
  「やってほしくなかった」「別の方向で直したかった」が事後に発覚してリカバリコストが増える
- 意図を先に噛み砕いて共有することで、ユーザーが判断する材料が揃い、その場で
  対応/非対応/別方針のいずれもスムーズに選べる
- レビュアーが人間の場合、対応方針そのものが人間同士のコミュニケーション事項

**回答の雛形は `~/.claude/references/responding_to_reviews.md` の最初の節にある。** 指摘を噛み砕いて尋ねるときに開く。

## 人間のレビューコメントへは勝手に返信しない

PR に付いた人間のレビュアーによるレビューコメントに対しては、こちらから勝手に返信を書き込まないでください。Resolve conversation も同じく、指示されたときだけ行います（下記）。

### 対象

- 人間のユーザーが投稿した PR レビューコメント（インライン・レビュー本文・PR コメント欄いずれも）
- 種別を問わず、`[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` 全てが対象

### 例外（自動返信してよいのはこの範囲のみ）

- AI レビュワー（ `github-actions[bot]` 等の bot アカウント）からのレビューコメント。
  - `/resolve-ai-reviews` スキルで扱う対象がこれに該当する。
- ユーザーが明示的に「このコメントに〇〇と返信して」「返信しておいて」等と指示した場合。
- `/resolve-human-reviews` の起動時に、マージまで指示された場合（「〜を `/resolve-human-reviews` したらマージしといて」）。マージすると PR が閉じ、指摘したレビュアーには対応内容が届かないまま終わるので、返信を投稿してからマージする。Resolve は含まない。

### 禁止する挙動

- 報告の末尾で返信の話題を持ち出すこと。「返信の投稿の判断だけ残っています」「明示指示をお待ちします」はいずれもこれに当たる。修正の報告はハッシュと対応表だけで閉じる
- **返信要否をユーザーへ確認すること**。尋ねること自体が判断領域への侵入になる（下記「返信要否をユーザーに確認しない」）
- 返信していないコメントへリアクションを付けること。リアクションも発信で、返信と同じ許可が要る
- **Resolve conversation すること**。閉じるのは指摘した本人の役目で、返信の許可では代替されない

### 期待する挙動

- 人間のレビューコメントに対しては、コード修正のみをこちらで行い、返信は書かない。
  - 修正した内容とコミットハッシュをユーザーに口頭で報告するに留める。
- 返信するかどうか・返信文言はユーザーが判断する領分。エージェントが勝手に決めない。
- `/resolve-ai-reviews` や類似スキルを起動する際も、対象を bot コメントに限定し、人間コメントには手を出さない（対象コメント抽出時に `user.type == "Bot"` 等でフィルタする）。

### なぜ

- 人間のレビュアーへの返信は、書き方・温度感・タイミングを含めて当事者間のコミュニケーションであり、エージェントが代理で書くとニュアンスがズレる／礼を欠く／議論の流れを壊す等の事故が起きる。
- AI レビュワーへの返信は「コミットハッシュを返して閉じる」等の機械的な運用で完結するため、自動化して問題ない。この2つは扱いを明確に分ける。

### 起動経路による制限（デフォルト "返信しない"）

`/resolve-ai-reviews` スキル起動時のみ、GitHub 上での bot コメントへのコミットハッシュ／理由返信を許可する。

`/resolve-human-reviews` の起動時にマージまで指示された場合も、返信を許可する（上記「例外」）。

それ以外の経路（ユーザーが「このコメントに対応して」「レビューを直しといて」等と自然文で依頼した場合を含む）では、投稿元が bot / 人間のいずれであっても、GitHub 上でのレビュー返信は行わない。

- コード修正のみをコミット & プッシュする
- コミットハッシュはユーザーに口頭（会話）で報告する
- ユーザーが必要と判断すれば、自身で GitHub 上へ返信する

これにより「文脈からの誤認で bot 扱いして人間コメントに返信してしまう」事故を、bot 判定の機械化に加え起動経路の側面からも防ぐ。

### 返信要否をユーザーに確認しない

自然文経路でレビュー対応を依頼された場合、以下を守る。

- ユーザーに「返信しますか？」「レビュアーが人間か bot かで扱いが変わるので教えてください」等の返信要否確認をしない。
- 修正・push 完了は口頭でハッシュ報告するのみにとどめ、返信の話題自体を持ち出さない。
- 返信が必要なら、ユーザーが「返信しておいて」「このコメントに〇〇と返して」等と明示指示を出す（これが「例外指示」節にあたる）。

理由: 「返信するかどうかはユーザーが判断する領分」であり、こちらから確認を投げること自体が判断領域への侵入。ユーザーは必要なら明示指示を出すので、こちらは受け身に徹する。

### Resolve conversation はこちらの役目ではない

**人間のレビューコメントのスレッドはコメントを付けたレビュアー自身が閉じます。** こちらは既定で Resolve しません。許可が要る作業なのではなく、そもそも相手の役目です。

返信を代行してよいと言われても、Resolve までは含まれません。

| 得た指示 | できること |
| --- | --- |
| 「レビューに対応して」 | コード修正のみ |
| 「返信していい」「〇〇と返しておいて」 | 返信まで。Resolve は含まない |
| 「Resolve していい」「閉じておいて」 | Resolve（例外。指示された分だけ） |

bot コメントとは扱いが違います。`/resolve-ai-reviews` は返信と Resolve をひと続きの手順として持ちますが、人間コメントでは分かれる。同じ「レビュー対応」でも、相手が人間なら Resolve は別の許可が要ると考える。

**「対応が完了したから閉じてよい」と判断しない。** 閉じるのは指摘した本人が納得したときで、こちらが完了と思ったときではありません。Resolve するとスレッドが畳まれ、レビュアーが見落とすか、確認の機会そのものが失われます。

### 例外指示

- ユーザーが「このコメントには自分で〇〇と返しておいて」「返信もしておいて」等と明示した場合のみ返信を代行してよい。
- **`/resolve-human-reviews` を起動し、あわせてマージを指示された場合**も返信を代行してよい。返信を投稿してからマージする。
- **Resolve は、Resolve すること自体を明示されたときだけ**行う。
- `/resolve-ai-reviews` を明示起動した場合は、そのスキルの仕様に従って bot コメントに返信する（本ルールの「起動経路による制限」が優先されるのは自然文経路のみ）。
- それ以外は本ルールが常に優先する。

## 返信したレビューコメントと、レビュー提出に 👍 を付ける

レビュー指摘にコードで対応し、かつその旨を返信したとき、その指摘コメントへ `+1` （👍）のリアクションを付けてください。AI レビュー・人間レビューのどちらも同じです。

**返信していないコメントには付けません。** リアクションもレビュアーへ向けた発信なので、返信と同じ許可のもとで動かす。

**付ける対象（コードを直して返信したものだけ）・レビュー提出に付ける条件・付け方は `~/.claude/references/responding_to_reviews.md` にある。** 返信を投稿するときに開く。

## 関連

- `decide_or_ask.md` （自分で決めるか尋ねるか）: 本ルールが扱う場面の判断軸を示す
- `plain_language_explanation.md` （技術説明の噛み砕き）: 意図の咀嚼は平易な表現で
- `summarize_after_each_task.md` （各作業後のサマリ）: 対応が終わった段階で改めてサマリ
- `/explain-review-comments` （レビューコメントの解説スキル）: 本ルールが土台で、あちらは取得と横断を足す。複数件を PR から取ってきて一覧にする手順はあちらが持つ。1件あたりの型は本ルールのまま
- `treat_user_suggestions_as_proposals.md` （ユーザーの案には賛否を返す）: 本ルールは他人の指摘、あちらはユーザー自身の案が対象。推奨判断を添える点は同じ
- `/resolve-human-reviews` （人間レビューへの対応スキル）: 本ルールが規定する「返信しない」を守ったうえで、では何をするか（修正の粒度・コミットの分け方・対応表の報告）を担う。人間コメントへの対応を依頼されたらこのスキルを使う
- `keep_records_current.md` （変えたら説明も直す）: 投稿した後に前提が消えたときの直し方はあちら。本ルールは投稿してよい場面かを決める
- `report_formatting.md` （報告の書式）: 返信しない段階では、会話の対応表だけが報告手段になる
- `/resolve-ai-reviews` / `/resolve-human-reviews`: 実行手段。本ルールが土台で、スキルは対象の絞り込み方を持つ
