# 仕様が書かれていないところは、既存の倒し方に合わせて着地する

仕様書・規約・契約のどれにも書かれていない箇所に出くわしたら、**既存の実装がどちらへ倒しているかを数えて**、その形に着地してください。
これは全プロジェクト共通の規約です。

**「妥当だと思った」では検証できません。** 自分の理屈で決めると、後から誰も確かめられない判断が残ります。既存の倒し方は数えられるので、根拠として渡せます。

## まず、本当に書かれていないかを確かめる

**「仕様が無い」と感じた時点では、隣を読んでいません。** 探す先は3つあります。

| 見る先 | 例 |
| --- | --- |
| **逆向きの操作** | 作る側が決まっていれば、消す側は自由ではない |
| **同じリソースの別の操作** | 一括版と単体版、管理者向けと利用者向け |
| **旧実装の相当箇所** | 移植であれば、そこが仕様の出どころ |

実際に、ある復元処理の仕様が書かれていないと判断して実装を2度ひっくり返しました。**逆向きの削除処理には明記があり**、しかも「旧実装の相当箇所」と書かれていました。片側が決まっていたので、消す案は最初から採れませんでした。

**片側が決まっているなら、それは制約です。** 書かれていないのは残りの半分だけです。

## 尋ねる側と着地する側の境界

**「書かれていない」は、たいてい「読み方が割れる」に見えます。** ここを分けないと、`decide_or_ask.md` と正反対の指示になります。

| 決め方 | 対象 |
| --- | --- |
| **尋ねる** | 方針・粒度・公開範囲・取り消せない操作（ `decide_or_ask.md` ） |
| **擦り合わせる** | **他のリポジトリと共有する契約**（ `implement_from_contract_inward_out.md` ） |
| **着地する** | **実装の細部で、契約にも規約にも書かれていないもの** |

**判定は「その判断が外へ出るか」。** 出るなら尋ねるか擦り合わせる。内側で閉じるなら着地する。

## 3つの軸で判定する

**1つ目を既定にします。** 残り2つは、既存の倒し方が見つからないときに使います。

| 軸 | 問い | 強さ |
| --- | --- | --- |
| **既存の倒し方** | 同じ状況を扱う既存のコードは、どちらへ倒しているか。**数える** | **強い** |
| 壊れたときの代償 | 誤ったとき、どちらが安いか。黙って通すか、止めるか | 中 |
| 後から変えられるか | 外へ出る値か、内側だけの値か | 中 |

**数えるのは実装の分岐です。** 並び順・命名・コメントは書き換えられるので根拠になりません（ `verify_before_asserting.md` ）。

**同じ処理の前例が無くても、パターンの段では見つかります。** 実際に、復元処理そのものの前例は旧実装に無かったものの、**同じ値を状態遷移に追随させる形が2箇所**にありました。そこに乗せることで、独自の判断を持ち込まずに済みました。

**自分の差分を数に入れないでください。** 同じ作業ツリーでは区別が付きません（ `verify_the_check_worked.md` ）。

## 着地したら、仕様書へ書く

**書かないと、次に触る人が同じ判断をやり直します。** 判断そのものより、判断が書かれていないことが問題でした。

- 決めた形を、その API・機能の仕様書へ足す
- **どちらへ倒したかだけでなく、倒さなかった側も書く**（対象にしない値・触らない経路）
- 経緯は書かない。**成果物に指示や検討の過程を残さない**（ `no_instruction_echo_in_output.md` ）

**その文書が規約本体なら、尋ねてから足します**（ `ask_before_editing_claude_assets.md` ）。同じ `docs/` の下に、**API の振る舞いを書いた仕様書**と、**次に触る人が従う規約**が混在していることがあります。判定はあちらと同じで、「その変更を知らないまま次のセッションが始まったとき、挙動が変わって見えるか」です。

**自分が書いた節を、その判断の根拠として引かないでください。** 循環します。根拠になるのは、既存の倒し方と隣の仕様です。

## 禁止する挙動

- **隣を読まずに「仕様が無い」と判断すること**。逆向きの操作・別の操作・旧実装の相当箇所を先に見る
- **自分の理屈だけで妥当さを決めること**。既存の倒し方を数える
- **並び順・命名・コメントを根拠にすること**。書き換えられるものは根拠にならない
- **外へ出る判断を、着地で済ませること**。方針・粒度・公開範囲は尋ねる（ `decide_or_ask.md` ）
- **他のリポジトリと共有する契約を、片方で決めること**（ `implement_from_contract_inward_out.md` ）
- **着地した形を仕様書へ書かないこと**。次に同じ判断をやり直すことになる
- **自分が書いた仕様を、その判断の根拠として引くこと**。循環する

## なぜ

- 仕様が無い箇所は必ず出る。**そこで止まると進まず、独自に決めると検証できない判断が残る**
- 既存の倒し方は**数えられる**。根拠として渡せるので、レビューでも次のセッションでも同じ結論に辿り着ける
- 片側の仕様は残りの半分を縛る。**読まずに決めると、決まっていることと矛盾する形へ着地する**
- 着地した判断は、書かなければ**次に触る人には「仕様が無い」ままに見える**。同じ往復が繰り返される

## 例外

- ユーザーが方針を明示した場合はそれに従う
- 試作・検証目的で、捨てる前提のコードを書く場合

## 関連

- `decide_or_ask.md` （自分で決めるか尋ねるか）: **境界を共有する**。あちらは**外へ出る判断**、本ルールは**内側で閉じる細部**。「読み方が割れる」を理由に本ルールへ寄せない
- `implement_from_contract_inward_out.md` （契約を先に決めて内側から積む）: **リポジトリを跨ぐ値の形はあちらの担当**。本ルールの範囲は、擦り合わせる相手がいない細部
- `verify_before_asserting.md` （断定の前に裏を取る）: **根拠の格付けはあちら**。仕組み → 実測 → 並び順や命名の順で、下2つは根拠にならない
- `verify_the_check_worked.md` （検査が成立していたかを疑う）: 既存の倒し方を数えるとき、**自分の差分を含めない**
- `no_instruction_echo_in_output.md` （成果物に指示を書かない）: 着地した形は書く。**そう決めた経緯は書かない**
- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: **書き足す先が規約本体なら、あちらが先に効く**。仕様書と規約が同じ `docs/` の下に混在していることがある
- `treat_user_suggestions_as_proposals.md` （ユーザーの案には賛否を返す）: 着地した形をユーザーが別案で示したら、賛否を返してから従う
