# 仕様が書かれていないところは、既存の倒し方に合わせて着地する

仕様書・規約・契約のどれにも書かれていない箇所に出くわしたら、まず隣（逆向きの操作・同じリソースの別の操作・旧実装の相当箇所）を読み、本当に書かれていないかを確かめてください。書かれていなければ、既存の実装がどちらへ倒しているかを数えて、その形に着地します。着地した形は仕様書へ書きます。方針・粒度・公開範囲のように外へ出る判断は、着地させずに尋ねます（ `decide_or_ask.md` ）。
これは全プロジェクト共通の規約です。

**仕様の無い箇所に出くわしたら、`~/.claude/references/decide_when_spec_is_silent.md` を読む。** 尋ねる側と着地する側の境界、判定の3つの軸と数え方、テストを先に書くときに課題へ残す根拠、禁止する挙動はそちらにある。

## 関連

- `decide_or_ask.md` （自分で決めるか尋ねるか）: **境界を共有する**。あちらは外へ出る判断、本ルールは内側で閉じる細部。「読み方が割れる」を理由に本ルールへ寄せない
- `implement_from_contract_inward_out.md` （契約を先に決めて内側から積む）: リポジトリを跨ぐ値の形はあちらの担当。本ルールの範囲は、擦り合わせる相手がいない細部
- `verify_before_asserting.md` （断定の前に裏を取る）: 根拠の格付けはあちら。仕組み → 実測 → 並び順や命名の順で、下2つは根拠にならない
- `verify_the_check_worked.md` （検査が成立していたかを疑う）: 既存の倒し方を数えるとき、自分の差分を含めない
- `no_instruction_echo_in_output.md` （成果物に指示を書かない）: 着地した形は書く。そう決めた経緯は書かない
- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: 書き足す先が規約本体なら、あちらが先に効く。仕様書と規約が同じ `docs/` の下に混在していることがある
- `treat_user_suggestions_as_proposals.md` （ユーザーの案には賛否を返す）: 着地した形をユーザーが別案で示したら、賛否を返してから従う
