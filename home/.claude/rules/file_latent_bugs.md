# 潜在バグは、表出を確かめてから起票する

画面で起きることを確かめていない不具合（潜在バグ）を課題管理ツールで起票するときの手順です。起票するかどうか、件名、本文の節の分け方をまとめています。
これは全プロジェクト共通の規約です。

確かめていないことを本文の冒頭に1行で書く規定は、`base_records_on_measurements.md` の「不具合の課題は、確かめ方を本文の冒頭に書く」が持ちます。

## 件名にも印を付ける

件名の末尾にも「（潜在バグ）」を付ける。課題の一覧には件名しか出ないので、本文の冒頭だけでは開くまで分からない。件名の書式がそのチームで文書として決まっていれば、そちらに従う。

## 呼び出し先のサーバーまで辿る

**潜在バグは、呼び出し先のサーバーまで辿って表出するかを書く。** クライアントのコードだけ読むと、「失敗したら」「この値が来たら」の前提が本当に起きるかが分かりません。

| 辿ること | 例 |
| --- | --- |
| どの実装に送られるか | 旧実装から移行中なら、フラグの本番値で有効な側を決めてから読む |
| その前提をサーバーが作るか | 失敗を返す条件・その値を返す経路・入力の検査 |

**表出しえないと分かったものは起票しない。** 判定は「本番で症状が出る経路があるか」で、仕組み（サーバーがその値や失敗を返す経路・画面の入力の制約）から決めます。「本番のデータに今その値が無い」は判定に使いません（ `verify_before_asserting.md` の「いま無い」は「作られない」を意味しない）。

実際に、型付けの作業で見つけた候補4件を辿ったところ、どれも表出しえませんでした。サーバーがその項目を必ず返す、値を必ず数値で返す、欄が読み取り専用で重複が起きない、空の行が末尾にしか並ばない、の4通りです。移行前の旧実装を根拠に書いた課題が2件あり、本番の側で読み直したこともあります。

## 条件と根拠を別の節に分ける

**書く先は「潜在バグが表出する条件」の節で、調べた結果は「根拠」の節へ分ける。** 全部そろうと起きる条件と、起きない場合を並べます。条件と根拠が1つの節に混ざると、読んだ人は自分の画面で起きるかを根拠の中から拾い出すことになります。条件の書き方は `explain_from_observables.md` の「症状を書いたら、それが起きる条件まで書く」に従う。

**「潜在バグが表出する条件」の節の末尾に、表出する頻度を書く。** 条件がそろったとして、どれくらい起きるかで対応の優先度が変わるためです。書くのは2つ。

| 書くこと | 書き方 |
| --- | --- |
| 起き方 | 条件がそろうと毎回起きるのか、障害のときだけなど限られるのか |
| 件数 | 本番のデータで数えないと分からないので「未計測」と書き、どこで数えられるか（DB のどの値・どの API のエラー件数など）を添える。数えられないなら、その理由 |

実際に、5件の課題へ足したところ、1件は「まれ」、残りは「毎回起きる。件数は未計測」でした。

## 禁止する挙動

- 表出しえないと分かった潜在バグを起票すること。判定は仕組みで行い、本番のデータに今その値が無いことを根拠にしない

## なぜ

- 課題の本文は症状を断定の形で書くので、読んだ人は起きる不具合として扱う。表出しえないものを起票すると、起きない不具合の調査と対応に時間を使わせる
- クライアントのコードだけでは、前提の値や失敗が本番で起きるかが分からない。起きるかを決めるのはサーバーの実装と画面の制約で、そこまで辿らないと判定できない

## 例外

- 件名の書式がチームで文書として決まっている場合は、そちらに従う

## 関連

- `base_records_on_measurements.md` （記録は実測に基づける）: 確かめていないことを本文の冒頭に1行で書く規定はあちら。本ルールは起票するかどうかと、件名・本文の組み立て
- `verify_before_asserting.md` （断定の前に裏を取る）: 表出しえないかの判定を、仕組みで行う根拠はあちらの「いま無い」の節
- `explain_from_observables.md` （観測できるものから始める）: 「潜在バグが表出する条件」の節の書き方はあちらの「症状を書いたら、それが起きる条件まで書く」
