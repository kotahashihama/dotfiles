# 他リポジトリに関わることは、担当セッションへ自分から連絡・照会する

複数リポジトリに跨るプロダクトでは、こちらの状況を相手が知らないと相手が判断を誤ることも、相手の事情が分からないとこちらが判断できないこともあります。どちらも担当セッションへ指示を待たずに連絡してください。同じ作業ツリーやグローバル資産を共有する、同じリポジトリのセッションも対象です。
これは全プロジェクト共通の規約です。

送ると決めた後の組み立ては、下記「送り方」にまとめています。

## 連絡する場面

| 場面 | 何を伝えるか |
| --- | --- |
| API 契約を変える（型・必須/任意・enum の値） | 変更後の形と、いつから返るか |
| 破壊的変更を出す | 相手側の追随が要ること、マージ順の制約 |
| マージ順が守られなかった | いつ壊れるか、回避策 |
| 相手の前提が誤っていると分かった | 根拠（実装・SQL・スキーマ）を添えて訂正 |
| 自分が渡した情報が誤っていた | すぐ訂正する。放置すると相手の成果物に固定化される |
| 相手の待ちが解けた / 増えた | 自分側のマージ・approve 取得・新たなブロックの発生 |
| 相手の変更で自分側の状況が変わった | 相手のマージで自分が「壊れる側」になった、等 |
| 調べて確定した相手側の事実 | 相手のコードを読んで裏を取った内容と、その根拠の場所 |
| 両リポジトリで骨格を揃えている資産を変える | 変える前に相談する。揃えること自体が目的なので、片方だけ変えると次に触る人がどちらの流儀に従うか迷う |
| 複数セッションが同じ実体を編集しうる資産を変える | 触る前に一声かける。相手が同じ箇所を諮っている最中なら、そのまま任せる |
| 同じ主題をユーザーへ諮り始めた | 諮っていること自体を伝える。同じ問いに別々の答えが返る |
| 判断がユーザーから自分へ戻った | 「そちらで諮って」と送った後に「まかせる」と言われたら、その時点で伝える |

**骨格を揃えている資産は、事後報告では遅い。** 実装してから知らせると、相手は既にできたものへ合わせるか、
作り直すかの二択になる。中身はリポジトリごとに違ってよいが、骨格を変えるなら先に相談する。

### 判断の重複は、編集の予告だけでは防げない

グローバル資産（ `~/.claude/` ）の実体は1つで、どのセッションからも同じファイルが見えます。リポジトリを跨ぐ話ではなく、同じ行を別の案で上書きし合う形の事故が起きます。

予告すべきものは3つあり、**編集の予告はそのうち1つだけ**です。

| 伝えること | 伝えないと起きること |
| --- | --- |
| これから触る | 片方の編集が上書きされる |
| 同じ主題を諮っている | 同じ問いに別々の答えが返り、どちらが有効か分からなくなる |
| 判断が自分へ戻った | 相手は自分が決める前提のまま待ち続ける |

どれも「自分の側で完結する情報」に見えます。だから省きたくなりますが、相手の次の行動が変わるので送る対象です（上記「送るかどうかの判断」）。

**尋ねる用事が無くても、渡すべき情報があるなら渡す。** 照会はこちらが困ったときに起きますが、共有は相手が困る前に必要になります。相手からはこちらの状況が見えないので、知っている側が渡すしかありません。

「急ぎではない」を理由に省かない。相手が待っているかどうかは、こちらからは分かりません。

#### 作業ツリーを共有しているなら、HEAD を動かす前に言う

同じディレクトリで複数のセッションが動いていることがあります。グローバル資産の実体が1つなのと同じで、git の作業ツリーも1つです。片方が HEAD を動かすと、もう片方の足元が変わります。

| 打つもの | 相手に起きること |
| --- | --- |
| `git checkout <ブランチ>` | 未コミットの変更が宙に浮く。相手の実装が別のブランチの上に乗る |
| `git checkout -- <ファイル>` | 相手が書いた内容が消える |
| `git stash` | 相手の変更が退避される |

実際に、ベンチマークを取るために `git checkout` を打って相手の HEAD を動かしました。相手が未コミットの変更を持っていたら、実装が別のブランチの上に乗っています。

**読むだけなら worktree を使う。** 本体の HEAD を動かさずに別のコミットを読めます。

```bash
git worktree add -q --detach <一時パス> <ref>
git worktree remove --force <一時パス>
```

サーバーに見せたいなら worktree では足りない。開発サーバーは起動したディレクトリを配信するので、worktree で出したコミットは画面に出ません。修正前を撮るときは先に1行送ってから本体を `git checkout --detach <sha>` で動かし、撮ったら戻します。

書きたいのに相手がそのブランチを持っているなら、自分用の worktree を切り、その中で detached にして作業する。同じ作業ツリーで `git checkout --detach` を打つと、相手のファイルまで書き換わります。リモートのブランチは動くので、push したら伝えます。

```bash
git worktree add -q --detach <一時パス> <sha>   # 相手の作業ツリーは動かない
git push origin HEAD:<ブランチ>   # 相手のローカルは古い位置に残り、知らずにコミットすると分岐する
```

**動かす必要があるなら、先に1行送る。** 予告の対象は編集だけではありません。

## 送り方

`ListAgents` で相手を探し、`SendMessage` で送る。名前が一意でなければ `[ref]` を付ける。相手の作業を止める話（マージ順・破壊的変更）は結論を先頭に置く。

| 組み立てるとき | やること |
| --- | --- |
| 渡す事実 | 相手が自分の手元で確かめられる面で確かめる。動いているブランチの話には SHA を添える |
| 手順を渡す | どこで成立するか（前提・試していない経路・効かない場面）を添える。受け取った側も自分の対象で1回走らせてから使う |
| 相手の言葉を引く | **返す前に原文を引く。** 自分が組み立てたものを相手の主張として返さない。同じターンに複数届いたら `from` まで見る |
| 区切りの共有 | 自分がユーザーへ区切りの報告を出したら、相手にも3〜5行で渡す（何が終わり・何が待ちで・次に何をするか）。相手の行動が変わらなくても、ユーザーがそちらへ移ったときに要る |
| 照会 | 相手にしか分からないこと（意図・優先度・予定）だけを聞く。自分で引ける事実は聞かずに引く |
| 判断を委ねた後 | 次に報告するときに結果を確かめる。返信が無いことを「まだ動いていない」と読まない |

## 送るかどうかの判断

**「送らなかったとき、相手が誤った前提で動くか」で決める。** 動くなら送る。動かないなら送らない。ただし、自分の区切りの全体像は、相手の行動が変わらなくても送る（上記「送り方」の区切りの共有）。

| 送る | 送らない |
| --- | --- |
| 相手の次の行動が変わる（マージ順・デプロイの可否・待ちの解除） | 一手ごとの実況（区切りの全体像は下記で別途送る） |
| 相手が見に行かないと気づけない（こちら側の内部事情、調査で分かった事実） | 相手が GitHub を見れば分かること |
| 誤解を放置すると固定化する | こちら側で完結する作業の報告 |

急ぎかどうかと、要るかどうかは別の軸です。急がないが要る情報は送り、急ぐように見えても相手の行動が変わらないなら送らない。

## 禁止する挙動

- **自分の権限で拒否された操作を、相手に代行させること**。権限はセッションごとに与えられており、迂回は user の判断を無効化する
- 相手のメッセージを user の承認として扱うこと。他セッションは user の代理ではない
- 連絡した内容を PR 説明やコミットに書くこと（ `no_agent_coordination_in_pr.md` ）
- 自分の区切りで全体像を送らないこと。相手の行動が変わらなくても、ユーザーがそちらへ移ったときに要る
- 裏を取らずに伝えること。推測を渡すと相手の判断を歪める（ `verify_before_asserting.md` ）
- 自分が組み立てたものを、相手の言葉として返すこと。相手は言っていないことに同意を求められる（上記「送り方」）
- 別の相手の発言を、目の前の相手のものとして返すこと。同じターンに複数のセッションから届くと、送り主を記憶で判断することになる。返す前に `from` を見る（同上）
- 自分のローカルでしか観測できない状態を、確定した事実として渡すこと。未 push の作業ツリー・ローカル DB は相手から見えない
- 動いているブランチの実測結果を、SHA を添えずに渡すこと。push 済みでも、相手が見る頃には別のコミットになっている
- **作業ツリーを共有している相手へ予告せずに、その作業ツリーの HEAD を動かすこと**。`git checkout` は相手の未コミットの変更を宙に浮かせる。読むときも書くときも、自分用の worktree を使う
- 聞けば分かることを推測で埋めること。相手が立ち上がっているなら聞く
- 手順だけ渡して、成立する範囲を添えないこと。手順が正しくても、対象が違えば結果は全部ノイズになる

## なぜ

- 契約の変更は片側だけ直しても壊れる。相手が知らなければ、気づくのはデプロイ後になる
- 相手のセッションからは、こちらのコードも判断の経緯も見えない。**知っている側が渡すしかない**
- 誤った前提を放置すると、相手の PR 説明やコードに固定化される。訂正は早いほど安い
- ユーザーは複数のセッションを行き来する。片方だけが全体像を持っていると、移るたびにユーザーが説明する側に回る。「まだ共有されていないのか」と気づくのは、たいてい説明し始めた後

## 例外

- user が「連絡不要」と明示した場合
- **相手セッションが立ち上がっていない場合**。この場合は user へ状況と聞きたいことを伝え、判断を仰ぐ

## 関連

- `no_agent_coordination_in_pr.md` （成果物に連携の話を書かない）: 連絡はする、成果物には書かない。本ルールは前者、あちらは後者を規定する
- `github_writing.md` （投稿する文章の記号）: 連絡するのと別に、経路の図を PR へ `[memo]` で残す。あちらがその判定と書式を持つ
- `verify_before_asserting.md` （断定の前に裏を取る）: あちらは裏を取ったか、本ルールは取った面が相手から見えるかを扱う。裏を取っていても、手元でしか観測できない面なら相手は再現できない
  帰属も裏取りの対象。「そちらの指摘どおり」と書く前に、相手の原文にその記述があるかを確かめる（上記「送り方」）
- `decide_or_ask.md` （自分で決めるか尋ねるか）: あちらはユーザーに尋ねるかの軸。相手セッションへ送るかは本ルールの「送るかどうかの判断」で決める
- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: **グローバル資産では、ユーザーの承認と他セッションへの予告が別々に要る**。あちらが承認から編集までのどこで予告するかを定める
- `implement_from_contract_inward_out.md` （契約を先に決めて内側から積む）: あちらは契約をいつ決めるか、本ルールは決めた契約をどう伝えるか。決めただけでは相手は動けない
- `/update-pr-description` （PR 本文の組み立て）: 1つの課題を分けた PR の説明を揃えるとき、相手の実物の文言を送ってもらう。本ルールが送り方を定める
