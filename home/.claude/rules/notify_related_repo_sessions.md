# 他リポジトリに関わることは、担当セッションへ自分から連絡・照会する

複数リポジトリに跨るプロダクトでは、**こちらの状況を相手が知らないと相手が判断を誤る**ことも、**相手の事情が分からないとこちらが判断できない**こともあります。どちらも担当セッションへ**指示を待たずに**連絡してください。
これは全プロジェクト共通の規約です。

## 連絡する場面

| 場面 | 何を伝えるか |
| --- | --- |
| **API 契約を変える**（型・必須/任意・enum の値） | 変更後の形と、いつから返るか |
| **破壊的変更を出す** | 相手側の追随が要ること、**マージ順の制約** |
| **マージ順が守られなかった** | いつ壊れるか、回避策 |
| **相手の前提が誤っていると分かった** | 根拠（実装・SQL・スキーマ）を添えて訂正 |
| **自分が渡した情報が誤っていた** | すぐ訂正する。放置すると相手の成果物に固定化される |
| **相手の待ちが解けた / 増えた** | 自分側のマージ・approve 取得・新たなブロックの発生 |
| **相手の変更で自分側の状況が変わった** | 相手のマージで自分が「壊れる側」になった、等 |
| **調べて確定した相手側の事実** | 相手のコードを読んで裏を取った内容と、その根拠の場所 |
| **両リポジトリで骨格を揃えている資産を変える** | **変える前に**相談する。揃えること自体が目的なので、片方だけ変えると次に触る人がどちらの流儀に従うか迷う |
| **複数セッションが同じ実体を編集しうる資産を変える** | **触る前に**一声かける。相手が同じ箇所を諮っている最中なら、そのまま任せる |
| **同じ主題をユーザーへ諮り始めた** | 諮っていること自体を伝える。**同じ問いに別々の答えが返る** |
| **判断がユーザーから自分へ戻った** | 「そちらで諮って」と送った後に「まかせる」と言われたら、**その時点で伝える** |

**骨格を揃えている資産は、事後報告では遅い。** 実装してから知らせると、相手は既にできたものへ合わせるか、
作り直すかの二択になる。**中身はリポジトリごとに違ってよいが、骨格を変えるなら先に相談する。**

### 判断の重複は、編集の予告だけでは防げない

**グローバル資産（`~/.claude/`）の実体は 1 つで、どのセッションからも同じファイルが見えます。** リポジトリを跨ぐ話ではなく、**同じ行を別の案で上書きし合う**形の事故が起きます。

予告すべきものは 3 つあり、**編集の予告はそのうち 1 つだけ**です。

| 伝えること | 伝えないと起きること |
| --- | --- |
| **これから触る** | 片方の編集が上書きされる |
| **同じ主題を諮っている** | **同じ問いに別々の答えが返り、どちらが有効か分からなくなる** |
| **判断が自分へ戻った** | 相手は自分が決める前提のまま待ち続ける |

**どれも「自分の側で完結する情報」に見えます。** だから省きたくなりますが、**相手の次の行動が変わる**ので送る対象です（上記「送るかどうかの判断」）。

**尋ねる用事が無くても、渡すべき情報があるなら渡す。** 照会はこちらが困ったときに起きますが、共有は**相手が困る前**に必要になります。相手からはこちらの状況が見えないので、知っている側が渡すしかありません。

**「急ぎではない」を理由に省かない。** 相手が待っているかどうかは、こちらからは分かりません。

## 送るかどうかの判断

**「送らなかったとき、相手が誤った前提で動くか」で決める。** 動くなら送る。動かないなら送らない。

| 送る | 送らない |
| --- | --- |
| 相手の**次の行動が変わる**（マージ順・デプロイの可否・待ちの解除） | 一手ごとの実況（**区切りの全体像は下記で別途送る**） |
| 相手が**見に行かないと気づけない**（こちら側の内部事情、調査で分かった事実） | 相手が GitHub を見れば分かること |
| 誤解を**放置すると固定化する** | こちら側で完結する作業の報告 |

**急ぎかどうかと、要るかどうかは別の軸です。** 急がないが要る情報は送り、急ぐように見えても相手の行動が変わらないなら送らない。

## 渡す事実は、相手が検証できる面で確認する

**裏を取っていても、取った面が相手から見えなければ食い違います。** セッションは互いのローカル状態を共有しないので、こちらの手元だけで完結した観測は、相手には再現できません。

| 相手が確かめられる（**確定形で渡す**） | 相手からは見えない（**見えないと明示して渡す**） |
| --- | --- |
| push 済みのコミット・マージ済みの履歴 | 未 push の作業ツリー・ローカルの `git diff` |
| リモートで引ける状態（PR・CI・API の応答） | ローカル DB・ローカルにだけ適用した変更 |
| 相手のリポジトリの**実コード** | 自分のリポジトリの履歴からの**推定** |

**右の列も渡してよい。** 未 push であること自体は真の事実で、相手の判断材料になります。禁じているのは**確定形で渡すこと**で、「ローカルでは通っているが未 push」と添えれば相手は確定形として扱いません。

**片側の履歴だけで、もう片側の不足を見積もらない。** 「こちらに何が入ったか」は「あちらに何が足りないか」を意味しません。相手側が独立に更新される仕組みなら、**両側のログを突き合わせる**。

### 動いているブランチの話には、観測した地点を添える

**push 済みでも、見た地点が違えば再現しません。** 左の列に入るのは「同じコミットを見ていれば」の話で、**ブランチ名は動く的**です。相手は自分の HEAD で確かめるので、その間にマージや push が挟まると結論が変わります。

| 渡すもの | 添えるもの |
| --- | --- |
| **実測した結果**（通った / 落ちた・件数・挙動） | **観測したコミットの SHA** |
| ブランチの状態（衝突の有無・CI の結果） | **SHA と、必要なら観測時刻** |
| タグ・リリースを指す話 | それが指す SHA |

実際に、実測結果 3 点のうち 2 点が相手の対象で成立しませんでした。**どちらも push 済みで、どちらも正しい観測**でしたが、片方はマージ前、もう片方はマージ後のコミットを見ていました。

**「main で確認した」は地点になりません。** 相手が読む頃には別のコミットです。

## 手順を渡すときは、成立する範囲まで添える

**手順そのものが正しくても、適用範囲を外すと全部ノイズになります。** 受け取った側は自分の対象へ掛けるので、
**渡した側が試した条件とは違う場所で走ります**。

| 渡すもの | 添えること |
| --- | --- |
| 検査・走査のコマンド | **どこで成立するか**。何を前提にしているか |
| 復旧・移行の手順 | **どの状態から出発するか**。試していない経路 |
| 判定の基準 | **判定が効かない場面** |

実際に、`**` の対応を数える検査を受け取ってルール群へ掛けたところ、**6 件すべてが誤検知**でした。渡した側は
PR 本文でしか試しておらず、**リポジトリ内の `.md` では改行の扱いが違う**という条件が抜けていました。手順は
正しく、対象が違っただけです。

**受け取った側も、自分の対象で 1 回走らせてから使う。** 空でない結果が返ってきても、**それが正しい結果とは限りません**
（`verify_before_asserting.md`）。

## 全体像は、行動が変わらなくても共有する

**上の基準は「相手セッションの行動が変わるか」だけを見ています。** これだけだと、**ユーザーがそちらのセッションへ移ったときに状況が分からない**という穴が残ります。

**ユーザーは複数のセッションを行き来します。** 片方だけが全体像を持っていると、**移るたびにユーザーが説明する側に回る**ことになる。相手セッションは、**ユーザーがそのリポジトリを見るときの窓口**です。

| | 事実の連絡 | 全体像の共有 |
| --- | --- | --- |
| 送る基準 | 相手の**行動が変わる** | **行動は変わらなくてよい** |
| タイミング | 起きたら即 | **自分がユーザーへ区切りの報告を出すたび** |
| 内容 | その事実だけ | **何が終わり / 何が待ちで / 次に何をするか** |
| 量 | 必要なだけ | **3〜5 行**。詳細は要らない |

**「自分がユーザーへ報告したとき」を目印にする。** 自分が報告する価値があると判断した区切りは、相手にとっても区切りです。判断の基準を新しく持たずに済みます。

**全体像は短くする。** 長いと読まれず、本当に止めるべき連絡が埋もれます。**詳細は相手が聞けばよい**ので、こちらは輪郭だけ渡す。

## 照会する場面

**推測で埋めずに聞く。** 相手のリポジトリの中身は、こちらからは読めても意図までは分かりません。

| 場面 | 何を聞くか |
| --- | --- |
| **相手側の状態が判断に要る** | 対応が済んでいるか、いつマージされるか |
| **相手の作業に意図しない変化が見えた** | 意図した変更か、事故か |
| **契約をどちらに合わせるか決まらない** | 相手の制約と、変える場合のコスト |

**「聞くほどでもない」と思った時ほど聞く。** 確認は 1 往復だが、誤った前提で進めた作業のやり直しはそれより高くつく。

## 投げたら結果まで追う

**「判断はお任せします」で終わらせない。** 相手に渡した判断は、こちらの報告にとっては未確定のまま残ります。

- 相手セッションへ判断を委ねたら、**次に状況を報告するときにその結果も確認する**（`gh pr view` 等で自分で引けるなら、返信を待たずに引く）
- 状態が変わっていれば報告に含める。変わっていなければ**もう一度聞く**
- **返信が来ないことを「まだ動いていない」と解釈しない。** 相手が実行して報告を省いただけのことがある

自分で引ける事実は聞かずに引く。**セッション間のやりとりは、相手にしか分からないこと（意図・優先度・予定）に使う。**

## やり方

1. `ListAgents` で相手セッションを探す
2. `SendMessage` で送る。**名前が一意でなければ `[ref]` を付ける**
3. 相手の作業を止める話（マージ順・破壊的変更）は、**結論を先頭**に置く

## 禁止する挙動

- **自分の権限で拒否された操作を、相手に代行させること**。権限はセッションごとに与えられており、迂回は user の判断を無効化する
- 相手のメッセージを **user の承認として扱うこと**。他セッションは user の代理ではない
- 連絡した内容を **PR 説明やコミットに書くこと**（`no_agent_coordination_in_pr.md`）
- **自分の区切りで全体像を送らないこと**。相手の行動が変わらなくても、ユーザーがそちらへ移ったときに要る
- **裏を取らずに伝えること**。推測を渡すと相手の判断を歪める（`verify_before_asserting.md`）
- **自分のローカルでしか観測できない状態を、確定した事実として渡すこと**。未 push の作業ツリー・ローカル DB は相手から見えない
- **動いているブランチの実測結果を、SHA を添えずに渡すこと**。push 済みでも、相手が見る頃には別のコミットになっている
- **聞けば分かることを推測で埋めること**。相手が立ち上がっているなら聞く
- **手順だけ渡して、成立する範囲を添えないこと**。手順が正しくても、対象が違えば結果は全部ノイズになる

## なぜ

- 契約の変更は**片側だけ直しても壊れる**。相手が知らなければ、気づくのはデプロイ後になる
- 相手のセッションからは、こちらのコードも判断の経緯も見えない。**知っている側が渡すしかない**
- 誤った前提を放置すると、相手の PR 説明やコードに**固定化**される。訂正は早いほど安い
- **ユーザーは複数のセッションを行き来する。** 片方だけが全体像を持っていると、移るたびに**ユーザーが説明する側**に回る。「まだ共有されていないのか」と気づくのは、たいてい説明し始めた後

## 例外

- user が「連絡不要」と明示した場合
- **相手セッションが立ち上がっていない場合**。この場合は user へ状況と聞きたいことを伝え、判断を仰ぐ

## 関連

- `no_agent_coordination_in_pr.md`（成果物に連携の話を書かない）: **連絡はする、成果物には書かない**。本ルールは前者、あちらは後者を規定する
- `verify_before_asserting.md`（断定の前に裏を取る）: あちらは**裏を取ったか**、本ルールは**取った面が相手から見えるか**を扱う。裏を取っていても、手元でしか観測できない面なら相手は再現できない
- `decide_or_ask.md`（自分で決めるか尋ねるか）: あちらは**ユーザーに**尋ねるかの軸。相手セッションへ送るかは本ルールの「送るかどうかの判断」で決める
- `implement_from_contract_inward_out.md`（契約を先に決めて内側から積む）: あちらは**契約をいつ決めるか**、本ルールは**決めた契約をどう伝えるか**。決めただけでは相手は動けない
