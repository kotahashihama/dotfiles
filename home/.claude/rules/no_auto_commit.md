# コミット・プッシュは明示指示があるときだけ

ユーザーから **明示的にコミット / プッシュを指示されたときだけ** `git commit` や `git push` を実行してください。
合言葉として「こみっとぷっしゅ」「コミットして」「プッシュして」「commit して」等の明確な指示がある場合のみ実行可。

**既定の挙動より厳しい運用を求めるため残しています。** 既定は「ユーザーが求めたときだけコミットする」までですが、
本ルールは**指示が1回で消費されること**と**`git add -A` を使わないこと**を足しています。

## 禁止する挙動

- 「変更を進めましょう」「修正します」等の **自分の作業フロー宣言の一部としてコミットを実行する**
- リファクタや修正が一段落した節目で、ユーザー指示を待たずに「ついでにコミットしておきます」と進める
- 「テストが通ったので、コミットしておきます」のような **自己判断の commit**
- 「リモートに反映しておきます」のような **自己判断の push**
- `git commit --amend` や `git push --force` 等の **書き換え系コマンドの独断実行**

## 期待する挙動

- ファイル編集が完了したら **作業内容を要約してユーザーに報告**し、コミット指示が来るのを待つ
- ユーザーが「commit してプッシュ」等を明示したときに、はじめて `git add` → `git commit` → `git push` を実行
- 大量の編集をまとめてコミットする場面でも、必ず一度立ち止まってユーザー判断を仰ぐ
- ユーザーが過去のターンで「commit してください」と言ったとしても、その指示は **そのコミット1回限り** で消費されており、次の編集分には適用されない

## なぜ

- コミット粒度・コミットメッセージはユーザーが管理したい責務
- 「ついでに」コミットされると、ユーザーがレビューしたい・統合したい単位とズレる
- push は外部に出るアクションなので、ユーザー意図の確認なしに実行するのは取り返しのつかない事故になりうる

## 例外

- ユーザーがメモリやルールで「自動コミットを許可する」と明示している場合のみ。
- それ以外は本ルールが常に優先する。

## 関連

- `no_operating_on_others_prs.md` （他人の PR は触らない）: **本ルールより先に効く**。他人のブランチなら、コミットの指示があっても別の判断が要る
- `decide_or_ask.md` （自分で決めるか尋ねるか）: 本ルールが扱う場面の**判断軸**を示す
- `no_auto_ready_pr.md` （レビュー依頼は明示指示のみ）: どちらも**外部に出るアクションを自己判断で実行しない**という同じ趣旨。本ルールは履歴、あちらは ready 化と再依頼を扱う
- `no_rebase_under_human_review.md` （レビュー中は履歴を書き換えない）: 本ルールが「指示なく実行しない」を定め、あちらが**指示があっても避けるべき場面**を定める
