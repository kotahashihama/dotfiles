# AI が書いたと分かる文章を出さない

量を出さないことと、AI が書いたと分かる文体で書かないことをまとめています。
これは全プロジェクト共通の規約です。

## AI が書いたと分かる文体で書かない

会話・PR 説明・コミット・レビューコメント・ドキュメント、こちらが書くものすべてが対象です。

**中身が良くても、文体で読む気が削がれます。** 読み手は1行目で「機械が書いたな」と判じ、そこから先を流し読みします。判断材料として正しくても、読まれなければ届きません。

**文体の規範は `/japanese-tech-writing` が正本です。** 演出の抑制・強調の密度・LLM っぽい空句・翻訳調の比喩と擬人化・冗長の排除・パラグラフライティング・論証の厳密さは、すべてあちらが持ちます。本ルールは、あちらが扱わないものだけを持ちます。

| 本ルールが持つ | `/japanese-tech-writing` が持つ |
| --- | --- |
| 定型の締め・助言の押し売り（下記） | 演出・強調・空句・比喩・擬人化・冗長 |
| 読点（息継ぎで置かない） | 段落と論証の構成、見出しの付け方 |
| 語を狩らない（判定の方法論） | 論証の厳密さ、読み手の負荷の管理 |
| 名詞で積まず動詞で書く | 視点と語り |
| いつ通すか（下記） | — |

### あちらが扱わない2つ

| 型 | 例 | 直し方 |
| --- | --- | --- |
| **定型の締め** | 「以上です」「他にあればお知らせください」 | 書かない |
| **助言の押し売り** | 聞かれていないのに「〜すべき」 | 判断材料を出して止める |

### 文章の点検を通す場面と順序

普段のやりとりでは通しません。速度が要るので、その場の短い応答は自分で書いて出します。

表記の規約は、通す・通さないにかかわらず常に効きます。数値と単位の空白・英字と日本語の空白・全角の約物は、**会話への応答を含むすべての出力**が対象です（ `no_space_between_number_and_unit.md` ）。ここで分けているのは文体の点検を回すかどうかだけで、表記は分けません。

通すのは、下の表の「通す」に当たる文章を出すときです。順序が決まっています。

| 順 | すること |
| --- | --- |
| 1 | `/japanese-tech-writing` を当てて自分で直す |
| 2 | 読み物なら `/cognitive-rhythm-writing` を当てて緩急を直す（下記） |
| 3 | `/yomiyasu:yomiyasu` で AI が書いたと分かる言い回しを直す（書き直した前後を同梱の `yomiyasu_check.py run` で突き合わせる） |

**1から順に当てます。** 段落と論証を先に直してから、言い回しを直します。言い回しを先に整えても、あとで段落を組み替えるとやり直しになります。

**読み物では3のあとに2の拍だけを見直します。** `/yomiyasu:yomiyasu` は平均文長を30〜45文字に寄せ、技術記事では箇条書きを15%以下に抑えます。そのため、2で付けた拍（短文で立て、長めの文で流し、短文で止める）と、箇条書きで作った間が均されることがあります。`/cognitive-rhythm-writing` の「執筆後の点検手順」の4（拍の点検）だけを当て直し、均された箇所を戻します。戻すのは文の長さと箇条書きの間だけで、段落は組み替えないので上の順序と食い違いません。この手順は2つのスキルの規定を読んで決めたもので、記事で実際に均されたかはまだ確かめていません。

**`/yomiyasu:yomiyasu` とユーザーの表記の規約が食い違うときは、規約を優先します。** 英字と日本語のあいだの空白は、`/yomiyasu:yomiyasu` が残す書式なので食い違いません（ `no_space_between_number_and_unit.md` ）。また `/yomiyasu:yomiyasu` は似たスキルを無効にするよう勧めていますが、ここでは1と2のあとに重ねて使います。

| 通す | 通さない |
| --- | --- |
| 説明・解説を頼まれたとき（スキルを呼んだかは問わない） | その場の短い応答 |
| 後から誰かが読むもの（コードコメント・ファイル・リポジトリの規約文書（README・`docs/`・ルール・スキル）・PR 本文・PR のコメント・課題管理ツールのコメント・記事） | |
| 文章を出力するスキルの成果物（レビューの総括・完了報告・PR 本文の組み立て） | |
| 出したあとの書き直し（語句だけの修正も含む） | |

スキル名では列挙しません。一覧を作ると、そこから漏れたものを構造的に見逃します（ `verify_the_check_worked.md` ）。判定は「その場で読み終わる応答か、後から読まれる文章か」です。投稿先が GitHub か画面かは問いません。

**長さでは判定しません。** `[fyi]` 1件やコードコメント1行のように短いものも、後から誰かが読むなら通す側です。1件ずつ見ると例外に入って見えるので、まとめて数えます。

実際に、1つの PR へ `[fyi]` 20件と補足コメントを1件ずつ投稿し、コードコメントも直しましたが、どれも通していませんでした。1件ずつは3〜5行で、例外に当てはまって見えたためです。

**2は読み物にだけ当てます。** 記事・本の章・長めの解説文のように、読み進めてもらうこと自体が目的の文章です。PR 本文・課題管理ツールのコメント・報告・会話の応答には当てません。このスキルは冒頭で答えの出ていない問いを作って読み進めさせる形で、一言目で答える規約（ `concise_first_then_detail.md` ）と逆を向きます。

書いている途中では回さず、書き終えてから回します。複数あるときはまとめて1回で通します。

**出したあとで書き直したら、そのたびに通します。** 一度通した文でも語句だけの修正でも例外にしません。書き直しは文体や段落まで動きやすく、「語句だけ」に見えた修正がそうでないことがあります。

実際に、課題へ投稿したコメントのアノテーションを替えて敬体から常体へ書き換えたとき、「語句を直すだけ」と扱って通さずに出しました。通し直すと、指す先が決まらない語が3か所と息継ぎの読点が残っていました。

**投稿する文章は、投稿の直前に通します。** 1件ずつ投稿していく作業では「書き終えた」時点が来ないので、まだ通していない分をためてから1回で通し、そのあとで投稿します。

**コミットする文書も同じで、コミットの直前に通します。** スクラッチパッドで書いて API でそのままコミットする経路では、エディタで書き終えた区切りが来ません。

実際に、別のリポジトリの規約文書（ルール2本と `docs/` の2本）をこの経路でコミットし、4本とも通していませんでした。規約文書を「設定」として扱い、読み物と見なしていなかったためです。

`require-writing-review.sh` が、そのターンに書いた `.md` を、その後で `/yomiyasu:yomiyasu` に通していなければ差し戻します。拾うのは Write / Edit と、Bash のリダイレクト・`sed -i`・`tee`・`--body-file` で書いた分です。スクリプトの中で書いた分は拾えないので、本節が受け持ちます。

MCP で投稿する文章（課題の本文やコメント）は、ファイルを経ずに引数で渡るので、上のフックでは見えません。投稿は取り消せないため、`require-review-before-post.sh` が投稿の直前に止めます。本文は `.md` に書いて点検を通し、その中身を渡します。

**急ぎは、点検を飛ばす理由になりません。** どうしても先に出すなら、出す時点で未点検だと会話で伝え、点検したあとで直します。直し方は `keep_records_current.md` の「まだ誰も読んでいない投稿は、書き換える」に従います。

実際に、急ぎの不具合対応で PR 本文と課題へのコメントを点検せずに投稿し、尋ねられるまで言いませんでした。後から通すと、常体の混在・指す先が決まらない語・結論を言い切った見出しが見つかっています。

`/yomiyasu:yomiyasu` の書き直しは取捨選択します。専門用語を平易な語へ置き換える提案や、断定を弱める提案が混ざるので、`/japanese-tech-writing`・`plain_language_explanation.md`・`base_records_on_measurements.md` を優先します。

### 語を狩らない。意味で判定する

**表の「例」は手がかりであって、置換の一覧ではありません。** 同じ語が別の意味で使われます。

| 語 | 対象になる意味 | 対象外の意味 |
| --- | --- | --- |
| 効く | 効果がある（「この対策が効く」） | 適用される・発動する（「本ルールが先に効く」「 `paths` が効かない」） |
| ただし | 対比が弱いのに置く | 本当に逆接 |
| すべき | 聞かれていないのに助言する | 規約として求める |

実際にルール群で「効く」を数えたら、大半が適用の意味でした。一括置換すれば、そちらまで壊れます。

同じ理由で逆向きにも壊れます。断定の語を一律に弱めると、実測が裏にあるものまで見込みの話になります（ `base_records_on_measurements.md` ）。

### 名詞で積まず、動詞で書く

**サ変名詞を並べると、主語と述語が遠ざかります。** 「〜の実施」「〜の増加」「〜が問題を提起する」の形は、誰が何をしたのかが読み取りにくい。

```
❌ 世界の人口増加が食料補給の問題を提起している
✅ 世界の人口が増加したので、食料の補給が問題になっている
```

**判定は「誰が何をしたか、1回読んで分かるか」。** 名詞が3つ以上続いたら、動詞へ開けないか見る。

### 読点で息継ぎを作らない

話すように書くと声に出す間隔で読点が増えます。書き言葉の読点は構造を示す記号なので、息継ぎで置くと構造を示していない読点が並びます。

```
❌ 変更履歴の中で、どこが重いのか
✅ 変更履歴の中でどこが重いのか

❌ 書き込みは、詳細より履歴の行が重い
✅ 書き込みは詳細より履歴の行が重い
```

**読点は打つ場所が決まっている。それ以外には打たない。** 本多勝一『日本語の作文技術』の打ち方に従います。

| 打つ場所 | 例 |
| --- | --- |
| 長い修飾語が2つ以上並ぶときの境目 | `昨日の夜に届いた長いメールを、帰りの電車で読んだ` |
| 重文の境目（中止法・逆接の「が」で節が並ぶ） | `設定ファイルが2つあり、片方は使われていない` |
| 語順が原則（ `plain_language_explanation.md` の「修飾語の並べ方」）の逆になったとき | `強調のために、ここでは打つ` |
| 外すと後ろの語と繋がるとき | `2種類あり、時間とは別` （ `あり時間` が1語に読める） |
| 倒置・呼びかけ・応答の後、挿入句の前後 | `はい、そのとおりです` |

打たない場所の典型は次の3つです。どれも外して読んで構造が崩れないなら打たない。

| 打たない場所 | 例 |
| --- | --- |
| 主題の直後 | `書き込みは、詳細より` `この memo は、出どころで` |
| 短い条件節・理由節の直後 | `差分が無ければ、` `損失が大きいので、` `確認が済むまでは、` |
| 接続詞の直後 | `ただ、` `そのため、` |

判定を文の長さで決めない。長い文でも主題の直後には打たず、短い文でも重文の境目には打つ。

実際に会話の応答と課題のコメントで主題の直後と短い条件節の直後に読点を打ち続け、「読点が無駄に多い」と指摘を受けました。1つのコメントで32か所落とし、残ったのは重文の境目と長い修飾語どうしの境目でした。

### 判定のしかた

**書き終えてから、次を機械的に見る。** 演出・強調・空句・比喩の点検は `/japanese-tech-writing` が持つので、ここには無い。

1. 読点。打つ場所の表に当たらなければ落とす
2. 名詞が3つ以上続く箇所。動詞へ開けないか見る
3. 定型の締め。付いていたら消す

### 禁止する挙動

- 定型の締めを付けること
- 聞かれていないのに「〜すべき」と助言すること。判断材料を出して止める
- **打つ場所の表に当たらない読点を置くこと**。主題・短い条件節や理由節・接続詞の直後は外しても構造が読める
- サ変名詞を積んで主語と述語を遠ざけること。動詞へ開く
- 表の例を置換の一覧として使うこと。同じ語の別の意味まで巻き込む
- **後から読まれる文章を、点検を通さずに出すこと**。`[fyi]` 1件のような短いものも含む。順序は `/japanese-tech-writing` が先
- 急ぎを理由に点検を飛ばし、そのことを伝えずに投稿すること
- **規約文書を設定として扱い、点検を通さずにコミットすること**。README・`docs/`・ルール・スキルも後から読まれる文章
- **出したあとの書き直しを、一度通したことや語句だけの修正であることを理由に通さずに出すこと**
- 普段の短いやりとりで通すこと。速度が落ちる

### なぜ

- 文体は中身より先に読まれる。演出が冒頭にあると、そこで読み手の期待が決まる
- **文体の規範を2箇所に持つと、食い違ったときにどちらが正しいか決められない**。正本を `/japanese-tech-writing` へ寄せ、本ルールはあちらが扱わないものだけを持つ
- 毎セッション読まれるのはルールのほう。重なったぶんは、呼ばれたときだけ読まれる側へ移すほうが安い

### 例外

- ユーザーが特定の文体を指定した場合
- 危険な操作の警告（強調が必要な場面）

## 量を出さない。自分の判断を通してから出す

会話・PR 説明・コミット・レビューコメント・ドキュメント、**こちらが書くものすべて**が対象です。

[AI slop](https://ja.wikipedia.org/wiki/AI%E3%82%B9%E3%83%AD%E3%83%83%E3%83%97) と呼ばれるものの本質は、労力・品質・意味の欠如と、それを覆い隠す量にあります。「AI が書いたか」は関係ありません。モデルが書いても、手を入れて判断を通したものはスロップになりません。判断が欠けたときになります。

**冗長の排除と、対象を具体的に指すことは `/japanese-tech-writing` が持ちます。** 本ルールは、あちらが扱わない「足す前の判定」だけを持ちます。

### 足す前に、これが無いと読み手は困るかを問う

困らないなら、書かないほうが良い文章になります。

| 足したくなるもの | 判定 |
| --- | --- |
| 節・見出し | その節が無いと読み始められないか |
| 表 | 同じ観点が3件以上あるか。2件なら文で足りる |
| 項目 | 中身が2つなら2つ。3つ目を作らない |
| 補足・前置き | 消して意味が変わるか |

**書き終えてから、節・表・項目の数を見ます。** 消して意味が変わらないなら消す。

### 禁止する挙動

- **量・網羅・体裁を、判断を通した証拠として扱うこと**
- 項目数に合わせず、3つに揃えること

### なぜ

- スロップは体裁が整っている。崩れていれば気づくが、整っていると読み手が中身の薄さに気づくまで時間がかかる
- **量は労力の証明にならない。** むしろ判断を省いたときのほうが増える

### 例外

- ユーザーが特定の文体・分量を指定した場合
- 危険な操作の警告（強調が必要な場面）
