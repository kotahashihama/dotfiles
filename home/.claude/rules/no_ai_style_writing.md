# AI が書いたと分かる文章を出さない

量を出さないことと、AI が書いたと分かる文体で書かないことをまとめています。
これは全プロジェクト共通の規約です。

## AI が書いたと分かる文体で書かない

会話・PR 説明・コミット・レビューコメント・ドキュメント、こちらが書くものすべてが対象です。

**中身が良くても、文体で読む気が削がれます。** 読み手は1行目で「機械が書いたな」と判じ、そこから先を流し読みします。判断材料として正しくても、読まれなければ届きません。

**文体の規範は `/japanese-tech-writing` が正本です。** 演出の抑制・強調の密度・LLM っぽい空句・翻訳調の比喩と擬人化・冗長の排除・パラグラフライティング・論証の厳密さは、すべてあちらが持ちます。本ルールは、あちらが扱わないものだけを持ちます。

| 本ルールが持つ | `/japanese-tech-writing` が持つ |
| --- | --- |
| 定型の締め・助言の押し売り（下記） | 演出・強調・空句・比喩・擬人化・冗長 |
| 読点（息継ぎで置かない） | 段落と論証の構成、見出しの付け方 |
| 語を狩らない（判定の方法論） | 論証の厳密さ、読み手の負荷の管理 |
| 名詞で積まず動詞で書く | 視点と語り |
| いつ通すか（下記） | — |

### あちらが扱わない2つ

| 型 | 例 | 直し方 |
| --- | --- | --- |
| **定型の締め** | 「以上です」「他にあればお知らせください」 | 書かない |
| **助言の押し売り** | 聞かれていないのに「〜すべき」 | 判断材料を出して止める |

### 文章の点検を通す場面と順序

普段のやりとりでは通しません。速度が要るので、その場の短い応答は自分で書いて出します。

表記の規約は、通す・通さないにかかわらず常に効きます。数値と単位の空白・英字と日本語の空白・全角の約物は、**会話への応答を含むすべての出力**が対象です（ `no_space_between_number_and_unit.md` ）。ここで分けているのは文体の点検を回すかどうかだけで、表記は分けません。

通すのは、下の表の「通す」に当たる文章を出すときです。順序が決まっています。

| 順 | すること |
| --- | --- |
| 1 | `/japanese-tech-writing` を当てて自分で直す |
| 2 | `/agy-review` で別のモデルに読ませる（Gemini が指摘を返す。ファイルは編集されない） |

**1を先に済ませます。** 自分で直せるものを残したまま渡すと、返ってくる指摘が表記と言い回しの細部に偏り、論証の穴が拾われにくくなります。

| 通す | 通さない |
| --- | --- |
| 説明・解説を頼まれたとき（スキルを呼んだかは問わない） | その場の短い応答 |
| 後から誰かが読むもの（コードコメント・ファイル・PR 本文・PR のコメント・課題管理ツールのコメント・記事） | 一度通した文の語句を直すだけの修正 |
| 文章を出力するスキルの成果物（レビューの総括・完了報告・PR 本文の組み立て） | 識別子・コマンド・数値だけの変更 |

スキル名では列挙しません。一覧を作ると、そこから漏れたものを構造的に見逃します（ `verify_the_check_worked.md` ）。判定は「その場で読み終わる応答か、後から読まれる文章か」です。投稿先が GitHub か画面かは問いません。

**長さでは判定しません。** `[fyi]` 1件やコードコメント1行のように短いものも、後から誰かが読むなら通す側です。1件ずつ見ると例外に入って見えるので、まとめて数えます。

実際に、1つの PR へ `[fyi]` 20件と補足コメントを1件ずつ投稿し、コードコメントも直しましたが、どれも通していませんでした。1件ずつは3〜5行で、例外に当てはまって見えたためです。

書き終えてから1回だけ回します。編集のたびには回しません。複数あるときは1つの呼び出しにまとめます（呼び出し方と並列度は `background_heavy_work.md` ）。

**投稿する文章は、投稿の直前に通します。** 1件ずつ投稿していく作業では「書き終えた」時点が来ないので、まだ通していない分をためてから1回で通し、そのあとで投稿します。

返ってきた指摘は取捨選択します。専門用語を平易な語へ置き換える提案や、断定を弱める提案が混ざるので、`/japanese-tech-writing`・`plain_language_explanation.md`・`base_records_on_measurements.md` を優先します。

### 語を狩らない。意味で判定する

**表の「例」は手がかりであって、置換の一覧ではありません。** 同じ語が別の意味で使われます。

| 語 | 対象になる意味 | 対象外の意味 |
| --- | --- | --- |
| 効く | 効果がある（「この対策が効く」） | 適用される・発動する（「本ルールが先に効く」「 `paths` が効かない」） |
| ただし | 対比が弱いのに置く | 本当に逆接 |
| すべき | 聞かれていないのに助言する | 規約として求める |

実際にルール群で「効く」を数えたら、大半が適用の意味でした。一括置換すれば、そちらまで壊れます。

同じ理由で逆向きにも壊れます。断定の語を一律に弱めると、実測が裏にあるものまで見込みの話になります（ `base_records_on_measurements.md` ）。

### 名詞で積まず、動詞で書く

**サ変名詞を並べると、主語と述語が遠ざかります。** 「〜の実施」「〜の増加」「〜が問題を提起する」の形は、誰が何をしたのかが読み取りにくい。

```
❌ 世界の人口増加が食料補給の問題を提起している
✅ 世界の人口が増加したので、食料の補給が問題になっている
```

**判定は「誰が何をしたか、1回読んで分かるか」。** 名詞が3つ以上続いたら、動詞へ開けないか見る。

### 読点で息継ぎを作らない

話すように書くと、声に出す間隔で読点が増えます。書き言葉の読点は構造を示す記号なので、息継ぎで置くと構造を示していない読点が並びます。

```
❌ 変更履歴の中で、どこが重いのか
✅ 変更履歴の中でどこが重いのか

❌ 書き込みは、詳細より履歴の行が重い
✅ 書き込みは詳細より履歴の行が重い
```

**判定は3つ。どれにも当たらなければ落とす。**

| | 例 |
| --- | --- |
| 外すと後ろの語と繋がる | `98.5% で、` ／ `2種類あり、時間とは別` （ `あり時間` が1語に読める） |
| 並列の区切り | `A、そうでなければ B` |
| 文全体が50文字以上 | 読点までではなく、その文の長さで見る |

**落とすのは、50文字未満でこの3つに当たらないもの。** 主題の直後（ `書き込みは、詳細より` ）、
短い条件節の直後（ `差分が無ければ、` ）、逆接・理由（ `点灯するため、` `保存しても、` ）が典型。

測るのは前の節ではなく文全体。前の節で見ると逆転する。実測した9件で、置くと判定されたものの前の節は
8文字から60文字まで散っており、落とすと判定された25文字より短いものが両側に現れた。
文全体なら、置く側の最小51文字と落とす側の最大48文字で分かれる。50文字はこの9件から引いた目安で、境界の前後は試していない。

「長い」を数で決めるのは、そうしないと抜け道になるから。実際に感覚で判定して18箇所残し、
2箇所まで落とし、そこから4箇所へ戻した。書き手は自分の文を読めるので、長さの感覚が読み手とずれる。

中止法（ `〜し、` `〜り、` ）は、それだけでは残す理由にならない。50文字未満なら落とす。

```
❌ 項目そのものが削がれ、変更履歴に残す項目も見直される
✅ 項目そのものが削がれ変更履歴に残す項目も見直される   ← 繋がらないので落とす

❌ 落ちる原因は2種類あり時間とは別                     ← 「あり時間」が1語に読める
✅ 落ちる原因は2種類あり、時間とは別
```

機械的に落とすと壊れます。実際に1つの文書で24箇所落とし、2箇所を残しました。残したのはどちらも中止法で、外すと後ろの語と繋がるものです。前節と同じで記号ではなく働きで判定する。

### 判定のしかた

**書き終えてから、次を機械的に見る。** 演出・強調・空句・比喩の点検は `/japanese-tech-writing` が持つので、ここには無い。

1. 読点。外して文意が変わらないなら落とす
2. 名詞が3つ以上続く箇所。動詞へ開けないか見る
3. 定型の締め。付いていたら消す

### 禁止する挙動

- 定型の締めを付けること
- 聞かれていないのに「〜すべき」と助言すること。判断材料を出して止める
- **息継ぎで読点を置くこと**。主題・短い条件節・逆接・理由の直後は外しても構造が読める
- サ変名詞を積んで主語と述語を遠ざけること。動詞へ開く
- 表の例を置換の一覧として使うこと。同じ語の別の意味まで巻き込む
- **後から読まれる文章を、2つを通さずに出すこと**。`[fyi]` 1件のような短いものも含む。順序は `/japanese-tech-writing` が先
- 普段の短いやりとりで通すこと。速度が落ちる

### なぜ

- 文体は中身より先に読まれる。演出が冒頭にあると、そこで読み手の期待が決まる
- **文体の規範を2箇所に持つと、食い違ったときにどちらが正しいか決められない**。正本を `/japanese-tech-writing` へ寄せ、本ルールはあちらが扱わないものだけを持つ
- 毎セッション読まれるのはルールのほう。重なったぶんは、呼ばれたときだけ読まれる側へ移すほうが安い

### 例外

- ユーザーが特定の文体を指定した場合
- 危険な操作の警告（強調が必要な場面）

## 量を出さない。自分の判断を通してから出す

会話・PR 説明・コミット・レビューコメント・ドキュメント、**こちらが書くものすべて**が対象です。

[AI slop](https://ja.wikipedia.org/wiki/AI%E3%82%B9%E3%83%AD%E3%83%83%E3%83%97) と呼ばれるものの本質は、労力・品質・意味の欠如と、それを覆い隠す量にあります。「AI が書いたか」は関係ありません。モデルが書いても、手を入れて判断を通したものはスロップになりません。判断が欠けたときになります。

**冗長の排除と、対象を具体的に指すことは `/japanese-tech-writing` が持ちます。** 本ルールは、あちらが扱わない「足す前の判定」だけを持ちます。

### 足す前に、これが無いと読み手は困るかを問う

困らないなら、書かないほうが良い文章になります。

| 足したくなるもの | 判定 |
| --- | --- |
| 節・見出し | その節が無いと読み始められないか |
| 表 | 同じ観点が3件以上あるか。2件なら文で足りる |
| 項目 | 中身が2つなら2つ。3つ目を作らない |
| 補足・前置き | 消して意味が変わるか |

**書き終えてから、節・表・項目の数を見ます。** 消して意味が変わらないなら消す。

### 禁止する挙動

- **量・網羅・体裁を、判断を通した証拠として扱うこと**
- 項目数に合わせず、3つに揃えること

### なぜ

- スロップは体裁が整っている。崩れていれば気づくが、整っていると読み手が中身の薄さに気づくまで時間がかかる
- **量は労力の証明にならない。** むしろ判断を省いたときのほうが増える

### 例外

- ユーザーが特定の文体・分量を指定した場合
- 危険な操作の警告（強調が必要な場面）

## 関連

- `/agy-review` （別のモデルに読ませる）: 2段目。指摘を集めるだけで、採否はこちらの基準で決める

- `github_writing.md` （1文ごとに改行し句点を落とす）: あちらは改行と句点、本ルールは読点。「読点では折らない」はあちらが定める
- `explain_from_observables.md` （観測できるものから始める）: 本ルールは名詞で積まず動詞へ開く、あちらは開いた動詞を具体にする
