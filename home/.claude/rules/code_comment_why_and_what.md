# コメントは WHY に熱量を、WHAT は簡潔に

**コメントは書かざるを得ないときだけ書いてください。** 既定は書かないほうです。
これは全プロジェクト共通の規約です。

残すのは2種類だけ。**WHY**（書かなければどこにも残らない理由）と、**公開しているものの doc**（hover で読ませる WHAT）です。

## 書く前に、書かない理由を探す

**書こうとしたら、上から順に問う。** 1つでも当たれば書かない。

| 問い | 当たったら |
| --- | --- |
| **コードを読めば分かるか** | 書かない |
| **名前を変えれば済むか** | **名前を変える。** コメントで補うより、読む人に届く |
| **構造を変えれば済むか** | 関数へ切り出す・早期リターンにする |

**ここを通り抜けたものだけが候補になる。** そのうえで次のどちらかに当たれば書く。

| 書く | なぜ |
| --- | --- |
| **WHY**（制約・根拠・避けた落とし穴） | 書かなければ**どこにも残らない**。次に触る人が同じ判断をやり直す |
| **公開しているものの doc** | **hover で読める**。定義へ飛ぶコストが毎回かかる |

**迷ったら書かない。** 足りなければ後から足せるが、**要らないコメントは誰も消さない**。

## 書き分け

| | WHY | WHAT |
| --- | --- | --- |
| **どこに** | 非自明な箇所の直上（インライン） | 公開している関数・型・変数の doc コメント |
| **熱量** | **ここに寄せる。** 制約・根拠・落とし穴を書く | **1〜2行。** 何であるか、どう処理するか |
| **無いとどうなるか** | 後から読む人が同じ判断を再現できない | hover しても何も出ず、定義まで飛ぶことになる |

```ts
/**
 * 記事の公開状態を判定する。下書きと掲載終了は非公開として扱う。   ← WHAT: 1〜2 行
 */
export function isPublished(post: Post): boolean {
  // 掲載期限は締め日の 23:59 まで有効。日付比較だと当日が落ちる。   ← WHY: 熱量はこちら
  return post.status === 'published' && post.expiresAt > now()
}
```

## WHAT を書く対象

**公開しているもの**に付ける。ファイル内部に閉じたものは不要。

- 関数・メソッド・クラス
- 型・インターフェースと、**その各フィールド**（hover で呼び出し側に伝わる）
- 定数・列挙

書式は言語の慣習に従う（TypeScript は JSDoc、Go は名前で始まる doc コメント）。

## それでも書かないもの

WHAT を書いてよいことは、**何でも書いてよいことではありません**。

| 書かない | なぜ |
| --- | --- |
| **名前の言い換えをインラインで** (`// ユーザーを取得` の下に `getUser()`) | hover では見えない位置で、情報が増えていない |
| **doc に書いたことを関数本体の先頭で繰り返す** | 同じ情報が2箇所に散り、片方だけ古くなる |
| 過去の経緯・段階的リファクタの説明 | 差分の意図はコミットメッセージが持つ |
| **いずれ自明になる事情**（バージョンの過渡期・移行の理由） | 数か月で価値を失う。PR の `[fyi]` へ置く（ `write_invariant_why_in_code.md` ） |
| チケット番号・レビュー指摘の逐語 | PR 説明が持つ（ `no_review_comment_echo_in_code.md` ） |
| 「二重防御」等の層の名称付け | 名前を付けても、なぜ必要かは伝わらない |
| **書けることを見つけたから書いたもの** | 判定を通っていない。**書かない理由を先に探す** |

## 複数行に分けたら、行末の句点を落とす

**改行が切れ目を示すので句点は働いていません。**

```ts
// ❌ 1行目にだけ句点がある
// 削除は件数ぶん API を呼ぶため途中で失敗すると一部だけ消えた状態になりうる。
// 1件でも失敗したら保存状態を変えない

// ✅ どちらの行にも置かない
// 削除は件数ぶん API を呼ぶため途中で失敗すると一部だけ消えた状態になりうる
// 1件でも失敗したら保存状態を変えない
```

**1行に2文置いたときだけ文中の句点が残ります**（ `hoge。fuga` ）。行末には来ません。

**`？` と `！` は残す。** 文の種類を示す記号なので改行では肩代わりできません。

**`.md` ファイルとは条件が違います。** あちらは単一改行が空白になるので句点が要りますが**コードコメントの改行はそのまま改行として効きます**。

## 禁止する挙動

- **書く前の問いを飛ばすこと**。書けることを見つけたから書く、が最も多い形
- **コードや変数名から読み取れることを書くこと**。直下の定義を言い換えただけのものが残りやすい
- **後から点検して削る前提で書くこと**。点検は取りこぼすうえ、**rebase で復活する**
- 名前や構造を変えれば済むものを、コメントで補うこと

## なぜ

- **WHY は失われる。** コードには結果だけが残り、検討して捨てた選択肢や外部の制約は残らない。書かなければ、次に触る人が同じ判断をやり直す
- **WHAT は hover のためにある。** 読めば分かるとしても、呼び出し側から定義へ飛ぶコストは毎回かかる。1行で足りるなら、その1行が何度も効く
- 熱量の置き場を決めておかないと、**書きやすい WHAT ばかりが増えて WHY が埋もれる**

## 例外

- ユーザーが「コメント不要」「この書式で」と明示した場合
- 生成されたコードや外部から取り込んだコードは、その出自の慣習に従う

## 関連

- `no_review_comment_echo_in_code.md` （レビュアーの文言を転記しない）: 本ルールが定める「書かないもの」のうち、レビュー由来の失敗パターンを詳しく規定する
- `write_invariant_why_in_code.md` （不変の WHY だけ残す）: 本ルールが「WHY を書け」を定め、あちらが**どの WHY か**を時間の軸で絞る
- `github_one_sentence_per_line.md` （1文ごとに改行し句点を落とす）: **句点を落とす根拠が同じ**（改行が切れ目を示す）。あちらは GitHub への投稿、本ルールはコードコメント。**`.md` ファイルはどちらの対象でもない**
- `concise_first_then_detail.md` （簡潔に）: WHAT の「1〜2行」は本ルールと同じ基準
- `review-comments` スキル: 書いた後の点検手順。本ルールは書くときの基準
