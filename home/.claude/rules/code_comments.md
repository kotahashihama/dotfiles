# コードコメントに何を書くか

コードコメントは、書かざるを得ないときだけ書いてください。何を書き、どの WHY を残し、何を持ち込まないかをまとめています。
これは全プロジェクト共通の規約です。

## コメントは WHY に熱量を、WHAT は簡潔に

**コメントは書かざるを得ないときだけ書いてください。** 既定は書かないほうです。

残すのは2種類だけ。WHY（書かなければどこにも残らない理由）と、公開しているものの doc（hover で読ませる WHAT）です。

### 書く前に、書かない理由を探す

書こうとしたら、上から順に問う。1つでも当たれば書かない。

| 問い | 当たったら |
| --- | --- |
| コードを読めば分かるか | 書かない |
| 名前を変えれば済むか | 名前を変える。コメントで補うより、読む人に届く |
| 構造を変えれば済むか | 関数へ切り出す・早期リターンにする |

ここを通り抜けたものだけが候補になる。そのうえで次のどちらかに当たれば書く。

| 書く | なぜ |
| --- | --- |
| WHY（制約・根拠・避けた落とし穴） | 書かなければどこにも残らない。次に触る人が同じ判断をやり直す |
| 公開しているものの doc | hover で読める。定義へ飛ぶコストが毎回かかる |

**迷ったら書かない。** 足りなければ後から足せるが、**要らないコメントは誰も消さない**。

### 書き分け

| | WHY | WHAT |
| --- | --- | --- |
| どこに | 非自明な箇所の直上（インライン） | 公開している関数・型・変数の doc コメント |
| 熱量 | **ここに寄せる。** 制約・根拠・落とし穴を書く | 1〜2行。何であるか、どう処理するか |
| 無いとどうなるか | 後から読む人が同じ判断を再現できない | hover しても何も出ず、定義まで飛ぶことになる |

```ts
/**
 * 記事の公開状態を判定する。下書きと掲載終了は非公開として扱う。   ← WHAT: 1〜2 行
 */
export function isPublished(post: Post): boolean {
  // 掲載期限は締め日の 23:59 まで有効。日付比較だと当日が落ちる。   ← WHY: 熱量はこちら
  return post.status === 'published' && post.expiresAt > now()
}
```

### WHAT を書く対象

**公開しているもの**に付ける。ファイル内部に閉じたものは不要。

- 関数・メソッド・クラス
- 型・インターフェースと、**その各フィールド**（hover で呼び出し側に伝わる）
- 定数・列挙

書式は言語の慣習に従う（TypeScript は JSDoc、Go は名前で始まる doc コメント）。

### それでも書かないもの

WHAT を書いてよいことは、**何でも書いてよいことではありません**。

| 書かない | なぜ |
| --- | --- |
| 名前の言い換えをインラインで (`// ユーザーを取得` の下に `getUser()`) | hover では見えない位置で、情報が増えていない |
| doc に書いたことを関数本体の先頭で繰り返す | 同じ情報が2箇所に散り、片方だけ古くなる |
| 過去の経緯・段階的リファクタの説明 | 差分の意図はコミットメッセージが持つ |
| いずれ自明になる事情（バージョンの過渡期・移行の理由） | 数か月で価値を失う。PR の `[fyi]` へ置く |
| チケット番号・レビュー指摘の逐語 | PR 説明が持つ |
| 「二重防御」等の層の名称付け | 名前を付けても、なぜ必要かは伝わらない |
| **書けることを見つけたから書いたもの** | 判定を通っていない。書かない理由を先に探す |

### 内部の呼び名で書かない

書き手はデータ構造の側から見ているので、自前の呼び名が出ます。ストアの配列の要素を「行」、DB の1件を「レコード」と呼ぶ類です。**画面に出ているものの名前で書く。**

```ts
// ❌ 「行」はストアの配列の要素を指す自前の呼び名
// 件数は total を見るため、消えた行数ぶん減らさないと行が無いのに件数が残る

// ✅ 画面に出ているもので書く
// 件数は total を見るため、消えた項目の数だけ減らさないと一覧が空でも件数が残る
```

**判定軸は `explain_from_observables.md` の「語を読んで、指すものが1つに決まるか」。** あちらの対象はコードコメントを含みませんが、判定は同じように当たります。

落ちるのは置き場所のせいです。判定軸はあちらにあり、コメントを書くときに開くのはこちらなので、本則が読まれない位置にある（ `rule_conventions.md` ）。

### 複数行に分けたら、行末の句点を落とす

**改行が切れ目を示すので句点は働いていません。**

```ts
// ❌ 1行目にだけ句点がある
// 削除は件数ぶん API を呼ぶため途中で失敗すると一部だけ消えた状態になりうる。
// 1件でも失敗したら保存状態を変えない

// ✅ どちらの行にも置かない
// 削除は件数ぶん API を呼ぶため途中で失敗すると一部だけ消えた状態になりうる
// 1件でも失敗したら保存状態を変えない
```

1行に2文置いたときだけ文中の句点が残ります（ `hoge。fuga` ）。行末には来ません。

**`？` と `！` は残す。** 文の種類を示す記号なので改行では肩代わりできません。

`.md` ファイルとは条件が違います。あちらは単一改行が空白になるので句点が要りますがコードコメントの改行はそのまま改行として効きます。

### 禁止する挙動

- **書く前の問いを飛ばすこと**。書けることを見つけたから書く、が最も多い形
- コードや変数名から読み取れることを書くこと。直下の定義を言い換えただけのものが残りやすい
- **後から点検して削る前提で書くこと**。点検は取りこぼすうえ、rebase で復活する
- 名前や構造を変えれば済むものを、コメントで補うこと
- 内部の呼び名で書くこと（行 / レコード / エントリ）。読み手が指すものを決められない

### なぜ

- **WHY は失われる。** コードには結果だけが残り、検討して捨てた選択肢や外部の制約は残らない。書かなければ、次に触る人が同じ判断をやり直す
- WHAT は hover のためにある。読めば分かるとしても、呼び出し側から定義へ飛ぶコストは毎回かかる。1行で足りるなら、その1行が何度も効く
- 熱量の置き場を決めておかないと、書きやすい WHAT ばかりが増えて WHY が埋もれる

### 例外

- ユーザーが「コメント不要」「この書式で」と明示した場合
- 生成されたコードや外部から取り込んだコードは、その出自の慣習に従う

## コードコメントに残す WHY は、不変のものだけにする

コード中のコメントに WHY を書くとき、**その理由が時間とともに自明になるなら書かない**でください。移ろう文脈は PR の `[fyi]` コメントへ置きます。

**WHY なら何でも書いてよい、ではありません。** WHY には賞味期限のあるものが混じります。

### 判定は「1年後も理由として成立するか」

| 不変の WHY（コードに書く） | 移ろう WHY（PR へ置く） |
| --- | --- |
| 仕様・ドメインの制約（締め日は23:59まで有効） | その時点のバージョン事情（「〜から読まれないため」） |
| 避けた落とし穴（ゼロ値が成功扱いになる） | 移行の経緯（旧形式から移した・統合された） |
| 外部システムの決まりごと | 過渡期の回避策（対応版が出るまでの措置） |
| なぜ素直な書き方を採らなかったか | 今は新しいが、いずれ常識になること |
| 自分がこの形を選んだ判断そのもの | 他リポジトリ・他ファイルとの比較（「別リポジトリの同種のワークフローも同じ形」） |

**「読み手が知らないから書く」ではなく、「読み手が調べても出てこないから書く」で決める。**

ツールやライブラリの仕様は、公式ドキュメントを引けば出てきます。一方、このコードがなぜその形を選んだかは、書かなければどこにも残りません。

新しい仕様ほど書きたくなります。自分が今調べたばかりで、非自明に感じているからです。その感覚は数か月で消えますが、コメントは残ります。

他リポジトリ・他ファイルとの比較も移ろう WHY です。相手が変われば根拠が崩れます。

### 移ろう文脈は、捨てずに PR へ置く

**説明が不要なのではありません。** 移行のような変更では、レビュアーはまさにその説明を必要としています。置き場が違うだけです。

| | コードコメント | PR の `[fyi]` コメント |
| --- | --- | --- |
| 読まれる期間 | 永久に残る | レビュー中だけ |
| 読み手 | 後からコードを読む人 | 今この差分を読む人 |
| 移行の説明 | 数か月で意味を失い、ノイズになる | ちょうど必要な期間だけ効く |

設定ファイルほど溜まりやすい。1行の設定に3行の由来が付き、次の移行でまた増える。設定の意味ではなく移行の履歴が積み上がります。

#### 置き方: 自分の PR へインラインで付ける

**該当する行に、自分でインラインコメントを付ける。** PR 本文へまとめて書くより、その行を見ている人にその場で届きます。

アノテーションは `[fyi]`。書式と使い分けは `github_writing.md` が定めます。

自分の PR に自分でコメントを付けるのは、遠慮する場面ではありません。書き手にしか見えていない前提を、
レビュアーが差分から読み取るのは無理があります。先回りして置いておくほうが、質問の往復より安い。

#### 削るときは、置くところまでを1つの作業にする

**削る手と置く手は、別のタイミングで動きます。** コードから消すのは編集中ですが、
インラインコメントはコミットを指すので、push するまで付けられません。

この時間差で落ちます。実際に、設定3箇所から実測値を削っておきながら、
どれも PR へ置かないまま次の作業へ進みました。削った時点では「後で置く」と思っており、
push した時点ではもう別のことを考えています。

| 順 | やること |
| --- | --- |
| 1 | 削る前に、削る内容を控える。消した瞬間に思い出せなくなる |
| 2 | コードから削る |
| 3 | コミットして push する |
| 4 | その push のコミットを指して `[fyi]` を付ける |

「あとでまとめて」にしない。削った箇所が増えるほど、どれを控えたか分からなくなります。

#### 既にあるコメントを短くするときも同じ

新しく書くときだけの話ではありません。既存のコメントから移ろう部分を削るのは、
書かないより起きやすい。既に書いてあるので、削ることに気を取られて行き先を忘れます。

**マージした後には置けません。** `[fyi]` はレビュー中しか読まれない場所なので、
マージしてから気づいても手遅れです。削るなら、その PR が開いている間に置き切る。

### 判断に迷ったときの問い

- **その理由を消したら、次に触る人が同じ間違いをするか。** するなら不変の WHY
- 公式ドキュメントを引けば同じことが書いてあるか。あるなら移ろう WHY
- 「〜から」「〜ため」の主語がバージョンや時期か。そうなら移ろう WHY

### 禁止する挙動

- バージョンの過渡期の事情をコードコメントに書くこと。数か月で自明になり、読み手の時間だけ奪う
- 移行の経緯をコードコメントに書くこと。差分の意図はコミットメッセージ、レビュー向けの説明は PR が持つ
- 「今は非自明だから」を根拠に書くこと。非自明さは書き手の側の一時的な状態
- 移ろう文脈だからと、説明ごと省くこと。PR の `[fyi]` へ置く
- PR 本文にまとめて書いて済ませること。該当行を見ている人には届かない。インラインで付ける
- **削って終わりにすること**。削る手と置く手は別のタイミングで動くので、削る前に控えて、push 後に置く
- **マージ後に置こうとすること**。`[fyi]` はレビュー中しか読まれない。その PR が開いている間に置き切る

### なぜ

- コードコメントは消される機会がほとんどない。書いた時点の正しさが、そのまま将来のノイズになる
- 移行の説明は**レビュー中に最も価値があり、マージ後に急速に価値を失う**。読まれる期間と価値の曲線が、コードコメントと合っていない
- 一方、設計判断の理由は時間が経つほど価値が上がる。当時の検討は誰の記憶にも残らないため

### 例外

- ユーザーが「この理由をコメントに残して」と明示した場合
- **過渡期が終わる時期が読めず、しかもその間に事故が起きうる場合**。この場合も、いつ消せるかを1行で添える

## レビュアーコメントをコード中のコメントにそのまま反映しない

PR レビュアーからもらった指摘の**文言・言い回し・理由づけ**を、そのままコード中の
コメント（doc コメント / 行内 // コメント / SQL コメント等）に転記しないでください。

### 禁止する挙動

- レビュアーが書いた「〜が良いと思いました」「〜のように倒す方が安全」「〜の設計です」等の
  **判断のナラティブ**をそのままコード中コメントに複製する
- 「Fail-Closed 側に倒す設計」「知らない値が来たら失敗として扱う」等、
  レビュアーが対応方針を説明するために使った言葉を、そのまま自然文でコードに残す
- 「〇〇さんの指摘で〜」「レビューコメントr12345の意図で〜」等、
  レビュー由来である旨や、コメント ID・レビュアー名への言及をコードに残す
- 対応時にレビュアーの説明ロジック（Before → After の対比、なぜダメだったか）を
  そのままコメントに書き写す

### 期待する挙動

- レビュー指摘を受けてコメントを足すときも、既定は書かないほう（上記「書く前に、書かない理由を探す」）。そのうえで次の3観点で決める
  - 例 (書くべき): `// Outcome 未設定 (ゼロ値) は SystemFailed に倒すセーフティネット。`
    （enum のゼロ値ハンドリング＝コードを読んだだけでは気づきにくい非自明な挙動）
  - 例 (書かない): `// 経路の追加漏れが「成功扱い」で握りつぶされないよう Fail-Closed 側に倒す設計。`
    （レビュアーの説明ロジックをそのまま転記した「設計ナラティブ」）
- 3観点（1つでも当たれば書く、どれにも当たらなければ書かない）
  1. 非自明性: コードから素直に読み取れない前提・設計判断・センチネル値等が絡む
  2. 再現コスト: 追加のドキュメント / チケット / issue を漁らないと意図が復元できない
  3. 失敗のダメージ: 誤解が本番事故・データ破損・回復不可能な副作用に直結する
- 必要と判定した場合は、レビュアー文言に引きずられず自分の言葉で最短化する
- レビュアーの説明・判断ロジックのうち、コードコメントにするほどではないものは
  コミットメッセージ本文に「なぜ」として残す
  （コミットメッセージは差分の意図を残す場、コード中コメントは実行時に読まれる場）

### なぜ

- レビュアーの説明は「その対応を採用する理由を PR 上で伝える」ための文脈依存の言葉であり、
  マージ後にコードだけを読む人には冗長・押し付けがましく映る
- 判断ナラティブがコードに残ると、後から仕様変更で反対方向に倒したくなった際に
  「元々の設計判断」として過剰に尊重され、変更のブレーキになる
- レビュアーの言葉遣いには個人差があり、コード中コメントの語調が不揃いになる原因になる
- 「なぜその形にしたか」の情報が本当に必要なら、コミットメッセージ本文または PR 説明で残すのが正しい場所

### 例外

- ユーザーが明示的に「このレビュー指摘の文言をコメントに残して」と指示した場合のみ。
- それ以外は本ルールが常に優先する。

## 関連

- `github_writing.md` （GitHub へ投稿する文章の書き方）: 1文ごとの改行の節とは句点を落とす根拠が同じ（改行が切れ目を示す）。あちらは GitHub への投稿、本ルールはコードコメントで、`.md` ファイルはどちらの対象でもない。PR へ置く `[fyi]` の書式もあちら
- `concise_first_then_detail.md` （簡潔に）: WHAT の「1〜2行」は本ルールと同じ基準
- `explain_from_observables.md` （観測できるものから始める）: **「指すものが1つに決まるか」の判定軸はあちら**。本ルールはそれをコードコメントへ当てる
- `review-comments` スキル: 書いた後の点検手順。本ルールは書くときの基準
- `/japanese-tech-writing` と `/agy-review` （文章の点検）: 日本語のコメントも対象。書く基準は本ルール、文章としての点検はあちら（通す順序と場面は `no_ai_style_writing.md` の「文章の点検を通す場面と順序」）
- `write_for_installed_versions.md` （入っているバージョンで書く）: あちらはコードをどのバージョンに合わせるか、本ルールはその事情をどこに書くか
- `adopt_tools_with_official_defaults.md` （ツールは公式の既定値から）: 設定コメントに実測値を書かない根拠として本ルールを参照している
- `no_instruction_echo_in_output.md` （成果物に指示を書かない）: あちらは出どころ（ユーザーの指示か）で弾く。本ルールは賞味期限で弾く
