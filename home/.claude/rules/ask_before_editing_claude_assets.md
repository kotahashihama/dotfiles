# Claude Code 資産は、尋ねてから手を入れる

`~/.claude/` と各リポジトリの `.claude/` への追加・変更・削除は、**ユーザーが明確に依頼していない限り先に尋ねて**ください。あわせて、会話の中で「**これは毎回言われている**」「**この記述は実態と違う**」と気づいたら、資産化・改善できないかを**自分から提案**します。
これは全プロジェクト共通の規約です。

**気づく側はユーザーとは限りません。** ユーザーが「ルール化しよう」と言うのを待たず、**自分が気づいた時点で提案する**。会話の中にいる側にしか見えない繰り返しと綻びがあります。

## 気づく手掛かり

**新しく作る**手掛かり。

| 手掛かり | 例 |
| --- | --- |
| **同じ指摘を 2 回以上受けた** | 「またこれ言われてる」と感じたとき |
| **同じ手順を毎回説明されている** | 作業のたびに順序を指示される |
| **ユーザーが理由を語った** | 「〜だからこうしてほしい」の「〜だから」は、書けば他の場面にも効く |
| **自分が同じ判断を繰り返した** | 毎回ゼロから考え直しているなら、判断基準を書ける |
| **既定の挙動が足りないと分かった** | 穴を埋める資産にできる |

**既存を直す**手掛かり。**こちらのほうが見落としやすい**——資産があるだけで「守られている」と錯覚するためです。

| 手掛かり | 例 |
| --- | --- |
| **書いてあるとおりにやって失敗した** | ルール側に穴がある。従った結果が事故なら、ルールが悪い |
| **ルールを守れなかった / 守らなかった** | 逸脱はルール側の欠陥を示す信号。書き方・置き場所・要否を見直す（`rule_conventions.md`） |
| **記述が実態と食い違っていた** | 列挙が古い・参照先が消えている・数が合わない。**実装を触ったついでに気づくことが多い** |
| **2 通りに解釈できた** | 自分が迷ったなら、次も迷う。判定基準を 1 通りに絞る |
| **資産どうしが矛盾していた** | 片方が古い。**両方直すか、正本を 1 つに決める** |
| **例外に当たる場面に出くわした** | 想定外の状況で判断に困ったら、`## 例外` に足せる |

**「1 行の修正だから黙って直す」もしない。** 何を常時ロードさせるかはユーザーの領分で、それは追加でも修正でも変わりません（例外は下記「その編集に付随する整理」）。

## どこに置くかの見立て

提案するときは**置き場所まで示す**。ユーザーが「どれにするか」ではなく「やるか否か」を判断できる形にする。

### まず範囲で振り分ける

**内容がグローバルならグローバル設定へ、そのリポジトリ固有ならプロジェクト設定へ置く。**

| 内容 | 置き場 | 例 |
| --- | --- | --- |
| **どのリポジトリでも効かせたい** | `~/.claude/` | コミットメッセージの書式、報告の粒度、レビュー対応の進め方 |
| **そのリポジトリだけで効く** | そのリポジトリの `.claude/` | ディレクトリ構成の規約、使用ライブラリの流儀、そのリポジトリ固有の点検手順 |

**判断は「どこで書いたか」ではなく「どこで効くか」。** プロジェクトの作業中に生まれた規約でも、内容が汎用ならグローバルへ置く。逆に、グローバル資産を整理していて出てきた話でも、特定リポジトリの事情ならプロジェクトへ置く。

迷ったら**プロジェクト側に倒す**。グローバルは毎セッション全文が展開されるので、関係ないリポジトリでも展開されるコストがかかる。後からグローバルへ上げるのは容易。

**プロジェクト固有の資産を促す仕組みは、その資産と同じ側に置く。** グローバルからプロジェクトのスキルやドキュメントを名指しすると、**それが無いリポジトリでは存在しないものを案内する**ことになります。

**「条件付きにすれば他リポジトリでも壊れない」は、置き場所が違うことの証拠です。** 回避策を足したくなったら、その時点で置き場所を疑う。

### 次に種類で振り分ける

| 性質 | 置き場 |
| --- | --- |
| 常に効かせたい振る舞いの規約 | `rules/*.md` |
| 呼ばれたときに踏む複数手順 | `skills/<name>/SKILL.md` |
| ツール実行に反応させたい自動処理 | `settings.json` の `hooks` |
| 知っていれば判断が変わる前提 | `CLAUDE.md` |

**プロジェクトのルールは `paths` で絞れる。** 特定のディレクトリやファイル種別でだけ効かせたいなら frontmatter に書く。グローバルルールに `paths` は効かない（`rule_conventions.md`）。

### 置き場は仕様を確認してから決める

**Claude Code の資産の種類と置き場は変わる。** 記憶で判断せず、[公式ドキュメント](https://code.claude.com/docs/en/features-overview)で毎回確かめる（`verify_before_asserting.md`）。

実際に起きた変更の例。

- **custom commands は skills へ統合された。** `commands/*.md` と `skills/<name>/SKILL.md` はどちらも `/name` を作る。既存は動き続けるが、**新規は skills に置く**
- `/output-style` コマンドは削除されたが、`output-styles/` ディレクトリは現役

確認するのは次の 3 点。

| 見るもの | なぜ |
| --- | --- |
| **その種類がまだ推奨されているか** | 統合・廃止された置き場に新規で足さないため |
| **より適した種類が増えていないか** | 手で書いていた手順が、機能として入っていることがある |
| **強制が要るなら hooks に寄せられないか** | ルールは読み飛ばされうるが、hooks は必ず走る。「毎回必ず」が要件なら hooks が正解 |

## 尋ねてから手を入れる

**新規作成だけでなく、変更・削除も同じです。** ユーザーが明確に依頼していない編集は、`~/.claude/` と `.claude/` 配下のどのファイルであっても**先に尋ねる**。

| 操作 | 例 |
| --- | --- |
| 追加 | 「これはルールにできそうです。作りますか？」 |
| **変更** | 「このルールの記述が実装と食い違っています。直しますか？」 |
| **削除** | 「このルールは既定の挙動に取り込まれています。消しますか？」 |

**例外は「そのファイルに手を入れる指示が既に出ているとき」だけ。** ユーザーが「このルールを直して」と言った作業の中で、`## 関連` の参照切れを直す・重複した節を畳むといった**その編集に付随する整理**は、確認を挟まず行ってよい（`rule_conventions.md` の「整理の契機」）。

## 編集したら永続化まで見る

`~/.claude/` の実体は dotfiles リポジトリで、**シンボリックリンク越しに編集しています**。編集しただけでは履歴に残らず、環境を作り直すと消えます。

| 実体の置き場 | git | 編集後 |
| --- | --- | --- |
| `home/.claude/`（rules / skills / hooks / agents / settings.json / CLAUDE.md） | **管理下** | **コミットが要る** |
| `private/.claude/` と `private/.claude-memory/`（メモリ・社内固有名を含むスキル） | `.gitignore` 対象 | 不要 |

**スキルは両方の区分にあります。** `~/.claude/skills/` からはスキル単位でリンクされていて見分けが付かないので、**編集したファイルの実体を `readlink -f` で確かめる**。`private/` 側なら連絡は要りません。

### 公開区分に社内固有名を書かない

**`home/` は公開リポジトリです。** 書いたものがそのまま外から読めます。

| 書ける | 書けない |
| --- | --- |
| 書式・構造・判定基準 | **リポジトリ名・GitHub ID・プロダクト名・社内 URL** |
| プレースホルダ（`OWNER/REPO`） | 実際に動かした出力をそのまま貼ったもの |

**最も混入しやすいのは出力例です。** 実際に動かした結果を貼るのが自然なので、コピーしたまま残ります。**例を書いたら固有名が混じっていないか読み返す。**

実データを含む例をどうしても残したいなら `private/` 側へ置く。`pre-commit` が走査していますが、**フックに気づかせてもらう前提で書かない**——止められてから直すのは手戻りですし、フックの無い経路（他リポジトリの公開ファイル、Gist、**会話への出力**）では素通りします。

**秘匿値（API キー・トークン・MFA シード等）は固有名より厳しく扱う。** ファイルに限らず**あらゆる出力**が対象で、こちらは `no_secret_values_in_output.md` が規定します。

**`home/` 側を編集したら、dotfiles のセッションが起動していないか `ListAgents` で確認する。**

- 起動していれば `SendMessage` で**何をどう編集したか**を伝えてコミットを促す（`notify_related_repo_sessions.md`）。向こうは編集したことを知らない
- 起動していなければ**ユーザーへ 1 行**添える。「dotfiles に未コミットの変更が N 件」で足りる
- **自分で dotfiles をコミットしない**（`no_auto_commit.md`）。作業中のリポジトリと別の履歴を勝手に作らない

**編集のたびに毎回連絡しない。** 一連の作業が一段落した時点でまとめて 1 回。細切れに送ると、向こうがコミット単位を切れなくなります。

## 提案のしかた

1. **何を足す / 直すか**を 1 行で言う
2. **どこに置くか**と、その理由を添える。既存を直すなら**どの記述がどう実態とズレているか**を引用する
3. **既定の挙動や既存資産で足りないか**を先に確かめ、足りるなら提案しない
4. 「そうしますか？」と可否を聞く。**選択肢が 2 つ以上あるなら `AskUserQuestion` で出す**（`decide_or_ask.md`）

## 禁止する挙動

- **確認なしに作る・変える・消すこと**。何を常時ロードさせるかはユーザーの領分
- 既定の挙動や既存資産と重なるものを提案すること（`rule_conventions.md`）
- **1 回きりの指示を資産化しようとすること**。繰り返しの兆候がないなら、その場で従えばよい
- 提案を溜めて後でまとめて出すこと。**気づいた時点で言う**（文脈が新しいうちのほうが判断しやすい）
- **既存資産の綻びに気づいて黙っていること**。「自分が守れば済む」で流すと、次のセッションの自分が同じところで転ぶ
- **資産があることを根拠に「守られている」と判断すること**。書いてあることと効いていることは別

## なぜ
 
- 繰り返し言われていることは、**言わせている側にコストがある**。書けばその往復が消える
- 気づけるのは会話の中にいる側だけ。ユーザーは「毎回言っている」ことに慣れてしまう
- **ユーザーの発案だけを待つと、資産は増えない。** 何を書けば効くかは、手順を実行している側のほうが見えている
- 一方で、何を常時ロードさせるかは**コンテキストの予算配分**そのもの。勝手に増やすと、本当に効かせたい資産が埋もれる（`rule_conventions.md`）
- 置き場を間違えると効かない。**プロジェクト固有の事情をグローバルへ置くと、関係ないリポジトリでも展開される**。逆に汎用の規約をプロジェクトへ置くと、他のリポジトリで同じ指摘を繰り返すことになる
- 資産の種類と置き場は変わる。統合された置き場へ新規で足すと、**動きはするが正典から外れた資産**が増えていく

## 例外

- ユーザーが「提案は不要」と明示した場合
- ユーザー自身が「ルール化して」「このルールを直して」と言った場合（確認は済んでいるので、そのまま手を入れる）
- その編集に**付随する整理**（参照切れの修正・重複の統合・命名の追随）

## 関連

- `rule_conventions.md`（ルールの書き方と整理）: **作ると決まった後**の書き方と、追加を契機とした棚卸しを規定する。グローバルとプロジェクトの違いもこちら
- `align_skill_md_format.md`（スキルの書き方と整理）: 同上、スキル側
- `verify_before_asserting.md`（断定の前に裏を取る）: 置き場の仕様も裏取りの対象
