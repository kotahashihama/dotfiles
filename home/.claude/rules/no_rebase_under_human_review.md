# 人間のレビューが付いた PR では履歴を書き換えない

ベースブランチの最新を取り込むとき、**人間のレビューコメントが付いている PR は `git merge`**、それ以外は `git rebase` を使ってください。
これは全プロジェクト共通の規約です。

## 使い分け

| 状況 | 取り込み方 |
| --- | --- |
| PR がまだ無い / PR はあるがコメントが**無い** | **`git rebase`**（履歴が直線に保たれる） |
| PR に **AI レビューのコメントだけ**付いている | **`git rebase`**（bot は履歴が変わっても困らない） |
| PR に **ユーザー本人のコメントだけ**付いている | **`git rebase`**（本人は履歴の書き換えを承知している） |
| PR に**他の人のレビューコメント**が付いている | **`git merge`**（履歴を書き換えない） |

**判定するのは「ユーザー本人でも bot でもない人のコメントが 1 件でも付いたか」だけ。** インライン・レビュー本文・PR コメント欄のいずれでも同じで、`[must]` か `[fyi]` かは問いません。

**ユーザー本人のコメントは数えません。** 本人は履歴が書き換わることを承知していますし、自分の PR に自分でメモを残すこともあります。判定は投稿者で行い、`gh api` の `user.login` がユーザー自身か bot かを見て、**どちらでもないものだけを数える**。

**一度 `merge` に切り替えたら、その PR ではマージのまま通す。** 途中で `rebase` に戻すと、結局それまでの履歴が書き換わって同じ問題が起きます。

### レビュー状況とは別に、設定ファイルが競合するなら merge

**`rebase` は片方の変更を黙って捨てることがあります。** コミットを 1 つずつ適用するので、「片側が 1 行足し、もう片側も同じ位置に 1 行足した」形を**衝突と見なさず後勝ち**にする。`merge` は共通祖先を 1 回だけ見るため、同じ箇所が衝突として表に出ます。

| 起きやすい場所 | 例 |
| --- | --- |
| **設定ファイル** | `tsconfig.json` の `compilerOptions`、`package.json` の `scripts` / 依存欄 |
| 短いキーバリューの集まり | ワークフローの `env`、lint 設定の除外リスト |

実際に、5 つのパッケージから設定が 1 行ずつ消えたまま `rebase` が成功し、**衝突表示も出ませんでした**。同じ取り込みを `merge` でやり直したら、その箇所が衝突として現れています。

**双方が同じ設定ファイルを触っているなら、レビューが付いていなくても `merge` を選ぶ。**

**取り込んだ後は、消えていないかを確かめる。** 成功表示は「衝突が無かった」ことしか意味しません。

```bash
git diff <取り込み前のブランチ>..HEAD -- '*/tsconfig.json' '*/package.json'
```

**片側の変更が `-` で消えていたら、それが黙って捨てられたもの**です。

## 禁止する挙動

- 人間のレビューが付いた PR で `git rebase` / `git commit --amend` / `git push --force` を実行すること
- 「コンフリクトが多いから」「履歴が汚いから」を理由に、レビュー中の PR を rebase すること。**読みやすさより、レビュアーが見ている足場のほうが優先**
- レビュー対応のコミットを既存コミットへ `--amend` で潰すこと。**指摘への対応は新しいコミットとして積む**（どう直したかが差分で追える）
- **取り込みが成功したことを、内容が保たれた証拠として扱うこと**。`rebase` は片側の変更を衝突なく捨てうる。設定ファイルの差分を見て確かめる

## なぜ

- **レビュアーが指摘したコミットが消える。** GitHub のレビューコメントは特定のコミットに紐づくので、履歴が変わるとコメントが `outdated` になり、どこへの指摘だったのか辿れなくなる
- **「前回見たところからの差分」が壊れる。** レビュアーは 2 回目以降、前回レビューしたコミットとの差分を見る。履歴が入れ替わると全体を読み直すことになる
- **相手の時間を奪う操作は取り消せない。** レビューをやり直させたことは、履歴を戻しても元に戻らない
- 一方、**自分と bot しか見ていない履歴を整える分にはコストが無い**。だから PR を出す前と、レビューが始まる前の段階では rebase でよい

## 例外

- ユーザーが「rebase して」と明示した場合
- レビュアー自身が「rebase してから見たい」と求めた場合

## 関連

- `no_operating_on_others_prs.md`（他人の PR は触らない）: 判定の軸が違う。あちらは**PR の作成者**、本ルールは**コメントの投稿者**。両方見る
- `no_auto_commit.md`（コミット・プッシュは明示指示のみ）: `--force` 系を独断で実行しないことを規定する。本ルールは**そもそも書き換えてよい場面かどうか**を規定する
- `split_and_stack_prs.md`（スタック化）: `gh stack rebase` は**上段の履歴も書き換える**。上段に人間のレビューが付いていたら使わず、下段のマージ後に `git merge` で取り込む。**PR 間に依存があるかの判定方法**もあちらが持つ
- `karma_commit_style.md`（コミットメッセージ）: 既存メッセージの書き換え手順を持つ。**レビューが始まった PR では実行しない**
