# 実装は契約を先に決め、内側から外側へ積む

機能を実装するときは、まず API 契約（キー名・型・必須/任意・列挙の値）を確定させ、相手のリポジトリのセッションと擦り合わせてから作り始めてください。バックエンドは内側の層（テーブルスキーマ → ドメインモデル → リポジトリ → API）から、フロントエンドは契約の型から作った模したデータから積みます。
これは全プロジェクト共通の規約です。

**機能の実装に取りかかる前に、`~/.claude/references/implement_from_contract_inward_out.md` を読む。** 契約を片方で決めずに擦り合わせる理由、連動して変わる値の伝え方、層ごとのテスト、繋ぎ込み後に模したデータを残すこと、禁止する挙動はそちらにある。

## 関連

- `notify_related_repo_sessions.md` （他リポジトリへの連絡）: **契約を決めたら、相手側へ伝えるところまでが1セット**。決めただけでは相手は動けない
- `verify_before_asserting.md` （断定の前に裏を取る）: 「相手側はもう対応済み」を推測で埋めない
- `write_for_installed_versions.md` （入っているバージョンで書く）: 本ルールは作る順序、あちらは何を使って書くか
- `decide_when_spec_is_silent.md` （仕様が無いところは既存の倒し方に合わせる）: リポジトリを跨ぐ値の形は本ルールの担当。あちらの範囲は、擦り合わせる相手がいない実装の細部に限る
- `/pstack:architect`・pstack の `principle-foundational-thinking` （型と境目を先に描く）: 中身を書く前に型・関数の形・データ構造を決める。本ルールはそれを、契約と層の順に具体化したもの
