# 実装は契約を先に決め、内側から外側へ積む

機能を実装するときは、**まず API 契約を確定**させ、そのうえでバックエンドは内側のレイヤーから、フロントエンドは契約を模したデータから積み上げてください。
これは全プロジェクト共通の規約です。

## まず契約を決める

**リクエストとレスポンスの形を、実装より先に確定して共有する。** キー名・型・必須/任意・列挙の値まで決める。

契約が決まっていないと、**バックエンドが作り終えるまでフロントエンドが動けません**。逆に契約さえあれば、両者は同時に進められます。

**契約は最後に決まるものではなく、最初に決めるものです。** 実装しながら決めると、フロントエンドは「後で覆る形」を前提に作ることになります。

### 片方で決めず、相手セッションと擦り合わせる

**機能を実装するとき、両側のセッションはたいてい同時に立ち上がっています。** 契約は両者の待ち合わせ点なので、**片方が決めて通知するのではなく、決める前に相手へ当てる**。

| | 片方で決めて通知 | 擦り合わせて決める |
| --- | --- | --- |
| 相手の事情 | 決めた後に判明する | **決める前に反映できる** |
| 食い違ったとき | どちらかが作り直す | 決め直すだけで済む |

**相手にしか分からないことがあります。** 画面がその値をどう使うか、1回の表示で何件要るか、どの単位で失敗を出し分けたいか。**コードを読んでも出てこない**ので、聞くしかありません。

**「聞くほどでもない」と思ったときほど当てる。** 確認は1往復ですが、誤った契約で両側が作り込んだ後のやり直しは、それよりずっと高くつきます。

### 値の形だけでなく、実際に起きる組み合わせも伝える

**形が合っていても、何と何が同時に来るかは受け取る側から読み取れません。** 1つの操作が複数の値を連動して変えることは、**出す側の実装にしか書かれていない**からです。

| 伝わるもの | 伝わらないもの |
| --- | --- |
| キー名・型・必須/任意・列挙の値 | **どの組み合わせが実際に飛ぶか** |
| 各項目が単独で取りうる値 | **1回の操作で連動して変わる項目の組** |

受け取る側は、形に沿った表示は作れます。ところが**起きない組み合わせのために作り込み、起きる組み合わせを検証データから落とす**。形だけ渡すと、この抜け方をします。

**連動があるなら名指しで伝える。** 「A を変えると B も一緒に変わる条件がある」の一言で足ります。

送り方と、決めた後に伝えることは `notify_related_repo_sessions.md` が持ちます。**相手セッションが立ち上がっていなければ、ユーザーへ判断を仰ぐ**（同ルールの例外）。

## バックエンド: 内側から外側へ

| 順 | 作るもの | なぜこの位置か |
| --- | --- | --- |
| 1 | **テーブルスキーマ** | 置き場が決まらないと、持ち回る値の形が決まらない |
| 2 | **ドメインモデル** | スキーマの値に意味と不変条件を与える |
| 3 | **リポジトリ** | モデルと保存先を繋ぐ。ここまでで「保存して読み戻せる」 |
| 4 | **API** | 揃った部品を外へ出す |

**API の中は分けて作らない。** 外向きの受け口を書き、**その中で必要になった処理をその場で切り出す**。先に処理だけを揃えると、受け口が要求する形と食い違って作り直しになります。**何が要るかは受け口を書いて初めて分かる**ので、必要になった時点で作るほうが無駄がありません。

**依存の向きと同じ順で作る。** 外側から作ると、内側の形が決まらないまま呼び出し側を書くことになり、内側が決まった時点で書き直しになります。

**各段でテストを書く。** 最後にまとめて書くと、どの層の問題で落ちているのか切り分けられません。層ごとに閉じたテストがあれば、失敗した層がそのまま原因の場所になります。

## フロントエンド: 契約を模したデータから

API がまだ無くても、**契約さえあれば作り始められます**。

| 順 | やること | 注意 |
| --- | --- | --- |
| 1 | **契約を模したデータを用意する** | **契約の型から作る。** 手書きの形で作ると、繋ぎ込みで食い違う |
| 2 | **UI・エラー時・読み込み中を整える** | **どんなエラーが起きうるかは契約から導く** |
| 3 | **API へ繋ぎ込む** | 型が同じなら差し替えだけで済む |
| 4 | **差し替え層を消す** | **データ自体は残す**（下記） |

**エラー時の表示は、契約が返しうるものから導く。** 想像で作ると、**起きない状態のために作り込み、起きる状態を見落とします**。

### 消すのは差し替え層だけ

繋ぎ込みが済んだら、**API を横取りする仕組み**は消します。ただし**用意したデータそのものは捨てない**。

| 消す | 残す |
| --- | --- |
| API を差し替える仕組み・分岐 | データの実体（カタログの表示例・テストの固定値として使う） |

作ったデータは「その画面が扱う代表的な状態の一覧」でもあります。**捨てると、同じものをテストのために作り直すことになります。**

## 禁止する挙動

- **契約を決めずに実装を始めること**。片方が待つか、後で覆る形を前提に作ることになる
- **契約を片方だけで決めて、実装後に通知すること**。相手の事情が反映されず、食い違えばどちらかが作り直しになる
- **値の形だけ渡して、連動して変わる組み合わせを伝えないこと**。受け取る側は起きる組み合わせを検証データから落とす
- **外側から作ること**。内側の形が決まらないまま呼び出し側を書くと、決まった時点で書き直しになる
- **API の中の処理だけを先に揃えること**。受け口が要求する形と食い違い、作り直しになる
- **テストを最後にまとめること**。どの層で壊れたのか切り分けられない
- 模したデータを**契約の型と無関係に手書きすること**。繋ぎ込みが差し替えで済まなくなる
- エラー時の表示を**想像で作ること**。起きない状態に作り込み、起きる状態を落とす
- 繋ぎ込み後に**データごと消すこと**。差し替え層だけ消す

## なぜ

- **契約は両者の待ち合わせ点**。ここが決まれば並行して進められ、決まらなければ必ずどちらかが待つ
- 待ち合わせ点である以上、**決めるのも片方の仕事ではない**。相手にしか分からない事情が必ずあり、それはコードを読んでも出てこない
- 依存の向きに逆らって作ると、**後から決まった内側に合わせて外側を直す**手戻りが必ず出る
- 層ごとのテストは、**失敗した場所がそのまま原因の場所**になる。まとめて書くと切り分けの手間が戻ってくる
- 模したデータは繋ぎ込みで役目を終えるように見えるが、**「起きうる状態の一覧」としての価値は残る**

## 例外

- 既存の契約に乗る変更（フィールドを1つ足すだけ等）は、契約を決める段を実質省いてよい
- 試作・検証目的で、捨てる前提のコードを書く場合
- ユーザーが順序を明示した場合はそれに従う

## 関連

- `notify_related_repo_sessions.md` （他リポジトリへの連絡）: **契約を決めたら、相手側へ伝えるところまでが1セット**。決めただけでは相手は動けない
- `verify_before_asserting.md` （断定の前に裏を取る）: 「相手側はもう対応済み」を推測で埋めない
- `split_and_stack_prs.md` （大きい変更は分ける）: 層ごとに区切ると、そのまま分割の単位になる
- `write_for_installed_versions.md` （入っているバージョンで書く）: 本ルールは**作る順序**、あちらは**何を使って書くか**
