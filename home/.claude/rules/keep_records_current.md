# 変えたら、それを説明している記述も同時に直す

コード・設定・PR を変えると、**それを説明している記述**（PR 本文、補足コメント、ルール、メモリ、ドキュメント）が古くなります。触った領域の記述を、その場で実態に合わせてください。
これは全プロジェクト共通の規約です。

**ズレは変更した本人にしか見えません。** 書いた側は実態を知っているので気づかず、読む側は説明を信じて動きます。

## 触った領域ごとに見るもの

| 触ったもの | 揃えるもの |
| --- | --- |
| **PR にコミットを足した** | 本文の実装内容・テスト内容・影響範囲、自分が投稿した補足コメント |
| **レビュー指摘に対応した** | 同上。**指摘が「説明の誤り」なら、本文の修正が対応そのもの**。既存の挙動に触れたなら影響範囲へ必ず書く |
| **ルール・スキルを編集した** | `## 関連` の参照、他ルールとの矛盾、**同じファイル内で同じ主題を述べている箇所**（例・導入文・手順の箇条書き）、実体の永続化（`ask_before_editing_claude_assets.md`） |
| **メモリを書いた** | ルールとの重複（`rule_conventions.md`）、記述が実装と合っているか、**索引の 1 行が本文と食い違っていないか**（下記） |
| **ドキュメントを直した** | 対になる `.claude/rules` の `paths`、列挙の網羅、参照先の実在 |
| **依存先がマージされた** | 「〜が前提」と書いた箇所。**前提ではなく完了事項**になっている |

### 索引と本文は、読まれる頻度が正反対

**メモリの索引（`MEMORY.md` の 1 行）と本文が食い違うと、誤っている側が勝ちます。** 索引は毎セッション全文が読まれ、**本文は必要なときしか開かれない**ためです。正しい本文があっても、開かなければ効きません。

**本文を直したら、索引の 1 行も直す。** 逆も同じ。要約を短くする過程で条件が落ちやすく、「〜も書かない」が「〜と書く」に反転することがあります。

**同じ非対称は他にもあります。** 常時ロードされるもの（グローバルルール・`CLAUDE.md`・索引）と、呼ばれたときだけ読まれるもの（スキル・`docs/`・メモリ本文）の組は、**すべてこの形**です。

## いつ・どう見るか

**作業の区切りで見る。** 1 行直すたびではなく、一段落した時点。

**ルールを変えたら、`## 関連` に列挙したスキルの例を読み返す。** 同じファイル内を並べても見つかりません。**土台を直した側は、上乗せしているスキルを見に行かない**ためです。辿る先は `## 関連` に既に書いてあります。

**節を足したら、同じ主題を述べている箇所を全部並べて読む。** 主題の語を `grep` し、ヒットした行をまとめて見比べる。1 箇所ずつ読むと、離れた場所にある古い記述に気づけません。

**主題の語は、そのファイルの節タイトルから採る。** 思いつきで選ぶと、語を外したときに空振りしたことにも気づけません。節タイトルはその主題が書かれている場所を指す索引なので、そこから拾えば漏れが減ります。

散らばる先は 3 種類あり、**どれも規定を読み直すだけでは目に入りません**。

| 散らばる先 | 見つけにくい理由 |
| --- | --- |
| **例**（NG / OK） | 規定の説明ではなく**実例**なので、規定を読み返す動きでは通らない |
| **節の導入文** | その節が何を言うかを述べただけの 1 行なので、読み飛ばす |
| **手順の箇条書き** | 別の節にあり、主題が同じでも並べて読まない |

**実行する側は規定より例と手順に従う。** 古いまま残っていると、規定を直しても振る舞いは変わりません。

**記憶で判断しない。** 書いたときは正しくても、その後の変更でズレます。数値は数え（`ls | wc -l`）、識別子は `grep` で実在を確かめ、状態は API で引く。伝聞で書き直さない（`verify_before_asserting.md`）。

PR に push したなら、本文と差分の食い違いを確認し、ズレていれば `/update-pr-description` で直す。**差分が動いたら AI レビューを回すかをユーザーに尋ねる**——1 周ごとに課金されるので、自動では回さない。

**自分の操作で CI やレビューが走ったら、結果を見るまでが 1 セット。** 尋ねるのは「回すかどうか」だけで、**走った後の確認は尋ねずにやる**。走らせただけで放置すると、指摘が残ったまま「終わった」と報告することになります。

| 起こした操作 | 走るもの | 確認すること |
| --- | --- | --- |
| push | CI | 失敗が**コード起因か承認待ちか** |
| **ready 化 / draft 解除** | **AI レビュー**（open 契機で自動実行される設定がある） | 新規指摘の有無。**既存の resolve 済みと混ざるので ID で照合する** |
| `/ai-review` の投稿 | AI レビュー | 同上 |

## 判断が覆ったときは、書き換えずに残す

**古くなった記述は直しますが、判断が覆ったときは別です。** 書き換えると、**訂正したこと自体が消えます**。

| 対象 | 覆ったとき |
| --- | --- |
| **事実の記述**（実装内容・テスト・影響範囲・CI の状態） | **直す。** 古い記述に価値は無い |
| **判断とその根拠**（採否・見送り・方針） | **残す。** 前を畳み、**新しい判断は別コメントで投稿する** |

**「前の判断を訂正します」と書いても、前が残っていなければ通じません。** 読み手には何のことか分からず、判断が動いた経緯も追えない。

### 残し方

**前のコメントは編集せず、GitHub の Hide comment で `Outdated` としてマークする。**
折りたたまれたうえで「marked as outdated」と表示され、**開けば当時の内容がそのまま読めます**。

```bash
gh api repos/OWNER/REPO/issues/comments/<id> --jq '.node_id'
gh api graphql -f query='mutation($id: ID!) { minimizeComment(input: {subjectId: $id, classifier: OUTDATED}) { minimizedComment { isMinimized } } }' -F id=<node_id>
```

**新しい判断は新規コメントとして投稿する。** 上から読めば「こう考えた → 覆った → こうなった」の流れが辿れます。

**新しい側から、前のコメントへリンクを貼る。** 畳まれている分、リンクが無いと**読み手が探しに行くことになります**。

```markdown
**[前のコメント](https://github.com/OWNER/REPO/pull/123#issuecomment-456)で〜と判断していましたが、それを訂正します**
```

コメントの URL は `gh api` の応答の `html_url`、または GitHub 上のコメントメニューの `Copy link` で取れます。

**`<details>` で自作しない。** GitHub の機能を使えば、**覆ったことが一目で分かる形**で表示されます。
自作すると、開くまで何が覆ったのか分からない見た目になります。

**調査の内容は消さない。** 結論が覆っても、**何を見て何が分かったか**は次に同じ壁へ当たった人の手がかりになります。

**うっかり上書きしてしまったら、編集履歴から戻せます。** GitHub はコメントの版を保持しています。

```bash
gh api graphql -f query='query($id: ID!) { node(id: $id) { ... on IssueComment { userContentEdits(first: 20) { nodes { editedAt diff } } } } }' -F id=<node_id>
```

## 禁止する挙動

- **自分が直した箇所だけ直して終えること**。それを説明している記述まで見る
- ズレに気づいて「今回のスコープ外」で流すこと。**1〜2 行の訂正なら、その場が最も安い**
- **覆った判断を書き換えて消すこと**。訂正した事実ごと消える。前は `Outdated` で畳み、新しい判断は別コメントにする
- 数値・件数・状態を**記憶で書き直すこと**
- **本文だけ直して索引を放置すること**。毎セッション読まれるのは索引のほうで、食い違えば誤りが勝つ
- 差分を動かしたのに**AI レビューを黙って回すこと**（課金が発生する）
- **自分が起こした CI / レビューの結果を見ずに完了と報告すること**。走らせたら結果まで見る
- **未返信の件数だけで新規指摘を判定すること**。resolve 済みもトップレベルとして残るので、**ID で既知のものと突き合わせる**

## なぜ

- 説明と実態がズレると、**読み手はどちらが正しいか判断できない**。両方を疑うことになり、書いてある意味が失われる
- 直すコストは時間とともに上がる。**変更した瞬間が最も安い**。後から直すには、何がどう変わったかを思い出す作業が要る

## 例外

- ユーザーが「今は触らないで」と明示した場合
- 大きな書き換えが要るズレは、**指摘までに留めて指示を待つ**。その場で直すのは 1〜2 行で済むものだけ

## 関連

- `verify_before_asserting.md`（断定の前に裏を取る）: あちらは**書くとき**、本ルールは**書いた後の鮮度**を扱う
- `ask_before_editing_claude_assets.md`（設定は尋ねてから）: 触る**前**に尋ねる側。本ルールは触った**後**の鮮度
- `/update-pr-description`（PR 本文と補足コメントの更新）: PR 側の実行手段
- `/list-prs`（PR 一覧）: 腐った参照をまとめて検出できる
- `verify_merge_with_checks.md`（マージは検査を通すまで終わっていない）: マージで差分が動いたら、本ルールの対象になる
- `no_guesswork_in_records.md`（記録に推測を混ぜない）: あちらは**確かさ**、本ルールは**鮮度**。どちらも記録が信用できる状態を保つ
- `no_instruction_echo_in_output.md`（成果物に指示を書かない）: あちらは**そもそも書かないもの**、本ルールは**書いたものを実態に合わせ続けること**
