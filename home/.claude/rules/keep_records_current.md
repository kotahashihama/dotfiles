# 変えたら、それを説明している記述も同時に直す

コード・設定・PR を変えると、それを説明している記述（PR 本文、補足コメント、ルール、メモリ、ドキュメント）が古くなります。触った領域の記述をその場で実態に合わせてください。
これは全プロジェクト共通の規約です。

**ズレは変更した本人にしか見えません。** 書いた側は実態を知っているので気づかず、読む側は説明を信じて動きます。

## 触った領域ごとに見るもの

| 触ったもの | 揃えるもの |
| --- | --- |
| PR にコミットを足した | 本文の実装内容・テスト内容・影響範囲、自分が投稿した補足コメント |
| レビュー指摘に対応した | 同上。指摘が「説明の誤り」なら、本文の修正が対応そのもの。既存の挙動に触れたなら影響範囲へ必ず書く |
| ルール・スキルを編集した | `## 関連` の参照、他ルールとの矛盾、同じファイル内で同じ主題を述べている箇所（例・導入文・手順の箇条書き）、実体の永続化（ `ask_before_editing_claude_assets.md` ） |
| メモリを書いた | ルールとの重複（ `rule_conventions.md` ）、記述が実装と合っているか、索引の1行が本文と食い違っていないか（下記） |
| ドキュメントを直した | 対になる `.claude/rules` の `paths`、列挙の網羅、参照先の実在 |
| 依存先がマージされた | 「〜が前提」と書いた箇所。前提ではなく完了事項になっている |
| 経緯のコメントを残した PR を変えた | 課題管理ツール側のコメント。見る先は PR 本文が指している（下記） |

### 課題管理ツール側のコメントは、視界の外で古くなる

**PR を見ている間、課題のコメントは目に入りません。** 別のツールなので、差分を読んでも本文を直しても、そこへ辿り着く動きが起きない。

実際に、ある PR で仕様を変えた（利用者が入力した値を上書きする形をやめた）とき、課題側へ残した経緯のコメントだけが古いまま残りました。気づいたのは push の直後ではなく、後からユーザーに尋ねられたときです。

**見る先は PR 本文が指しています。** Backlog 節へ経緯のコメントの URL を1行足す規定があるので（ `karma_commit_style.md` ）、その行があれば対象が決まります。無ければ、そもそも経緯を残していないか、相互参照が欠けています。

直し方は `/update-backlog-comments` が持ちます。投稿先の書式の検査が走らないこと・編集と追記の使い分け・長さの測り方は、そちら。

### 索引と本文は、読まれる頻度が正反対

**メモリの索引（ `MEMORY.md` の1行）と本文が食い違うと、誤っている側が勝ちます。** 索引は毎セッション全文が読まれ、本文は必要なときしか開かれないためです。正しい本文があっても、開かなければ効きません。

**本文を直したら、索引の1行も直す。** 逆も同じ。要約を短くする過程で条件が落ちやすく、「〜も書かない」が「〜と書く」に反転することがあります。

同じ非対称は他にもあります。常時ロードされるもの（グローバルルール・`AGENTS.md`・索引）と、呼ばれたときだけ読まれるもの（スキル・`docs/`・メモリ本文）の組は、すべてこの形です。

PR 本文と補足コメントも同じ形です。読み手の違いは `/update-pr-description` の「本文は軸、細部は別コメント」が定めており、食い違えば本文の側が勝ちます。

ただし向きが対称ではありません。索引と本文は互いの要約ですが、PR では本文がコメントの要約なので、落ちるのはいつもコメント側の条件です。直すのは「落ちた例外を本文へ戻す」か「例外があることを本文に1語残す」のどちらか。

実際に、本文の根拠の表へ「応募の履歴を持つ選考は1件もありません」と書き、同じ PR の補足コメントには263件と書いてありました。

## いつ・どう見るか

作業の区切りで見る。1行直すたびではなく、一段落した時点。

ルールを変えたら、`## 関連` に列挙したスキルの例を読み返す。同じファイル内を並べても見つかりません。土台を直した側は、上乗せしているスキルを見に行かないためです。辿る先は `## 関連` に既に書いてあります。

節を足したら、同じ主題を述べている箇所を全部並べて読む。主題の語を `grep` し、ヒットした行をまとめて見比べる。1箇所ずつ読むと、離れた場所にある古い記述に気づけません。

**同じ主題を複数の文書で扱っているなら、この見直しを文書の外へ広げる。** 1つを直したら、残りの文書も主題の語で引いて見直します。結論をまとめた文書と、その材料を置いた文書（課題の `[fyi]` と `[memo]` など）は、片方に足した内容がもう片方の表や条件に入らないまま残りやすい。指摘を受けた箇所だけを直すと、指摘された文書の外は見ないことになります。

実際に、比較の対象を2つ足したとき、結論のコメントの表と順位には入れたのに、条件を並べた別の memo の表には入れていませんでした。足した1つは自社の環境で動かせるモデルで、「社外へ送れない」場合の答えが変わる内容です。ユーザーに「指摘しなくても改善できるところはそうして」と言われて見直すまで、気づいていません。

主題の語は、そのファイルの節タイトルから採る。思いつきで選ぶと、語を外したときに空振りしたことにも気づけません。節タイトルはその主題が書かれている場所を指す索引なので、そこから拾えば漏れが減ります。

その節が何かと対比しているなら、相手の語も採る。「〜と紛らわしいですが別です」と書いた時点で、相手もその節の主題です。節タイトルには出てこないので、そこからだけ拾うと落ちます。

実際に、足した節の主題（ `否定` ）は引いたのに対比の相手（ `対句` ）を引かず、同じファイルの43行上にある定義と矛盾したまま投稿しました。

散らばる先は3種類あり、どれも規定を読み直すだけでは目に入りません。

| 散らばる先 | 見つけにくい理由 |
| --- | --- |
| 例（NG / OK） | 規定の説明ではなく実例なので、規定を読み返す動きでは通らない |
| 節の導入文 | その節が何を言うかを述べただけの1行なので、読み飛ばす |
| 手順の箇条書き | 別の節にあり、主題が同じでも並べて読まない |

**実行する側は規定より例と手順に従う。** 古いまま残っていると、規定を直しても振る舞いは変わりません。

記憶で判断しない。書いたときは正しくても、その後の変更でズレます。数値は数え（ `ls | wc -l` ）、識別子は `grep` で実在を確かめ、状態は API で引く。伝聞で書き直さない（ `verify_before_asserting.md` ）。

PR に push したなら、本文と差分の食い違いを確認し、ズレていれば `/update-pr-description` で直す。差分が動いたら AI レビューを回すかをユーザーに尋ねる。1周ごとに課金されるので、自動では回さない。

**自分の操作で CI やレビューが走ったら、結果を見るまでが1セット。** 尋ねるのは「回すかどうか」だけで、走った後の確認は尋ねずにやる。走らせただけで放置すると、指摘が残ったまま「終わった」と報告することになります。

| 起こした操作 | 走るもの | 確認すること |
| --- | --- | --- |
| push | CI | 失敗がコード起因か承認待ちか |
| ready 化 / draft 解除 | AI レビュー（open 契機で自動実行される設定がある） | 新規指摘の有無。既存の resolve 済みと混ざるので ID で照合する |
| `/ai-review` の投稿 | AI レビュー | 同上 |

## 後から分かった事実は、過去のコメントへ遡って入れない

**時点を残すコメントは、書いた時点の記録です。** 経緯の報告や締めた調査の結果のように、時系列に積んでいくコメントがこれに当たります。後から分かった事実は新しいコメントに書き、前のコメントへ遡って反映しません。全部を同期させ続けることはできないためです。

| 書いた先 | 後から分かった事実 |
| --- | --- |
| 今の状態を説明する文書（PR 本文・自分の補足コメント・ルール・ドキュメント） | 直す（上記「触った領域ごとに見るもの」） |
| 進行中の調査の memo（今の結論を示すもの） | 直す。新しいコメントを積まない（下記「進行中の調査の memo は、書き換えて1つに育てる」） |
| 時点を残すコメント（経緯の報告・締めた調査の結果） | 新しいコメントに書く。前のコメントは直さない |

遡って直すのは、次の3つに当たるときだけです。

| 直す場合 | 例 |
| --- | --- |
| 書いた時点で既に誤っていた | 確かめていないことを言い切っていた |
| コメントどうしの参照が切れた | 前のコメントを書き換えて、後のコメントが引いていた記述が消えた |
| 古いまま読まれると、誤った行動につながる | 手順や前提を書いたコメントで、その手順が使えなくなった（上記「課題管理ツール側のコメントは、視界の外で古くなる」） |

**判定は「後から分かったことか、書いた時点の誤りか」。** 前者は新しいコメントで足り、後者は直す。

実際に、1つの課題に3件の memo を積んだあと、全部を最新の事実に揃えるかを確かめました。直したのは、書いた時点で推定を言い切っていた箇所と、前の memo の書き換えで参照先が消えた1行だけです。ただしこの調査はまだ進行中で、memo はその後7件まで増え、下記「進行中の調査の memo は、書き換えて1つに育てる」のとおり2件へまとめ直しています。

**最新の事実が後続のコメントで読めるなら、前のコメントは古いままでよい。** 遡って直すと、事実が分かるたび・方針が変わるたびに過去のコメントを直すことになり、更新が積み上がります（更新負債）。書いた時点の記録には、そのとき何を根拠に何を判断したかが残るので、記録として残すこと自体にも価値があります。

**直すときも、後から分かった事実を混ぜない。** 書いた時点の誤りを直していると、同じ文へ新しい事実も足したくなります。実際に、推定の印を付ける直しのついでに、後のコメントで出した比較表の構成数を括弧で書き足し、指摘を受けて元の文面へ戻しました。

### 書いて間もないなら、元のコメントを直す

上の扱いは、時間が経ったコメントのためのものです。書いて間もないコメントへの追記は、元のコメントを直すほうが読み手の手間が少ない。

**手がかりを組み合わせて決める。** どれか1つを閾値にしません。

| 手がかり | 元のコメントを直す | 新しいコメントに書く |
| --- | --- | --- |
| 経った時間 | 短い（数時間、当日のうち） | 長い（日をまたいだ） |
| 作業の区切り | 同じ区切りの中 | 調査や実装を「終わり」と締めた、PR を出し直した |
| 内容 | 前の内容の延長（表に行が増える） | 判断や方針が変わった |
| 読まれた痕跡 | 無い | 誰かが読んで動いた可能性がある |

判断や方針が変わったときは、時間が短くても新しく書きます。**迷ったら新しく書く。** 新しく書きすぎてもコメントが1件増えるだけですが、直しすぎると時点の記録が消えます。

実際に、1つの課題で調査の結果を、締めたあとに追加で照らした分を別のコメントに書きました。1件へまとめ直すかを尋ねたところ、「最新の情報が後続のコメントでアップデートされているのならば残しておいてもいい」「書いた時点の記録として残ってるのも重要」と言われています。一方で「そんなに時間が経ってないから元のコメントを更新することで済ませたいものもある」とも言われ、時間で区切るのも「ときにはあり」です。

### 進行中の調査の memo は、書き換えて1つに育てる

**調査が終わるまで、読み手はその memo を今の結論として読みます。** 事実が分かるたびにコメントを足すと、どれが最新の結論かを読み手が組み立てることになります。

実際に、1つの課題へ調査の memo を足し続けて7件になり、「まとめられなかったの？」と指摘を受けました。調べた結果の memo と、方針と社内で決めることの memo の2件へまとめ直しています。

**判定は「その memo が今の結論として読まれているか」。** 読まれているなら、既に読まれた後でも書き換えて育てる。下記「まだ誰も読んでいない投稿は、書き換える」は読まれた痕跡で判定しますが、こちらは memo の役割で判定します。

育てる memo でも、判断（採否・見送り・方針）が覆ったときは下記「判断が覆ったときは、書き換えずに残す」に従います。書き換えてよいのは事実と、事実が増えて変わった数値や試算です。調査を締めたら、以降は時点を残すコメントとして扱います。

## 判断が覆ったときは、書き換えずに残す

**古くなった記述は直しますが、判断が覆ったときは別です。** 書き換えると訂正したこと自体が消えます。

| 対象 | 覆ったとき |
| --- | --- |
| 事実の記述（実装内容・テスト・影響範囲・CI の状態、別 PR へ出し直した・閉じた・分けた） | 直す。古い記述に価値は無い |
| 判断とその根拠（採否・見送り・方針） | 残す。前を畳み、新しい判断は別コメントで投稿する |

「前の判断を訂正します」と書いても、前が残っていなければ通じません。読み手には何のことか分からず、判断が動いた経緯も追えない。

判定の単位は記述ごとで、コメント単位ではありません。1つのコメントに事実と判断が混ざっていたら、事実の部分だけ書き換えます。

**迷ったら残す側に倒す。** 事実を残しすぎても畳まれたコメントが1つ増えるだけですが、判断を書き換えると訂正した事実ごと消えます。

### まだ誰も読んでいない投稿は、書き換える

上の表は、その投稿が既に読まれていることを前提にしています。読まれていないなら残すべき経緯がまだ存在しません。畳んで残しても、読み手には知らない判断が1つ畳まれているとしか見えない。

**中身が事実か判断かより先に、こちらを見る。** 誰も読んでいない段階では、判断であっても書き換えてよい。

読んだかどうかは分からないので、読んだ痕跡のほうを見る。

| 痕跡 | 確かめ方 |
| --- | --- |
| リアクションが付いている | `gh api repos/OWNER/REPO/pulls/comments/<id>/reactions` |
| 後続のコメントが付いている | `in_reply_to_id` がその ID のものを数える |
| スレッドが Resolve されている | GraphQL の `reviewThreads` で `isResolved` を見る |

**3つとも無ければ、元の投稿を書き換える。** 1つでもあれば、上の表のとおりに扱う。

追記にすると、読み手は消えた前提を追うことになります（「先程〜と書きましたが」）。誰も読んでいないならその往復ごと省ける。

**要らなくなった投稿は削除する。** ほかの投稿へまとめた・取り下げたものが該当します。「こちらにまとめました」のような経緯は書きません。誰も読んでいないので、伝える相手がいないためです。

提出済みのレビューのように削除できないもの（API が `Can not delete a non-pending pull request review` を返す）は、本文を生成者表示だけにし、用途に合う理由で畳む。まとめた先があるなら `Duplicate`、内容が古くなったなら `Outdated`、片付いたなら `Resolved` を選ぶ。

投稿してよい場面かどうかは、この節では決めません（ `responding_to_reviews.md` ）。ここが扱うのは、投稿済みのものをどう直すかだけです。

### 残し方

前のコメントは編集せず、GitHub の Hide comment で `Outdated` として畳み、新しい判断は新規コメントで投稿して前のコメントへリンクを貼る。調査の内容は消さない。手順（GraphQL の呼び方・編集履歴からの戻し方）は `/update-pr-description` の `references/multi-pr.md` が持ちます。

## 既存の環境だけに要る手順は、恒久的な文書に書かない

README や手順書は、これから環境を作る人が読みます。移行のために既存の環境だけが1回打つ手順（旧コンテナの削除・残骸の片付け）は、周知や PR の本文へ置き、恒久的な文書からは外す。

**判定は「新しく環境を作る人に要るか」。** 要らないなら移行が済んだ時点で誰も読まない行になります。

自動化も同じ基準で決めます。既存の環境のためだけの自動化（旧コンテナを片付けるフラグ・残骸を隠す除外設定）は入れず、周知で済ませる。

実際に、開発環境の構成を寄せる変更で、旧コンテナの片付けを起動コマンドへ、残骸の除外を `.gitignore` へ、消し方を README へ入れました。どれも既存の環境のためだけのもので、周知へ移して外しています。

## 課題管理ツールには、PR のマージの状態を書かない

**課題の本文やコメントに「マージ済み」「main に入った」と書かない。** 状態は PR を開けば分かります。書くと、PR がマージされるたびに直す記述が増えます。

| 書かない | 書いてよい |
| --- | --- |
| 「#123（マージ済み）」「10/27に main へ入った」 | 「#123 を #124 より先に main へ入れる」（順番） |
| 「QA 待ち」「レビュー中」のような PR の状態 | 「#123 がマージされた後に出す」（マージの前に満たす条件） |

**判定は「その PR がマージされても、書き直さずに済むか」。** 順番とマージの前の条件は、マージの前後で意味が変わらないので書いてよい。

上の「触った領域ごとに見るもの」の「依存先がマージされた」の行は、PR の本文の話です。課題管理ツールの記述は、順番の書き方のまま直しません。

実際に、課題の PR の表に「マージ済み」と書き、PR がマージされるたびに表を直していたところ、「マージされるたびに更新しなきゃいけないコメントになってしまう」と言われました。

## 課題管理ツールの外で決まったことも、課題に残す

**チャットや口頭、会議で決まったことも、その課題へコメントで残す。** 課題を開けば今の状況が分かる状態を保つためです。決まった場にいなかった人（後から担当する人・QA の担当者・PO）は、課題しか見ません。

| 残すもの | 例 |
| --- | --- |
| リリースの扱い | 「今回のリリースから外す」「次のリリースで出す」 |
| 方針と範囲の変更 | 「PO の確認を通してから出す」「〜は別の課題で扱う」 |
| ほかの課題との順番とまとめ方 | 「〜を戻す PR は、この課題の PR の上に重ねる」 |

**判定は「その場にいなかった人が、課題だけを読んで今の状況と次にすることを言えるか」。**

書くのは、決まった中身とそれで変わる次の手です。誰が言ったか、どこで決まったかは書きません（ `github_writing.md` の帰属の節）。マージの状態を書かないのは上の節のとおりで、「リリースから外す」は状態ではなく決まった方針なので書いてよい。

実際に、ある課題をリリースから外すことがチャットで決まり、外すための PR まで作りましたが、課題には何も残していませんでした。ユーザーに「課題を見れば状況が分かるようにすべき」と言われ、決まったことと、入れ直すときに要ることを `[fyi]` で残しています。

## 禁止する挙動

- **自分が直した箇所だけ直して終えること**。それを説明している記述まで見る
- ズレに気づいて「今回のスコープ外」で流すこと。1〜2行の訂正なら、その場が最も安い
- **覆った判断を書き換えて消すこと**。訂正した事実ごと消える。前は `Outdated` で畳み、新しい判断は別コメントにする
- 後から分かった事実を、時点を残す過去のコメントへ遡って入れて回ること。新しいコメントに書く。直すのは書いた時点の誤り・切れた参照・誤った行動につながる古い記述だけ
- 進行中の調査で、事実が分かるたびに memo を積み足すこと。今の結論を示す memo を書き換えて育てる
- まだ読まれていない投稿まで、畳んで残すこと。残すべき経緯がまだ無く、読み手には知らない判断が畳まれているとしか見えない
- 数値・件数・状態を記憶で書き直すこと
- 本文だけ直して索引を放置すること。毎セッション読まれるのは索引のほうで、食い違えば誤りが勝つ
- PR 側だけ直して、課題管理ツールのコメントを放置すること。別のツールなので視界に入らず、後から読む人はどちらが正しいか判断できない
- 差分を動かしたのに AI レビューを黙って回すこと（課金が発生する）
- 自分が起こした CI / レビューの結果を見ずに完了と報告すること。走らせたら結果まで見る
- 未返信の件数だけで新規指摘を判定すること。resolve 済みもトップレベルとして残るので、ID で既知のものと突き合わせる
- 既存の環境だけが1回打つ移行の手順を、README や手順書に書くこと。周知や PR の本文へ置く
- 課題管理ツールの本文やコメントに、PR のマージの状態を書くこと。マージのたびに直す記述になる。順番とマージの前の条件で書く
- チャットや口頭で決まったことを、課題に残さないこと。その場にいなかった人は課題しか見ない

## なぜ

- 説明と実態がズレると、読み手はどちらが正しいか判断できない。両方を疑うことになり、書いてある意味が失われる
- 直すコストは時間とともに上がる。変更した時点が最も安い。後から直すには、何がどう変わったかを思い出す作業が要る

## 例外

- ユーザーが「今は触らないで」と明示した場合
- 自分の変更を説明していない記述で、大きな書き換えが要るズレは、指摘までに留めて指示を待つ。自分の変更を説明する記述（PR 本文・自分の補足コメント）は、行数によらずその場で直す

- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: 触る前に尋ねる側。本ルールは触った後の鮮度

- `/update-backlog-comments` （課題管理ツールのコメントの点検と更新）: 課題側の実行手段。過不足・実態とのずれ・読みやすさを測る
- `/list-prs` （PR 一覧）: 古くなった参照をまとめて検出できる
- `verify_merge_with_checks.md` （マージは検査を通すまで終わっていない）: マージで差分が動いたら、本ルールの対象になる
- `recheck_after_every_revision.md` （書き直すたびに全体を確かめ直す）: 本ルールは実態とのズレ、あちらは出どころとのズレ。触っていない箇所でも後者は起きる
- `base_records_on_measurements.md` （記録は実測に基づける）: あちらは確かさ、本ルールは鮮度。どちらも記録が信用できる状態を保つ
- `no_instruction_echo_in_output.md` （成果物に指示を書かない）: あちらはそもそも書かないもの、本ルールは書いたものを実態に合わせ続けること
- `code_comments.md` （移ろう理由は PR へ）: 時間が経つと要らなくなる記述を恒久的な置き場から外す、という同じ形。あちらはコードコメント、本ルールの「既存の環境だけに要る手順」は README と手順書
- `explain_from_observables.md` （観測できるものから始める）: どちらも文書をまたぐ。本ルールは片方に足した内容をもう片方へ揃えること、あちらの「抜き出して組み立てた文書では、定義と前提を開き直す」は抜き出すときに定義と前提を持っていくこと
- `decide_when_spec_is_silent.md` （仕様が書かれていないところは既存の倒し方に合わせる）: 仕様から外れて実装したときは、仕様の記述を直さず、違う点を課題と PR に別に残す。本ルールは実態に合わせて記述を直す側
