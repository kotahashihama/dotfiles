# 各作業後に簡潔かつ噛み砕いたサマリを添える

**あらゆる作業単位**が一区切り終わった時点で、何をどう行ったかを **簡潔かつ噛み砕いたサマリ**
で伝えてください。実装・編集だけでなく、調査・レビュー・PR チェック・
コメント対応・スキル起動 (`/resolve-ai-reviews`, `/finalize-pr` 等) 等の
「書かない作業」も含みます。
これは全プロジェクト共通の規約です。

## 対象となる「作業」

「1つの目的を持ってひとまとまりで実行したもの」すべて。

- 書く作業: 実装コードの追加・修正・削除、リファクタ・改名・ファイル分割、ドキュメント/スキル/ルール作成
- **読む・調べる作業**: コードベース調査、レビューコメント精読、規約確認、ログ解析
- 判断する作業: レビュー結果のトリアージ、bot 指摘の対応可否判定、設計方針の検討
- 外部操作を伴う作業: `/cp` によるコミット・プッシュ、`/resolve-ai-reviews` による返信・resolve、PR 説明更新
- 一連の関連作業（例: interface 変更 + 実装追随 + テスト追随 + Registry 配線 + コミット）が一段落した直後
- ユーザーからの質問への調査・回答を終えたタイミング

## 期待する挙動

1. 各作業のあとで区切る: 作業単位が終わった時点で1度サマリを出す
2. 粒度: 何を対象にしたか / どう行ったか / 結果として何が変わったか・分かったかを噛み砕く
3. 簡潔さ: 差分の羅列や実行ログの再掲ではなく、意図と結果を短くまとめる
4. 平易な表現: 技術用語は必要に応じて噛み砕く（BE/インフラの技術説明は特に）
5. 配置: 作業直後、付帯報告 (テスト実行結果・コミットハッシュ等) よりも上か直後に、独立した区切りとして置く
6. **手が要るものが残っているかを、出力の最後に1行で書く**（下記）

## 終わったかどうかを、最後の1行で示す

状態を並べただけでは伝わりません。表や一覧を読んだ人は「これで全部か」を自分で組み立てることになります。

| 状態 | 最後の1行 |
| --- | --- |
| 全部終わった | 「もう積み残しはありません」「これで作業はひと段落です」 |
| 待ちがある | 「残りは〇〇の返信待ちです」。何を待っているか名指しする |
| 判断が要る | 「〇〇の判断だけ残っています」 |

**区別するのは「終わった」と「待ちがある」。** どちらも手を動かしていない状態なので、書かないと同じに見えます。

出力の最後に置く。途中に書くと、その後の記述で埋もれます。

### 積み残しに数えるのは、自分の作業だけ

「積み残しなし？」は、Claude Code の作業に残りがあるかを聞いています。ユーザーの仕事は数えません。

| 数える | 数えない |
| --- | --- |
| 自分が流している検査の回収、本文の差し替え、後片付け | draft の ready 化・レビューの依頼・マージ（ユーザーの仕事） |
| 自分の作業を進めるのに要る、ユーザーの判断 | 自分の作業と関係なく、ユーザーがいつか決めること |

「判断が要る」の行に書くのは、その答えが無いと自分の作業が進まないものだけです。ready 化を判断待ちとして並べると、尋ねていなくても可否を聞いた形になります（ `no_auto_ready_pr.md` ）。

実際に「積み残しなし？」への答えに draft の ready 化を残りとして並べ、「それは私の仕事なので含めないで」と言われました。

### 「終わった」と書く前に、自分の報告から未検証と残した状態を拾う

**自分で書き出したものを、言い換えて完了に数えない。** 「確かめていない」「残っている」と書いた項目は、どれも「終わった」の反証です。

| 拾うもの | 例 | 扱い |
| --- | --- | --- |
| 未検証の項目 | 「〜の順序が必要かは確かめていない」 | 自分で確かめられるなら、確かめてから報告する |
| 作業で残した状態 | 切り替えたブランチ・作り直したコンテナ・置いたファイル | 作業前の状態へ戻してから報告する |
| 片付けられないもの | 相手の返事・ユーザーの判断 | 「待ちがある」「判断が要る」の行で書く |

実際に、未検証の手順と未追跡のファイルを報告の中に並べたまま「このセッションの残作業はありません」と締めました。「相手が今の順で書くと決めた」「置いたままで問題ない」と言い換えていたためで、ユーザーに「たしかめてよ」「後始末もしようよ」と言われてから片付けています。

**判定は「その項目を、自分の手で今片付けられるか」。** 片付けられるなら、終わっていません。

`block-pointless-stop.sh` が、完了の言い回しと未検証・残置の言い回しが同じ応答に並んだ形を1回差し戻します。言い回しを変えれば通るので、判定の本体は本節が持ちます。

## 禁止する挙動

- 差分や実行ログだけを機械的に列挙してサマリなしで終わる（ユーザー側で解釈させる形にしない）
- 「〜を修正しました」「〜を確認しました」の一言で済ませて **意図と結果** に触れない
- 差分と関係のない話（今後の予定・次のタスク案・懸念点の再説明）でサマリを埋める
- サマリ節を省略して直接コミット・push 報告や次アクションに飛ぶ
- **終わったかどうかを書かずに締めること**。状態の一覧だけ置くと、読み手が「これで全部か」を組み立てることになる
- **未検証の項目や残した状態を自分で書き出しながら「終わった」と締めること**。自分で片付けられるものは、片付けてから報告する

## テンプレート例

```markdown
## 変更サマリ / 調査サマリ / 対応サマリ 等

**目的**: [なぜこの作業をしたか - 1 行]

**やったこと**:
- [対象/領域 A] を [どう処理したか]
- [対象/領域 B] を [どう処理したか]

**結果**: [変更後にどう振る舞うようになったか / 何が分かったか / 何が決まったか - 1〜2 行]
```

粒度が小さい場合は3〜5行のパラグラフでもよい。テンプレート厳守ではなく **簡潔・噛み砕き・意図と結果** の3点さえ揃っていれば形式は問わない。

## なぜ

- ユーザーは大量の tool 出力・差分・ログを追いきれない。**サマリなしだと「結局何が起きたか」を再構築するコストがユーザー側に発生する**
- 「〜しました」の一言では、意図・影響範囲・副次効果・判断根拠が伝わらない
- 作業直後は書いた側が最も文脈を持っているタイミングで、要約の質が高い
- コミットメッセージや PR 説明とは別の役割: そちらは "成果物としての恒久記録"、こちらは "その場の対話コンテキストでの区切り"

## 例外

- ユーザーが「サマリ不要」「差分だけ出して」「短くて OK」と明示指示した場合はそれに従う
- 1行の typo 修正・1コマンドの確認結果など、意図と結果が自明な微小作業ではスキップしてよい
- 会話の質問応答のみで実行を伴わない場合は対象外（そもそも作業ではない）

## 関連

- `focus_insights_on_judgment.md` （洞察は判断材料に絞る）: サマリは「何をしたか」、あちらは「**なぜそう決めたか**」。**実装を代行したときは、捨てた選択肢と固有の制約もあちらの対象**
- `plain_language_explanation.md` （技術説明の噛み砕き）と併用する。特に BE/インフラの変更は平易さを優先
- `concise_first_then_detail.md` （結論ファースト・全体簡潔）と併用: サマリ自体も結論から
- `report_formatting.md` （報告に貼る識別子の書式）と併用: サマリ内でハッシュや URL を示す際も同様
- `verify_the_check_worked.md` （検査が成立していたかを疑う）: 「壊して確かめたら、戻ったことを確かめてから離れる」は、本ルールの「作業で残した状態」の一形態。あちらは検査のための改変、本ルールは作業全般で残した状態
- `decide_or_ask.md` （確認が要らないなら止まらない）: どちらも `block-pointless-stop.sh` が形で差し戻す。あちらは許可を待って止まる形、本ルールは片付けずに終わったと書く形
- `no_auto_ready_pr.md` （レビュー依頼は明示指示のみ）: ready 化はユーザーの仕事なので、本ルールの積み残しにも数えない。あちらは実行しないこと、本ルールは報告に並べないこと
