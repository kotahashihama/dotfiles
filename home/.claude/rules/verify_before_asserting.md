# 断定する前に一次情報で裏を取る

「〜は非推奨」「〜が仕様」「〜はこう動く」のような**事実の断定**をドキュメント・コード・PR 説明・コミットメッセージに書く前に、**一次情報で裏を取って**ください。
これは全プロジェクト共通の規約です。

## 裏取りが要る発言

- **仕様・挙動の断定**: 「commands は非推奨」「このオプションはこう効く」「この API はこれを返す」
- **他リポジトリ・他チームの状態**: 「BE はもう対応済み」「あの PR はマージされた」
- **バージョン・移行の状況**: 「v2 から使えない」「この記法は廃止された」

## 期待する挙動

1. **一次情報を優先する**: 公式ドキュメント → リポジトリの実コード → 実行結果。ブログ記事や検索結果の要約は補助に留める
2. **書かれていないことを「書かれている」ことにしない**: 「統合された」と書いてあっても「非推奨」とは限らない。**原文の語を確認し、そこにない含意を足さない**
3. **裏が取れなければそう書く**: 「公式ドキュメントでは確認できていない」「実測していない」と明示する。断定の形にしない
4. **実測できるものは実測する**: スクリプトの挙動なら実際に走らせて前後を比べる。「壊れないはず」ではなく「壊れないことを確認した」

## その実測が成立していたかを確かめる

**実測したつもりで、何も測れていないことがあります。** 実行結果は一次情報ですが、**壊れた実行の結果は一次情報ではありません**。

**「空の結果」を「該当なし」と読まない。** 空が返る経路は 2 つあり、**出力を見るだけでは区別できません**。

| 経路 | 例 |
| --- | --- |
| 探し方が正しく、本当に該当が無い | 違反が無いので `grep` が何も返さない |
| **探し方が壊れていて、何も探せていない** | パターンやパスが誤っている / 変数が空で引数が渡っていない / 参照が手元に無く `stderr` に出た警告をパイプで捨てている |

区別するには、**探し方のほうを先に確かめる**。次のどれかで足ります。

- **必ず当たるはずの入力**で試し、ちゃんと当たることを見る
- **別の方法で数え直す**（件数を出す経路を 2 つ持つ）
- **`stderr` を捨てていないか**見る

**成功を前提に後続を繋がない。** `&&` の前が黙って失敗すると**後続ごと消え**、期待した出力が出ないまま別の出力だけが並ぶので「実行したつもり」になります。**出力は末尾だけでなく、期待した行が出ているかで確かめる。**

## ユーザーの発言も裏を取る

**ユーザーが述べた事実も、裏取りの対象です。** 記憶違い・古い情報・伝聞であることがあります。

- 鵜呑みにして書くと、誤りがドキュメントやコードに固定化される
- 裏を取った結果が食い違ったら、**どこがどう違うかを示して報告**する（否定ではなく事実の提示）
- 結果としてユーザーが正しければ、それも「確認した」と伝える

これはユーザーを疑う姿勢ではなく、**書いたものが後から参照される**ことへの責任です。

## 禁止する挙動

- 裏取りせずに「〜は非推奨です」「〜が仕様です」と書くこと
- ユーザーの発言をそのまま事実としてドキュメント・PR 説明に転記すること
- 検索結果の要約だけを根拠に断定すること（一次情報に当たる）
- 「たぶん」「はず」で判断したものを、断定の文体で書くこと
- 一次情報に無い含意を足すこと（「統合された」→「非推奨になった」等）
- **空の出力を「該当なし」として報告すること**。探し方が正しかったことを先に確かめる
- コマンドが**成功したことを確かめずに**、その結果を根拠に使うこと

## なぜ

- ドキュメントやコードコメントは**後から参照される**。誤りが固定化されると、それを根拠にした判断が連鎖する
- 「非推奨」と「統合された」では、既存資産をどう扱うかの判断が変わる。**言葉の精度がそのまま意思決定の精度になる**
- ユーザーは大量の情報を扱っており、記憶違いは自然に起きる。裏取りはその補完であって、信頼の欠如ではない

## 例外

- 会話の中での見立て・仮説の提示（「たぶん〜だと思いますが確認します」）は、断定でなければよい
- ユーザーが「裏取り不要、そのまま書いて」と明示した場合はそれに従う
- リポジトリ固有の運用ルール（そのリポジトリの人が決めること）は、ユーザーの発言が一次情報になる

## 関連

- `keep_records_current.md`（変えたら説明も直す）: 本ルールは**書くとき**、あちらは**書いた後の鮮度**を扱う。裏を取って書いた内容も、対象が変われば古くなる
- `plain_language_explanation.md`（噛み砕いた説明）: 平易にすることと、正確さを落とすことは別
- `concise_first_then_detail.md`（簡潔に）: 出典を示すのは冗長ではない。1 行で足りる
- `background_heavy_work.md`（重い作業の流し方）: 「結果は必ず回収する」を定める。**回収した結果が成立しているか**は本ルールが扱う
