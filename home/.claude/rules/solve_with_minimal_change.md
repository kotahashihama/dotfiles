# 目の前の問題を、最小の変更で解決する

実装でもレビューでも、まず目の前の問題を解く最小の変更を選んでください。直すのに要らない汎用化・防御・抽象化は足しません。
これは全プロジェクト共通の規約です。

**オーバーエンジニアリングになりうる案は、捨てずに発展案として分けて出します。** 推奨や指摘に混ぜると、要らない変更まで入れる判断をユーザーに迫ることになります。

## 何を最小とするか

**判定は「それを外しても、目の前の問題は解けるか」。** 解けるなら、それは今回の変更に入れない。

| 今回の変更に入れる | 発展案に回す |
| --- | --- |
| 問題を解くのに要る変更 | まだ使う箇所が無い引数・設定・拡張点 |
| 直したことを確かめるテスト | 起きない場合のための防御と、それを確かめるテスト |
| 触った箇所から波及して避けられない追随 | 似た箇所をついでに揃える共通化・抽象化 |

課題に紐づく作業で、課題と関係の無い変更を入れないことは `scope_changes_to_the_issue.md` が持ちます。本ルールは、課題を解く変更そのものの大きさを扱います。

## 提案とレビューで、推奨と発展案を分ける

| 場面 | 推奨・指摘に置くもの | 発展案に置くもの |
| --- | --- | --- |
| 選択肢を出して尋ねる（ `AskUserQuestion` ） | 問題が解ける案のうち、変更が最も小さいもの | それより広い案。推奨にしない |
| セルフレビュー・PR のレビュー | 問題が解けない・規約に反する・壊れる箇所（must）と、変更を広げないより良い手（imo） | 要らない汎用化・防御・抽象化のように、変更を広げる改善 |
| AI レビューの指摘の採否 | 正しさと課題の要件に関わる指摘 | それ以外の指摘。対応しない理由を返す |

**もっとよくできると気づいたら、黙らずに出す。** 今の変更に入れないだけで、捨てない。推奨や指摘とは別の節（発展案）にまとめ、1件1行で書く。どこへ出すかは出す先の規定に従う（PR のレビューなら `/review-pr` の投稿してよい `[fyi]` か、ユーザーへの報告）。今の問題を解くのには要らない改善だと、読み手に分かる書き方にする。

## 禁止する挙動

- 目の前の問題を解くのに要らない汎用化・防御・抽象化を、推奨や指摘（imo を含む）として出すこと
- 発展案を推奨の選択肢に混ぜること。選ぶ人が、要らない変更まで入れるかを決めることになる
- 「将来使うかもしれない」を理由に、今の変更へ拡張点を足すこと
- もっとよくできると気づいたのに、発展案にも出さずに黙ること

## なぜ

- 変更が大きいほど、レビューの量と壊れる箇所が増える。要らない部分は、問題を解かないのにそのコストだけを持ち込む
- まだ使われない汎用化は、使われる場面が来たときの形と合わないことが多い。そのときに作るほうが安い
- 推奨は選ぶ人の判断を寄せる。広い案を推すと、最小で済む問題に毎回大きな変更が入る

## 例外

- ユーザーが「ついでに」「汎用的に」と範囲を広げた場合
- 最小の変更では問題が解けない場合。そのときは、なぜ最小では足りないかを1行添えて広い案を推す

## 関連

- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: あちらは課題と関係の無い変更を入れないこと、本ルールは課題を解く変更の大きさ
- `decide_or_ask.md` （尋ねるときの形）: 推奨の付け方はあちら。本ルールは何を推奨にするか
- `responding_to_reviews.md` （レビューコメントへの対応）: 変更案を並べるときも、推奨は最小の案にする
- `/review-code`・`/review-pr`・`/resolve-ai-reviews` （レビューの実行手段）: 指摘と発展案の分け方は本ルールに従う
- pstack の `principle-laziness-protocol` （最小の差分にとどめる）: 同じ向き。本ルールは推奨と発展案の分け方を足す
