# 目の前の問題を、最小の変更で解決する

実装でもレビューでも、まず目の前の問題を解く最小の変更を選んでください。直すのに要らない汎用化・防御・抽象化は足しません。
これは全プロジェクト共通の規約です。

**オーバーエンジニアリングになりうる案は、捨てずに「今回は要らない」と分かる形で出します。** 推奨や must に混ぜると、要らない変更まで入れる判断を相手に迫ることになります。

## 何を最小とするか

**判定は「それを外しても、目の前の問題は解けるか」。** 解けるなら、それは今回の変更に入れない。

| 今回の変更に入れる | 今回は入れない |
| --- | --- |
| 問題を解くのに要る変更 | まだ使う箇所が無い引数・設定・拡張点 |
| 直したことを確かめるテスト | 起きない場合のための防御と、それを確かめるテスト |
| 触った箇所から波及して避けられない追随 | 似た箇所をついでに揃える共通化・抽象化 |

課題に紐づく作業で、課題と関係の無い変更を入れないことは `scope_changes_to_the_issue.md` が持ちます。本ルールは、課題を解く変更そのものの大きさを扱います。

## 今回は要らない改善の出し方

**もっとよくできると気づいたら、黙らずに出す。** 今の変更に入れないだけで、捨てない。出す先ごとに、今回は要らないと分かる形にする。

| 場面 | 推奨・指摘に置くもの | 今回は要らない改善の出し方 |
| --- | --- | --- |
| 選択肢を出して尋ねる（ `AskUserQuestion` ） | 問題が解ける案のうち、変更が最も小さいもの | 発展案として本文に1件1行で書く。推奨の選択肢にしない |
| セルフレビュー・PR のレビュー | 問題が解けない・規約に反する・壊れる箇所（must） | 範囲の中は imo（PR では `[iaio]` ）にして「この PR で対応する必要はありません」を添える。範囲の外は `[fyi]` |
| AI レビューの指摘の採否 | 正しさと課題の要件に関わる指摘 | 対応しない理由を返す。残したい改善はユーザーへの報告に書く |

PR のレビューで投稿してよい `[fyi]` の種類は `/review-pr` が持ちます。

## 禁止する挙動

- 目の前の問題を解くのに要らない汎用化・防御・抽象化を、推奨や must として出すこと
- 今回は要らない改善を、推奨の選択肢に混ぜること。選ぶ人が、要らない変更まで入れるかを決めることになる
- 「将来使うかもしれない」を理由に、今の変更へ拡張点を足すこと
- もっとよくできると気づいたのに、どこにも出さずに黙ること

## なぜ

- 変更が大きいほど、レビューの量と壊れる箇所が増える。要らない部分は、問題を解かないのにそのコストだけを持ち込む
- まだ使われない汎用化は、使われる場面が来たときの形と合わないことが多い。そのときに作るほうが安い
- 推奨は選ぶ人の判断を寄せる。広い案を推すと、最小で済む問題に毎回大きな変更が入る

## 例外

- ユーザーが「ついでに」「汎用的に」と範囲を広げた場合
- 最小の変更では問題が解けない場合。そのときは、なぜ最小では足りないかを1行添えて広い案を推す

## 関連

- `scope_changes_to_the_issue.md` （課題の範囲へ変更を閉じる）: あちらは課題と関係の無い変更を入れないこと、本ルールは課題を解く変更の大きさ
- `decide_or_ask.md` （尋ねるときの形）: 推奨の付け方はあちら。本ルールは何を推奨にするか
- `responding_to_reviews.md` （レビューコメントへの対応）: 変更案を並べるときも、推奨は最小の案にする
- `/review-code`・`/review-pr`・`/resolve-ai-reviews` （レビューの実行手段）: 今回は要らない改善の出し方は本ルールに従う
- pstack の `principle-laziness-protocol` （最小の差分にとどめる）: 同じ向き。本ルールは今回は要らない改善の出し方を足す
