# GitHub へ投稿する文章の書き方

PR 説明・コメント・レビュー返信・issue へ書く文章の書き方をまとめています。アノテーションの節だけは、課題管理ツールのコメントにも当てます。生成者表示は `github_note_generated_by_claude.md` が持ちます。
これは全プロジェクト共通の規約です。

## GitHub へ書く日本語は1文ごとに改行し、行末の句点を落とす

PR 説明・レビューコメント・返信・issue に書く日本語は、**1文で改行し、その行末の句点を書かない**でください。

```markdown
<!-- ❌ NG: 1 行に複数の文が入り、行末に句点がある -->
`Create` は 4 文、`Update` は 3 文を続けて発行します。トランザクションは呼び出し側が張る opt-in の仕組みです。

<!-- ✅ OK: 1 文ごとに改行し、行末の句点は落とす -->
`Create` は 4 文、`Update` は 3 文を続けて発行します
トランザクションは呼び出し側が張る opt-in の仕組みです
```

2つは1つの形を作ります。1文で折るから句点が行末へ来て、行末だから落とせる。結果として各行は句点なしで終わります。

落とすのは `。` だけ。`？` と `！` は残す。`。` は改行が肩代わりできますが、`？` は文の種類そのものを示す記号です。落とすと平叙文と区別が付かず、問われていることに相手が気づけません。

**判定は「改行で代替できるか」。** 行末にあるかどうかではありません。

### 対象

Claude がユーザーに代わって GitHub へ書き込む日本語のテキスト全般。

- PR 説明（新規作成・更新のいずれも）
- レビューコメント（総括・インラインの両方）
- レビューコメントへの返信、PR コメント、issue の本文とコメント

### 期待する書き方

- **改行するのは文の区切りだけ。** 読点（ `、` ）では折らない
- 箇条書き・表のセルの中も同じ。セル内に2文入るなら、そのセルは長すぎるので分ける
- 文中の句点は残す。意図して1行に2文置いたとき（ `hoge。fuga` ）だけ、前の句点が文中に残る
- 段落を分けたいところでは空行を入れる。行間が広がって区切りが見える
- GitHub の issue / PR / discussion では、単一改行がそのまま改行として描画される。1文ごとに行が分かれ、長い段落も追いやすくなる
- リポジトリ内の `.md` ファイルは挙動が違う（単一改行は空白になる）。本ルールが対象にするのは GitHub 上の投稿だけ

### 確認のしかた

書き終えたら**行末の句点を機械的に拾う**。目視だと、長い本文の後半だけ崩れているのを見逃します。

```bash
grep -nE '。\s*$' <本文ファイル> | grep -v '^\s*[0-9]*:>'
```

`>` 始まりを除くのは、生成者表示 Note の定型文を対象外にするため。**残った件数が0になるまで直す。**

#### 一括で書き換えたら、対になる記法も数える

**句点を一括削除すると、対になる記法が壊れることがあります。** 実際に PR 本文で `**` の対応が崩れ、
太字が行をまたいで効いていました。10行が影響を受けています。

目視では見つかりません。崩れた行そのものは普通に読めてしまい、表示を見て初めて分かる。
書いた側は本文を見ているので気づけません。

```bash
awk '{ n = gsub(/\*\*/, "&"); if (n % 2) print FILENAME ":" FNR ": " $0 }' <本文ファイル>
```

`**` の出現数が奇数の行を拾う。残った件数が0になるまで直す。

対象は句点の削除に限りません。置換・整形・改行の入れ直しなど、まとめて書き換えたときは常に数える。
`` ` `` や `~~` も同じ形で壊れます。

**NG 例も書き換わります。** 「こう書かない」として置いた行は、規約に違反している形で正しい。一括置換はそれを「修正」してしまい、例が例でなくなります。

実際に、数値と単位の空白を詰める規約を書いた直後、その規約の `❌ 2 万件 / 21 秒` の行まで詰めてしまいました。表示上は何も壊れないので、目視では気づけません。

| 守るもの | 見分け方 |
| --- | --- |
| NG 例・悪い例 | `❌` `<!-- ❌ NG` `悪い例` の付いた行 |
| 引用・ログの原文 | 引用記法の中、コードブロックの中 |

置換の対象から先に外す。直してから戻すと、どれを戻すか分からなくなります。

この検査が使えるのは GitHub へ投稿する本文だけです。リポジトリ内の `.md` は単一改行が空白になるため、
強調が行をまたいでも正しく描画されます。同じ検査を掛けると誤検知が並びます（実際に自分のルール群へ
掛けたら6件出て、すべて正常なものでした。コードブロック内の `/**`、行をまたぐ強調、
`` `**` `` のような記法そのものの引用）。

投稿する本文では1文1行なので、強調は行をまたげません。だから奇数=壊れているが成立します。

### なぜ

- **差分が文単位で出る。** 1文1行なら、後から本文を直したときに変えた文だけが差分に出る。1行に詰めると段落全体が差し替わったように見え、レビュアーはどこが変わったか読み直すことになる
- レビューコメントの引用が文単位でできる。相手が返信で一部を引用するとき、行単位で選べる
- 折り返し位置が読み手の画面幅で変わるため、書き手が段落の見た目を制御しても意味がない。文の区切りで折るほうが構造として安定する
- `。` は次の文との切れ目を示す記号で、改行が同じ役目を果たす場所では働いていない。無くても意味が変わらないなら、無いほうが軽い。`？` `！` は文の種類を示す記号なので、改行では肩代わりできない
- 表のセルや箇条書きでは特に目立つ。同じ長さの項目が並ぶと、句点の有無が揃っていないことだけが目に付く

### 例外

- 英語の文章は対象外（英語圏の慣習に従う）
- **コードブロック・引用の中身**はそのまま。原文の改行も句点も変えない
- 生成者表示 Note の定型文。文言は `github_note_generated_by_claude.md` が固定している
- PR テンプレートに元から書かれている固定文。リポジトリ側の文章なので逐語のまま残す
- コマンドコメント（ `/ai-review` 等）は本文をコマンド1行に保つ
- ユーザーが文面を指定して「これをそのまま投稿して」と指示した場合

## GitHub へ書く文章は、ですます調で揃える

**同じ本文の中で敬体と常体を混ぜない。** 読み手は書き手が変わったのかと一度立ち止まります。

```markdown
<!-- ❌ NG: 1 つの本文で混ざっている -->
`label` を参照する箇所の追随が必要です
移行のあいだは両方の値が返る

<!-- ✅ OK -->
`label` を参照する箇所の追随が必要です
移行のあいだは両方の値が返ります
```

体言止めは混在に数えません。見出し・表のセル・箇条書きの項目名は、どちらの文体でも名詞で終わります。

コミットメッセージは対象外。あちらは体言止めが規約です（ `karma_commit_style.md` ）。

`[memo]` は だ・である調で書きます。自分用のメモなので敬体が要らず、文体が違うこと自体が「これは自分用」の印になります。

混在にはなりません。`[memo]` のコメントはそれ自体が1つの本文なので、その中で だ・である調に揃っていれば上記を満たします。

実測で混ざります。過去の PR 本文30件で、ですます205行に対し、だ・である194行でした。どちらかに寄せる意識が無いと、書いた場所ごとに揺れます。

## 投稿する文章では、伝わる形を選んで書く

PR 本文・コメント・レビュー返信・課題管理ツールのコメントでは、散文で書くと長くなるものを別の形へ畳んでください。

手段の選び方は `/format-github-post` が持ちます（表・Mermaid・Alert・`<details>`・脚注・パーマリンク・別コメント）。PR 本文やコメントを書き始めたら、そちらを開く。

**アノテーションだけは本ルールが持ちます。** 投稿先を問わず要るうえ、**フックもスキルも通らない経路がある**ためです。課題管理ツールへは MCP 経由で投稿するので `lint-github-body.sh` （ `Bash` の `gh` しか見ない）が走らず、どのスキルの手順にも入りません。

### アノテーションで、相手に求めることを示す

レビューで使う `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` は、受け取った側が何をすべきかを1行目で示す記号です。

| 記号 | 相手に求めること |
| --- | --- |
| `[must]` | 直してほしい |
| `[imo]` | 検討してほしい |
| `[nits]` | 気が向けば直してほしい |
| `[ask]` | 答えてほしい |
| `[fyi]` | 読むだけでよい |

**自分の PR へ補足を置くときは `[fyi]`。** 調査の結果・移行の事情・判断の根拠は、対応も返信も求めていないので `[fyi]` が合います。

```
[fyi]
<本文>
```

1行目に置き、次の行から本文を書く（間に空行は入れない）。

`[memo]` は自分用のメモに使います。`[fyi]` との違いは宛先だけで、**人のために残すなら `[fyi]`、自分のために残すなら `[memo]`**。

図解・調べた経路・後で自分が確かめ直したいことは `[memo]` が合います。その PR を次に開くときに要るので、手元のノートではなくそこへ置く。

`[memo]` の本文は だ・である調で書きます。宛先が自分なので敬体が要りません。

複数のリポジトリを跨ぐ修正では、経路の図を `[memo]` で残します。片方のリポジトリしか見ていない人には差分から辿れず、散文で書くと数段落かかります。

使うのは `sequenceDiagram`。跨ぐ変更で読み手が詰まるのはどちらがどの順で呼ぶかなので、登場人物と順序を持つ形が合います（種類の一覧は `concise_first_then_detail.md` ）。

この PR で足した経路は、既存の経路と線で分けます。分けないと、その PR が何を変えたのかではなく仕組みの説明になります。

課題管理ツールのコメントでも同じ記号を使います。ただし使うのは `[fyi]` と `[memo]` の2つです。

課題のコメントを読んで誰かがコードを直すことはないので、`[must]` / `[imo]` / `[nits]` は出てきません。
`[ask]` も使いません。質問はチャットで直接聞くほうが早く、課題のコメントには残らないためです。

### 禁止する挙動

- bot の指摘へコミットハッシュだけを返す返信に、何かを足すこと。1行目からハッシュを機械抽出する運用（ `/resolve-ai-reviews` ）を壊す
- **`[fyi]` と `[memo]` を取り違えること**。判定は宛先で、人のために残すなら `[fyi]`、自分のためなら `[memo]`
- 投稿先がスキルやフックの外だからと、畳まずに散文で出すこと。判断軸は投稿先で変わらない

### なぜ

- レビュアーは差分を読むために来ており、本文を読むのは前段。前段が長いほど、本題に入るまでの負担が増える
- アノテーションは**1行目で相手の次の行動を決める**。記号を誤ると、対応が要らないものに対応させる
- 強調も記号も相対的にしか働かない。全部を強調すると、何も強調していないのと同じになる

### 例外

- ユーザーが形式を指定した場合
- **コマンドコメント**は本文をコマンド1行に保つ

## GitHub で他リポジトリの PR / issue を参照するときは owner を省略しない

GitHub へ書く文章（PR 説明・コメント・レビュー返信）で他リポジトリの PR / issue に触れるときは、**`owner/repo#123` の形**で書いてください。

### 期待する書式

| 参照先 | 書き方 |
| --- | --- |
| 他リポジトリ | `owner/other-repo#2950` |
| 同一リポジトリ | `#392` |
| コメントへのアンカー付き | `[このコメント](https://github.com/owner/repo/pull/123#issuecomment-...)` |

GitHub が自動でリンクにし、タイトルと open/closed も表示されます。生 URL より短く、リポジトリ名が変わっても腐りません。

### 禁止する書き方

- **owner を省略すること**。`other-repo#2950` も `#2950` も、同一リポジトリの2950番として解釈されます。番号が存在しなければリンクにならず、存在すれば無関係な PR に飛びます
- 同じ文書の2回目以降を省略すること。「一度フルで書いたから以降は短くてよい」は成立しません。読み手はどの段落から読み始めるか分からず、リンクは1箇所ずつ独立に解決されます
- **バッククォートで囲むこと**。`` `owner/repo#123` `` はコード片として描画され、GitHub が参照として解釈しません。タイトルも open / closed も出ないので、読み手は番号を手で開くことになります

### なぜ

- 番号だけの参照はリポジトリを跨いだ瞬間に意味が変わる。書き手には自明でも、読み手には判別できない
- リンクが機能しないと、レビュアーは依存先を自分で探すことになる。依存関係を示すために書いた参照が、かえって手間を増やす
- **囲むべきものと囲んではいけないものが混在する。** パス・コマンド・識別子は囲むのが正しいので（ `wrap_values_in_inline_code.md` ）、同じ癖で参照まで囲むとリンクが消える。種類ごとに判定する

### 確認のしかた

書き終えたら、**本文中のすべての `#数字` を拾って、同一リポジトリのものか確かめる**。1箇所ずつ見ないと、前半だけ正しく後半で崩れている状態を見逃します。**owner の有無だけを見る検査では足りません**（囲まれていても当たる）。囲まれた側を別に数えて0件にする。

## GitHub のコマンドコメントは通常のコメントと別扱いにする

`/ai-review` のように、**ワークフローが本文そのものを検知して動くコメント**は、人が読むためのコメントとは別のものとして扱ってください。

### 対象

投稿先が GitHub のコメント欄でも、**宛先が人ではなく機械**のもの。

- `/ai-review` 等のスラッシュコマンド（GitHub Actions が `issue_comment` の本文で検知する）
- bot への指示として定義された定型文字列（ `@dependabot rebase` 等）

### 書くとき: 本文はコマンドだけにする

コマンド以外の文字を一切入れない。**挨拶・追加説明・前後の空白・`[fyi]` 等のアノテーション・末尾の生成者表示 Note、いずれも付けない。**

検知は本文の文字列そのものに対して行われるため、何かを足した時点で**ワークフローが起動せず、意味の無いコメントだけが残ります**。`github_note_generated_by_claude.md` はここでは適用しません。

### 読むとき: 補足コメントとして扱わない

PR 説明の更新時に「自分が投稿したコメント」を点検する場面では、コマンドコメントを対象から外す。

**投稿者名で判別できません。** Claude が投稿してもアカウントはユーザー自身なので、`user.login` で絞ると混ざります。**本文を trim して、コマンド1行だけかどうかで判定する。**

ユーザーへ報告するときも、コマンドコメントを「補足コメント」と呼ばない。情報を提供していないので、点検しても更新すべき事実が無いからです。

### なぜ

- コマンドコメントは**起動のための手段**であって、後から読み返される情報ではない。情報コメントと同じ土俵に載せると、点検のたびにノイズとして出てくる
- 「自分が投稿したコメント」という括りは、**書き手ではなく役割で分ける**べきもの。GitHub 上のアカウントは両方ユーザー名義なので、投稿者では分けられない

## GitHub の文章で、書き手の帰属を匂わせない

PR 説明・コミットメッセージ・コメントで、**「自分の言葉で」「〜と判断した」のように、誰が書いた・決めたかを匂わせる表現**を使わないでください。

### 期待する書き方

- 変更点・理由は**変更そのものを主語**にして書く。「〜という事情があったため、〜に書き直した」のように、書いた人を主語に置かない
- 経緯を書きたいときも「〜と判断し」ではなく「〜のため」「〜という理由で」のように、**帰属の無い接続**にする

### 禁止する書き方

- **ユーザーが自分で書いた・理解したかのような表現**（「自分の言葉で」「自分の判断で」等）。実際に手を動かしているのは Claude で、ユーザーは方向付けと承認をする側なので、書き手を偽ることになる
- 逆に**「AI が書いた」「Claude が判断して」と、本文中で改めて主張すること**。生成者の開示は末尾の Note ブロック（ `github_note_generated_by_claude.md` ）が担っており、本文中で重ねて書くとその一文だけ書き手が浮く

### なぜ

- **ユーザーの方針とエージェントの実装がどちらも混ざって1つの差分になる。** どちらの言葉で書いても実態の半分しか表せず、文責をどちらかに寄せる表現は不正確になる
- 帰属を書くと、後から読む人が「これは誰の判断か」を気にする必要が生まれる。**変更の中身が伝われば足り、誰が言い出したかは判断に不要な情報**
- 生成者の開示はすでに末尾の Note ブロックが担っている。本文中で重ねて触れると情報が重複し、その文だけ浮く

### 例外

- ユーザーが特定の文面をそのまま使うよう指定した場合

## 関連

- `github_note_generated_by_claude.md` （生成者表示）: その定型文だけは本ルールの対象外。文言をあちらが固定している
- `karma_commit_style.md` （コミットメッセージ）: 句点を落とす点は同じだが、あちらは commit subject の1行だけ。本ルールは GitHub 上の文章全体
- `code_comments.md` （コードコメントに何を書くか）: 同じく句点を落とすが、あちらはコードコメント。本ルールが `.md` を対象外にしている理由（単一改行が空白になる）は、コードコメントには当てはまらない。不変の WHY の節から出た移ろう文脈の行き先が `[fyi]` で、その書式は本ルールが定める
- `/format-github-post` （投稿する文章の畳み方）: あちらは構造の選び方、本ルールは文の表記
- `no_space_between_number_and_unit.md` （数値と単位の空白）: どちらも日本語の表記を定める。**一括置換で対になる記法と NG 例が壊れる**のは本ルールが扱う
- `recheck_after_every_revision.md` （書き直すたびに確かめ直す）: 本ルールの検査は3周目（形）で使う。あちらが周ごとの観点を定める
- `concise_first_then_detail.md` （簡潔に）: あちらは量を扱う。本ルールは改行と表記
- `/review-pr` / `/create-pr` / `/update-pr-description` / `/resolve-ai-reviews` / `/resolve-human-reviews`: 本ルールが土台で、各スキルは投稿先固有の事情を上乗せする
- `report_formatting.md` （報告に貼る識別子の書式）: `path:line` の扱いが逆になる。会話ではクリックできるので使い、GitHub では差分が動くので使わない
- `wrap_values_in_inline_code.md` （値と識別子は囲む）: 囲むかどうかの判定はあちら。本ルールが定めるのは、囲んではいけない側の1つ
- `/create-pr` / `/update-pr-description` / `/review-pr` / `/resolve-ai-reviews` / `/resolve-human-reviews`: 本ルールが土台。他リポジトリの PR を挙げる場面はどのスキルでも出る
- `/request-ai-reviews` （ `/ai-review` の投稿）: 投稿側の手順。本文をコマンド1行に保つ責務を持つ
