`/review-pr` の **Step 4（レビューの実施）だけ**を並列化したものです。それ以外の手順は一切持ちません。

| 手順 | 担当 |
| --- | --- |
| PR の特定・過去レビューの確認（Step 1） | **`/review-pr`** |
| レビュー規約の読み取り（Step 2） | **`/review-pr`** |
| 規約ドキュメントの本体を読む（Step 3） | **`/review-pr`** |
| **レビューの実施（Step 4）** | **本スキル**（並列化） |
| 裏取り・敵対的検証・報告・投稿（Step 5〜9） | **`/review-pr`** |

**`/review-pr` の手順をここに複写しない。** 差し替えるのは Step 4だけで、他は原文に従います。

## 起動時のコスト確認

**サブエージェントを複数並列起動するので、`/review-pr` より大きくトークンと時間を使います。** ユーザーがそれを承知しているかで分ける。

| 起動経路 | 扱い |
| --- | --- |
| **`/review-pr-deeply` と打たれた** | 承知しているとみなし、確認せず進む |
| **自然文から自動起動した**（「徹底的に見て」等） | **`AskUserQuestion` で1度確認する** |

確認するときは、軽く済ませる代替として `/review-pr` があることも示す。**了承を得るまで起動しない。**

判定に迷ったら**確認する側に倒す**。

## 進め方

### 1. Step 1〜3を `/review-pr` のとおり踏む

**規約を読まずに並列起動しない。** サブエージェントへ渡す規約のパスは、ここで集めたものを使います。

Step 3で辿った `docs/` 配下のファイルは、**サブエージェントにも Read させる**（起動プロンプトに本文を複写せず、パスだけ渡す）。

### 2. プロジェクト側に深いレビュースキルがあれば、そちらへ委譲する

**あるなら自前で並列しない。** ディレクトリ構成と規約の対応を知っているのはそちらで、こちらが組み直すと精度が落ちます。

- 判定は**利用可能なスキルの一覧**で行う。`.claude/skills/` と `.claude/commands/` の両方を見る
- 名前を決め打ちしない。「差分を多観点・レイヤー別に見る」と読めるものを探す
- 委譲したら **Step 3〜4は飛ばし**、返ってきた指摘を持って `/review-pr` の Step 5へ進む

### 3. 自前で並列レビューを起動する

プロジェクト側に無いときだけ、ここへ来ます。

#### 分けかた

**変更ファイルをディレクトリの近さで束ねる。** 言語やフレームワークに依存しない軸なので、どのリポジトリでも成立します。

| 束 | 目安 |
| --- | --- |
| 1エージェントあたり | **5〜8ファイル** |
| 束が1つしかできない（変更が小さい） | **観点で分ける**（下記） |
| 1つの束が15ファイルを超える | さらに分ける |

**観点で分ける場合**は、差分の性質から選ぶ。全部を並べない。

| 観点 | 選ぶ条件 |
| --- | --- |
| 正確性・境界値 | 常に1体 |
| 規約適合 | Step 3で規約ドキュメントが見つかっている |
| テストの網羅 | テストファイルが差分にある |
| セキュリティ | 認証・権限・入力値・外部への送信が差分にある |
| 性能 | 繰り返し処理・大量データ・重い再計算の経路が差分にある |

**条件は領域で読み替える。** 同じ「性能」でも、**サーバー側ならループ内のクエリや N+1、画面側なら不要な再描画やバンドルの肥大**が該当します。表の語をそのまま探すのではなく、**その領域で事故になりやすい形**を選ぶ。

**表に無い観点を足してよい。** 差分がその領域固有の危うさを持つなら、そちらを優先する。

**横断レビュアーを1体、必ず起動する。** ファイル単位に分けると見えなくなるもの（呼び出し経路の不整合、層をまたいだ契約のズレ、設計の歪み）を担当します。

#### 起動のしかた

**すべて1メッセージの中で、バックグラウンド起動する**（ `run_in_background: true` ）。完了を待たずに Step 4へ進みます。

サブエージェントは**会話の文脈を引き継ぎません**。次を漏れなく渡す。

```markdown
あなたは [対象] の [担当範囲] を見るコードレビュアーです。

## レビュー条件

- 差分の取り方: `git diff <base>...<head> -- <担当ファイル>`
- 担当ファイル:
  - [パス一覧]
- 必ず読む規約（Read で全文。要約・記憶に頼らない）:
  - [Step 3 で辿ったパス]
- 追加の重点観点: [引数の指定。無ければ「なし」]

## 出力

指摘ごとに次の 3 点を書いてください。**根拠が差分から追えないものは出さないでください。**

- 該当箇所（`path:line`。行番号は `git show <head>:<path> | grep -n` でファイル単体から採る）
- なぜ問題か（規約の引用、または「この入力・状態 → 壊れる行」の失敗シナリオ）
- どう直すか

重要度は付けなくて構いません。呼び出し元が判定します。
```

**重要度をサブエージェントに決めさせない。** 判定基準は `/review-pr` の Step 6が持っており、こちらで確定します。

### 4. 待っている間、自分でも差分全体を見る

**サブエージェントの完了を待たない。** ここを直列にすると、並列にした意味がなくなります。

見るのは**個々のファイルに分解すると消えるもの**。

- 変更全体として「どこに何を足したか」が、その PR の目的と合っているか
- 束をまたいだ重複・矛盾
- PR 本文の説明と差分の食い違い

### 5. 回収して `/review-pr` の Step 5へ渡す

全サブエージェントの結果を回収し、次を済ませてから引き渡す。

| やること | 内容 |
| --- | --- |
| **重複の集約** | 同じ箇所・同じ種類の指摘を1件にまとめ、該当箇所を列挙する |
| **根拠の無いものを落とす** | 差分から追えない指摘は、この時点で捨てる |
| **失敗したエージェントの補完** | 空応答・エラーなら、その担当を自分で見る |

**委譲先が重要度を付けてきたら、体系ごと読み替える。** プロジェクトスキルの `must` と、そのリポジトリの `[must]` （かならず変更して）は**別の基準**です。前者の判定表をそのまま持ち越すと、意味がずれたまま投稿することになります。

**上げるときは、下げるとき以上に裏を取る。** 下げすぎても相手の時間は奪いませんが、**上げすぎるとマージを止めます**。委譲先が `imo` としたものを `must` へ上げるなら、次の2つを必ず確かめる。

| 確かめること | やり方 |
| --- | --- |
| **規約に明文化されているか** | 該当する語で走査し、**必ず当たる語で検算する** |
| **慣習として定着しているか** | **同種の変更を数える。** 1例を見て「慣習」と判断しない |

実際に、仕様書の更新を1例だけ見て `must` へ上げ、**同種の変更15件を数えたら0件だった**ことがあります。

**ここから先は `/review-pr` の手順です。** 裏取り（Step 5）・敵対的検証（Step 6）・報告（Step 7）・投稿（Step 8〜9）を、いつもどおり行う。

**サブエージェントが出した指摘も、反証の対象です。** 自分で書いたものと扱いを変えない。**むしろ根拠を確かめていない分、落ちる率が高い**。

## やってはいけないこと

- **`/review-pr` の手順を本スキルに複写すること**。差し替えるのは Step 4だけ
- **規約を読む前に並列起動すること**。サブエージェントへ渡すパスが決まらない
- **プロジェクト側に深いレビュースキルがあるのに自前で並列すること**。精度が落ちるうえ二重に走る
- **サブエージェントの完了を待ってから自分の確認を始めること**。壁時計時間が最も伸びる
- **サブエージェントが付けた重要度を、そのまま使うこと**。判定は `/review-pr` の基準で
- **委譲先スキルの重要度体系を、そのまま持ち越すこと**。`must` の定義がリポジトリ側と違う
- **重要度を上げるとき、規約と慣習を数えずに決めること**。**1例を「慣習」と読むと、多数派が逆だったときに気づけない**
- **回収した指摘を反証せずに報告へ回すこと**。根拠を確かめていないぶん、落ちる率は自分の指摘より高い
- **自然文から起動したのに、コストを確認せず走ること**
- **サブエージェントを増やせば精度が上がると考えること**。**同じ差分を重複して見るだけ**なので、束の大きさで決める

## 出力の目安

`/review-pr` の Step 7に従います。そのうえで、**どう分けたか**を報告に足す。

- 起動したエージェントの数と担当範囲
- 委譲した場合は、委譲先のスキル名
- **回収した指摘のうち、反証で落とした件数**

## 関連

- `/review-pr` （土台）: **Step 1〜3と5〜9はすべてあちら**。本スキルは Step 4の差し替えだけを持つ
- `/review-code-deeply` 等のプロジェクトスキル: **あれば委譲する**。ディレクトリ構成と規約の対応を持っているのはそちら
- `align_skill_md_format.md` （スキルの書き方）: ラッパーとプリミティブの分け方
- `background_heavy_work.md` （重い作業の流し方）: バックグラウンド起動と、待ち時間の使い方
