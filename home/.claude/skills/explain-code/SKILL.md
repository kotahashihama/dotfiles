コードを**上から順に読み下し**、1 かたまりずつ何をしているかを説明します。**抜粋が主役**で、その言語に不慣れなら**文法・言語機能も開く**のが `/break-down` との違いです。

**説明だけを行い、コードは書き換えません。**

## 対象

| 引数 | 例 | 読む単位 |
| --- | --- | --- |
| **ファイル** | `import_csv.go` | 上から順に、宣言・関数のかたまりで |
| **関数・メソッド** | `BulkCreate` | 処理の順に、ブロックで |
| 型・値オブジェクト | `OrderStatus` | 定義 → メソッドの順 |
| 差分の一部 | `gh pr diff` の特定ファイル | 変わった行を含むかたまりで |

第 2 引数は**観点の指定**として使う（「エラー処理を中心に」「並行処理まわりだけ」等）。

**俯瞰が要るなら先に `/break-down`。** 「これは何で、なぜこの形か」はあちら、「この行は何をしているか」が本スキル。**両方が要るなら順に呼ぶ**——地図を見てから歩くほうが迷わない。

## `/break-down` との違い

**同じコードでも、読み手の問いが違います。**

| | `/break-down` | 本スキル |
| --- | --- | --- |
| 答える問い | **なぜこの形なのか** | **この行は何をしているか** |
| 骨格 | 図・表・「なぜ」 | **抜粋そのもの** |
| 進む向き | 構造の内側から外へ | **コードの上から下へ / 処理順** |
| 文法・言語機能 | 1 行に留める | **開く** |
| 分量 | 畳む | **長くてよい**（読み下しなので畳めない） |
| 読み終えた人は | 全体像を得る | **その 1 本を自分で読めるようになる** |

**判定は「読み終えた人が次に何をするか」。** 他の箇所へ進むなら `/break-down`、同じコードをもう一度自分で読むなら本スキル。

## 進め方

### 1. 実物を読む。呼び出し元まで

**その場の行だけでは「何をしているか」は書けません。** 引数に何が入るか、戻り値をどう使うかで意味が変わる。

- 関数なら**呼び出し元を 1 つは見る**（`git grep` で足りる）
- 型なら**組み立てている場所**を見る。ゼロ値で使われるのか、コンストラクタを通すのか
- 差分なら `git show <base>:<file>` で**変更前**を見る。「何が変わったか」は前を知らないと書けない

**裏を取らずに書かない**（`verify_before_asserting.md`）。読み下しは断定の連続になるので、推測が混ざると気づかれません。

### 2. 読む単位に切る

**行単位では細かすぎ、関数単位では粗すぎます。** 意味のまとまりで切る。

| 切り方 | 目安 |
| --- | --- |
| **1 かたまり 5〜20 行** | 検証・組み立て・分岐・後始末など、目的が 1 つのまとまり |
| **順序は基本コードの上から** | 読み手はファイルを開いて上から見るため |
| **ただし処理順が違うならそちら** | 早期 return、遅延実行、並行処理。**書かれている順と走る順が違うときは、走る順で説明して、その旨を言う** |

**切った単位に見出しを付ける。** 「引数の検証」「保存する形へ組み替える」のように、**何をするかたまりか**を名前にする。

### 3. かたまりごとに、抜粋して読み下す

**順番を固定する。** `file:line` → 抜粋 → 説明。

- **抜粋は 5〜20 行。** 省いた所は `// ...` で明示する
- **書き換えない。** 整形すると実物と違うものになる
- **説明はその抜粋の中だけを扱う。** 先の話を混ぜると、読み手が今どこを読んでいるか見失う

**1 かたまりに 1 抜粋。** 同じかたまりで 2 回貼るなら、切り方が粗い。

### 4. 文法・言語機能も開く

**ここが `/break-down` と最も違います。** 向こうは「開くのは判断であって文法ではない」ですが、**本スキルは文法も開く**。読み下しの途中で知らない構文が出たら、そこで詰まるからです。

**どこまで開くかは言語ごとの習熟度で決める**（`plain_language_explanation.md` と `CLAUDE.md`）。同じ「バックエンド」でも言語によって必要な粒度が違う。

| 習熟度 | 開く範囲 |
| --- | --- |
| **初心者の言語** | 言語機能そのものから（レシーバ、埋め込み、遅延実行、並行処理の起動、ポインタと値の違い 等） |
| 中級の言語 | 込み入った型・初見のライブラリ・その言語特有の落とし穴だけ |
| **強みの言語** | 一般的な用語はそのまま。**そのコード固有の仕掛けだけ** |

**そのコードに出てくるものだけを開く。** 教科書の順に並べない。**「ついでに関連する機能も」と広げると、読み下しが言語入門にすり替わります。**

**1 つにつき 2〜4 行。** それ以上要る概念は、**そこだけ節を立てて先に済ませる**か、公式ドキュメントへ送る。

### 5. 「なぜそう書いたか」まで届かせる

**何をしているかだけでは、書き写しと変わりません。** かたまりごとに、次のどれかを 1 行添える。

- **素直に書くとどうなるか。** なぜその形を選ばなかったか
- **崩すと何が起きるか。** 順序を入れ替えたら / この行を消したら
- **書かれていないもの。** 比較していない項目、指定していない並び順、握りつぶしていないエラー

**全部のかたまりに付けなくてよい。** 引数を詰め替えているだけの所に「なぜ」は無い。**無いなら書かない**ほうが、ある所が目立ちます。

### 6. 分量と締め

**長くなります。畳もうとしない。** 読み下しは順に追うためのもので、要約すると役目を失います。

- **冒頭に 3〜5 行の見取り図。** 「この関数は 4 つのかたまりでできています」と先に言う。読み手が現在地を把握できる
- **末尾に、読み終えた人向けの 1〜3 行。** 次に読むと繋がる場所（呼び出し元、対になる実装、テスト）
- **まとめの表は要らない。** 本文が既に順を追っているので、同じ情報を 2 度持つことになる

## 出力の目安

| 対象 | 目安 |
| --- | --- |
| 関数 1 つ（〜50 行） | かたまり 2〜4 個。**抜粋は各 1 個** |
| ファイル 1 つ（〜300 行） | かたまり 5〜10 個。見出しで区切る |
| **それ以上** | **範囲を絞るか、対象を分けて 2 回に分ける**。1 回で読み下せる量には限りがある |

**図は基本要らない。** 順に読むための説明なので、**図を入れると視線がそこで止まります**。例外は、書かれている順と走る順が違うとき（`sequenceDiagram` で走る順を先に見せる）。

## やってはいけないこと

- **コードを書き換えること。** 説明だけを行う。修正が要るなら指摘に留め、ユーザーの指示を待つ
- **呼び出し元を見ずに書くこと。** その場の行だけでは意味が決まらない
- **抜粋を整形・改変すること。** 実物と違うものを見せることになる
- **全行を貼ること。** 意味のまとまりで切る。切れないなら対象が大きすぎる
- **「ついでに関連する言語機能も」と広げること。** そのコードに出てくるものだけ。**広げると言語入門にすり替わる**
- **何をしているかだけ書いて終えること。** 書き写しと変わらない。「なぜ」が要る所には 1 行添える
- **要約して畳もうとすること。** 読み下しは順に追うためのもので、畳むと役目を失う
- **図やまとめの表で締めること。** それは `/break-down` の形
- 実装手順（ステップ 1, 2, 3…）を勝手に添えること。聞かれたら出す

## 関連

- `/break-down`（噛み砕いて説明する）: **兄弟。** あちらは俯瞰（なぜこの形か）、本スキルは逐行（この行は何か）。**両方要るなら `/break-down` を先に**
- `/explain-review`（レビューコメントの意図を解説する）: **同じ explain 系。** あちらは出口が**対応可否の判断**
- `plain_language_explanation.md`（噛み砕いた説明）: **どこまで文法を開くかはあちらが決める。** 言語ごとの習熟度は `CLAUDE.md`
- `report_formatting.md`（報告に貼る識別子の書式）: `file:line` で指す規定はあちらが持つ
- `verify_before_asserting.md`（断定の前に裏を取る）: 読み下しは断定の連続になる。**推測が混ざると気づかれない**
- `/review-pr`（他人の PR をレビューする）: **あちらは良し悪しを判断する**。本スキルは理解を助けるだけで、指摘はしない
