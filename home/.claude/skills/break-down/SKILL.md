対象が**何をしていて、なぜそうなっているか**を噛み砕いて説明します。実装を読んで裏を取り、**図と表で構造を見せる**のが中心です。

**説明だけを行い、コードは書き換えません。**

## 対象

| 引数 | 例 | 読むもの |
| --- | --- | --- |
| **PR 番号 / URL** | `3002` | `gh pr view` の本文と `gh pr diff` の差分 |
| ファイル / 関数 / 型 | `import_csv.go` / `BulkCreate` | Read / Grep で実コード |
| 概念・仕組み | 「変更履歴の作られ方」 | 関係するコードを横断で探す |
| **レビューコメント** | 対象 ＋ コメント本文 | 該当箇所のコードと、指摘の前提 |

**PR 番号だけ渡されたら PR 全体**を扱う。コメントの解説はその一部で、**コメント本文が渡されたときだけ**そちらに絞る。

第 2 引数は**観点の指定**としても使う（「テストの意図を中心に」「なぜこの設計にしたか」等）。

## 進め方

### 1. 実物で裏を取る

**PR 本文やコメントの記述をそのまま信じない。** 本文は書いた時点のもので、その後の変更で古くなっています。**実装を読んでから書く**（`verify_before_asserting.md`）。

- PR なら `gh pr diff` で差分を見て、要点になるファイルは Read で前後の文脈まで読む
- 関数なら定義と**呼び出し元**の両方を見る。使われ方が分からないと「なぜ」が書けない
- 「変更前はどうだったか」が要るなら `git show <base>:<file>` で比べる

### 2. 構造を図にする

**順序・分岐・関係が主題なら、散文で書かずに図にする。** ` ```mermaid ` フェンスがそのまま描画されます。

| 主題 | 使うもの |
| --- | --- |
| 処理の順序、その順でないと壊れる理由 | `flowchart LR` |
| 複数の登場人物のやりとり、並行操作の衝突 | `sequenceDiagram` |
| 前と後の対比、経路ごとの違い | `flowchart` の `subgraph` を 2 つ |
| テーブルの関係 | `erDiagram` |

**図が効くのは「並べて見ないと分からない」もの**です。1 本道の処理や、名前を見れば分かることに図は要りません。

### 3. 内部の呼び名を開く

**型名・関数名・SQL ファイル名をそのまま置かない。** 読み手はそのコードを知りません。

| そのまま置かない | 開く |
| --- | --- |
| `BulkCreate` を追加 | 複数件を**まとめて作る入口**を追加 |
| 排他ロックを取得 | 対象の行に**鍵をかける** |
| トランザクション内で | **1 つの保存処理の中で** |
| `snapshotBeforeUpdate` | 変換で書き換わる**前の値を控える** |

**識別子を出すなら、何をするものかを一言添える。** 消すのではなく、初見で意味が取れる形にする。

### 4. 「なぜ」まで届かせる

**何をしているかだけでは足りない。** 読み手が知りたいのは、たいてい次のどれかです。

- **なぜこの形なのか。** 素直に書くとどうなり、それの何が困るのか
- **崩すと何が起きるか。** 順序を入れ替えたら / この行を消したら
- **どこが壊れやすいか。** 特に**エラーにならずに静かに壊れる**箇所

**「静かに壊れる」ものは必ず書く。** 落ちてくれる問題は気づけますが、履歴が空になる・値が 0 になる類は気づかれません。**そこが説明の要る唯一の理由**であることも多い。

### 5. 実物へ繋ぐ

**解説を読んだ後、読み手はその実物を開きます。** 開く先を書かないと、説明はその場で読み捨てになる。

**要点になった箇所は `file:line` で指す**（`report_formatting.md`）。名前だけ挙げて済ませない。

**繋ぎ方は対象の大きさで変わる。** 3 のとおり呼び名は開いたうえで、そこへ行き先を添える。

| 対象 | 繋ぎ方 |
| --- | --- |
| **レビューコメント 1 件** | **該当行 1 つだけ。** 読む順も索引も要らない |
| 関数・ファイル 1 つ | 要点になった数行を指す |
| **PR・機能全体** | **下記の「読む順」まで出す** |

### 6. 大きい対象では、読む順を出す

**機能やレイヤーを跨ぐ対象は、説明を読んでも「どこから読めばいいか」が残ります。** 全ファイルを並べても、読み手は結局どれから開くか決められない。

**このスキルは、対象を理解してもらうためのものです。** 読み終えたときに**自分で続きを読める状態**になっているかまでが範囲。

- **停留所を 3〜5 個に絞る。** ファイルの列挙ではなく、**どの順に何が分かるか**を出す。依存の内側から外へ、処理の順に、など対象に合う軸で
- **重心を名指しする。** 「最初に読むならここ」を 1〜2 か所。**残りはそこから導ける**もの
- **疑問 → 場所の索引を作る。** 読んでいて「なぜ？」となる所を、**答えのあるコメントや実装の行**へ繋ぐ。表にすると引きやすい
- **テストが仕様書として読めるなら、それも渡す。** 境界や「どう変えたら何が起きるか」は、実装よりテストのほうが早く分かることが多い

**全部を出さない。** 停留所も索引も、**読み手が自分で辿れるようになるための最小限**でよい。網羅は目的ではありません。

### 7. 分量と締め

**長さは対象の複雑さで決める。** レビューコメント 1 件なら 10 行、PR 全体なら図と表を含めて数十行になる。**散文が続いたら畳めていない合図**です。

- **結論を先に置く。** 「この PR は〇〇をします」から入り、細部は後
- **最後に 1 つの表でまとめる**（変更 ＋ 何のため）。PR や、仕掛けが複数ある対象のとき
- レビューコメントの解説なら、末尾に「対応しますか？」を 1 行

## 出力の目安

| 対象 | 目安 |
| --- | --- |
| レビューコメント 1 件 | **10 行程度**。図は要らないことが多い。**該当行 1 つを添える** |
| 関数・ファイル 1 つ | 10〜20 行 ＋ 必要なら図 1 つ |
| **PR 全体** | 見出しで区切り、**図 2〜4 個 ＋ 表**。仕掛けごとに節を分ける |
| **機能・レイヤーを跨ぐもの** | 上記 ＋ **読む順と索引を別の節に立てる**。解説と混ぜない |

## やってはいけないこと

- **コードを書き換えること。** 説明だけを行う。修正が要るなら指摘に留め、ユーザーの指示を待つ
- **実物を読まずに PR 本文の要約を返すこと。** 本文が古い可能性があり、それを裏取りするのがこのスキルの中心
- **内部の呼び名をそのまま並べること。** 読み手はそのコードを知らない
- **1 本道の処理に図を足すこと。** 図は並べて見ないと分からないものに使う
- **設計原則の名前で説明を済ませること**（「Tell-Don't-Ask だから」等）。**そのコード固有の事情**を書く
- 網羅のために全ファイルを列挙すること。**要点になる箇所だけ**
- **要点を名前だけで指すこと。** 読み手が grep から始めることになる。`file:line` で開ける形にする
- **レビューコメント 1 件に読む順を付けること。** 該当行 1 つで足りる。停留所も索引も過剰
- 実装手順（ステップ 1, 2, 3…）を勝手に添えること。聞かれたら出す

## 関連

- `plain_language_explanation.md`（噛み砕いた説明）: 土台。**このスキルはその粒度を、実装の解説に具体化したもの**
- `concise_first_then_detail.md`（簡潔に）: 図と表で畳む判断はあちらが持つ
- `report_formatting.md`（報告に貼る識別子の書式）: **`file:line` で指す規定はあちらが持つ**。このスキルは、その上に**読む順の案内**を足す
- `/review-pr`（他人の PR をレビューする）: **あちらは良し悪しを判断する**。このスキルは理解を助けるだけで、指摘はしない
