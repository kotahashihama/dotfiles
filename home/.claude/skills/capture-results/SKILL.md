PR で変えた画面が動くことを確かめ、その証拠をスクリーンショットと動画で PR に残すスキルです。

撮り方と貼り方は `/update-pr-description` の `references/testing.md` が持ちます（描画を待って撮る、ログインを録画しない、表への並べ方、`--attach` の挙動）。このスキルが持つのは、その前後の4つだけです。

| このスキル | `testing.md` |
| --- | --- |
| 差分から確認項目を作る | どの位置を撮るか、描画の待ち方 |
| データを用意して元へ戻す | 副作用のある操作で状態を見る3つの時点 |
| 塗りつぶしと、その検算 | ログインを別の context で済ませる |
| 結果の表と、撮れなかった項目の書き方 | 画像の並べ方、添付の貼り方 |

画面へ辿り着く手順（ログイン、強制ログイン、手元で API を動かす条件）はプロジェクトごとに違います。プロジェクト向けの撮影スキルと、そのリポジトリのメモリを先に読みます。

このスキルを呼ぶこと自体が撮影の指示に当たります。`--screenshot` と `--video` は要りません。

## 引数

| 引数 | 意味 |
| --- | --- |
| `#<PR 番号>` | 対象の PR。複数並べてよい |
| `--env <環境名>` | 動かす環境（ `local` / `dev1` 等）。省略したら尋ねる |

環境を省略されたら `AskUserQuestion` で尋ねます。共有の環境では他の人のデータに触れうるので、こちらで決めません。

## 進め方

### 1. 確認項目を差分から作る

PR の差分を読み、変えた操作ごとに1行の確認項目を作ります。

| 列 | 書くこと |
| --- | --- |
| 画面 | 利用者が見る画面の名前 |
| 操作 | 画面の文言で書いた操作 |
| 期待する動き | 操作の後に画面で見えること |

**修正前と比べるか、修正後が動くことだけを見るかを先に決めます。** 環境で症状を再現できないなら（例: 読み取り用の DB の遅れが原因で、手元には読み取り用の DB が無い）、比べても差が出ません。その場合は修正後だけを見ると、コメントの冒頭に理由と一緒に書きます。

画面に出ない項目（フラグで隠れている、データが0件で出ない）は、撮る前に分かる範囲で外し、理由を控えます。結果の表の下に「撮っていないもの」として書きます。

### 2. データを用意する

**触ってよいのは、自分で足したデータだけです。** 既存のデータを書き換えて確かめると、戻し忘れたときに他の人の状態を変えます。

1. 足す前に、戻す手順を書いておく（ SQL なら削除と元の値への更新）
2. 足す行の ID は、結合で引いて確かめる。近い ID を目で選ぶと、別の事業者や別の利用者の行に入れる
3. 一時的に既存の値を変えるとき（ログインの日時、パスワード）は、変える前の値を控える

### 3. 塗りつぶす語を集める

**DB の値ではなく、画面に出ている文字から集めます。** DB の名前と画面の表示が一致するとは限りません（姓名の並べ方、「、」で並べた一覧）。

1. 撮る画面を一度開き、顧客の企業名と社員の氏名・メールアドレスを `innerText` から集める
2. 「、」や「,」で並んだものは1語ずつに分ける
3. `MASK` に渡す

`scripts/record.mjs` は、静止画を撮るたびに画面の文字に `MASK` の語が残っていないかを数え、残っていれば失敗にして動画を消します。漏れを目視で探さないためです。

### 4. 撮る

シナリオは1項目1スクリプトにし、`scripts/record.mjs` の `record` で包みます。使い方はファイルの冒頭にあります。

```bash
OUT_DIR=<スクラッチパッド>/out MASK='<集めた語>' node <シナリオ>.mjs
```

認証情報は、コマンドの引数に書かずにファイルから読みます。値も出力しません（ `no_secret_values_in_output.md` ）。

1項目ごとに、静止画を「操作の直後」と「読み直した後」の2枚撮ります。保存した値が直後だけ出て、読み直すと消える不具合を見分けるためです。

### 5. 戻す

撮り終えたら、手順2で書いた戻し方を流し、**戻ったことを数えて確かめます**（足した行が0件、変えた値が元の値）。戻す SQL の成功表示は、戻ったことを示しません。

自分で起動したサーバー、コンテナ、worktree も止めます。もともと動いていたものは止めません。止めてよいか分からなければ、ユーザーに尋ねます。

### 6. 組み立てて貼る

画像と動画が数枚なら PR 本文に、それより多ければ補足コメントにまとめます。コメントにしたら、本文の「テスト内容」から1行でリンクを張ります。

コメントは次の順に組みます。

1. `[fyi]` と、何を確かめたかの1〜2行（修正前と比べたか、修正後だけを見たかと、その理由）
2. 環境の表（動かしたコミット、接続先、データの出どころ）
3. 塗りつぶしたものと、録画していないもの（ログイン）
4. 結果の表: `判定 / 画面 / 操作 / 期待する動き / 結果`
5. 表の下に、撮っていないものとその理由、途中で見つけたこと
6. 項目ごとの `<details>`。中に画像の表と動画

結果の列には、画面で見えた値を書きます（「保存の直後も読み直した後も『年収を重視』」）。「問題なし」とだけ書くと、何を見たかが残りません。

途中で見つけた別件は、確かめた範囲を添えて書きます。手元でしか見ていないものは、そう書きます（ `base_records_on_measurements.md` ）。

投稿の前に文章の点検を通し（ `no_ai_style_writing.md` ）、投稿した後は `./` の参照が残っていないことを確かめます。

## やってはいけないこと

- 自分で足していないデータを書き換えて確かめること
- 戻したことを、戻す操作の成功表示だけで確かめること
- 塗りつぶしの漏れを、画像の目視で確かめること
- 再現できない環境で、修正前と比べた体裁の表を作ること。差が出ないので、比べたことにならない
- プロジェクト固有の到達手順（ログインの方法、手元の API の起動）をこの本文に書くこと。プロジェクトの撮影スキルかメモリへ置く
- 撮り方・貼り方を本文に書き写すこと。`testing.md` と二重になる
