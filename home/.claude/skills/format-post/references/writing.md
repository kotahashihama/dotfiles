# /format-post の参照: 文章の量と流れ

投稿する文章（PR 本文・補足コメント・課題管理ツールの課題とコメント）に共通する書き方。本体の該当する節から開く。PR だけの事情（テンプレの節・レビュアーへの確認事項）は `/update-pr-description` の `references/body.md` が持つ。

## 過不足なく書く

- **過不足なく書く**。読み手が判断に使う情報は削らず、**重複と前置きを削る**。差分や添付を見れば分かることは書かない。PR では、判断に使う情報は `/update-pr-description` の `references/body.md` の「読み手が拾う4点を軸にする」の4点を指す
  - **行数の上限は置かない。** 長さで判定すると、必要な情報まで落として行数に合わせることになる。判定は、読み手が要る情報を拾うまでの手間で行う
  - **散文が続いたら、構造を疑う。** 同じ観点の項目が並んでいるなら表、順序や関係を説明しているなら Mermaid、根拠の実体なら `<details>` か別コメントへ移す
  - **足すたびに、読み手のどの問いに答える文かを見る。** 1〜2行ずつ足すと、どの問いにも答えない文が気づかないうちに溜まる
  - **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・残す理由の断り書き・丁寧さの水増し・自明な補足）と同じ

## 概要から詳細へ流す

- **概要から詳細へ流す**。各節の中で結論・全体像を先に置き、根拠や細部を後に続ける。最初の1〜2行で「何の話か」が掴めるようにし、結論が最後に来る流れは避ける。テンプレートがあるなら節順は変えない
  - 文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる
  - **見出しを足して流れを作らない。** 「概要」「詳細」のような節を新設すると、テンプレートの構成が崩れるうえ、読み手は見出しだけ追って中身を読まなくなる。**節の中の文の順序**だけで実現する
  - **対応が複数あるなら症状を箇条書きで並べる。** 1つの投稿が3件以上の症状・変更を含むとき、散文で続けると**何件あるのかが読み取れない**。**読み手が観測できる形**（画面でどう見えるか）で1行ずつ並べると、差分を読む前に対象の広さが伝わる
    - 観点が1つ（症状だけ）なら**箇条書き**、観点が2つ以上（修正前と修正後、経路と対象）なら**表**
    - **3件以上で役立つ。** 2件以下なら散文のままでよい

## 読み手はその機能を知らないエンジニア

- **読み手はその機能を知らないエンジニア**として書く（土台は `rules/plain_language_explanation.md` と `rules/explain_from_observables.md` ）。**画面の見え方・エラー文など読み手が観測できるものから始め、登場人物が2つ以上あるなら誰が何を決めるかを先に置く**。**1機能を1人が担当する体制では、レビュアーは必ず別の文脈から来ます**。設計の議論に同席しておらず、その領域のコードも読んでいない
  - **内部の呼び名をそのまま置かない。** 型名・サービス名・SQL ファイル名・スキーマの挙動は、初めて見る人には意味を持たない。**何を指すか / 結果どうなるか**を一言添えるか、論理名で書く。「パースが落ちる」は「一覧が表示できなくなる」まで書く
  - **言語・フレームワークの一般的な仕組みも、原因の説明に要るなら1行開く。** 「なぜその形だと壊れるか」の理屈（例: 戻り値でエラーを返す言語では、後続処理を止めない限りそのまま次へ進む）について、読み手がその言語に習熟している前提を置かない
  - **前提を1行で補う。** 「この経路はドメインモデルを経由せず直接書き込む」のような背景は、知らない人には差分から読み取れない
  - **判断の分かれ目を書く。** 「なぜ A ではなく B か」は、その機能に詳しい人ほど自明として省きやすい
  - ただし**言い換えを重ねない**。1行足せば大半は解ける。結論を噛み砕き直して2度言うと、短さも読みやすさも同時に失う

## 表と Mermaid 図で畳む

- **表と Mermaid 図で畳む**（土台は `rules/concise_first_then_detail.md`。ここでは投稿する文章の事情だけを足す）
  - **表**: 同じ観点の項目が3件以上並ぶもの（設計判断とその理由、カラム定義、採用案と却下案、変更ファイルと役割）。1セル1〜2行に収め、長い根拠は本文に逃がす
    - **1列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、1列目がファイルパスや長い識別子だと**残りの列が潰れて縦書きになる**。パスは basename に短縮し（フルパスが要るなら本文かコードブロックへ）、長い識別子は後ろの列へ回す
    - 短くできないなら**表をやめて箇条書きにする**。列を無理に維持するより読める
  - **Mermaid**: 差分の羅列から読み取れない構造・関係・流れを示すとき。GitHub は ` ```mermaid ` フェンスをそのままレンダリングする
    - `erDiagram`: テーブルの新設・リレーション変更。**FK ありを実線 (`||--o{`)、FK を張らない論理参照を点線 (`|o..o{`)** で描き分けると設計判断がそのまま図になる
    - `sequenceDiagram`: 複数のコンポーネント・サービス・リポジトリをまたぐフロー / `flowchart`: 分岐・状態遷移・処理順
    - **順序が正しさの根拠になっているものは図にする。** 「A を B より先にしないと壊れる」は散文だと数段落かかるが、図なら一目で追える。**別文脈から来たレビュアーが最初に詰まるのがここ**
  - **擬似コード**: **分岐が入れ子で、表にすると列が破綻するときだけ**。実行順・呼び出し関係・状態遷移は Mermaid、分岐と条件の網羅は**表**が先。擬似コードはその表が破綻したときの最後の手段
    - **差分と二重になる。** 後のコミットで実装が動くと嘘になるので、**追随の対象が1つ増える**（ `keep_records_current.md` ）
    - **「差分が大きいから」を理由にしない。** 大きい差分ほど擬似コードも大きくなり、二重管理の量が比例して増える
  - 置くなら**図（全体像）→ 表（項目ごと）** の順。**同じ情報を2つの形式で持たない**。差分から自明なこと（小さな修正、単純なリネーム）に図は足さない

## 投稿前に拾うもの

書き終えたら、投稿の前に1行ずつ次を拾う。

- **指すものが決まらない語**: **1行ずつ「その行だけを読んだ人が、指すものを決められるか」で見る**（ `explain_from_observables.md` ）

  | 拾うもの | 例 |
  | --- | --- |
  | **動詞** | `飛ぶ` `走る` `回る` `叩く` `動く` `効く` `通る` `落ちる` `切り替わる` |
  | **初出の名前** | 画面・ダイアログ・hook・状態・処理の呼び名 |
  | **内部の呼び名** | `行` `レコード` `B5` `A0` `下段の2本` `上段`、会話で決めた略称 |
  | **参照** | `同じく` `同様に` `上記` `そちらも` |

  - **表のセルと見出しで最も落ちる。** 短く書こうとして主語・対象・参照先が消える。**セルは独立して読まれるので隣を指せない**
  - **置き換えは語を具体にするだけでは足りない。** 「対象を指定しないまま飛びます」を「送られます」へ直しても**何が起きるか**は伝わらない。「まとめて消す要求として扱われます」まで書く
  - **その現場で1つに決まる語は残す**（「テストが落ちる」「lint が通る」）。`plain_language_explanation.md`
  - **ルールに書いてあっても防げない。** あちらは `飛ぶ` を名指しで挙げているのに使った。**投稿前にこの段で拾う**

- **読点**: **1つずつ「打つ場所に当たるか」を見る**（ `no_ai_style_writing.md` の表）。当たらないなら落とす。打つのは長い修飾語どうしの境目・重文の境目・語順が逆のとき・外すと後ろの語と繋がるときなど。主題・短い条件節や理由節・接続詞の直後には打たない
  - **機械では判定できない。** 打つ形（重文の境目の `あり、` ）と打たない形（短い理由節の `ので、` ）が似た語尾で現れるので、**語の一覧では分けられない**
  - **書いた直後は気づけない。** 書き手は係りを知っているので、読点が無くても読めてしまう。**投稿前にこの段で通す**
  - 「そのため」「だから」で繋いだ箇所は、**前段が本当に後段の理由になっているか**を見る。繋いだつもりで飛んでいることがある
  - 補うのは**1行**。因果を書くことを理由に節を増やさない
  - **書き手には見えない。** 実装した直後は前提が身についているので、自分で読んでも飛びに気づけない。**機械的に1文ずつ問う**
- **1文の長さ**: **70文字以上の文と、読点が3つ以上ある文を拾う**（ `<details>` の中・コードブロック・表の行は除く）
  - **長いこと自体は問題ではない。** 識別子・URL・リンクが入ると字数は膨らむが、**文の構造は単純**なので直す先が無い。**判定を数より前に置く**
  - **直す価値があるのは「1行へ複数の事柄を詰めた形」**。1つの課題を分けた4本の PR で直した9箇所は、すべてこれだった（2つのリンクを1行に / 条件と理由を1文に / 列挙を1行に）
  - **畳み先は表**。列挙を表へ移すと散文が減るので、上の行数の目安とも噛み合う
  - **読点の判定に文の長さを使わない。** ここの70文字は**文を畳むかの判定**で、読点を打つかは `no_ai_style_writing.md` の打つ場所の表で決める
  - **行数を詰めると、この指標は悪くなる。** 短く見せるために2行を1行へ畳むと、読点の多い長文になる。行数を減らすより、表へ畳むほうが読み手の手間は減る
- **否定**: 「〜ではない」で終わる文と「〜ではなく、〜」の1文形を拾い、**否定した側を読み手が実際に選びうるか**を問う（ `no_ai_style_writing.md` ）
  - 選びうるなら残す（「レンジではなく個々のハッシュ」は、読み手が実際にレンジを使いうる）
  - **誰も言っていないなら落とす。** 「分離は設計ではなく〜」は誰も設計だと言っていないので、却下された仮説を一度持たせるだけ
  - **形で一律に落とさない。** 正当な用法のほうが多い
