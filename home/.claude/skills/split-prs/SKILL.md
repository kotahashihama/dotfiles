1つの PR に収まらない規模の変更は、**着手前にブランチを分けて**スタックにします。

## ブランチ名

`<type>/<slug>` の形で、**slug は kebab-case**（ `feat/talent-work-history-v1-passthrough` ）。type はコミットの `<type>` と同じ語彙を使う（ `karma_commit_style.md` ）。

**アンダースコア繋ぎにしない。** 個人の好みではなく**チームの慣習に合わせる**もので、一覧に並んだとき自分のブランチだけ表記が違うと目に付きます。

**既に push 済み・PR 化済みのブランチは直さない。** 改名すると PR を作り直すことになり、**レビューコメントと履歴が失われます**。次に切るブランチから揃えれば足ります。

**迷ったら実際のブランチ名を見る。** リポジトリごとに慣習が違うことがあります。

```bash
gh pr list --state merged --limit 20 --json headRefName -q '.[].headRefName'
```

## 分割の判断

**判断軸はレビュアーが1回で読めるか。依存の有無ではない。**

**独立してマージできることは、分ける理由になりません。** 2行 + 2行の変更は、触るファイルが重ならなくても1本で足ります。逆に、依存があっても1回で読めない量なら分けてよく、その場合はマージ順を明示します。

**着手前に「1 PR で収まるか」を見積もる。** 収まらないなら最初から分ける。

| 兆候 | 対応 |
| --- | --- |
| **目的が2つ以上ある**（リファクタ + 機能追加） | 目的ごとに分ける。混ざるとレビュアーが「なぜこの変更が要るか」を判断できない |
| **分けると決めた中に、独立してマージできる塊がある** | 先に出せるものを下段へ。上段が長引いても下段は進む。**独立していること自体は分ける理由にならない** |
| 書いているうちに**変更ファイルが増え続けている** | 途中でも下段を切り出す。**後から分けるより、書きながら分けるほうが安い** |
| レビュアーが1回で読み切れない量になった | 分ける。指摘が1 PR に集中すると、どれがどの変更への指摘か追えなくなる |
| **既に複数の PR を出した後で、依存関係が読み取れないと気づいた** | **後からスタック化する**（下記）。分け直しは要らない |

判断に迷ったら**分ける側に倒す**。スタックなら下段から順にレビューが進むので、分けすぎても損は小さい。逆に1本へ詰め込むと、**レビューが止まったとき全部が止まる**。

### マージ順を書くときは、依存を実体で判定する

**この節は分割の可否を決める手順ではありません。** 分けると決めた後、**どちらを先にマージするか**を書くために見ます。重なりが0件でも、それは「分けてよい」を意味しません。

**PR 本文が他の PR に触れていても、依存とは限りません。** 「残りは #123が担当する」のような分担の説明は、マージ順を縛らない。

| 見るもの | コマンド | 依存の判定 |
| --- | --- | --- |
| **触るファイルが重なるか** | `git diff --name-only main...<branch>` を突き合わせる | 重なれば衝突しうる |
| **相手のコミットを含むか** | `git merge-base --is-ancestor <A> <B>` | 含むなら実質スタック |
| マージできるか | `git merge-tree --write-tree main <branch>` | 非ゼロなら衝突 |

**一部のペアだけ見て「独立」と断定しない。** N 本あれば組は N(N-1)/2通りある。実際に10本のうち4組だけ調べて「全部独立」と報告し、**後から8組で重なりが見つかった**。

### 検査を厳しくする PR は、他のすべてに依存する

lint ルールの追加・型検査の導入・閾値の引き上げは、**その時点のコード全体が対象**になる。他の PR が違反を含んでいれば、どちらを先にマージしても片方が落ちる。

| マージ順 | 何が起きるか |
| --- | --- |
| 検査が先 | 後続の PR が CI で落ちる |
| コードが先 | 検査 PR のマージ時点で違反が残っていれば落ちる |

**規模で決める。**

| 違反の修正量 | 扱い |
| --- | --- |
| **小さい**（数十行） | **検査と同じ PR にまとめる**。分けると必ず順序の問題が出る |
| **大きい**（1 PR に収まらない） | 分けたまま、**本文にマージ順を書く**。「〜が入った後にマージする」の1行 |

**「依存があるから1本にする」ではない。** ここでも本則（冒頭の「レビュアーが1回で読めるか」）が効く。依存があっても分けてよく、その代わり順序を明示する。

## 期待する挙動

1. **下段から順にブランチを adopt する**（ローカル操作。GitHub には影響しない）

   ```bash
   gh stack init <下段ブランチ> <上段ブランチ>
   ```

   既存ブランチはそのまま取り込まれる。`--base` でトランクを指定できる（既定はデフォルトブランチ）。

2. **GitHub 上のスタックへリンクする**

   ```bash
   gh stack submit --auto
   ```

   push・PR の base 更新・スタックの作成をまとめて行う。**既に PR があるブランチは新規作成されず、base とリンクだけが更新される**（本文・draft 状態は変わらない）。

- `gh stack view` で現在の並びを確認できる
- 下段の変更を上段へ伝播するときは `gh stack rebase`、リモートと揃えるときは `gh stack sync`
  - **上段に他の人のレビューが付いていたら `gh stack rebase` を使わない**。上段の履歴まで書き換わる（ `no_rebase_under_human_review.md` ）。その PR だけ `git merge` で取り込む
- PR 本文にも**どのブランチの上に積んでいるか**を1行書く。スタック表示に気づかないレビュアーがいる

### 既に PR が出ている群を、後からスタック化する

**分け直しは要りません。** PR 番号を下段から順に並べるだけで、GitHub 上のスタックだけを作れます。

```bash
gh stack link <下段のPR> <次のPR> ... <上段のPR>
```

`link` は**ローカルの追跡を伴わない**ので、`init` の adopt も `submit` の push も起きません。**PR 本文・draft 状態・レビューコメントは一切変わりません。**

**鎖にマージ済みの PR が混ざっていると `gh stack unstack` は失敗します。** 並びを組み直したいときは unstack を経由せず、`link` で残った PR だけを張り直す。
