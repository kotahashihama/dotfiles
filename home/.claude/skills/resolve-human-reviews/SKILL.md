人間のレビュアーから付いたコメントを、**コードの修正だけで解決**します。GitHub 上には何も書き込まず、**どのコメントにどのコミットで応えたか**を会話でユーザーに報告するところまでが責務です。

bot コメントを扱う `/resolve-ai-reviews` と対になりますが、**GitHub への書き込みの有無が決定的に違います**。

| | `/resolve-ai-reviews` | このスキル |
| --- | --- | --- |
| 対象 | bot (`user.type == "Bot"`) | **人間 (`user.type == "User"`)** |
| GitHub への返信 | ハッシュ or 理由を返信 | **しない** |
| Resolve conversation | する | **しない** |
| 対応結果の報告先 | GitHub + 会話 | **会話のみ** |

返信するかどうか・何と返すかは**レビュアーとの当事者間のやりとり**であり、ユーザーが決めることです。こちらは修正と報告に徹し、返信の要否を尋ねもしません (`no_auto_reply_human_review_comments.md`)。

## 進め方

### 1. 対象 PR とコメントの特定

- 引数に PR 番号があればそれを使う。無ければ `gh pr view --json number` で現在のブランチから特定する (該当 PR が無ければユーザーに確認)
- `gh repo view --json nameWithOwner -q .nameWithOwner` で `OWNER/REPO` を取得する
- インラインコメントを取得し、**人間かつトップレベル**に絞る:

  ```bash
  gh api repos/OWNER/REPO/pulls/<PR>/comments --paginate \
    -q '.[] | select(.in_reply_to_id == null) | select(.user.type == "User") | "[\(.id)] \(.user.login) | \(.path):\(.line // .original_line)\n\(.body)\n---"'
  ```

- レビュー本文 (`gh pr view <PR> --json reviews`) にサマリがあれば併せて読む
- 接頭辞 (`[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]`) を優先度の一次判断に使う
- **複数 PR にコメントが付いている場合は PR ごとに区切って進める**。ブランチを跨ぐので、混ぜると対応表が崩れる

### 2. 意図の咀嚼と現状コードの照合

コメント 1 件ごとに、**何を問題視しているか**と**現状のコードがどうなっているか**を突き合わせる。指摘が既に解消済み・前提が誤っている (誤検知) ケースがあるので、**指摘を鵜呑みにせず実物を読む**。

指摘が事実を主張している場合 (「BE は `""` を返しうる」「この関数は他でも使われている」等) は、**一次情報で裏を取る** (`verify_before_asserting.md`)。他リポジトリのコードがローカルにあるなら読む。

### 3. トリアージ

すべてのコメントを次のいずれかに割り当てる。**放置しない**。

| 判定 | 基準 |
| --- | --- |
| **対応** | `[must]` は原則すべて。`[imo]` / `[nits]` は「直した結果が本当に良くなるか」で判断する |
| **非対応** | 既に満たされている / 前提が誤っている / 直すとかえって劣化する。**理由を必ず言語化する** |
| **ユーザー判断待ち** | セッション内の合意・PR 本文の明記事項と抵触し、どちらが正か即断できない |

**セッション文脈と照合する。** ユーザーが「〇〇は残して」と言った箇所、PR 本文で「意図的に採用しなかった」と書いた項目、memory に記録した好みに抵触する指摘は、優先度に関わらず自動で従わない。文脈で方針が確定済みなら独断で非対応にしてよく、迷うならユーザーに尋ねる (AskUserQuestion で「対応 / 非対応 / 別方針」を選ばせる)。

### 4. 修正の適用と品質チェック

- 対応すると決めたものをコードに反映する。1 つの指摘が複数箇所に波及する場合 (文言変更、リネーム等) は**参照元・テスト・モックまで漏れなく追随する**
  - 文言を変えたら、その文言を期待するテストを grep で洗う。**ただしテスト内のローカル定数は追随不要**なので、実装を参照しているかを確かめてから直す
- 修正後、影響範囲のテスト・lint・format を通す。**テスト一式は `run_in_background: true` で流し、待つ間に残りの修正を進める**

### 5. コミット & プッシュ

このスキルの起動を、**このレビュー対応分のコミット & プッシュへの明示的な承認**とみなす (`no_auto_commit.md` の言う「明示的な指示」に該当)。確認質問は挟まない。

- **コメントとコミットが対応付く粒度で分ける**。1 コメント 1 コミットが基本だが、同一ファイルの同趣旨の指摘 (定数の位置と doc の表記など) はまとめてよい。逆に、性質の違う指摘 (文言変更とテスト追加) を 1 コミットに混ぜない
- `karma_commit_style.md` に従う。subject は日本語の体言止めで、**差分の意図そのもの**を書く。「レビュー対応」「指摘修正」のような meta は入れない
- 対象ファイルを名指しで `git add` する。`--amend` / `--no-verify` / force 系は使わない

### 6. 対応表の報告

**GitHub には何も書かず、会話で報告する。** これがこのスキルの成果物。

- **1 つの表にまとめ、GitHub の Conversation と同じ順で並べる**（`report_formatting.md`）。Step 1 の取得順がそのまま Conversation の順なので、**優先度や対応可否で並べ替えない**。ユーザーは PR を上から見ながら返信する
- 列は「コメント ID / 種別 / 位置 / 指摘の要約 / 結果」。結果にはコミットハッシュか非対応の理由を入れ、裏取りの根拠が長ければ表の下に回す
- ハッシュは**レンジではなく個別に列挙**する
- PR が複数なら PR ごとに節を分ける

## 出力の目安

- 対応表を主役にする。表の外に長い解説を積まない
- 非対応の理由は 1〜2 行。裏取りの根拠 (ファイル名・関数名) があれば添える
- 全件対応で非対応ゼロなら、対応表だけで完結してよい

## やってはいけないこと

- **GitHub 上でレビューコメントに返信すること**。`gh api .../replies`、`gh pr comment`、`gh pr review` のいずれも使わない
- **Resolve conversation すること**。解決したかの判断はレビュアーとユーザーの領分
- **返信の要否をユーザーに尋ねること**。尋ねること自体が判断領域への侵入になる。必要ならユーザーが明示指示を出す
- bot コメントを混ぜて処理すること。bot は `/resolve-ai-reviews` の責務で、返信の扱いが正反対
- レビュアーの文言・判断のナラティブを**コード中のコメントに転記すること** (`no_review_comment_echo_in_code.md`)。必要な「なぜ」はコミットメッセージ本文に置く
- 対応表を出さずにコミットハッシュだけ報告すること。**どのコメントに応えたか**が対応表の本体
- `[must]` を根拠なく見送ること。非対応にするなら理由を言語化する
- 修正なのにテスト・lint を通さずにコミットすること

## 例外

- ユーザーが「このコメントには〇〇と返信して」と明示指示した場合は、そのコメントに限り返信を代行してよい (末尾に生成者表示の Note ブロックを付ける)
- ユーザーが特定のコメントについて「対応しないで」と指示した場合は、トリアージせずその指示に従う
- レビュー対応で差分が動いたら、続けて `/finalize-pr` を呼んでよい (点検と PR 説明の整合確認)。ユーザーが不要と指示した場合はスキップする
