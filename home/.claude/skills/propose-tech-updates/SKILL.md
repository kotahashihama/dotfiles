今いるリポジトリに**実際に効く技術更新だけ**を提案します。「新しいものの紹介」ではなく、**このコードベースのどこがどう変わるか**まで書けたものだけを出します。

**該当が無ければ「今回は無し」と答えて終わります。** 無理に絞り出すと、本当に効く提案が埋もれます。

## 進め方

### 1. 現状を読む（推測で書かない）

**バージョンは必ず実物から取る。** 記憶にある値は古くなっています。

```bash
gh repo view --json name -q .name        # どのリポジトリにいるか
cat package.json                          # ルートの依存とスクリプト
ls apps packages 2>/dev/null              # モノレポなら構成
```

| 見るもの | なぜ |
| --- | --- |
| **各 package.json の依存** | 提案の可否がここで決まる。**古い前提で書くと全部外れる** |
| ビルド・テスト・lint の設定 | 何を使っているか。設定ファイルの実物を読む |
| `.github/workflows/` | CI で何を検査しているか |
| **規約ドキュメント** | `docs/` や `CLAUDE.md`。**技術方針が書かれていることがある** |

**規約に反する提案をしない。** 「このアプリではキャッシュライブラリを使わない」のような方針が書かれていたら、それに反する提案は最初から候補に入れません。

### 2. 一次情報を当たる

**二次記事は裏取りにだけ使う。** 公式より速い情報源はありません。

| 情報源 | 引き方 |
| --- | --- |
| **GitHub Releases** | `gh release list --repo <owner>/<repo> --limit 10` |
| リリースの本文 | `gh api repos/<owner>/<repo>/releases/latest --jq .body` |
| **Issue / Discussion / RFC** | **破壊的変更はリリースノートより先にここで議論される** |
| 公式ブログ | `WebFetch` で読む |
| 補助 | `WebSearch`。気になった話題の裏を取る |

**調べる先は、手順 1 で読んだ依存から決める。** 使っていないものを調べても意味がありません。

**公開リポジトリなら認証なしで読めます。** 自社の private リポジトリと違い、OSS の Releases・Issue は `gh api` でそのまま引けます。

### 3. 3 つの型に当てはまるものだけを残す

| 型 | 中身 |
| --- | --- |
| **1. 活かせていない機能** | 今使っているものに、まだ使っていない機能がある |
| **2. 先回りできる変更** | 破壊的変更・非推奨化が来ている。今なら安く対応できる |
| **3. 課題を解く選択肢** | 今の構成に実際の課題があり、別の選択肢が解く |

**「新しいから」は理由になりません。** 特に新しい構成を追っているリポジトリでは、紹介系の提案はほぼ空振りします。

### 4. 落とすもの

- **規約・技術方針に反するもの**（手順 1 で読んだもの）
- **実際に困っていない問題への対処**
- **既に Issue や PR になっているもの**（`gh issue list --state all` / `gh pr list --state all` で確認）
- 流行っているだけで、このリポジトリに効かないもの

**既存の Issue を確認せずに提案しない。** 毎回同じ提案が積み上がります。

### 5. 出す

**1 提案につき、次の 4 点を書く。** どれか 1 つでも書けないなら、その提案は落とします。

| 項目 | 中身 |
| --- | --- |
| **何が変わったか** | 一次情報へのリンク付き |
| **どこに効くか** | **ファイルパスと現在のバージョンを実際に読んで書く** |
| **コスト** | 入れる場合の作業量。入れない場合に何が起きるか |
| **推奨** | 入れる / 見送る / 様子を見る と、その理由 |

**3 件を超えて出さない。** 多いと読まれません。

最後に**調べた範囲**（見た情報源と本数）と、**提案しなかった理由**を簡潔に添えます。何を見ていないかが分かると、次に自分で調べる場所が決まります。

## 出力の目安

- **該当なし**: 2〜3 行。調べた範囲と、なぜ無かったか
- **該当あり**: 1 提案につき表 1 つか 5 行程度。**3 件まで**
- Issue にするかはユーザーが決める。**勝手に作らない**

## やってはいけないこと

- **バージョンを記憶で書くこと**。必ず実物を読む
- **規約ドキュメントを読まずに提案すること**。方針に反する提案は最初から候補外
- **既存の Issue / PR を確認せずに出すこと**。同じ提案が毎回積み上がる
- **無理に提案を作ること**。該当が無ければ「無し」でよい
- **3 件を超えて出すこと**。読まれない量は出さないのと同じ
- **Issue や PR を勝手に作ること**。提案までが責務で、起票はユーザーが決める
- **コードを変更すること**。検証のための一時的な変更も、必ず元へ戻す
- 二次記事だけを根拠に断定すること（`verify_before_asserting.md`）

## 関連

- `verify_before_asserting.md`（断定の前に裏を取る）: **バージョンも「非推奨」も裏取りの対象**。公式に無い含意を足さない
- `write_for_installed_versions.md`（入っているバージョンで書く）: あちらは**書くときにどの版へ合わせるか**、本スキルは**版を上げるべきかの判断**
- `concise_first_then_detail.md`（簡潔に）: 提案も結論から。3 件までに絞るのは同じ理由
