# /update-pr-description の参照: multi-pr

本体の手順3から切り出した詳細。本体の該当する項目から開く。

## 1つの課題を複数の PR に分けたなら、他の PR と書き方を揃える

- **1つの課題を複数の PR に分けたなら、他の PR と書き方を揃える**。レビュアーは並べて読むので、**同じことを別の言い方で書くと差があるのかを毎回確かめることになる**

  | 揃える | 揃えない |
  | --- | --- |
  | **課題の一覧表**（列名・症状の文言・どの行を太字にするか） | **散文の量**。その PR が持つ情報で決まる |
  | **用語**（同じものを2通りで呼ばない） | **影響範囲の形式**。画面が変わるなら表、件数や通知なら散文 |
  | **他リポジトリの参照形式**（ `owner/repo#123` ） | **テンプレ由来の差**（HTML コメントの件数・節の構成） |

  - **揃えるのは読み手が突き合わせる部分だけ。** まったく同一にすると、**中身の違いが潰れて嘘になる**
  - **相手が別セッションなら、実物の文言を送ってもらってから決める**（ `notify_related_repo_sessions.md` ）。記憶で揃えると、片方だけ古い文言が残る
  - **課題の一覧表は、その課題に紐づく PR にだけ置く**。派生した別件の PR に置くと、関係のない情報が乗る
  - **3本以上に分けたなら、「なぜこの本数なのか」は1箇所だけに置き、残りからリンクする**。課題の一覧表とは別で、あちらは**課題単位**（③ → この PR）、こちらは**原因単位**（原因1つがどこに何本として出たか・後段が前段の結果かどうか・分割の都合ではないこと）。置くのは**レビュー順の先頭の PR**で、そこから読み始める。**レビュアーが PR ごとに別の人なら、各 PR へ短く置く**（重複が読み手ごとに1回で済む）。判定は `explain_from_observables.md` の「複数の PR に分けたなら、どこから入っても全体へ着けるようにする」
  - **課題の一覧表とは別に、課題票の記述と修正の対応を補足に置く**。一覧表は課題単位（③ → この PR）で、**記述の言葉までは繋がらない**。冒頭は課題 → 原因 → 直し方 → 原因が取り除かれる理由の筋で書き、対応表は置かない。付随した変更は筋の後ろに分け、解決する状態を添える。判定は `explain_from_observables.md` の「課題票に紐づくなら、課題票の記述から繋ぐ」
  - **実測してから直す**。散文の行数・表の数・用語の出現数を数え、**どこがずれているかを特定してから**手を入れる（数えずに直すと、揃ったつもりで別の箇所がずれる）


## Backlog 節への対応

- **Backlog 節への対応**:
  - 会話コンテキストで Backlog 課題番号（ `PROJ-XXX` 等）または URL が提供されているか確認する。既存 PR 本文の Backlog 節に既に URL が入っていればそれを維持する
  - **貼るのは PBI。関連する課題があれば行を追加して並べる**: テンプレが複数行を許すなら、**PBI を先頭に置き**、その配下の開発タスクなど直接の動機になった課題があれば続けて貼る。どちらも「Pull Request」カスタム属性へ自動で入るので、**PBI 側で機能全体の PR 群を、タスク側でその作業の PR を追える**
    - **PBI かどうかは issueType で確かめる**。親子関係だけでは判定できない（親がさらに上位の課題であることもある）
    - **本文を編集すると紐づけのワークフローが再実行される**（ `pull_request` の `edited` を拾う設定の場合）。既存の紐づけは消えず、追記した課題が増えるだけ。ただし**成功表示では紐づいたか分からない**ので、Backlog 側の属性を引いて確かめる
  - **その課題の調査中に見つけた別件でも貼る**: 閉じる条件に入らなくても、**その課題から辿れるように**貼る。判定は `karma_commit_style.md` の「PR に番号を付けるか」
  - **貼ったら、課題の側へ発見の経緯を `[fyi]` で残す**: 課題に並ぶのは PR のタイトルと URL だけなので、**なぜそれが並んでいるのか**が読めない。書く3つ（何が起きていたか / どう見つけたか / その課題との関係）はあちらが持つ
    - **課題管理ツールへは MCP 経由で投稿するので、書式のフックが走らない**。行末の句点・数値の表記・生成者表示を自分で確かめる（ `github_writing.md` ）
  - **新たに提供されている場合**: Backlog 節に **URL を貼る**（Backlog 側の GitHub Actions ワークフローが URL を検知して PR と課題を自動で関連付ける）。番号だけ提供された場合は、リポジトリ内の過去 PR 本文で URL フォーマットを確認して組み立てる。過去 PR にも例が無ければユーザーに URL を尋ねる
  - **提供されておらず既存本文にも無い場合**: ユーザーに `Backlog 課題番号 or URL はありますか？` と尋ねる。番号や URL を貼らずに勝手に「なし」で埋めない
  - **ユーザーが「なし」と返した場合**: テンプレの案内どおり `- なし` に理由を添える（例: `- なし (BE 側の UX 改善対応)` ）

## 複数の PR に分けたなら、どこから入っても全体へ着けるようにする

**分けた本人は、隣としか繋がっていないことに気づけません。** 各 PR は直前の PR を見ながら書くので、毎回1〜2本先までは正しく繋がります。全体は連鎖しているのに、どこから入っても2本先が見えない状態になる。

実際に、1つの課題を4本へ分けた PR 群で、4本とも依存とマージ順を書いているのに「なぜ4本なのか」を一覧にした箇所がどこにもありませんでした。4本とも自分で書いたのに、並べて読むまで気づいていません。

**判定は「どの1本を開いた読み手も、全体へ着けるか」。** 着けないなら、全体像を1箇所に置いて残りから指す。

マージ順があることは、全体へ着けることを意味しません。マージ順は「どれを先に入れるか」で、全体像は「なぜこの本数なのか」。分割の都合で分かれたのか、前段の結果として後段が生まれたのかは、順序からは読めません。

置き方は `/update-pr-description` が持ちます（正本をどの PR へ置くか・何を並べるか）。

## 判断が覆ったコメントの残し方

**前のコメントは編集せず、GitHub の Hide comment で `Outdated` としてマークする。**
折りたたまれたうえで「marked as outdated」と表示され、開けば当時の内容がそのまま読めます。

```bash
gh api repos/OWNER/REPO/issues/comments/<id> --jq '.node_id'
gh api graphql -f query='mutation($id: ID!) { minimizeComment(input: {subjectId: $id, classifier: OUTDATED}) { minimizedComment { isMinimized } } }' -F id=<node_id>
```

新しい判断は新規コメントとして投稿する。上から読めば「こう考えた → 覆った → こうなった」の流れが辿れます。

新しい側から、前のコメントへリンクを貼る。畳まれている分、リンクが無いと読み手が探しに行くことになります。

```markdown
**[前のコメント](https://github.com/OWNER/REPO/pull/123#issuecomment-456)で〜と判断していましたが、それを訂正します**
```

コメントの URL は `gh api` の応答の `html_url`、または GitHub 上のコメントメニューの `Copy link` で取れます。

`<details>` で自作しない。GitHub の機能を使えば、覆ったことが一目で分かる形で表示されます。
自作すると、開くまで何が覆ったのか分からない見た目になります。

**調査の内容は消さない。** 結論が覆っても、何を見て何が分かったかは次に同じ壁へ当たった人の手がかりになります。

うっかり上書きしてしまったら、編集履歴から戻せます。GitHub はコメントの版を保持しています。

```bash
gh api graphql -f query='query($id: ID!) { node(id: $id) { ... on IssueComment { userContentEdits(first: 20) { nodes { editedAt diff } } } } }' -F id=<node_id>
```
