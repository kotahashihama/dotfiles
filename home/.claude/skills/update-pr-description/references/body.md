# /update-pr-description の参照: body

本体の手順3から切り出した詳細。本体の該当する項目から開く。

## 概要には4つを順に書く

- **概要には4つを順に書く。** 目的 → 選択 → 解決 → 結果

  | 要素 | 書くこと |
  | --- | --- |
  | **目的** | **いま何が困っているか**。直さないと何が起きるか |
  | **選択** | **採れた案が複数あったなら、選んだ案と根拠**。1つしか無ければ省く |
  | **解決** | 選んだ案でどう直したか |
  | **結果** | マージ後にどうなるか |

  - **これは順序の規定で、行数を増やす規定ではない。** 1文に畳んでよい（「〜が困っていたので、〜を選び、〜した。結果〜」）
  - **4つを別々の見出しにしない。** 節の中の文の順序で実現する（見出しはテンプレが決める）
  - **不具合の修正なら、目的に「その形がなぜ破綻するか」まで書く。** 症状と判定の形だけでは、レビュアーには**値を足した変更**に見える
    - **段は3つ。** 症状 → 判定の形 → **その形が破綻する理由**。3段目を書くと、**解決で形を変えた理由**（列挙を対応表へ、条件を分岐へ）が目的から読める
    - 実際に、症状と形だけ書いて**3回指摘を受けました**。最終形は「一方の軸で、もう一方の判定を代用していた」で、**代用という1語**が説明になっています
  - **選択を省くのは、案が1つしか無いときだけ。** 省くと「なぜこの形なのか」がレビュアーに残る
  - **差分から届く範囲が読み取れないなら、1行目で決める。** ローカルだけか、本番の動作が変わるか。**書いていないと、レビュアーは本番の話かと疑う**（実際に「デプロイ環境に影響しないよね」と3回問われた）
    - **実装コードの修正では書かない。** 本番の動作が変わるのは自明で、「本番の動作が変わります」だけの行が残る（実際に不具合修正の PR へ書いて「当たり前すぎる」と指摘された）
    - **書くのは CI・ビルド設定・設定ファイルのように、届く先が読み取れないとき**
    - **画面が変わる PR で「見た目は変わりません」と書かない。** スクリーンショットを貼る PR では、本文と添付が食い違う
  - **結果は、読み手が数えられる形にする**。消える手作業の回数、減るコマンド数、短くなる時間。「簡単になる」「改善する」は書き手の感想で、検算できない
  - **数で示せないなら、直さなかったときの壊れ方を書く**。「画面は出るのにアップロードだけ失敗する」のように、**症状と気づきにくさ**を添えると優先度が伝わる
  - **目的と結果は別の情報**。目的は過去向き（何が困っていたか）、結果は未来向き（マージ後にどうなるか）。前者だけで済ませない

## 届く範囲が差分から読み取れないときは、段を分けて書く

- **届く範囲が差分から読み取れないときは、段を分けて書く**。CI・ビルド設定・設定ファイルの変更が該当する。**読み手が最初に疑うところ**なので、書いていないと差分で確かめることになる
  - **段を分けて書く。** 「デプロイ環境に影響しない」の一言では、どこで止まるのかが伝わらない

    | 段 | 確かめ方 |
    | --- | --- |
    | ワークフローが起動するか | `paths` / `paths-ignore` と**変更ファイル全件**を突き合わせる。**1件でも外にあれば起動する** |
    | 成果物が変わるか | ビルドが読む対象に差分があるか（ `COPY` の対象、コンパイル対象） |
    | 動作が変わるか | 起動するもの（ `ENTRYPOINT` / `CMD` ）が読む対象に差分があるか |

  - **「起動しない」と「動作が変わらない」は別の主張。** 混ぜると、片方の誤りでもう片方まで疑われる。実際に、変更6ファイルのうち2件だけ見て「ワークフローそのものが起動しません」と書き、`Makefile` が `paths-ignore` の外にあって誤りになった

## 既存の構成を変えるなら、いまの構造が歴史的経緯によるものだと示す

- **既存の構成を変えるなら、いまの構造が歴史的経緯によるものだと示す**。レビュアーは「**なぜ今の形なのか分からないまま変えてよいのか**」を疑うので、そこを埋めないと妥当性の議論が進まない
  - **肯定形で名前を付ける。** 「設計ではない」と否定から入ると、読み手は却下された仮説を一度受け取ることになる
  - 示すのは3つで、**どれも履歴と設定から引ける**

    | 見るもの | 何が言えるか |
    | --- | --- |
    | **入った順**（ `git log --diff-filter=A` ） | 別々の時期に別々の目的で入ったのか、同時に設計されたのか |
    | **名前と値の一致**（両側の設定を突き合わせる） | 一致しているなら、同じものを見る前提で書かれている |
    | **既存の案内**（README・手順書） | 回避策として書かれているなら、その構造は前提ではなく症状 |

  - **いまの形が選ばれた理由が別にあるなら、それも書く。** その理由が消えることまで示せて初めて妥当性が立つ。実際に「連携する Lambda を載せられるのが片側だけ」という制約があり、**設定1語で消える**ことを示して決着した
  - **記憶で書かない。** 「たしか経緯があったはず」は根拠にならない（ `verify_before_asserting.md` ）
- レビュー観点を意識して、注目してほしい箇所・トレードオフがあれば明記
- テスト内容は実施済みの事実として**通常の箇条書き**で書く（ `- [ ]` / `- [x]` のチェックボックスは未消化の TODO に見えるため使わない）
  - **実装を戻したときに何件落ちるかを書く。** レビュアーは「テストがある」と「**そのテストが効いている**」を区別できない。件数を書くと検算になる
    - **反転させて実際に走らせた件数を書く**（推定で書かない）。検算のために置いた数字が検算されていないと最悪の形になる（ `base_records_on_measurements.md` ）
    - **戻して `git status` が clean になったことを確かめる。** 反転した分とその検証で見つけた修正が同時に未コミットなら、`git checkout` は両方を消す（ `verify_the_check_worked.md` ）

## 修正前と修正後を、観測できる挙動で並べる

- **修正前と修正後を、観測できる挙動で並べる**。レビュアーが知りたいのは「**どういう状態からどういう状態になるか**」で、実装の語（どの関数が何を渡すか）で並べると差分を読んでから翻訳し直すことになる。**画面が無い変更（API・バッチ・インフラ）でも、状況ごとの挙動を同じ形で対比できる**
  - 操作や状況を軸に「修正前の挙動 / 修正後の挙動」を対で置く。実際の値が分かるなら「実測 / 修正前 / 修正後」の3列にすると誤りの向きまで伝わる
  - **表にするのは同じ観点が3件以上あるとき**。1〜2件なら文で足りる

## 量を絞る

- **量を絞る**。レビュアーが判断に使う情報（挙動の変化・トレードオフ・見てほしい点・前提条件）は残し、**重複と前置きを削る**。差分を見れば分かることは書かない。説明が要るのは「なぜそうしたか」と「何に注意すべきか」
  - 目安は**散文で1節5行以内、本文全体30行以内**（テンプレ固定文は除く）。読む負担は散文の量で決まるので、表・図・コードブロックはこの数えから外す。超えたら表に畳むか別コメントへ切り出す
  - **足すたびに測る。** 「超えたら切り出す」は、**測る契機が無いと発動しない**。一度に大量へ書けば気づくが、**1〜2行ずつ足すと閾値を静かに越える**
    実際に、指摘を受けるまで測り直さないまま本文が59行まで伸びた
  - **書き直しは短くする機会**。既存本文で節を埋めるためだけに膨らんだ記述、冗長な箇条書きの羅列は畳む
  - **テンプレの節は削らない**。短くするのは中身。該当なしなら `- なし` と理由を書き、`## レビューのルール` 等の固定文は維持する
    - **ただしレビュアーへの確認事項を書く節は例外で、中身を空にする**（見出しは残し、`- なし` も書かない）。見てほしい点は実装内容の節で挙げるので、**ここへ書くと重複する**
  - **テンプレの HTML コメントは、宛先で残すか消すかを分ける**。埋めたら役目を終えるものと、消すと機能が止まるものがある

    | 宛先 | 例 | 扱い |
    | --- | --- | --- |
    | **書き手への指示** | `<!-- 変更の目的 & issue -->` | **消す**。埋めた時点で役目が終わる |
    | **読み手・ツールへの指示** | レビュー言語の指定、AI レビューの適用範囲を囲むもの | **残す**。**消すと AI レビューの挙動が変わる** |

    **判断が付かないものは残す。** 消して壊れるほうが、残して読みにくいより高くつく
  - **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・残す理由の断り書き・丁寧さの水増し・自明な補足）と同じ
  - **PR 説明では「網羅のための記述」が特に出る。** テンプレの節を埋めようとして、挙げる必要のない項目まで表に並べてしまう。**該当なしは `- なし` の1行で足りる**

## 概要から詳細へ流す

- **概要から詳細へ流す**。各節の中で結論・全体像を先に置き、根拠や細部を後に続ける。最初の1〜2行で「何の話か」が掴めるようにし、結論が最後に来る流れは避ける。テンプレの節順は変えない
  - 文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる
  - **見出しを足して流れを作らない。** 「概要」「詳細」のような節を新設すると、テンプレの構成が崩れるうえ、読み手は見出しだけ追って中身を読まなくなる。**節の中の文の順序**だけで実現する
  - **対応が複数あるなら症状を箇条書きで並べる。** 1つの PR が3件以上の症状・変更を含むとき、散文で続けると**何件あるのかが読み取れない**。**読み手が観測できる形**（画面でどう見えるか）で1行ずつ並べると、差分を読む前に対象の広さが伝わる
    - 観点が1つ（症状だけ）なら**箇条書き**、観点が2つ以上（修正前と修正後、経路と対象）なら**表**
    - **3件以上で効く。** 2件以下なら散文のままでよい

## 読み手はその機能を知らないエンジニア

- **読み手はその機能を知らないエンジニア**として書く（土台は `rules/plain_language_explanation.md` と `rules/explain_from_observables.md` ）。**画面の見え方・エラー文など読み手が観測できるものから始め、登場人物が2つ以上あるなら誰が何を決めるかを先に置く**。**1機能を1人が担当する体制では、レビュアーは必ず別の文脈から来ます**。設計の議論に同席しておらず、その領域のコードも読んでいない
  - **内部の呼び名をそのまま置かない。** 型名・サービス名・SQL ファイル名・スキーマの挙動は、初めて見る人には意味を持たない。**何を指すか / 結果どうなるか**を一言添えるか、論理名で書く。「パースが落ちる」は「一覧が表示できなくなる」まで書く
  - **言語・フレームワークの一般的な仕組みも、原因の説明に要るなら1行開く。** 「なぜその形だと壊れるか」の理屈（例: 戻り値でエラーを返す言語では、後続処理を止めない限りそのまま次へ進む）は、読み手がその言語に習熟している前提を置かない
  - **前提を1行で補う。** 「この経路はドメインモデルを経由せず直接書き込む」のような背景は、知らない人には差分から読み取れない
  - **判断の分かれ目を書く。** 「なぜ A ではなく B か」は、その機能に詳しい人ほど自明として省きやすい
  - ただし**言い換えを重ねない**。1行足せば大半は解ける。結論を噛み砕き直して2度言うと、短さも読みやすさも同時に失う

## 表と Mermaid 図で畳む

- **表と Mermaid 図で畳む**（土台は `rules/concise_first_then_detail.md`。ここでは PR 固有の事情だけを足す）:
  - **表**: 同じ観点の項目が3件以上並ぶもの（設計判断とその理由、カラム定義、採用案と却下案、変更ファイルと役割）。1セル1〜2行に収め、長い根拠は本文に逃がす
    - **1列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、1列目がファイルパスや長い識別子だと**残りの列が潰れて縦書きになる**。パスは basename に短縮し（フルパスが要るなら本文かコードブロックへ）、長い識別子は後ろの列へ回す
    - 短くできないなら**表をやめて箇条書きにする**。列を無理に維持するより読める
  - **Mermaid**: 差分の羅列から読み取れない構造・関係・流れを示すとき。GitHub は ` ```mermaid ` フェンスをそのままレンダリングする
    - `erDiagram`: テーブルの新設・リレーション変更。**FK ありを実線 (`||--o{`)、FK を張らない論理参照を点線 (`|o..o{`)** で描き分けると設計判断がそのまま図になる
    - `sequenceDiagram`: 複数のコンポーネント・サービス・リポジトリをまたぐフロー / `flowchart`: 分岐・状態遷移・処理順
    - **順序が正しさの根拠になっているものは図にする。** 「A を B より先にしないと壊れる」は散文だと数段落かかるが、図なら一目で追える。**別文脈から来たレビュアーが最初に詰まるのがここ**
  - **擬似コード**: **分岐が入れ子で、表にすると列が破綻するときだけ**。実行順・呼び出し関係・状態遷移は Mermaid、分岐と条件の網羅は**表**が先。擬似コードはその表が破綻したときの最後の手段
    - **差分と二重になる。** 後のコミットで実装が動くと嘘になるので、**追随の対象が1つ増える**（ `keep_records_current.md` ）
    - **「差分が大きいから」を理由にしない。** 大きい差分ほど擬似コードも大きくなり、二重管理の量が比例して増える
  - 置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を2つの形式で持たない**。差分から自明なこと（小さな修正、単純なリネーム）に図は足さない

## 本文は軸、細部は別コメント

- **本文は軸、細部は別コメント**。本文に置くのは、この PR が**何を変え / なぜ変え / 何に注意して見るか**という軸だけ。判断に迷ったら「**この節が無いと差分を読み始められないか**」で決める

  | | 本文（軸） | 別コメント（細部） |
  | --- | --- | --- |
  | 例 | 変更の目的 / 主要な設計判断 / 影響範囲 / 前提条件・注意点 | API 契約の全文 / データモデル / 調査ログ / 他リポジトリ向けの申し送り / 検討したが採らなかった案の詳細 |
  | 読み手 | **全レビュアーが必ず読む** | 実装者・後任が必要なときだけ開く |

  切り出したら本文からリンクを貼り、**同じ情報を両方に持たない**。別コメントにも末尾の Note ブロックを付ける（ `github_note_generated_by_claude.md` ）。切り出したコメントの点検は手順7

  **補足コメントは冒頭に `[fyi]` を置き、その後で改行する。** レビュアーが使う接頭辞（ `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` ）と同じ語彙で、**対応を求めるものではない**ことが一目で伝わる。申し送りや保留条件のような「読んでほしいが返信は不要」なコメントも同じ

  ```
  [fyi]
  本文の 1 行目...
  ```

  `[fyi] 本文...` と同じ行に続けない。**アノテーションは本文と分離した1行**にする

### 差分から理由が読めない行には、その行へ `[fyi]` を置く

**本文の表に並べるだけでは足りない。** レビュアーは差分を上から読み、引っかかった行でその理由を知りたくなる。本文へ戻って探させると、読むのが止まる。

| 置く | 置かない |
| --- | --- |
| 検査（lint・型・スペルチェック）に合わせた書き換え（ `cause` を足す、初期値を外す、`??` を消す） | 差分を読めば意図が分かる変更（依頼どおりの機能追加・素直なバグ修正） |
| 名前の変更（関数名・無効化コメントが指すルール名） | 機械が一括で書き換えた整形 |
| 無効化コメントの追加・削除・範囲の変更 | |
| 辞書や設定への語・依存の追加（ `cspell.json` 、`devDependencies` ） | |

書くのは3つ。**何を変えたか・なぜ要ったか・動作が変わるか**。同じ理由で複数箇所を直したなら、代表の1件に置いて件数を添える（「このファイルの3か所」「この PR で9か所」）。消した行へ置くときは、main 側の行（ `side=LEFT` ）を指す。

**判定は「その行だけを見たレビュアーが、なぜ変えたかを当てられるか」。** 当てられないなら置く。**PR を作った直後に、差分を上から読んで置き切る。** 指摘されてから1件ずつ足すと、レビュアーの手を止める。

**投稿する前に、置く分をまとめて `/japanese-tech-writing` → `/agy-review` に通す**（ `no_ai_style_writing.md` の「文章の点検を通す場面と順序」）。1件が短くても点検の対象になる。

置く理由がコードを読む人にも要るなら、`[fyi]` ではなくコードコメントにする（ `code_comments.md` ）。`[fyi]` はレビュー中だけ読まれる。

## 課題票に紐づくなら、課題票の記述から繋ぐ

何をどう直したかが読めても、それで課題が解決するのかは読めないことがあります。課題票は報告者の言葉で書かれていて、原因を突き止めた書き手の言葉とは語彙が違います。読み手（レビュアー・品質保証の担当・報告者）は課題票を手元に置いて読むので、課題票の言葉から入れないと、修正との繋がりを自分で組み立てることになります。

**冒頭は「マージすると直る」を、課題 → 原因 → 直し方 → 原因が取り除かれる理由の筋で支える。**

| 順 | 書くこと |
| --- | --- |
| 1 | 課題が何か（課題票の言葉で） |
| 2 | 原因になっていた処理。報告者の操作から順に、どこで何が出て、それが課題票のどの記述に当たるかまでを番号付きで書く |
| 3 | どう直すか |
| 4 | その直し方で原因が取り除かれる理由（直した後の処理の流れ。記述ごとの直り方は2段目に書く） |
| 5 | マージすると直ること |

**4を省くと、原因と直し方が並んでいるだけになります。** 書き手は因果を知っているので繋がって見えますが、読み手は「なぜそれで直るのか」を自分で組み立てることになる。直した後の処理を順に書き、なぜ原因が取り除かれるかを示す。記述ごとの直り方は2段目の流れに書くので、ここでは繰り返さない。

実際に、原因の表と直し方の段落を並べた PR 本文は、「原因は分かったが、なぜその対応で直るのかが分からない」と指摘を受けました。

2段目では、報告の言葉と実際の現象の橋渡しを流れの中で書く。報告者は見えたものを自分の言葉で書くので、「登録に失敗することがある」と報告されても、失敗していたのは前段の処理ということがあります。「ここで〜が出る。これが課題票の『〜』」と操作の順に対応を示すと、読み手は課題票を手元に置いたまま筋を追えます。起きない記述も流れの最後に置く。

流れの各段には、修正後にどうなるかも1行添える。どう起きていたかだけでは、その記述が直るのかを読み手が後の段から探すことになります。課題票の記述1つにつき、起き方と直り方が同じ段に並ぶ形にする。

補足に置く記述ごとの対応表とは役割が違います。あちらは記述を1つずつ突き合わせる入口、2段目は操作の順に並べた流れです。実際に、原因を処理の説明だけで書いた PR 本文に対して、報告の裏で起きていたことを番号付きで並べた説明のほうが伝わると指摘を受けました。

複数の変更が要るなら「この2本で直る」の肯定形で書く。「単体ではここまで」と断りから入ると、読み手は「結局直るのか」を抱えたまま先へ進みます。マージ順などの条件はその後に添える。

付随して行った変更は、筋と並べずに分けて書く。筋の中へ混ぜると、どの変更が課題の解決に要るのかが読めません。筋の後ろに表で置き、1つずつ「何を変え、どの状態を解決したか」を添える。解決する状態は、修正前に起きていたこととして書く（結果を書くと、行ごとに向きが揃わない）。

| 変更 | 解決する状態 |
| --- | --- |
| 同じ判定で、別の状態の行も戻るようになる | 作り直しで ID が変わる（課題票の本文にはあるが、受入基準の外） |
| 戻すときの値の初期化を、一部の経路だけに絞った | 利用者が自分で答えた値まで消してしまう |

受入基準に要る変更がどれかも示す。課題票の本文に書かれた症状でも、受入基準に入っていないものがあります。実際に、2つの症状を同じ重みで並べた PR 本文は、「直接の解決に要らない変更を並べて書くのは違う」と指摘を受けました。

付随した変更が大きいなら、先に PR を分けるかを考える。分けて書けば同じ PR に入れてよい、ということではありません。

課題票の記述ごとの対応は、補足に表で置く。冒頭に置くと筋が読めなくなります。表を探しに来る読み手（品質保証の担当・報告者）の入口として残す。

| 課題票の記述 | 実際に起きていたこと |
| --- | --- |
| 「登録に失敗することがある」 | 失敗していたのは登録ではなく、その前段の処理 |
| 「同じものがもう1つできる」 | 2つ目ができたのではなく、作り直しで置き換わっていた |
| 「〜の場合もある（再現性なし）」 | その経路が存在しないので起きない |

起きない記述も書く。省くと、読み手はその記述がどうなったのかを探しに行きます。

実際に、対応表を冒頭に置き単体の限界を断ってから書いた PR 本文は、「マージしたら直るのか」が読み取りにくいと指摘を受けました。

対象は PR 本文に限りません。会議での説明・課題へのコメント・完了報告でも、同じところで読み手が詰まります。
