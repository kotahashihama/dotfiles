現在のブランチに紐づく PR の説明を、ベースブランチに対する差分観点で書き直して更新してください。**PR 本文に加えて、自分が投稿した補足情報用のコメントも更新対象**です。

## 進め方

1. **PR の特定**:
   - `git branch --show-current` で現在のブランチを確認
   - `gh pr view --json number,title,body,baseRefName` で対応する PR を特定（該当 PR が無ければユーザーに確認）
   - **作成者を確かめる**（ `gh pr view <PR> --json author -q '.author.login'` ）。ユーザー本人でなければ中断して報告する（ `no_operating_on_others_prs.md` ）
   - `baseRefName` を以降の差分計算のベースに使う
   - **本文に自分が書いていない内容が入っていないか見る**
     - **投稿者では判定できない。** ユーザー名義で投稿するので、こちらの編集も相手の編集も同じ login になる
     - **添付の参照を数える。** `![` `user-attachments` `<video` `githubusercontent` を現在の本文から拾い、**新しい本文にも同じものがあるか**を見る
     - **画像・動画・スクリーンショットが最も消えやすい。** 本文をテキストとして組み立てるので、添付は持ち回らない
     - 消したことに気づけるのは投稿者だけで、**こちらからは見えない**。取得しただけでは足りず、**添付という観点で数える**
     - 消してしまったら `userContentEdits` から復元できる（ `keep_records_current.md` ）。ただし**指摘されるまで気づけない**

2. **差分の把握**（並列実行可）:
   - `git diff <base>...HEAD --stat` でファイル単位の規模感
   - `git diff <base>...HEAD` で全変更内容（大きい場合は要点だけ抜き出す）
   - **テンプレートは base のブランチから読む**（ `git show origin/<base>:<テンプレートのパス>` ）。存在しない場合はシンプルな「Summary」「Test plan」構成にフォールバック
     - **作業ツリーのものを Read しない。** 別のブランチの版を読むことになる。**base が `develop` のとき、`main` にしか入っていない節を読んでしまう**。リリースの流れが一方向だと、上流の変更が下流へ降りていないことがある
     - **ファイル名の大文字小文字はリポジトリで違う。** macOS のファイルシステムは区別しないので `Read` では気づけない。`git ls-tree origin/<base> .github/ --name-only` で実体を見る
     - 既存本文から構成を推測しない。テンプレが更新されていることがある

3. **本文・補足コメントの組み立て方針**:

   > **この節が正本。** `/create-pr` からも参照される。
   > **あちらへ写さない。** 写すと片方だけ古くなる（実際に58行ずれた）。
   > 作成のときにだけ要るもの（テンプレの埋め方・Backlog 節）は `/create-pr` 側に置く。

   **この方針は PR 本文と別コメントの両方に等しく適用する。** 別コメントは「細部を置く場所」であって「基準を緩める場所」ではない。量・流れ・表と図・過程を書かないことは同じく守る。

   - **PR 内のコミット履歴・レビュー対応の経緯は書かない**。merge された時点のスナップショットとしての変更観点に徹する
   - 「なぜ変えたか」「何が変わったか」「テスト方針」を簡潔に
   - **概要には「何をするか」と「マージすると何が良くなるか」の両方を書く**。前者だけだと、レビュアーは差分を読んでから価値を逆算することになる
     - **良くなることは、読み手が数えられる形にする**。消える手作業の回数、減るコマンド数、短くなる時間。「簡単になる」「改善する」は書き手の感想で、検算できない
     - **数で示せないなら、直さなかったときの壊れ方を書く**。「画面は出るのにアップロードだけ失敗する」のように、**症状と気づきにくさ**を添えると優先度が伝わる
     - **動機と効果は別の情報**。「なぜ変えたか」は過去向き（何が困っていたか）、「何が良くなるか」は未来向き（マージ後にどうなるか）。前者だけで済ませない
   - **その変更がどこまで届くかを書く**。ローカルだけで済むのか、CI が動くのか、本番の動作が変わるのか。**読み手が最初に疑うところ**なので、書いていないと差分で確かめることになる
     - **段を分けて書く。** 「デプロイ環境に影響しない」の一言では、どこで止まるのかが伝わらない

       | 段 | 確かめ方 |
       | --- | --- |
       | ワークフローが起動するか | `paths` / `paths-ignore` と**変更ファイル全件**を突き合わせる。**1件でも外にあれば起動する** |
       | 成果物が変わるか | ビルドが読む対象に差分があるか（ `COPY` の対象、コンパイル対象） |
       | 動作が変わるか | 起動するもの（ `ENTRYPOINT` / `CMD` ）が読む対象に差分があるか |

     - **「起動しない」と「動作が変わらない」は別の主張。** 混ぜると、片方の誤りでもう片方まで疑われる。実際に、変更6ファイルのうち2件だけ見て「ワークフローそのものが起動しません」と書き、`Makefile` が `paths-ignore` の外にあって誤りになった
   - **既存の構成を変えるなら、いまの構造が歴史的経緯によるものだと示す**。レビュアーは「**なぜ今の形なのか分からないまま変えてよいのか**」を疑うので、そこを埋めないと妥当性の議論が進まない
     - **肯定形で名前を付ける。** 「設計ではない」と否定から入ると、読み手は却下された仮説を一度受け取ることになる
     - 示すのは3つで、**どれも履歴と設定から引ける**

       | 見るもの | 何が言えるか |
       | --- | --- |
       | **入った順**（ `git log --diff-filter=A` ） | 別々の時期に別々の目的で入ったのか、同時に設計されたのか |
       | **名前と値の一致**（両側の設定を突き合わせる） | 一致しているなら、同じものを見る前提で書かれている |
       | **既存の案内**（README・手順書） | 回避策として書かれているなら、その構造は前提ではなく症状 |

     - **いまの形が選ばれた理由が別にあるなら、それも書く。** その理由が消えることまで示せて初めて妥当性が立つ。実際に「連携する Lambda を載せられるのが片側だけ」という制約があり、**設定1語で消える**ことを示して決着した
     - **記憶で書かない。** 「たしか経緯があったはず」は根拠にならない（ `verify_before_asserting.md` ）
   - レビュー観点を意識して、注目してほしい箇所・トレードオフがあれば明記
   - テスト内容は実施済みの事実として**通常の箇条書き**で書く（ `- [ ]` / `- [x]` のチェックボックスは未消化の TODO に見えるため使わない）
   - **修正前と修正後を、画面の見え方で並べる**。レビュアーが知りたいのは「**どういう状態からどういう状態になるか**」で、実装の語（どの関数が何を渡すか）で並べると差分を読んでから翻訳し直すことになる
     - 操作を軸に「修正前の表示 / 修正後の表示」を対で置く。実際の値が分かるなら「実測 / 修正前 / 修正後」の3列にすると誤りの向きまで伝わる
     - **表にするのは同じ観点が3件以上あるとき**。1〜2件なら文で足りる
   - **動作確認をしていない旨を書かない**。画面での確認はユーザーが行い、必要ならスクリーンショットや動画をユーザーが貼る。テスト内容の節には**自分が実行した検証だけ**を書く
     - **画像や動画を受け取ったら `--attach` で本文へ貼る**。`--attach 'path/to/shot.png#修正後の一覧'` の形で、`#` の後ろが代替テキストになる。画像と GIF は10MBまで
     - **差し込む位置は自分で決める**。末尾へ追記されるので、節の中へ置きたいなら本文側に参照を書いてから貼る
   - 機密（ `.env` / credentials / 内部 URL）を含まないことを念のため確認
   - **量を絞る**。レビュアーが判断に使う情報（挙動の変化・トレードオフ・見てほしい点・前提条件）は残し、**重複と前置きを削る**。差分を見れば分かることは書かない。説明が要るのは「なぜそうしたか」と「何に注意すべきか」
     - 目安は**散文で1節5行以内、本文全体30行以内**（テンプレ固定文は除く）。読む負担は散文の量で決まるので、表・図・コードブロックはこの数えから外す。超えたら表に畳むか別コメントへ切り出す
     - **書き直しは短くする機会**。既存本文で節を埋めるためだけに膨らんだ記述、冗長な箇条書きの羅列は畳む
     - **テンプレの節は削らない**。短くするのは中身。該当なしなら `- なし` と理由を書き、`## レビューのルール` 等の固定文は維持する
       - **ただしレビュアーへの確認事項を書く節は例外で、中身を空にする**（見出しは残し、`- なし` も書かない）。見てほしい点は実装内容の節で挙げるので、**ここへ書くと重複する**
     - **テンプレの HTML コメントは、宛先で残すか消すかを分ける**。埋めたら役目を終えるものと、消すと機能が止まるものがある

       | 宛先 | 例 | 扱い |
       | --- | --- | --- |
       | **書き手への指示** | `<!-- 変更の目的 & issue -->` | **消す**。埋めた時点で役目が終わる |
       | **読み手・ツールへの指示** | レビュー言語の指定、AI レビューの適用範囲を囲むもの | **残す**。**消すと AI レビューの挙動が変わる** |

       **判断が付かないものは残す。** 消して壊れるほうが、残して読みにくいより高くつく
     - **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・残す理由の断り書き・丁寧さの水増し・自明な補足）と同じ
     - **PR 説明では「網羅のための記述」が特に出る。** テンプレの節を埋めようとして、挙げる必要のない項目まで表に並べてしまう。**該当なしは `- なし` の1行で足りる**
   - **概要から詳細へ流す**。各節の中で結論・全体像を先に置き、根拠や細部を後に続ける。最初の1〜2行で「何の話か」が掴めるようにし、結論が最後に来る流れは避ける。テンプレの節順は変えない
     - 文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる
     - **見出しを足して流れを作らない。** 「概要」「詳細」のような節を新設すると、テンプレの構成が崩れるうえ、読み手は見出しだけ追って中身を読まなくなる。**節の中の文の順序**だけで実現する
     - **対応が複数あるなら症状を箇条書きで並べる。** 1つの PR が3件以上の症状・変更を含むとき、散文で続けると**何件あるのかが読み取れない**。**読み手が観測できる形**（画面でどう見えるか）で1行ずつ並べると、差分を読む前に対象の広さが伝わる
       - 観点が1つ（症状だけ）なら**箇条書き**、観点が2つ以上（修正前と修正後、経路と対象）なら**表**
       - **3件以上で効く。** 2件以下なら散文のままでよい
   - **読み手はその機能を知らないエンジニア**として書く（土台は `rules/plain_language_explanation.md` と `rules/explain_from_observables.md` ）。**画面の見え方・エラー文など読み手が観測できるものから始め、登場人物が2つ以上あるなら誰が何を決めるかを先に置く**。**1機能を1人が担当する体制では、レビュアーは必ず別の文脈から来ます**。設計の議論に同席しておらず、その領域のコードも読んでいない
     - **内部の呼び名をそのまま置かない。** 型名・サービス名・SQL ファイル名・スキーマの挙動は、初めて見る人には意味を持たない。**何を指すか / 結果どうなるか**を一言添えるか、論理名で書く。「パースが落ちる」は「一覧が表示できなくなる」まで書く
     - **前提を1行で補う。** 「この経路はドメインモデルを経由せず直接書き込む」のような背景は、知らない人には差分から読み取れない
     - **判断の分かれ目を書く。** 「なぜ A ではなく B か」は、その機能に詳しい人ほど自明として省きやすい
     - ただし**言い換えを重ねない**。1行足せば大半は解ける。結論を噛み砕き直して2度言うと、短さも読みやすさも同時に失う
   - **Alert / `<details>` / 脚注も使う**（土台は `rules/github_rich_formatting.md` ）。Alert は `IMPORTANT` と `WARNING` だけを、**本文に1〜2個**（生成者表示の Note は数えない）。**先に「読み飛ばすと事故るか」で選び**、超えたら畳み方を見直す
   - **表と Mermaid 図で畳む**（土台は `rules/concise_first_then_detail.md`。ここでは PR 固有の事情だけを足す）:
     - **表**: 同じ観点の項目が3件以上並ぶもの（設計判断とその理由、カラム定義、採用案と却下案、変更ファイルと役割）。1セル1〜2行に収め、長い根拠は本文に逃がす
       - **1列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、1列目がファイルパスや長い識別子だと**残りの列が潰れて縦書きになる**。パスは basename に短縮し（フルパスが要るなら本文かコードブロックへ）、長い識別子は後ろの列へ回す
       - 短くできないなら**表をやめて箇条書きにする**。列を無理に維持するより読める
     - **Mermaid**: 差分の羅列から読み取れない構造・関係・流れを示すとき。GitHub は ` ```mermaid ` フェンスをそのままレンダリングする
       - `erDiagram`: テーブルの新設・リレーション変更。**FK ありを実線 (`||--o{`)、FK を張らない論理参照を点線 (`|o..o{`)** で描き分けると設計判断がそのまま図になる
       - `sequenceDiagram`: 複数のコンポーネント・サービス・リポジトリをまたぐフロー / `flowchart`: 分岐・状態遷移・処理順
       - **順序が正しさの根拠になっているものは図にする。** 「A を B より先にしないと壊れる」は散文だと数段落かかるが、図なら一目で追える。**別文脈から来たレビュアーが最初に詰まるのがここ**
     - 置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を2つの形式で持たない**。差分から自明なこと（小さな修正、単純なリネーム）に図は足さない
   - **個人環境にしか無いものを前提に書かない。** グローバルスキル（ `~/.claude/skills/` ）やグローバルルール（ `~/.claude/rules/` ）は自分の環境にしか存在せず、**他のレビュアーには無い**。「 `/cp` で代替できる」のような説明は成立しないので、リポジトリにコミットされているもの（プロジェクトスキル・`.claude/rules`・`docs/` ）だけを根拠にする
     - 同じ理由で、**個人環境のルールを根拠にプロジェクトの資産を消さない**。リポジトリにあるファイルはチーム全員のもの
   - **外部ドキュメントで足りることは書かない**。Design Doc / PBI / Figma / 他 PR の背景・仕様・経緯は**1〜2行に要約してリンク**を貼り、PR 本文で再構成しない。例外は差分を読むのに必要な前提で、その場合も必要な部分だけ引用する
     - **DD で決まっている判断に独自の根拠を足さない**。「DD の方針どおり」で足りる。根拠を書くのは**DD から外れた点**と**DD 執筆後に決めた点**だけ
   - **他リポジトリの PR / issue は `owner/repo#123`**（同一リポジトリなら `#123` ）。GitHub が自動でリンクにし、タイトルと open/closed も表示される。生 URL より短く腐らない。**owner を省略しない**（ `repo#123` は同一リポジトリの番号と解釈されてリンクにならない）。例外はコメントへのアンカー付き参照（ `#123#issuecomment-...` ）で、これは Markdown link にする
   - **本文は軸、細部は別コメント**。本文に置くのは、この PR が**何を変え / なぜ変え / 何に注意して見るか**という軸だけ。判断に迷ったら「**この節が無いと差分を読み始められないか**」で決める

     | | 本文（軸） | 別コメント（細部） |
     | --- | --- | --- |
     | 例 | 変更の目的 / 主要な設計判断 / 影響範囲 / 前提条件・注意点 | API 契約の全文 / データモデル / 調査ログ / 他リポジトリ向けの申し送り / 検討したが採らなかった案の詳細 |
     | 読み手 | **全レビュアーが必ず読む** | 実装者・後任が必要なときだけ開く |

     切り出したら本文からリンクを貼り、**同じ情報を両方に持たない**。別コメントにも末尾の Note ブロックを付ける（ `github_note_generated_by_claude.md` ）。切り出したコメントの点検は手順7

     **補足コメントは冒頭に `[fyi]` を置き、その後で改行する。** レビュアーが使う接頭辞（ `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` ）と同じ語彙で、**対応を求めるものではない**ことが一目で伝わる。申し送りや保留条件のような「読んでほしいが返信は不要」なコメントも同じ

     ```
     [fyi]
     本文の 1 行目...
     ```

     `[fyi] 本文...` と同じ行に続けない。**アノテーションは本文と分離した1行**にする
   - **Backlog 節への対応**:
     - 会話コンテキストで Backlog 課題番号（ `PROJ-XXX` 等）または URL が提供されているか確認する。既存 PR 本文の Backlog 節に既に URL が入っていればそれを維持する
     - **貼るのは PBI。関連する課題があれば行を追加して並べる**: テンプレが複数行を許すなら、**PBI を先頭に置き**、その配下の開発タスクなど直接の動機になった課題があれば続けて貼る。どちらも「Pull Request」カスタム属性へ自動で入るので、**PBI 側で機能全体の PR 群を、タスク側でその作業の PR を追える**
       - **PBI かどうかは issueType で確かめる**。親子関係だけでは判定できない（親がさらに上位の課題であることもある）
       - **本文を編集すると紐づけのワークフローが再実行される**（ `pull_request` の `edited` を拾う設定の場合）。既存の紐づけは消えず、追記した課題が増えるだけ。ただし**成功表示では紐づいたか分からない**ので、Backlog 側の属性を引いて確かめる
     - **新たに提供されている場合**: Backlog 節に **URL を貼る**（Backlog 側の GitHub Actions ワークフローが URL を検知して PR と課題を自動で関連付ける）。番号だけ提供された場合は、リポジトリ内の過去 PR 本文で URL フォーマットを確認して組み立てる。過去 PR にも例が無ければユーザーに URL を尋ねる
     - **提供されておらず既存本文にも無い場合**: ユーザーに `Backlog 課題番号 or URL はありますか？` と尋ねる。番号や URL を貼らずに勝手に「なし」で埋めない
     - **ユーザーが「なし」と返した場合**: テンプレの案内どおり `- なし` に理由を添える（例: `- なし (BE 側の UX 改善対応)` ）
   - **本文の末尾に生成者表示を置く**（ `github_note_generated_by_claude.md` ）。**文言と主語の使い分けはあちらが持つ**ので、ここには写さない
4. **タイトルの妥当性チェック**:
   - 現在の PR タイトルがベースブランチに対する差分の意図を正確に表現しているかを判断
   - スコープ拡張・方向転換・修正対象の変化などで乖離している場合はタイトルも更新対象に含める
   - 70文字以内、要点が動詞で始まる形（例: `feat: ...`, `refactor: ...` ）を維持
   - **チケット番号は、その課題を直接（全部または一部）解決する PR にだけ付ける**

     | 付ける | 付けない |
     | --- | --- |
     | その課題を全部解決する | **課題を持たない**（派生したリファクタ・雑務） |
     | その課題を一部解決する（分割した1本目） | 課題の作業中に見つけた、閉じる条件に入らない改善 |

     判定は「**この PR がマージされたとき、課題の消化が進むか**」。進まないなら付けない
     **Backlog 節と突き合わせる**。**Backlog が「なし」なのにタイトルが番号を名乗る形が最も出やすく**、課題側の「Pull Request」属性から辿った人が期待と違うものを見る
     関連しているだけなら本文で述べれば足りる
   - 現タイトルが差分の核と一致しているならそのまま（本文だけで十分なケースが多い）。微妙なら更新しない

5. **本文と差分の照合**: 更新する前に、書いた内容が**実際の差分と食い違っていないか**を機械的に確認する。**書き直しは既存本文の古い記述を持ち越しやすい**ので、既存を流用した箇所ほど疑う。

   - **照合は作業ツリーではなく ref を指定して行う**。`git show <ref>:<path>` と `git diff <base>...<ref>` で数える
     - **作業ツリーは自分の操作だけで決まらない。** 同じディレクトリを別のセッションが使っていると、**checkout した記憶が当てにならない**
     - **スタックした PR では特に起きる。** 段ごとに別のブランチなので、**どれを見ているかで結果が変わる**
     - **0件が返っても手が止まらない。** 「まだ実装していない」と読めるので、**空振りだと気づけない**
     - 作業ツリーで数えるなら、**先に `git branch --show-current` で対象と一致していることを見る**
   - **数値**: 変更ファイル数・テスト件数・使用箇所数など。`git diff --name-only | wc -l` や実行結果と突き合わせる。**「N 箇所」と書いたら必ず数える**
   - **識別子**: 型名・関数名・定数名・ファイルパス・コミットハッシュ・マイグレーション名が実在するか。`grep` / `git log` で確認する
   - **主張**: 「〜には影響しない」「〜は変わらない」と書いたなら、その根拠をコードで裏取りする。**影響範囲の断定は誤ると事故になる**
   - **決着済みの記述**: 「未確定」「判断待ち」としていた項目が、その後決まっていないか
   - **他リポジトリへの言及**: 依存する PR 番号・ファイル名が正しいか。参照先が変わっていないか。**本文中の `#数字` をすべて拾い、他リポジトリのものに owner が付いているか1箇所ずつ確かめる**（前半だけ正しく後半で崩れているのを見逃しやすい）
   - **因果の鎖**: **前提を知らない人が上から読んで、各主張の理由が本文の中だけで辿れるか**。1文ずつ「なぜそう言えるか」を問い、答えが本文に無ければ暗黙の前提が残っている
   - **指すものが決まらない語**: **1行ずつ「その行だけを読んだ人が、指すものを決められるか」で見る**（ `explain_from_observables.md` ）

     | 拾うもの | 例 |
     | --- | --- |
     | **動詞** | `飛ぶ` `走る` `回る` `叩く` `動く` `効く` `通る` `落ちる` `切り替わる` |
     | **初出の名前** | 画面・ダイアログ・hook・状態・処理の呼び名 |
     | **内部の呼び名** | `行` `レコード` `B5` `A0` `下段の2本` `上段`、会話で決めた略称 |
     | **参照** | `同じく` `同様に` `上記` `そちらも` |

     - **表のセルと見出しで最も落ちる。** 短く書こうとして主語・対象・参照先が消える。**セルは独立して読まれるので隣を指せない**
     - **置き換えは語を具体にするだけでは足りない。** 「対象を指定しないまま飛びます」を「送られます」へ直しても**何が起きるか**は伝わらない。「まとめて消す要求として扱われます」まで書く
     - **その現場で1つに決まる語は残す**（「テストが落ちる」「lint が通る」）。`plain_language_explanation.md`
     - **ルールに書いてあっても防げない。** あちらは `飛ぶ` を名指しで挙げているのに使った。**投稿前にこの段で拾う**

   - **読点**: **1つずつ「外すと文意が変わるか」を見る**（ `no_ai_style_writing.md` ）。変わらないなら落とす。残すのは**前の節が長い**ときと**外すと後ろの語と繋がる**ときだけ
     - **機械では判定できない。** 落とす形（ `おり、` `ず、` `すると、` ）と残す形（ `2種類あり、時間とは別` ）が同じ語尾で現れるので、**語の一覧では分けられない**
     - **書いた直後は気づけない。** 書き手は係りを知っているので、読点が無くても読めてしまう。**投稿前にこの段で通す**
     - 「そのため」「だから」で繋いだ箇所は、**前段が本当に後段の理由になっているか**を見る。繋いだつもりで飛んでいることがある
     - 補うのは**1行**。因果を書くことを理由に節を増やさない（本文30行以内は変わらない）
     - **書き手には見えない。** 実装した直後は前提が身についているので、自分で読んでも飛びに気づけない。**機械的に1文ずつ問う**
   - **否定**: 「〜ではない」で終わる文と「〜ではなく、〜」の1文形を拾い、**否定した側を読み手が実際に選びうるか**を問う（ `no_ai_style_writing.md` ）
     - 選びうるなら残す（「レンジではなく個々のハッシュ」は、読み手が実際にレンジを使いうる）
     - **誰も言っていないなら落とす。** 「分離は設計ではなく〜」は誰も設計だと言っていないので、却下された仮説を一度持たせるだけ
     - **形で一律に落とさない。** 正当な用法のほうが多い
   - 食い違いが見つかったら**本文を実態に合わせる**（差分の方を本文に合わせない）

6. **更新**:
   - **投稿の直前にもう一度本文を取得し、Step 1 から増えていないか見る**。組み立てている間に追記されることがある
     - **比べる前に改行コードと末尾の空行を揃える。** 取得した本文は **CRLF で返る**ので、ローカルで組み立てた LF のファイルと素で比べると**毎回「差あり」になる**。警告として働かなくなり、本物の差分が混ざっても手が止まらない
     - **添付の数はここで数え直す。** Step 1 で0件でも、**組み立てている間にユーザーが貼る**ことがある。実際に、貼られた動画2本を全文置換で消した
     - **差分が出たら投稿しない。** 何が増えたのかを確かめ、新しい本文へ取り込んでから出す
   - 本文はファイルに書き出し、`--body-file` で渡す
     - **そのファイルを作るのと同じ呼び出しに入れない。** 書式を検査するフックは **PreToolUse で走る**ため、その時点でファイルが無いと「Note が無い」「添付が消えている」と誤検知して弾く。**作成と投稿を別の呼び出しに分ける**（ `decide_or_ask.md` ）
     - **これは全文置換で、渡さなかった行は消える。** 自分が書いていない内容も組み立てへ含める
   - タイトルも更新する場合は `--title "..."` も併用（シェル展開されないクオートに注意）

7. **補足情報用コメントの点検と更新**:

   PR 本文に入りきらない情報を別コメントに切り出している場合、**本文と同じ鮮度で保つ**。本文だけ直してコメントが古いまま残ると、読み手はどちらが正しいか判断できない。

   - **対象の抽出**: `gh api repos/OWNER/REPO/issues/<PR>/comments --paginate` で自分が投稿したコメントを取得し、**情報を提供しているもの**に絞る
     - 対象: BE 向けの契約・データモデル、調査結果、確認手順、設計判断の記録など、**後から参照される情報**
     - 対象外: `/ai-review` 等のコマンドコメント（ `github_command_comments.md` ）、単なるリンク共有、レビュー返信（ `pulls/<PR>/comments` 側）
     - **`[fyi]` が付いていても中身が情報提供なら対象**（切り出した補足コメントには `[fyi]` を付ける規約のため、接頭辞では除外しない）
     - 見出し (`##`) を持つ長文かどうかで機械的に絞れる。前後の空白でコマンドを取りこぼすことがあるので、**本文を trim してから判定する**
     - **除外したものを「補足コメント」としてユーザーに報告しない。** 投稿者はユーザー名義でも中身はコマンドで、点検しても更新すべき事実が無い
   - **点検の観点**: 最新差分と突き合わせ、**事実がズレていないか**を機械的に確認する
     - コメントが挙げている型・フィールド・定数が、実装に存在するか
     - 件数・行数・テスト数などの数値が実測と合うか
     - 「未確定」「判断待ち」としていた項目が、その後決着していないか
     - **手順3の「削る型」に当てはまる記述が無いか**。断り書き・検討の過程・本文との重複は、点検のたびに落とす。コメントは追記で伸びやすい
   - **更新**: ズレがあれば `gh api -X PATCH repos/OWNER/REPO/issues/comments/<comment_id> -f body="$(cat <<'EOF' ... EOF)"` で更新する
     - **末尾の Note ブロックを消さない**（ `github_note_generated_by_claude.md` 参照）。本文を差し替えるときは Note を含めて組み立てる
   - **本文からのリンクを確認する**。切り出したコメントが**本文から辿れる状態か**を見る。無ければ本文に足す
     - 新たに切り出して投稿した場合も同じ。`gh pr comment` が返す URL を本文へ差し込む。投稿時は**冒頭に `[fyi]` を単独行で置き（次の行から本文）、末尾に Note ブロック**を付ける
     - 置き場所は「その情報を探す人が見る節」。契約なら実装内容、調査ログなら補足
     - リンクが無いと**本文だけ読んだ人がコメントの存在に気づけない**
   - **本文とコメントで同じ情報を二重に持たない**。詳細はコメント側に置き、本文からは参照リンクを貼る形にする

8. **完了報告**: 更新後の PR URL、書き換えた本文の要約、タイトル変更があればその旨も返す。**補足コメントを更新した場合はその URL と更新内容も併記**する。

## 出力の目安

- **本文/タイトル/コメントとも変更なしで済んだ場合**: 「差分と本文・コメントが既に整合。更新なし」で2〜3行報告
- **本文更新した場合**: 更新後 URL + 主な変更点（追加した節・修正した節・タイトル変更の有無）を簡潔に
- **補足コメントも更新した場合**: コメント URL と、どの記述が実態とズレていたかを1〜2行で添える

## やってはいけないこと

- コミット履歴・レビュー対応の経緯を本文に書くこと（差分スナップショットに徹する）
- 同一内容の本文を再送すること（差分と本文が既に整合しているなら更新しない）
- タイトルが差分の核と一致しているのに、微修正のためだけに変更すること
- **複数の対応を含む PR で症状を散文のまま並べること**。何件あるのかが読み取れない
- **テンプレの構成から外れること**。節の追加・削除・並べ替えのいずれもしない。`.github/pull_request_template.md` が正で、短くするのは各節の中身だけ
- **Design Doc / PBI に書かれている仕様をゼロベースで説明し直すこと**。要約1〜2行 + リンクで足りる
- **別コメントへ切り出したのに本文からリンクを貼らないこと**（読み手がコメントの存在に気づけない）
- **本文だけ更新して補足コメントを古いまま放置すること**（どちらが正しいか読み手が判断できなくなる）
- 補足コメントを更新する際に**末尾の Note ブロックを落とすこと**（ `github_note_generated_by_claude.md` ）
- 本文に書いた数値・識別子・影響範囲の主張を、**差分と照合せずに更新すること**（Step 5）。既存本文を流用した箇所ほど古い記述が残りやすい
- **届く範囲を、変更ファイルの一部だけ見て断定すること**。`paths-ignore` は全件が一致したときだけ効くので、1件見落とすと結論が逆になる
- **自分が書いていない内容を、全文置換で消すこと**。画像・動画は特に消えやすく、消したことに気づけるのは投稿者だけ
- 他人が投稿したコメントを編集すること（対象は自分が投稿したものだけ）
