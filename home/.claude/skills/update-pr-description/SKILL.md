現在のブランチに紐づく PR の説明を、ベースブランチに対する差分観点で書き直して更新してください。**PR 本文に加えて、自分が投稿した補足情報用のコメントも更新対象**です。

## 進め方

1. **PR の特定**:
   - `git branch --show-current` で現在のブランチを確認
   - `gh pr view --json number,title,body,baseRefName` で対応する PR を特定（該当 PR が無ければユーザーに確認）
   - `baseRefName` を以降の差分計算のベースに使う

2. **差分の把握**（並列実行可）:
   - `git diff <base>...HEAD --stat` でファイル単位の規模感
   - `git diff <base>...HEAD` で全変更内容（大きい場合は要点だけ抜き出す）
   - **`.github/pull_request_template.md` を Read で読む**（既存本文から構成を推測しない。テンプレが更新されていることがある）。存在しない場合はシンプルな「Summary」「Test plan」構成にフォールバック

3. **本文・補足コメントの組み立て方針**:

   > この節は `/create-pr` と `/update-pr-description` で**共通**。片方を直したらもう片方も同じ内容に揃える。

   **この方針は PR 本文と別コメントの両方に等しく適用する。** 別コメントは「細部を置く場所」であって「基準を緩める場所」ではない。量・流れ・表と図・過程を書かないことは同じく守る。

   - **PR 内のコミット履歴・レビュー対応の経緯は書かない**。merge された時点のスナップショットとしての変更観点に徹する
   - 「なぜ変えたか」「何が変わったか」「テスト方針」を簡潔に
   - レビュー観点を意識して、注目してほしい箇所・トレードオフがあれば明記
   - テスト内容は実施済みの事実として**通常の箇条書き**で書く（`- [ ]` / `- [x]` のチェックボックスは未消化の TODO に見えるため使わない）
   - 機密（`.env` / credentials / 内部 URL）を含まないことを念のため確認
   - **量を絞る**。レビュアーが判断に使う情報（挙動の変化・トレードオフ・見てほしい点・前提条件）は残し、**重複と前置きを削る**。差分を見れば分かることは書かない。説明が要るのは「なぜそうしたか」と「何に注意すべきか」
     - 目安は**散文で 1 節 5 行以内、本文全体 30 行以内**（テンプレ固定文は除く）。読む負担は散文の量で決まるので、表・図・コードブロックはこの数えから外す。超えたら表に畳むか別コメントへ切り出す
     - **書き直しは短くする機会**。既存本文で節を埋めるためだけに膨らんだ記述、冗長な箇条書きの羅列は畳む
     - **テンプレの節は削らない**。短くするのは中身。該当なしなら `- なし` と理由を書き、`## レビューのルール` 等の固定文は維持する
     - **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむので、次の型を名指しで探して落とす:

       | 型 | 例 |
       | --- | --- |
       | 言い換えの反復 | 同じことを「つまり」「言い換えると」で 2 度書く |
       | 自明な補足 | 「テストも通しています」「影響がないことを確認しました」だけの行 |
       | 網羅のための記述 | 挙げる必要のない項目まで表に並べる。**該当なしは 1 行で足りる** |
       | 過程の説明 | 検討の経緯・試した順序・一度覆した判断。**最終方針だけでよい** |
       | 残す理由の断り書き | 「〜のため残しておきます」「参考までに記載します」。**残すなら黙って残す** |
       | 丁寧さの水増し | 「〜という点にご注意ください」「〜と考えております」 |

   - **概要から詳細へ流す**。各節の中で結論・全体像を先に置き、根拠や細部を後に続ける。最初の 1〜2 行で「何の話か」が掴めるようにし、結論が最後に来る流れは避ける。テンプレの節順は変えない
     - 文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる
     - **見出しを足して流れを作らない。** 「概要」「詳細」のような節を新設すると、テンプレの構成が崩れるうえ、読み手は見出しだけ追って中身を読まなくなる。**節の中の文の順序**だけで実現する
   - **「つまりどういうこと？」で止まらせない**。用語・内部の呼び名・スキーマの挙動をそのまま置かず、**何を指すか / 結果どうなるか**を一言添える。「パースが落ちる」は「一覧が表示できなくなる」まで書く
     - ただし**言い換えを重ねない**。1 行足せば大半は解ける。結論を噛み砕き直して 2 度言うと、短さも読みやすさも同時に失う
   - **表と Mermaid 図で畳む**:
     - **表**: 同じ観点の項目が 3 件以上並ぶもの（設計判断とその理由、カラム定義、採用案と却下案、変更ファイルと役割）。1 セル 1〜2 行に収め、長い根拠は本文に逃がす
       - **1 列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、1 列目がファイルパスや長い識別子だと**残りの列が潰れて縦書きになる**。パスは basename に短縮し（フルパスが要るなら本文かコードブロックへ）、長い識別子は後ろの列へ回す
       - 短くできないなら**表をやめて箇条書きにする**。列を無理に維持するより読める
     - **Mermaid**: 差分の羅列から読み取れない構造・関係・流れを示すとき。GitHub は ` ```mermaid ` フェンスをそのままレンダリングする
       - `erDiagram`: テーブルの新設・リレーション変更。**FK ありを実線 (`||--o{`)、FK を張らない論理参照を点線 (`|o..o{`)** で描き分けると設計判断がそのまま図になる
       - `sequenceDiagram`: 複数のコンポーネント・サービス・リポジトリをまたぐフロー / `flowchart`: 分岐・状態遷移・処理順
     - 置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を 2 つの形式で持たない**。差分から自明なこと（小さな修正、単純なリネーム）に図は足さない
   - **個人環境にしか無いものを前提に書かない。** グローバルスキル（`~/.claude/skills/`）やグローバルルール（`~/.claude/rules/`）は自分の環境にしか存在せず、**他のレビュアーには無い**。「`/cp` で代替できる」のような説明は成立しないので、リポジトリにコミットされているもの（プロジェクトスキル・`.claude/rules`・`docs/`）だけを根拠にする
     - 同じ理由で、**個人環境のルールを根拠にプロジェクトの資産を消さない**。リポジトリにあるファイルはチーム全員のもの
   - **外部ドキュメントで足りることは書かない**。Design Doc / PBI / Figma / 他 PR の背景・仕様・経緯は**1〜2 行に要約してリンク**を貼り、PR 本文で再構成しない。例外は差分を読むのに必要な前提で、その場合も必要な部分だけ引用する
     - **DD で決まっている判断に独自の根拠を足さない**。「DD の方針どおり」で足りる。根拠を書くのは**DD から外れた点**と**DD 執筆後に決めた点**だけ
   - **他リポジトリの PR / issue は `owner/repo#123`**（同一リポジトリなら `#123`）。GitHub が自動でリンクにし、タイトルと open/closed も表示される。生 URL より短く腐らない。**owner を省略しない**（`repo#123` は同一リポジトリの番号と解釈されてリンクにならない）。例外はコメントへのアンカー付き参照（`#123#issuecomment-...`）で、これは Markdown link にする
   - **本文は軸、細部は別コメント**。本文に置くのは、この PR が**何を変え / なぜ変え / 何に注意して見るか**という軸だけ。判断に迷ったら「**この節が無いと差分を読み始められないか**」で決める

     | | 本文（軸） | 別コメント（細部） |
     | --- | --- | --- |
     | 例 | 変更の目的 / 主要な設計判断 / 影響範囲 / 前提条件・注意点 | API 契約の全文 / データモデル / 調査ログ / 他リポジトリ向けの申し送り / 検討したが採らなかった案の詳細 |
     | 読み手 | **全レビュアーが必ず読む** | 実装者・後任が必要なときだけ開く |

     切り出したら本文からリンクを貼り、**同じ情報を両方に持たない**。別コメントにも末尾の Note ブロックを付ける（`github_note_generated_by_claude.md`）。切り出したコメントの点検は手順 7

     **補足コメントは冒頭に `[fyi]` を置き、その後で改行する。** レビュアーが使う接頭辞（`[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]`）と同じ語彙で、**対応を求めるものではない**ことが一目で伝わる。申し送りや保留条件のような「読んでほしいが返信は不要」なコメントも同じ

     ```
     [fyi]
     本文の 1 行目...
     ```

     `[fyi] 本文...` と同じ行に続けない。**アノテーションは本文と分離した 1 行**にする
   - **Backlog 節への対応**:
     - 会話コンテキストで Backlog 課題番号（`RA_DEV-XXX` 等）または URL が提供されているか確認する。既存 PR 本文の Backlog 節に既に URL が入っていればそれを維持する
     - **新たに提供されている場合**: Backlog 節に **URL を貼る**（Backlog 側の GitHub Actions ワークフローが URL を検知して PR と課題を自動で関連付ける）。番号だけ提供された場合は、リポジトリ内の過去 PR 本文で URL フォーマットを確認して組み立てる。過去 PR にも例が無ければユーザーに URL を尋ねる
     - **提供されておらず既存本文にも無い場合**: ユーザーに `Backlog 課題番号 or URL はありますか？` と尋ねる。番号や URL を貼らずに勝手に「なし」で埋めない
     - **ユーザーが「なし」と返した場合**: テンプレの案内どおり `- なし` に理由を添える（例: `- なし (BE 側の UX 改善対応)`）
   - **本文の末尾に GitHub Note アノテーションで生成者表示を添える**（人間のレビュアーが AI 生成と判別できるため）。空行を 1 行挟んで置く。モデル名ではなくクライアント名 `Claude Code` を使い、**必ず末尾**に配置する
     ```
     > [!NOTE]
     > この PR 説明は Claude Code で作成されています。
     ```
4. **タイトルの妥当性チェック**:
   - 現在の PR タイトルがベースブランチに対する差分の意図を正確に表現しているかを判断
   - スコープ拡張・方向転換・修正対象の変化などで乖離している場合はタイトルも更新対象に含める
   - 70 文字以内、要点が動詞で始まる形（例: `feat: ...`, `refactor: ...`）を維持
   - 現タイトルが差分の核と一致しているならそのまま（本文だけで十分なケースが多い）。微妙なら更新しない

5. **本文と差分の照合**: 更新する前に、書いた内容が**実際の差分と食い違っていないか**を機械的に確認する。**書き直しは既存本文の古い記述を持ち越しやすい**ので、既存を流用した箇所ほど疑う。

   - **数値**: 変更ファイル数・テスト件数・使用箇所数など。`git diff --name-only | wc -l` や実行結果と突き合わせる。**「N 箇所」と書いたら必ず数える**
   - **識別子**: 型名・関数名・定数名・ファイルパス・コミットハッシュ・マイグレーション名が実在するか。`grep` / `git log` で確認する
   - **主張**: 「〜には影響しない」「〜は変わらない」と書いたなら、その根拠をコードで裏取りする。**影響範囲の断定は誤ると事故になる**
   - **決着済みの記述**: 「未確定」「判断待ち」としていた項目が、その後決まっていないか
   - **他リポジトリへの言及**: 依存する PR 番号・ファイル名が正しいか。参照先が変わっていないか。**本文中の `#数字` をすべて拾い、他リポジトリのものに owner が付いているか 1 箇所ずつ確かめる**（前半だけ正しく後半で崩れているのを見逃しやすい）
   - 食い違いが見つかったら**本文を実態に合わせる**（差分の方を本文に合わせない）

6. **更新**:
   - `gh pr edit <number> --body "$(cat <<'EOF' ... EOF)"` で HEREDOC を使って本文を更新
   - タイトルも更新する場合は `--title "..."` も併用（シェル展開されないクオートに注意）
   - HEREDOC の終端は `EOF` シングルクォート版で、本文の `$` や `` ` `` がシェル展開されないようにする

7. **補足情報用コメントの点検と更新**:

   PR 本文に入りきらない情報を別コメントに切り出している場合、**本文と同じ鮮度で保つ**。本文だけ直してコメントが古いまま残ると、読み手はどちらが正しいか判断できない。

   - **対象の抽出**: `gh api repos/OWNER/REPO/issues/<PR>/comments --paginate` で自分が投稿したコメントを取得し、**情報を提供しているもの**に絞る
     - 対象: BE 向けの契約・データモデル、調査結果、確認手順、設計判断の記録など、**後から参照される情報**
     - 対象外: `/ai-review` 等のコマンドコメント（`github_command_comments.md`）、単なるリンク共有、レビュー返信（`pulls/<PR>/comments` 側）
     - **`[fyi]` が付いていても中身が情報提供なら対象**（切り出した補足コメントには `[fyi]` を付ける規約のため、接頭辞では除外しない）
     - 見出し (`##`) を持つ長文かどうかで機械的に絞れる。前後の空白でコマンドを取りこぼすことがあるので、**本文を trim してから判定する**
     - **除外したものを「補足コメント」としてユーザーに報告しない。** 投稿者はユーザー名義でも中身はコマンドで、点検しても更新すべき事実が無い
   - **点検の観点**: 最新差分と突き合わせ、**事実がズレていないか**を機械的に確認する
     - コメントが挙げている型・フィールド・定数が、実装に存在するか
     - 件数・行数・テスト数などの数値が実測と合うか
     - 「未確定」「判断待ち」としていた項目が、その後決着していないか
     - **手順 3 の「削る型」に当てはまる記述が無いか**。断り書き・検討の過程・本文との重複は、点検のたびに落とす。コメントは追記で伸びやすい
   - **更新**: ズレがあれば `gh api -X PATCH repos/OWNER/REPO/issues/comments/<comment_id> -f body="$(cat <<'EOF' ... EOF)"` で更新する
     - **末尾の Note ブロックを消さない**（`github_note_generated_by_claude.md` 参照）。本文を差し替えるときは Note を含めて組み立てる
   - **本文からのリンクを確認する**: 切り出したコメントが**本文から辿れる状態か**を見る。無ければ本文に足す
     - 新たに切り出して投稿した場合も同じ。`gh pr comment` が返す URL を本文へ差し込む。投稿時は**冒頭に `[fyi]` を単独行で置き（次の行から本文）、末尾に Note ブロック**を付ける
     - 置き場所は「その情報を探す人が見る節」。契約なら実装内容、調査ログなら補足
     - リンクが無いと**本文だけ読んだ人がコメントの存在に気づけない**
   - **本文とコメントで同じ情報を二重に持たない**。詳細はコメント側に置き、本文からは参照リンクを貼る形にする

8. **完了報告**: 更新後の PR URL、書き換えた本文の要約、タイトル変更があればその旨も返す。**補足コメントを更新した場合はその URL と更新内容も併記**する。

## 出力の目安

- **本文/タイトル/コメントとも変更なしで済んだ場合**: 「差分と本文・コメントが既に整合。更新なし」で 2〜3 行報告
- **本文更新した場合**: 更新後 URL + 主な変更点（追加した節・修正した節・タイトル変更の有無）を簡潔に
- **補足コメントも更新した場合**: コメント URL と、どの記述が実態とズレていたかを 1〜2 行で添える

## やってはいけないこと

- コミット履歴・レビュー対応の経緯を本文に書くこと（差分スナップショットに徹する）
- 同一内容の本文を再送すること（差分と本文が既に整合しているなら更新しない）
- タイトルが差分の核と一致しているのに、微修正のためだけに変更すること
- **テンプレの構成から外れること**。節の追加・削除・並べ替えのいずれもしない。`.github/pull_request_template.md` が正で、短くするのは各節の中身だけ
- **Design Doc / PBI に書かれている仕様をゼロベースで説明し直すこと**。要約 1〜2 行 + リンクで足りる
- **別コメントへ切り出したのに本文からリンクを貼らないこと**（読み手がコメントの存在に気づけない）
- **本文だけ更新して補足コメントを古いまま放置すること**（どちらが正しいか読み手が判断できなくなる）
- 補足コメントを更新する際に**末尾の Note ブロックを落とすこと**（`github_note_generated_by_claude.md`）
- 本文に書いた数値・識別子・影響範囲の主張を、**差分と照合せずに更新すること**（Step 5）。既存本文を流用した箇所ほど古い記述が残りやすい
- 他人が投稿したコメントを編集すること（対象は自分が投稿したものだけ）
