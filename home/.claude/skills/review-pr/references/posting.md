本体から切り出した詳細。本体の該当する節から開く。

## 8. 総括コメント + インラインコメントを1レビューで投稿

**payload を組む前に `git fetch` する。** 規約を読んで差分を追って反証するあいだに、相手が直していることがある。

実際に、投稿したインラインの `diff_hunk` が想定と違い、**指摘した6行が投稿の直前のコミットで全部解消されていた**ことがある。的外れなコメントを消して回るより、fetch 1回のほうが安い。

| 見ること | 動いていたら |
| --- | --- |
| HEAD が読み始めたときと同じか | **Step 1からやり直す。** 差分が変われば指摘も変わる |
| 指摘した箇所がまだ残っているか | `grep` で数え直す。0件なら落とす |

**両方をセットで出す。** 総括だけだと該当箇所が辿れず、インラインだけだと**全体で何件あるか**が分からない。

**1回の API 呼び出しにまとめる。** 個別に投げるとレビュアーに通知が指摘の件数だけ飛ぶ。

```bash
# payload.json: {"event":"COMMENT","body":"<総括>","comments":[{"path":"...","line":123,"side":"RIGHT","body":"<指摘>"}, ...]}
gh api repos/OWNER/REPO/pulls/<PR>/reviews -X POST --input payload.json \
  --jq '"投稿完了: review_id=\(.id) state=\(.state)"'
```

- **`event` は `COMMENT` 固定。** `APPROVE` / `REQUEST_CHANGES` は**このスキルでは扱わない**（下記「承認は GitHub に書かず、見立てはユーザーへ渡す」）
- **本文は下記「コメント本文の書き方」に従う**（量・流れ・表と図・`suggestion` ）
- **総括は短く、事実だけを書く**。**種別ごとの件数**を1〜3行。`must` だけを数えない。**CI・テストの結果は書かない**（下記「CI と approve は GitHub へ書かない」）
- **インラインに置いた指摘を、総括で要約し直さない**（下記「総括に内訳を書かない」）
- **本文の1行目を PR 作成者へのメンションにする。** 総括・インラインのすべてに付け、次の行から prefix を書く

  ```markdown
  @<PR 作成者の GitHub ID>
  [must]
  <本文>
  ```

  ID は `gh pr view <PR> --json author -q .author.login` で引いた値をそのまま使う。**ユーザーが会話で書いた綴りを鵜呑みにしない**（ `taro` と `tarou` のような揺れがある）

- **prefix は裸で書き、直後で改行する。** バッククォートで囲わず、同じ行に本文を続けない。**総括・インラインのどちらも同じ**

  ```markdown
  <!-- ❌ NG: コードスパンにしている -->
  `[iaio]`

  <!-- ❌ NG: prefix が本文に埋もれる -->
  [iaio] フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです

  <!-- ✅ OK: 裸の prefix だけの行にして、本文は次の行から -->
  [iaio]
  フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです
  ```

  **prefix を立てるのは、その本文が指摘そのもののときだけ。** 件数を述べる文は指摘ではないので、**prefix を立てず地の文で書く**。

  ```markdown
  <!-- ❌ NG: 総括そのものが iaio の指摘に見える -->
  [iaio]
  1 件です

  <!-- ✅ OK: 括弧を外して地の文にする。総括はこの 1 行で足りる -->
  iaio が 1 件です
  ```

  **総括に prefix が立ってよいのは、そこに本文を持つ指摘を置くときだけ**（差分外の行や PR 本文への指摘）。件数の行と混在してよい。

- インラインは `line` が**差分に含まれる行**である必要がある。含まれない行への指摘は総括側に回す
- **同じ主題が複数箇所にまたがるときは、主となる1箇所に本文を置き、残りは短く参照させる**
- **総括と各インラインのすべてに生成者表示の Note ブロックを付ける**（ `github_note_generated_by_claude.md` ）。Files changed タブではインラインが総括と離れて表示されるため、総括側だけでは書き手が伝わらない。**付けるかどうかの判定はあちら**で、自分たちが管理していないリポジトリでは付けない

## コメント本文の書き方

土台は `rules/concise_first_then_detail.md`。ここではレビューコメント固有の事情だけを足す。

**インラインコメントは差分の途中に挟まる。** PR 本文より条件が厳しく、長いと**差分そのものが読めなくなる**。

- **散文は1コメント5行以内**。読む負担は散文の量で決まるので、表・図・コードブロック・`<details>` の中身はこの数えから外す。超えたら畳む
- **1コメント1主題**。複数を詰めると、相手はどれに対応済みか管理できなくなる。主題が増えたらコメントを分ける
- **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・丁寧さの水増し・自明な補足）と同じ

**結論から流す。** 1行目で何の指摘かが掴めるようにし、根拠と代案を後に続ける。

| 順 | 書くこと |
| --- | --- |
| 1 | **何が問題か**（1行で言い切る） |
| 2 | **なぜ問題か**（規約の引用・影響・前例） |
| 3 | **どうするか**（代案。無いなら「判断を仰ぎたい」で止めてよい） |

**3は方針ではなく、変更後の形まで書く。** 「〜を並べるとよいです」で止めると、相手はどう書けばよいかを自分で組み立て直すことになる。**置き換えが数行で確定しているなら、必ずコード片を添える**。

| 直す行が | 渡し方 |
| --- | --- |
| **差分に含まれる** | **`suggestion`**（下記「コード片は `suggestion` で渡す」）。ワンクリックで適用できる |
| **差分の外** | **変更後の行をコードブロックで示し、`path:line` を添える**。`suggestion` は差分内の行にしか付かない |

**差分の外だから省く、をしない。** 指摘した箇所と直す箇所が別ファイルになるのは普通で、**そのときほど相手は探すことになる**。

文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる。

**「つまりどういうこと？」で止まらせない。** 「規約違反です」で終えず、**そのまま進むと何が起きるか**まで書く。「検証が通らない」は「フリガナを触っていない編集でも保存できなくなる」まで。ただし**言い換えを重ねない**。1行足せば大半は解ける。

## 長くなったら畳む

| 使うもの | いつ | 注意 |
| --- | --- | --- |
| **表** | 同じ観点が3件以上（観点と所見、案の比較、影響範囲） | **1列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、先頭列がファイルパスや長い識別子だと残りの列が潰れる。短くできないなら箇条書きにする |
| **Mermaid** | 差分の羅列から読み取れない構造・関係・流れ | GitHub は ` ```mermaid ` フェンスをそのままレンダリングする |

Mermaid の使い分けは、`flowchart` が分岐・処理順・依存、`sequenceDiagram` が複数コンポーネントをまたぐフロー、`erDiagram` がテーブルとリレーション。**集約の境界・呼び出し経路・不変条件が崩れる筋道**のように、コードを追わないと見えない関係を示すときに効く。

置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を2つの形式で持たない。** 差分から自明な指摘（命名、並び順、typo）に図は足さない。

**畳む手段は表と Mermaid だけではない。** Alert / `<details>` / 脚注の使い分けは `/format-github-post` が持つ。

**レビューコメントでは `<details>` が効く。** 「散文は1コメント5行以内」を守ると根拠を書き切れないことがあるが、**畳めば本文を短く保ったまま置ける**。

| 畳む中身 | なぜ本文に置かないか |
| --- | --- |
| 規約の原文の引用 | 指摘を読むだけなら要らない。**反論するときに要る** |
| 既存の件数の内訳（「101本中86本」の数え方） | 結論だけで足りる。**疑ったときに開く** |
| 落とした候補と落とした理由 | 相手の行動が変わらない |

`<summary>` は「根拠」「数え方」のように**中身が分かる名前**にする。

### コード片は `suggestion` で渡す

置き換えが1〜数行で確定しているなら、**相手がワンクリックで取り込める形**にする。

````markdown
```suggestion
	maxClientAssigneeCount      = 50
```
````

- **インデントを含め、その行を丸ごと置き換えた結果**を書く。差分の行に対してそのまま適用されるため、字下げがずれるとビルドが壊れる
- 設計の選択が絡むもの、複数箇所に波及するものには使わない。**相手が考えずに適用できてしまう**
- 相手のコードを長く引用しない。インラインコメントは**既にその行に付いている**ので、再掲は場所を取るだけ

## 投稿し直すとき

**取り消しやすさが対象によって違う。** インラインは消えるが、レビュー本体は消えない。

| 対象 | できること |
| --- | --- |
| インラインコメント | **削除できる**。`gh api "repos/OWNER/REPO/pulls/comments/<comment_id>" -X DELETE` |
| レビュー本体 | **削除できない**（ `DELETE .../reviews/<id>` は pending 専用で、submitted 済みには `422` が返る）。本文の編集か、**非表示化**のみ |

レビュー本体を引っ込めるには GraphQL の `minimizeComment` を使う。`PullRequestReview` も対象になっていて、UI 上は「This comment was marked as low quality.」と折り畳まれる。

```bash
# node_id は gh api graphql の reviews(first:20){nodes{id databaseId}} で引く
gh api graphql -f query='mutation { minimizeComment(input: {subjectId: "<node_id>", classifier: LOW_QUALITY}) { minimizedComment { isMinimized minimizedReason } } }'
```

- ID をループで回すときは、**1行ずつ読む**（ `while read -r id` 等）。コマンド置換の結果をそのまま変数展開すると全 ID が1つの文字列として渡り、**1件も処理されないまま「実行した」ように見える**
- 削除・非表示のあとは**残存件数を数えて確かめる**
- **ユーザーが approve 済みの PR にも `COMMENT` レビューは追加できる**。承認の状態は変わらないので、後から指摘を足してよい

**不要になったコメントは残さず削除する。** 投稿後に的外れだったと分かったもの、前提が変わって意味を失ったもの、貼り直しで重複したものが対象。

- **誤検知は放置しない。** 消さずにおくと相手が対応を検討する時間を奪う。指摘の取り下げは、コメントを消したうえで**ユーザーへ口頭で報告**する
- 一方、**相手が既に対応・返信したコメントは消さない**。やりとりの経緯が失われる
- レビュー本体が消せず非表示だけになった場合、その旨をユーザーに伝える。**「消しました」と報告しない**
