# --deep のときの手順

`/review-pr --deep` のときの手順です。**Step 4（レビューの実施）だけ**を並列化し、それ以外の手順は持ちません。

| 手順 | 担当 |
| --- | --- |
| PR の特定・過去レビューの確認（Step 1） | **`/review-pr`** |
| レビュー規約の読み取り（Step 2） | **`/review-pr`** |
| 規約ドキュメントの本体を読む（Step 3） | **`/review-pr`** |
| **レビューの実施（Step 4）** | **この手順**（並列化） |
| 裏取り・敵対的検証・報告・投稿（Step 5〜9） | **`/review-pr`** |

**`SKILL.md` の手順をここに複写しない。** 差し替えるのは Step 4だけで、他は原文に従います。

**並列レビューそのものの手順は `/review-code --deep` が持っています。** ここでは**対象を PR にして、そこへ委譲するだけ**です。コスト確認・束の分けかた・起動のしかた・俯瞰の並走・回収とマージは、すべてあちらの規定に従う。

## 進め方

### 1. Step 1〜3を `/review-pr` のとおり踏む

**規約を読まずに並列起動しない。** 委譲先へ渡す規約のパスは、ここで集めたものを使います。

Step 3で辿った `docs/` 配下のファイルは、**サブエージェントにも Read させる**（本文を複写せず、パスだけ渡す）。

### 2. プロジェクト側に深いレビュースキルがあれば、そちらへ委譲する

**あるなら自前で並列しない。** ディレクトリ構成と規約の対応を知っているのはそちらで、こちらが組み直すと精度が落ちます。

- 判定は**利用可能なスキルの一覧**で行う。`.claude/skills/` と `.claude/commands/` の両方を見る
- 名前を決め打ちしない。「差分を多観点・レイヤー別に見る」と読めるものを探す
- 委譲したら **Step 3〜4は飛ばし**、返ってきた指摘を持って `/review-pr` の Step 5へ進む

### 3. プロジェクト側に無ければ `/review-code --deep` へ委譲する

**手順を組み直さず、Skill ツールで `review-code` を `--deep` 付きで呼ぶ。** 渡すのは次の4つだけです。

| 渡すもの | 中身 |
| --- | --- |
| **diff 範囲** | `<base>...<head>`。PR のベースと先端から作る |
| **規約のパス** | Step 3で辿ったファイル |
| **追加の重点観点** | `--focus` の指定。無ければ「なし」 |
| **課題の主題** | `/review-pr` の Step 1「課題票を読み、PR の範囲と突き合わせる」で取り出した1文。課題票が無ければ「課題票なし」 |

**コスト確認は委譲先が行います。** ただし自然文から `--deep` で起動したときは、**呼ぶ前にこちらで1度確認する**（軽く済ませる代替として `--deep` 無しの `/review-pr` があることも示す）。

### 4. 待っている間、PR 固有の確認をする

**委譲先の Phase 2は差分の中だけを見ます。** PR にしか無い情報との突き合わせは、こちらの担当です。

- **PR 本文の説明と差分の食い違い**
- 課題票の本来の挙動・受入基準のうち、PR が満たしていない項目（ `/review-pr` の Step 1で並べたもの）
- 変更全体として「どこに何を足したか」が、**その PR の目的**と合っているか
- 過去のレビューで指摘済みの箇所が、そのまま残っていないか

### 5. 回収して `/review-pr` の Step 5へ渡す

**重複の集約・根拠の無いものの除去・失敗したエージェントの補完は、委譲先が済ませています。** こちらでやり直さない。

**残るのは重要度の読み替えだけです。**

**課題票との突き合わせで見つかった項目も、ここで重要度を決める。** 委譲先は差分の中だけを見るので、課題が求めていて PR が直していない箇所は返ってこない。手順4で見つけたものに `severity.md` の「差分の外は、課題の主題に関わるときだけ must」を当てる。主題が解決するなら、残りは `[iaio]` にしてマージを止めない。

**委譲先が重要度を付けてきたら、体系ごと読み替える。** プロジェクトスキルの `must` や `/review-code --deep` の `must` と、そのリポジトリの `[must]` （かならず変更して）は**別の基準**です。判定表をそのまま持ち越すと、意味がずれたまま投稿することになります。

**上げるときは、下げるとき以上に裏を取る。** 下げすぎても相手の時間は奪いませんが、**上げすぎるとマージを止めます**。委譲先が `imo` としたものを `must` へ上げるなら、次の2つを必ず確かめる。

| 確かめること | やり方 |
| --- | --- |
| **規約に明文化されているか** | 該当する語で走査し、**必ず当たる語で検算する** |
| **慣習として定着しているか** | **base 側で全件数え、数える単位と内訳を添える**（ `/review-pr` の Step 6）。1例を見て「慣習」と判断しない |

実際に、仕様書の更新を1例だけ見て `must` へ上げ、**同種の変更15件を数えたら0件だった**ことがあります。

**件数の基準は `/review-pr` の Step 6が持ちます。** 数えた結果が割れていれば、慣習は無いので上げる根拠になりません。

**ここから先は `/review-pr` の手順です。** 裏取り（Step 5）・敵対的検証（Step 6）・報告（Step 7）・投稿（Step 8〜9）を、いつもどおり行う。

**サブエージェントが出した指摘も、反証の対象です。** 自分で書いたものと扱いを変えない。**むしろ根拠を確かめていない分、落ちる率が高い**。

## やってはいけないこと

- **`SKILL.md` の手順をここに複写すること**。差し替えるのは Step 4だけ
- **並列レビューの手順をここに書くこと**。束の分けかた・起動のしかた・俯瞰の並走・回収とマージは `/review-code --deep` が持つ。**ここへ書き戻すと、片方だけ古くなる**
- **規約を読む前に委譲すること**。サブエージェントへ渡すパスが決まらない
- **プロジェクト側に深いレビュースキルがあるのに `/review-code --deep` を呼ぶこと**。精度が落ちるうえ二重に走る
- **委譲先が済ませた集約・除去・補完を、こちらでやり直すこと**
- **委譲先の重要度体系を、そのまま持ち越すこと**。`must` の定義がリポジトリ側と違う
- **重要度を上げるとき、規約と慣習を数えずに決めること**。**1例を「慣習」と読むと、多数派が逆だったときに気づけない**
- **回収した指摘を反証せずに報告へ回すこと**。根拠を確かめていないぶん、落ちる率は自分の指摘より高い
- **自然文から起動したのに、コストを確認せず走ること**

## 出力の目安

`/review-pr` の Step 7に従います。そのうえで、**どこへ委譲したか**を報告に足す。

- 委譲先のスキル名（プロジェクト側 / `/review-code --deep` のどちらか）
- 起動したエージェントの数と担当範囲（委譲先の報告から引く）
- **回収した指摘のうち、反証で落とした件数**
