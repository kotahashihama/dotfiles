**他の人が書いた PR** をレビューし、**総括コメント + インラインコメント**を 1 つのレビューとして GitHub へ投稿します。

指摘を**受ける側**の `/resolve-human-reviews` と対になります。**書き込みの向きが逆**なので、混同しないこと。

| | `/resolve-human-reviews` | このスキル |
| --- | --- | --- |
| 対象 | **自分の PR** に付いた指摘 | **他の人の PR** の差分 |
| やること | コードを直す | **指摘を書いて投稿する** |
| GitHub への書き込み | しない | **する（総括 + インライン）** |

## 進め方

### 1. 対象 PR の特定と、レビューしてよいかの確認

- 引数の PR 番号 / URL から `gh pr view <PR> --json number,title,author,state,isDraft,baseRefName,headRefName,body,changedFiles,url` を引く
- **作成者が自分でないことを確かめる**。自分の PR なら `/finalize-pr` の領分なので、このスキルは使わない
- `gh repo view --json nameWithOwner -q .nameWithOwner` で `OWNER/REPO` を取る
- **draft でもレビューしてよい**。ただし本人が仕上げ途中の可能性があるので、報告時に draft である旨を添える

### 2. そのリポジトリのレビュー規約を読む

**prefix の語彙と意味はリポジトリごとに違う。** 記憶で決めず、そのつど拾う。

- **PR 本文**に「レビューのルール」等の節があれば、そこに書かれた prefix をそのまま使う
- 無ければ `.github/pull_request_template.md` / `CONTRIBUTING.md` を見る
- それも無ければ、**既存の PR に付いたコメントを読んで慣習を推定する**

  ```bash
  gh api "repos/OWNER/REPO/pulls/<直近のPR>/comments?per_page=20" -q '.[].body' | head -40
  ```

- 慣習が読み取れなければ prefix を付けず、**重要度を文章で明示**する

**投稿してよいのは `[must]` / `[imo]` / `[nits]` の 3 つだけ。** 語彙がリポジトリごとに違っても、**投稿するのは「直すべきか」を述べる指摘に限る**という原則は変わらない。

| 種別 | 扱い |
| --- | --- |
| `[must]` / `[imo]` / `[nits]`（**直すかどうかを述べるもの**） | **投稿する** |
| `[ask]`（質問） | **投稿しない。** 相手に問いかけるかは、聞き方も含めてユーザーが決める |
| `[fyi]`（参考情報） | **投稿しない。** 相手の行動を変えないうえ、指摘の中に混ざると読む量だけ増える |

質問・参考情報として書きたくなったものは、**ユーザーへの報告（Step 6）に回す**。PR 本文で「ここを確認してほしい」と依頼されている点も同じで、**回答は報告に書く**。指摘として成立するなら `[imo]` / `[nits]` に言い換えて投稿する。

### 3. レビューの実施

**そのリポジトリのレビュースキルがあれば必ず委譲する**（`/review-code`、`/review-code-deeply` 等）。規約の在り処とレイヤー構成を知っているのはそちらなので、ここで自前の観点を組み直さない。

無い場合は、リポジトリの規約ドキュメント（`.claude/rules/`、`docs/` 配下）を読んでから差分を見る。

### 4. 断定する前に裏を取る

**投稿は取り消せない。** 指摘の根拠は、書く前に実物で確かめる（`verify_before_asserting.md`）。

| 確かめること | やり方 |
| --- | --- |
| **行番号** | **`gh pr diff` の出力行番号を使わない。** 新規ファイルはヘッダと先行ファイル分のオフセットが乗る。`git show <ref>:<path> \| grep -n <アンカー>` でファイル単体から採る |
| **ビルド・テスト** | 「規約違反なし」「テストが通る」と書くなら実測する。ブランチを `git worktree add <一時パス> origin/<head> --detach` で取り出して流し、**終わったら `git worktree remove` する** |
| **規約の引用** | 規約ドキュメントの原文を読んで引く。「〜のはず」で書かない |
| **既存パターン** | 「既存と不揃い」と言う前に、既存側を `grep` で数える。**優勢な流儀の方が少数派だったことがある** |

**確信が持てないものは重要度を 1 段階下げる。** 誤検知は相手の時間を奪ううえ、レビュー全体の信頼を落とす。

### 5. 的外れでないかを、1 件ずつ潰す

**書けた指摘を、今度は自分で反証する。** ここが最も手を抜きやすく、最も損失が大きい工程です。

**1 件でも的外れがあると、正しい残りの指摘まで疑われます。** レビューの価値は指摘の件数ではなく、**書いてあることが信用できるか**で決まる。落とすことを恐れない。

| 疑うこと | 潰し方 |
| --- | --- |
| **その規約は本当に存在するか** | 原文を開いて引用する。要約・記憶・「たしかそう書いてあった」で書かない |
| **その項目の定義を読んだか** | 書式・記入値への指摘は、**定義（テンプレート・スキーマ・列の説明）を開いてから**。定義は別ファイルにあることが多い |
| **「該当なし」は本当に該当なしか** | 検索が空を返しただけのことがある。**必ず当たる入力で検算してから**「使われていない」「前例がない」と書く |
| **規約どおりに書くと本当に動くか** | 推奨手段が実装の都合で機能しないことがある。**規約と実物が食い違うなら、実物が正しい** |
| **ガイドライン自身に公認例・例外がないか** | 同じドキュメントに「✅ OK」として載っている書き方を、違反と呼ばない |
| **既存コードは本当に違う流儀か** | 同種のファイルを 2〜3 本開いて**数える**。「不揃い」と思った側が多数派だったことがある |
| **PR 本文で既に説明されていないか** | 「後続 PR で対応」「意図的にこうした」と書かれている点を、知らずに指摘しない |
| **差分の別の場所で対応済みでないか** | 指摘対象のシンボルを差分全体で `grep` する |
| **この PR のスコープ内か** | 触っていない既存コードへの指摘は出さない。伝えたいならユーザーへの報告に回す |

**「規約に書いてあるから違反」で止まらない。** 規約が示す手段が、そのコードベースでは機能しないことがある（エラー型に判定メソッドが無く、規約推奨の比較方法が常に false になる、等）。**規約 → 実物の順で確かめ、食い違ったら指摘ではなく規約側の問題として扱う。**

反証して残ったものだけを Step 6 の報告に載せる。**落とした指摘は報告しない**（検討の過程はユーザーの判断材料にならない）。

### 6. 会話で報告し、GO を待つ

**投稿はここでは行わない。** 重要度順に整理して会話へ出し、ユーザーの明示的な承認を得る（`decide_or_ask.md`）。

- 重要度ごとに畳んで出す。件数が多ければ表にする
- **投稿先の行**（`path:line`）を指摘ごとに決めておく。ここで確定していないと、投稿段で貼り直しになる
- ユーザーが指摘を落とす・言い回しを変える判断をしたら、それに従う

### 7. 総括コメント + インラインコメントを 1 レビューで投稿

**両方をセットで出す。** 総括だけだと該当箇所が辿れず、インラインだけだと全体の判断（マージしてよいか）が伝わらない。

**1 回の API 呼び出しにまとめる。** 個別に投げるとレビュアーに通知が指摘の件数だけ飛ぶ。

```bash
# payload.json: {"event":"COMMENT","body":"<総括>","comments":[{"path":"...","line":123,"side":"RIGHT","body":"<指摘>"}, ...]}
gh api repos/OWNER/REPO/pulls/<PR>/reviews -X POST --input payload.json \
  --jq '"投稿完了: review_id=\(.id) state=\(.state)"'
```

- **`event` は `COMMENT` 固定。** `APPROVE` / `REQUEST_CHANGES` は**このスキルでは扱わない**（下記「承認と是非の表明はしない」）
- **本文は下記「コメント本文の書き方」に従う**（量・流れ・表と図・`suggestion`）
- **総括は短く、事実だけを書く**。`[must]` の有無と、実測したなら何を確かめたかを 1〜3 行
- **prefix の直後で改行する。** 同じ行に本文を続けない

  ```markdown
  <!-- ❌ NG: prefix が本文に埋もれる -->
  [imo] フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです。

  <!-- ✅ OK: prefix だけの行にして、本文は次の行から -->
  [imo]
  フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです。
  ```
- インラインは `line` が**差分に含まれる行**である必要がある。含まれない行への指摘は総括側に回す
- **同じ主題が複数箇所にまたがるときは、主となる 1 箇所に本文を置き、残りは短く参照させる**
- **総括と各インラインのすべてに生成者表示の Note ブロックを付ける**（`github_note_generated_by_claude.md`）。Files changed タブではインラインが総括と離れて表示されるため、総括側だけでは書き手が伝わらない

### 8. 投稿結果を確認する

```bash
gh api "repos/OWNER/REPO/pulls/<PR>/comments?per_page=100" \
  --jq '.[] | select(.pull_request_review_id==<review_id>) | "\(.path):\(.line)\t\(.body | split("\n")[0][0:50])"'
```

**意図した行に付いたかを 1 件ずつ見る。** 行がズレていても API はエラーを返さず、無関係なコードに指摘が付いた状態になる。

## 承認と是非の表明はしない

**このスキルの成果物は指摘であって、判定ではない。** 承認するか、マージしてよいと言うかは**ユーザーが決めて、ユーザーが書く**。

| 書いてよい（事実） | 書かない（是非の表明） |
| --- | --- |
| 「`[must]` はありません」 | 「LGTM です」 |
| 「`go build` と `go test` が通ることを確認しました」 | 「マージして問題ありません」 |
| 「規約違反は見つかりませんでした」 | 「良い実装だと思います」「問題なさそうです」 |

**指摘がゼロでも同じ。** 「`[must]` はありません」で止め、そこから先の判断はユーザーに委ねる。**投稿する `event` は `COMMENT` だけで、`APPROVE` / `REQUEST_CHANGES` は使わない。**

事実と表明の境目は、**その一文が消えたときにユーザーの選択肢が減るか**で見分ける。減るなら表明なので書かない。

## コメント本文の書き方

土台は `rules/concise_first_then_detail.md`。ここではレビューコメント固有の事情だけを足す。

**インラインコメントは差分の途中に挟まる。** PR 本文より条件が厳しく、長いと**差分そのものが読めなくなる**。

- **散文は 1 コメント 5 行以内**。読む負担は散文の量で決まるので、表・図・コードブロックはこの数えから外す。超えたら畳む
- **1 コメント 1 主題**。複数を詰めると、相手はどれに対応済みか管理できなくなる。主題が増えたらコメントを分ける
- **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・丁寧さの水増し・自明な補足）と同じ

**結論から流す。** 1 行目で何の指摘かが掴めるようにし、根拠と代案を後に続ける。

| 順 | 書くこと |
| --- | --- |
| 1 | **何が問題か**（1 行で言い切る） |
| 2 | **なぜ問題か**（規約の引用・影響・前例） |
| 3 | **どうするか**（代案。無いなら「判断を仰ぎたい」で止めてよい） |

文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる。

**「つまりどういうこと？」で止まらせない。** 「規約違反です」で終えず、**そのまま進むと何が起きるか**まで書く。「検証が通らない」は「フリガナを触っていない編集でも保存できなくなる」まで。ただし**言い換えを重ねない**。1 行足せば大半は解ける。

### 表と Mermaid で畳む

| 使うもの | いつ | 注意 |
| --- | --- | --- |
| **表** | 同じ観点が 3 件以上（観点と所見、案の比較、影響範囲） | **1 列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、先頭列がファイルパスや長い識別子だと残りの列が潰れる。短くできないなら箇条書きにする |
| **Mermaid** | 差分の羅列から読み取れない構造・関係・流れ | GitHub は ` ```mermaid ` フェンスをそのままレンダリングする |

Mermaid の使い分けは、`flowchart` が分岐・処理順・依存、`sequenceDiagram` が複数コンポーネントをまたぐフロー、`erDiagram` がテーブルとリレーション。**集約の境界・呼び出し経路・不変条件が崩れる筋道**のように、コードを追わないと見えない関係を示すときに効く。

置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を 2 つの形式で持たない。** 差分から自明な指摘（命名、並び順、typo）に図は足さない。

### コード片は `suggestion` で渡す

置き換えが 1〜数行で確定しているなら、**相手がワンクリックで取り込める形**にする。

````markdown
```suggestion
	maxClientAssigneeCount      = 50
```
````

- **インデントを含め、その行を丸ごと置き換えた結果**を書く。差分の行に対してそのまま適用されるため、字下げがずれるとビルドが壊れる
- 設計の選択が絡むもの、複数箇所に波及するものには使わない。**相手が考えずに適用できてしまう**
- 相手のコードを長く引用しない。インラインコメントは**既にその行に付いている**ので、再掲は場所を取るだけ

## 投稿し直すとき

**取り消しやすさが対象によって違う。** インラインは消えるが、レビュー本体は消えない。

| 対象 | できること |
| --- | --- |
| インラインコメント | **削除できる**。`gh api "repos/OWNER/REPO/pulls/comments/<comment_id>" -X DELETE` |
| レビュー本体 | **削除できない**（`DELETE .../reviews/<id>` は pending 専用で、submitted 済みには `422` が返る）。本文の編集か、**非表示化**のみ |

レビュー本体を引っ込めるには GraphQL の `minimizeComment` を使う。`PullRequestReview` も対象になっていて、UI 上は「This comment was marked as low quality.」と折り畳まれる。

```bash
# node_id は gh api graphql の reviews(first:20){nodes{id databaseId}} で引く
gh api graphql -f query='mutation { minimizeComment(input: {subjectId: "<node_id>", classifier: LOW_QUALITY}) { minimizedComment { isMinimized minimizedReason } } }'
```

- ID をループで回すときは、**1 行ずつ読む**（`while read -r id` 等）。コマンド置換の結果をそのまま変数展開すると全 ID が 1 つの文字列として渡り、**1 件も処理されないまま「実行した」ように見える**
- 削除・非表示のあとは**残存件数を数えて確かめる**
- **ユーザーが approve 済みの PR にも `COMMENT` レビューは追加できる**。承認の状態は変わらないので、後から指摘を足してよい

**不要になったコメントは残さず削除する。** 投稿後に的外れだったと分かったもの、前提が変わって意味を失ったもの、貼り直しで重複したものが対象。

- **誤検知は放置しない。** 消さずにおくと相手が対応を検討する時間を奪う。指摘の取り下げは、コメントを消したうえで**ユーザーへ口頭で報告**する
- 一方、**相手が既に対応・返信したコメントは消さない**。やりとりの経緯が失われる
- レビュー本体が消せず非表示だけになった場合、その旨をユーザーに伝える。**「消しました」と報告しない**

## 出力の目安

- 報告は重要度順。ブロッカーの有無を先頭 1 行で断定する
- 投稿後は、件数の内訳と PR の URL を出す。指摘本文を会話へ再掲しない（GitHub 側にある）
- 良かった点があれば 1〜2 行添える。**水増ししない**

## やってはいけないこと

- **`APPROVE` / `REQUEST_CHANGES` を投稿すること**。承認はユーザーがやる（上記「承認と是非の表明はしない」）
- **「LGTM」「マージして問題ない」「良い実装だと思います」と書くこと**。指摘がゼロでも事実だけを述べて止める
- **ユーザーの GO を得ずに投稿すること**。レビュアーに通知が飛び、取り消せない
- **反証（Step 5）を飛ばして投稿すること**。書けた指摘をそのまま出さない
- **規約の原文を開かずに「規約違反」と書くこと**。引用できないものは指摘にしない
- **`gh pr diff` の行番号をそのまま引用すること**（Step 4）
- **投稿してから形式を直せばよいと考えること**。インラインは消せてもレビュー本体は消えない（下記「投稿し直すとき」）。形式は投稿前に確定する
- 総括だけ、またはインラインだけで済ませること
- **Note ブロックを省くこと**。1 行の `[nits]` でも付ける
- 自動生成ファイル（`*_mock.go`、`mock/` 配下等）へ指摘すること
- 相手の書き方の好みを規約と偽って指摘すること。**規約に無いものは `[imo]` 以下**にする
- **件数を揃えるために指摘を水増しすること**。反証で全部落ちたなら「ブロッカーなし」だけでよい
- **散文を長く積むこと**。同じ観点が 3 件以上なら表、構造・流れなら Mermaid に畳む
- **1 コメントに複数の主題を詰めること**。相手がどれに対応済みか管理できなくなる
- **設計判断が絡むものを `suggestion` で渡すこと**。相手が考えずに適用できてしまう
- 相手のコードを長く引用すること。**インラインは既にその行に付いている**
- 指摘の並びを重要度で組み替えて報告すること。ユーザーは PR を上から追う（`report_formatting.md`）

## 例外

- ユーザーが「まとめて 1 コメントで」と指示した場合は、インラインに分けず総括のみで投稿する
- レビュー結果を投稿せず会話に留めたい場合（下読みだけ頼まれた場合）は、Step 6 で終える

## 関連

- `/resolve-human-reviews`（受ける側）: 指摘の**受け手**の手順。本スキルは出し手
- `/review-code`・`/review-code-deeply` 等のプロジェクトスキル: レビューの**中身**。本スキルは対象特定・裏取り・整形・投稿を担う
- `no_auto_reply_human_review_comments.md`: 人間のコメントへ勝手に返信しないことを定める。**本スキルが扱うのは新規レビューの投稿**であり、既存コメントへの返信ではない
- `concise_first_then_detail.md`（簡潔に、表と Mermaid で畳む）: 「コメント本文の書き方」の土台。`/create-pr`・`/update-pr-description` も同じ土台に乗る
- `github_note_generated_by_claude.md`: 生成者表示の書式
- `verify_before_asserting.md`: Step 4〜5 の土台。**ユーザーの発言も裏取りの対象**という点は、PR 本文の主張にもそのまま当てはまる
