**他の人が書いた PR** をレビューし、**総括コメント + インラインコメント**を 1 つのレビューとして GitHub へ投稿します。

指摘を**受ける側**の `/resolve-human-reviews` と対になります。**書き込みの向きが逆**なので、混同しないこと。

| | `/resolve-human-reviews` | このスキル |
| --- | --- | --- |
| 対象 | **自分の PR** に付いた指摘 | **他の人の PR** の差分 |
| やること | コードを直す | **指摘を書いて投稿する** |
| GitHub への書き込み | しない | **する（総括 + インライン）** |

## 進め方

### 1. 対象 PR の特定と、レビューしてよいかの確認

- 引数の PR 番号 / URL から `gh pr view <PR> --json number,title,author,state,isDraft,baseRefName,headRefName,body,changedFiles,url` を引く
- **作成者が自分でないことを確かめる**。自分の PR なら `/finalize-pr` の領分なので、このスキルは使わない
- `gh repo view --json nameWithOwner -q .nameWithOwner` で `OWNER/REPO` を取る
- **draft でもレビューしてよい**。ただし本人が仕上げ途中の可能性があるので、報告時に draft である旨を添える

### 2. そのリポジトリのレビュー規約を読む

**prefix の語彙と意味はリポジトリごとに違う。** 記憶で決めず、そのつど拾う。

- **PR 本文**に「レビューのルール」等の節があれば、そこに書かれた prefix をそのまま使う（**`imo` だけは置き換える。下記**）
- 無ければ `.github/pull_request_template.md` / `CONTRIBUTING.md` を見る
- それも無ければ、**既存の PR に付いたコメントを読んで慣習を推定する**

  ```bash
  gh api "repos/OWNER/REPO/pulls/<直近のPR>/comments?per_page=20" -q '.[].body' | head -40
  ```

- 慣習が読み取れなければ prefix を付けず、**重要度を文章で明示**する

**投稿してよいのは `[must]` / `[iaio]` / `[nits]` の 3 つだけ。** 語彙がリポジトリごとに違っても、**投稿するのは「直すべきか」を述べる指摘に限る**という原則は変わらない。

| 種別 | 扱い |
| --- | --- |
| `[must]` / `[iaio]` / `[nits]`（**直すかどうかを述べるもの**） | **投稿する** |
| `[ask]`（質問） | **投稿しない。** 相手に問いかけるかは、聞き方も含めてユーザーが決める |
| `[fyi]`（参考情報） | **投稿しない。** 相手の行動を変えないうえ、指摘の中に混ざると読む量だけ増える |

質問・参考情報として書きたくなったものは、**ユーザーへの報告（Step 7）に回す**。指摘として成立するなら `[iaio]` / `[nits]` に言い換えて投稿する。

### `imo` は使わず `iaio` と書く

**意見を述べる指摘は `[iaio]`（in AI opinion）にする。** リポジトリの規約が `[imo]`（in my opinion）を定義していても、**こちらは `[iaio]` を使う**。

| prefix | 書き手 |
| --- | --- |
| `[imo]` | 人間のレビュアーの意見 |
| **`[iaio]`** | **AI の意見** |

**`must` と `nits` は置き換えない。** 規約違反・事実誤りの指摘と、typo や表記揺れの指摘は、**誰が書いても内容が変わらない**。意見だけが書き手によって重みの変わるものなので、そこだけ分ける。

読み手が **prefix の時点で重みを判断できる**ようにするため。末尾の Note ブロックでも生成者は分かるが、一覧で prefix だけを追っているときには目に入らない。

**リポジトリのテンプレートに無い語彙なので、総括で 1 度だけ開く。** インラインには付けない。

```markdown
iaio が 1 件です（iaio = in AI opinion）
```

テンプレートへ足すかは**リポジトリの合意事項**なので、こちらからは動かさない。

**ただし報告へ回すのは、こちらが調べて初めて分かることだけ。** PR 本文に「ここを確認してほしい」と書かれていても、**PR を出した側が既に把握していることには答えない**。

| 報告に書く | 書かない |
| --- | --- |
| 差分を読んで分かった影響（読み出し箇所の有無、既存テストの欠落） | **マージ順・リリース順**。出した側が組み立てた計画 |
| 規約や実装を当たって確かめた事実 | 相手が本文で自ら説明している前提の言い換え |

**「聞かれたから答える」で判断しない。** 本文の確認依頼は、たいていレビュアー全員に向けた念押しであって、**こちらが調べ直す必要のあるものとは限らない**。答える前に「これは自分が調べて初めて分かったことか」を見る。

### 3. 規約ドキュメントの本体を読む

**差分を見る前に読む。** 規約を知らないまま差分を読むと、目に付いた違いを規約と思い込んで指摘してしまう。

**規約の本体は `.claude/rules/` ではない。** ルール側は `paths` で対象を絞る入口で、中身は `@docs/...` の参照先が持つ。**入口だけ読んで「規約違反」と書かない**（Step 6）。

| 順 | やること |
| --- | --- |
| 1 | **置き場を実際に見る**。`ls docs/` で規約ドキュメントのディレクトリを特定する |
| 2 | **差分のファイルパスに `paths` がマッチする `.claude/rules/**` を集める** |
| 3 | そこから参照されている `docs/` 配下のファイルを辿る |
| 4 | **辿った先を並列で読む**（1 メッセージに複数の Read を並べる） |

**置き場の名前はリポジトリごとに違う。** 揃っている前提で決め打ちせず、毎回 `ls docs/` で見る。よく触るリポジトリの対応は `CLAUDE.private.md` が持つ。

**全部読まない。** 数十本あることが多いので、**差分が触れた領域に絞る**。ただし絞った結果が 10 本を超えても、並列で読めば 1 往復で済む。

**横断的な規約は、領域を問わず読む。** テストの書き方・命名・アーキテクチャの原則は `paths` で絞られないことがあり、**領域別のドキュメントが「上書きする標準ルール」として参照している側**にある。領域別だけ読むと、上書きされていない本則を見落とす。

### 4. レビューの実施

**そのリポジトリのレビュースキルがあれば必ず委譲する**（`/review-code`、`/review-code-deeply` 等。**`.claude/skills/` と `.claude/commands/` の両方を見る**）。レイヤー構成と観点を知っているのはそちらなので、ここで自前の観点を組み直さない。

**委譲しても Step 3 は省かない。** 規約の原文を自分で読んでいないと、返ってきた指摘を検証できない。

### 5. 断定する前に裏を取る

**投稿は取り消せない。** 指摘の根拠は、書く前に実物で確かめる（`verify_before_asserting.md`）。

| 確かめること | やり方 |
| --- | --- |
| **行番号** | **`gh pr diff` の出力行番号を使わない。** 新規ファイルはヘッダと先行ファイル分のオフセットが乗る。`git show <ref>:<path> \| grep -n <アンカー>` でファイル単体から採る |
| **ビルド・テスト** | 「規約違反なし」「テストが通る」と書くなら実測する。ブランチを `git worktree add <一時パス> origin/<head> --detach` で取り出して流し、**終わったら `git worktree remove` する** |
| **規約の引用** | 規約ドキュメントの原文を読んで引く。「〜のはず」で書かない |
| **既存パターン** | 「既存と不揃い」と言う前に、既存側を `grep` で数える。**優勢な流儀の方が少数派だったことがある** |

**確信が持てないものは重要度を 1 段階下げる。** 誤検知は相手の時間を奪ううえ、レビュー全体の信頼を落とす。

### 6. 的外れでないかを、1 件ずつ潰す

**書けた指摘を、今度は自分で反証する。** ここが最も手を抜きやすく、最も損失が大きい工程です。

**1 件でも的外れがあると、正しい残りの指摘まで疑われます。** レビューの価値は指摘の件数ではなく、**書いてあることが信用できるか**で決まる。落とすことを恐れない。

| 疑うこと | 潰し方 |
| --- | --- |
| **その規約は本当に存在するか** | 原文を開いて引用する。要約・記憶・「たしかそう書いてあった」で書かない |
| **その項目の定義を読んだか** | 書式・記入値への指摘は、**定義（テンプレート・スキーマ・列の説明）を開いてから**。定義は別ファイルにあることが多い |
| **「該当なし」は本当に該当なしか** | 検索が空を返しただけのことがある。**必ず当たる入力で検算してから**「使われていない」「前例がない」と書く |
| **規約どおりに書くと本当に動くか** | 推奨手段が実装の都合で機能しないことがある。**規約と実物が食い違うなら、実物が正しい** |
| **ガイドライン自身に公認例・例外がないか** | 同じドキュメントに「✅ OK」として載っている書き方を、違反と呼ばない |
| **既存コードは本当に違う流儀か** | 同種のファイルを 2〜3 本開いて**数える**。「不揃い」と思った側が多数派だったことがある |
| **PR 本文で既に説明されていないか** | 「後続 PR で対応」「意図的にこうした」と書かれている点を、知らずに指摘しない |
| **差分の別の場所で対応済みでないか** | 指摘対象のシンボルを差分全体で `grep` する |
| **この PR のスコープ内か** | 触っていない既存コードへの指摘は出さない。伝えたいならユーザーへの報告に回す |

**「規約に書いてあるから違反」で止まらない。** 規約が示す手段が、そのコードベースでは機能しないことがある（エラー型に判定メソッドが無く、規約推奨の比較方法が常に false になる、等）。**規約 → 実物の順で確かめ、食い違ったら指摘ではなく規約側の問題として扱う。**

**投稿するのは反証して残ったものだけ。** ただし**落とした候補は、落とした理由とセットでユーザーへ報告する**（Step 7）。「規約はあったが実装では機能しない」「既存を数えたら少数派だった」は、**次にユーザー自身がレビューするときの判断材料**になる。1 件 1 行に収める。

### 7. 会話で報告し、GO を待つ

**投稿はここでは行わない。** 重要度順に整理して会話へ出し、ユーザーの明示的な承認を得る（`decide_or_ask.md`）。

- 重要度ごとに畳んで出す。件数が多ければ表にする
- **投稿先の行**（`path:line`）を指摘ごとに決めておく。ここで確定していないと、投稿段で貼り直しになる
- ユーザーが指摘を落とす・言い回しを変える判断をしたら、それに従う

### 報告に入れるもの

**ユーザーは自分でもレビューする。** 指摘の一覧だけ渡すと、**次に自分でレビューするときに再現できない**。何を見て、何を見なかったかまで渡す。

**先頭 1 行は結論。** ブロッカーの有無と、`must` が無いなら approve の見立てを言い切る。下記の 1〜5 はその後に続ける。

| 節 | 中身 |
| --- | --- |
| **1. どういう PR か** | 何をする変更か、差分の性質（新規追加 / 既存改修 / 契約変更）、規模。**2〜3 行** |
| **2. どの観点で見たか** | 観点・見たもの・結果を表で。**指摘に至らなかった観点も載せる** |
| 3. 指摘の一覧 | 重要度順。投稿先の行を添える |
| 4. 落とした候補 | 落とした理由とセットで 1 件 1 行（Step 6） |
| 5. approve の見立て | 下記「ユーザーへ伝える見立て」 |

**2 が成長の材料になる。** 「規約ドキュメントを 6 本読んだ」「既存 101 本を数えた」「CI の失敗が承認待ちか実害かを見た」は、**指摘がゼロでも次に効く**。逆に「見なかった領域」も書く——読み切れなかった箇所があるなら、そこは保証していないと分かる形にする。

土台は `focus_insights_on_judgment.md`「代行するほど、渡す責任が増える」。本節はそれをレビューの報告に具体化したもの。

**観点は水増ししない。** 実際に見たものだけを書く。見ていない観点を並べると、**裏取りの範囲を過大に伝える**ことになり、指摘そのものより害が大きい。

### 8. 総括コメント + インラインコメントを 1 レビューで投稿

**両方をセットで出す。** 総括だけだと該当箇所が辿れず、インラインだけだと**全体で何件あるか**が分からない。

**1 回の API 呼び出しにまとめる。** 個別に投げるとレビュアーに通知が指摘の件数だけ飛ぶ。

```bash
# payload.json: {"event":"COMMENT","body":"<総括>","comments":[{"path":"...","line":123,"side":"RIGHT","body":"<指摘>"}, ...]}
gh api repos/OWNER/REPO/pulls/<PR>/reviews -X POST --input payload.json \
  --jq '"投稿完了: review_id=\(.id) state=\(.state)"'
```

- **`event` は `COMMENT` 固定。** `APPROVE` / `REQUEST_CHANGES` は**このスキルでは扱わない**（下記「承認は GitHub に書かず、見立てはユーザーへ渡す」）
- **本文は下記「コメント本文の書き方」に従う**（量・流れ・表と図・`suggestion`）
- **総括は短く、事実だけを書く**。**種別ごとの件数**を 1〜3 行。`must` だけを数えない。**CI・テストの結果は書かない**（下記「CI と approve は GitHub へ書かない」）
- **インラインに置いた指摘を、総括で要約し直さない**（下記「総括に内訳を書かない」）
- **本文の 1 行目を PR 作成者へのメンションにする。** 総括・インラインのすべてに付け、次の行から prefix を書く

  ```markdown
  @<PR 作成者の GitHub ID>
  [must]
  <本文>
  ```

  ID は `gh pr view <PR> --json author -q .author.login` で引いた値をそのまま使う。**ユーザーが会話で書いた綴りを鵜呑みにしない**（`taro` と `tarou` のような揺れがある）

- **prefix は裸で書き、直後で改行する。** バッククォートで囲わず、同じ行に本文を続けない。**総括・インラインのどちらも同じ**

  ```markdown
  <!-- ❌ NG: コードスパンにしている -->
  `[iaio]`

  <!-- ❌ NG: prefix が本文に埋もれる -->
  [iaio] フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです

  <!-- ✅ OK: 裸の prefix だけの行にして、本文は次の行から -->
  [iaio]
  フリガナの検証は shared の値オブジェクトへ切り出す余地がありそうです
  ```

  **prefix を立てるのは、その本文が指摘そのもののときだけ。** 件数を述べる文は指摘ではないので、**prefix を立てず地の文で書く**。

  ```markdown
  <!-- ❌ NG: 総括そのものが iaio の指摘に見える -->
  [iaio]
  1 件です

  <!-- ✅ OK: 括弧を外して地の文にする。総括はこの 1 行で足りる -->
  iaio が 1 件です
  ```

  **総括に prefix が立ってよいのは、そこに本文を持つ指摘を置くときだけ**（差分外の行や PR 本文への指摘）。件数の行と混在してよい。

- インラインは `line` が**差分に含まれる行**である必要がある。含まれない行への指摘は総括側に回す
- **同じ主題が複数箇所にまたがるときは、主となる 1 箇所に本文を置き、残りは短く参照させる**
- **総括と各インラインのすべてに生成者表示の Note ブロックを付ける**（`github_note_generated_by_claude.md`）。Files changed タブではインラインが総括と離れて表示されるため、総括側だけでは書き手が伝わらない

### 9. 投稿結果を確認する

```bash
gh api "repos/OWNER/REPO/pulls/<PR>/comments?per_page=100" \
  --jq '.[] | select(.pull_request_review_id==<review_id>) | "\(.path):\(.line)\t\(.html_url)"'
```

**意図した行に付いたかを 1 件ずつ見る。** 行がズレていても API はエラーを返さず、無関係なコードに指摘が付いた状態になる。**`diff_hunk` の末尾行を見れば、どのコードに付いたかまで確かめられる**。

**`html_url` はここで拾って報告へ回す**（`report_formatting.md`）。確認と報告で 2 回叩かない。

## 再レビュー

**対応後にもう一度呼ばれたときも、Step 1〜9 は同じ。** 差分が動いた以上、規約の読み直しも裏取りも反証も改めて行う。**前回の記憶で済ませない。**

**書き換わったファイルは本体を読む。** 前回 `grep` や構造の確認で済ませた箇所も、対応で中身が変わっているなら**改めて全部読む**。前回と同じ深さで見ると、**書き換えで新しく入った問題を見落とす**。

| 前回のやり方 | 再レビューでのやり方 |
| --- | --- |
| `grep` で関数名・構造だけ確認した | **本体を読む**。テストなら各ケースの検証内容まで |
| 差分の該当箇所だけ読んだ | 対応でファイルが書き換わったなら**ファイル単位で読む** |

そのうえで、再レビュー固有の工程が 2 つ増える。

### 前回の指摘が片付いたかを 1 件ずつ確かめる

**相手の「対応しました」を信じて数えない。** 実物を見る。

| 確かめること | やり方 |
| --- | --- |
| コードが実際に変わったか | 返信のコミットハッシュではなく、**現在の HEAD の中身**を読む |
| 直した先に穴が残っていないか | 同じ経路の別メソッドに同じ防御が要らないか見る |
| **PR 本文への指摘** | 本文を引き直す。返信が付かないことが多く、直ったかは本文でしか分からない |

### 返信に 👍 を付ける

**対応を確認したコメントには `+1` を付ける。** 相手が**対応しない・説明だけで返した場合も同じ**。返信を読んで判断が済んだ、という合図なので、対応の有無では分けない。

```bash
gh api -X POST "repos/OWNER/REPO/pulls/comments/<comment_id>/reactions" -f content='+1'
```

- 対象は**自分が出した指摘への返信**だけ。他のレビュアーへの返信には付けない
- **まとめて付ける。** 1 件ずつ間を空けると通知が細切れになる
- ループで回すときは**1 件ずつ実行して結果を見る**。まとめて流すと、失敗した ID に気づかないまま「付けた」ことになる

`react_to_addressed_reviews.md` は**受け手側**（自分の PR に付いた指摘へ 👍）を定める。本節は**出し手側**で、向きが逆。

## 承認は GitHub に書かず、見立てはユーザーへ渡す

**是非の表明を GitHub に書かないことと、ユーザーに何も言わないことは別。** 宛先で書き分ける。

| | GitHub | ユーザーへの報告 |
| --- | --- | --- |
| 承認の操作 | **しない。** `event` は `COMMENT` 固定で `APPROVE` / `REQUEST_CHANGES` は使わない | — |
| 是非の表明 | **書かない**（「LGTM」「マージして問題ありません」「良い実装だと思います」） | **伝える。** 「approve して問題なさそう」まで踏み込む |
| 事実 | 書いてよい（「must はありません」） | 同じ |
| **CI・テストの結果** | **書かない**（下記「CI と approve は GitHub へ書かない」） | 書く |

**承認するのはユーザー本人。** こちらは判断材料と見立てを渡すところまでで、**ボタンを押さない**。

### ユーザーへ伝える見立て

反証（Step 6）を通した結果から、次のどれかを**報告の先頭 1 行**で言い切る。

| 状況 | 伝えること |
| --- | --- |
| `must` がある | ブロッカーの件数。approve の見立ては出さない |
| `iaio` / `nits` だけ | **「approve して問題なさそう」と添える。** 指摘は投稿するが、止める理由ではない |
| **指摘がゼロ** | **「approve して問題なさそう」だけ伝える。** レビューは投稿しない（下記） |

**見立てには根拠を 1 行添える。** 何を実測し、どの規約に照らしたか。根拠のない「問題なさそう」は、裏取りをしていない場合と区別が付かない。

### 指摘がゼロなら投稿しない

**中身の無いレビューを投稿しない。** 「must はありません」だけの総括はレビュアーへ通知が飛ぶ一方、相手の行動は何も変わらない。

- Step 7 の報告で「指摘なし。approve して問題なさそう」と伝え、**そこで終える**
- ユーザーが「その旨をコメントしておいて」と指示したときだけ投稿する

## 総括に内訳を書かない

**総括に書くのは件数だけ。** 何をどう直すかはインライン側にあるので、**総括で要約し直すと同じ指摘が 2 箇所に載る**。

| | 総括 | インライン |
| --- | --- | --- |
| 書くもの | **種別ごとの件数だけ** | 指摘の本文（何が / なぜ / どうする） |
| 直すとき | 触らない | ここだけ直せばよい |

```markdown
<!-- ❌ NG: インラインと同じ内容を総括にも書いている -->
must が 2 件です
トランザクション契約とテスト構造の規約違反で、いずれもインラインに置いています

<!-- ✅ OK -->
must が 2 件です
```

**「インラインに置いています」も書かない。** Files changed タブを開けば見えるので、相手に情報が増えない。

**例外は、インラインに置けない指摘。** 差分に含まれない行への指摘や、PR 本文・タイトルへの指摘は、置き場が総括しかないので**本文ごと総括に書く**。これは二重ではない。

**なぜ**: 二重に書くと、指摘を取り下げたり言い回しを変えたりするたびに 2 箇所を直すことになり、**片方だけ古くなる**。読む側も、同じ話を 2 回読まされたうえで「総括とインラインで温度が違うのでは」と余計な解釈をすることになる。

## レビューは直す候補だけを出す

**書くのは「ここは直した方がよさそう」だけ。** 良かった点・評価・所感は、総括にもインラインにもユーザーへの報告にも書かない。

**approve の見立てと、見た観点は別枠。** どちらも評価ではなく事実なので、ユーザーへの報告には載せる（Step 7「報告に入れるもの」、上記「承認は GitHub に書かず、見立てはユーザーへ渡す」）。

| 評価（書かない） | 事実（報告に載せる） |
| --- | --- |
| 「設計は妥当だと思います」 | 「規約ドキュメントを 6 本読み、既存 101 本を数えた」 |
| 「テストが丁寧です」 | 「`must` が無いので approve して問題なさそう」 |

**「水増ししなければ 1〜2 行は添えてよい」ではない。** 分量の問題ではなく、**混ぜること自体をしない**。

| 書く | 書かない |
| --- | --- |
| 直す候補（`[must]` / `[iaio]` / `[nits]`） | 良かった点・評価・所感 |
| approve の見立て（**ユーザーへの報告のみ**） | — |
| 裏を取った事実（規約の引用、既存の件数） | 「丁寧に書けています」「設計は妥当だと思います」 |
| — | **CI の状態と approve の話**（下記） |

### CI と approve は GitHub へ書かない

**どちらも PR を開けば見えるか、こちらが決めることではない。**

| 主題 | GitHub | ユーザーへの報告 |
| --- | --- | --- |
| **CI の状態** | **書かない。** green も fail も PR に出ている | 書く。失敗を切り分けたなら、承認待ちか実害かまで |
| **approve の見立て・承認の可否** | **書かない。** 押すのはユーザー本人で、レビュアーへ伝える話ではない | 書く（上記「ユーザーへ伝える見立て」） |

**例外は `.github/` を触る PR。** CI そのものが差分の対象なら、指摘として書く。

**「失敗の原因を調べた」も書かない。** 調べた事実に価値はあるが、宛先はユーザーで、PR 作成者は自分の CI を見れば足りる。

**評価に見えない書き方でも同じ。** 「〜は規約に正面から沿っています」「〜は適切です」は、指摘ではなく評価なので落とす。

理由は 3 つある。

- 相手が読むのは**何を直すか**。評価が混ざると、直す対象を拾う手間が増える
- **褒めた箇所は「見た上で問題なしと判断された」と読まれる。** 裏取りの深さは箇所ごとに違うので、この含意は渡せない
- 評価は是非の表明に近づく。**GitHub 上で承認の是非を書かない**（上記「承認は GitHub に書かず、見立てはユーザーへ渡す」）

## コメント本文の書き方

土台は `rules/concise_first_then_detail.md`。ここではレビューコメント固有の事情だけを足す。

**インラインコメントは差分の途中に挟まる。** PR 本文より条件が厳しく、長いと**差分そのものが読めなくなる**。

- **散文は 1 コメント 5 行以内**。読む負担は散文の量で決まるので、表・図・コードブロック・`<details>` の中身はこの数えから外す。超えたら畳む
- **1 コメント 1 主題**。複数を詰めると、相手はどれに対応済みか管理できなくなる。主題が増えたらコメントを分ける
- **書き終えたら削る前提で読み返す**。AI が書くと網羅と丁寧さに寄って必ず膨らむ。落とす型は `concise_first_then_detail.md` の表（言い換えの反復・過程の説明・丁寧さの水増し・自明な補足）と同じ

**結論から流す。** 1 行目で何の指摘かが掴めるようにし、根拠と代案を後に続ける。

| 順 | 書くこと |
| --- | --- |
| 1 | **何が問題か**（1 行で言い切る） |
| 2 | **なぜ問題か**（規約の引用・影響・前例） |
| 3 | **どうするか**（代案。無いなら「判断を仰ぎたい」で止めてよい） |

文と文は**接続詞で繋いで流れを作る**（「そのため」「一方」「ただし」）。箇条書きの断片を並べただけだと、読み手が関係を組み立て直すことになる。

**「つまりどういうこと？」で止まらせない。** 「規約違反です」で終えず、**そのまま進むと何が起きるか**まで書く。「検証が通らない」は「フリガナを触っていない編集でも保存できなくなる」まで。ただし**言い換えを重ねない**。1 行足せば大半は解ける。

### 長くなったら畳む

| 使うもの | いつ | 注意 |
| --- | --- | --- |
| **表** | 同じ観点が 3 件以上（観点と所見、案の比較、影響範囲） | **1 列目に長い値を置かない。** GitHub は内容幅で列幅を決めるので、先頭列がファイルパスや長い識別子だと残りの列が潰れる。短くできないなら箇条書きにする |
| **Mermaid** | 差分の羅列から読み取れない構造・関係・流れ | GitHub は ` ```mermaid ` フェンスをそのままレンダリングする |

Mermaid の使い分けは、`flowchart` が分岐・処理順・依存、`sequenceDiagram` が複数コンポーネントをまたぐフロー、`erDiagram` がテーブルとリレーション。**集約の境界・呼び出し経路・不変条件が崩れる筋道**のように、コードを追わないと見えない関係を示すときに効く。

置くなら**図（全体像）→ 表（項目ごと）**の順。**同じ情報を 2 つの形式で持たない。** 差分から自明な指摘（命名、並び順、typo）に図は足さない。

**畳む手段は表と Mermaid だけではない。** Alert / `<details>` / 脚注の使い分けは `github_rich_formatting.md` が持つ。

**レビューコメントでは `<details>` が効く。** 「散文は 1 コメント 5 行以内」を守ると根拠を書き切れないことがあるが、**畳めば本文を短く保ったまま置ける**。

| 畳む中身 | なぜ本文に置かないか |
| --- | --- |
| 規約の原文の引用 | 指摘を読むだけなら要らない。**反論するときに要る** |
| 既存の件数の内訳（「101 本中 86 本」の数え方） | 結論だけで足りる。**疑ったときに開く** |
| 落とした候補と落とした理由 | 相手の行動が変わらない |

`<summary>` は「根拠」「数え方」のように**中身が分かる名前**にする。

### コード片は `suggestion` で渡す

置き換えが 1〜数行で確定しているなら、**相手がワンクリックで取り込める形**にする。

````markdown
```suggestion
	maxClientAssigneeCount      = 50
```
````

- **インデントを含め、その行を丸ごと置き換えた結果**を書く。差分の行に対してそのまま適用されるため、字下げがずれるとビルドが壊れる
- 設計の選択が絡むもの、複数箇所に波及するものには使わない。**相手が考えずに適用できてしまう**
- 相手のコードを長く引用しない。インラインコメントは**既にその行に付いている**ので、再掲は場所を取るだけ

## 投稿し直すとき

**取り消しやすさが対象によって違う。** インラインは消えるが、レビュー本体は消えない。

| 対象 | できること |
| --- | --- |
| インラインコメント | **削除できる**。`gh api "repos/OWNER/REPO/pulls/comments/<comment_id>" -X DELETE` |
| レビュー本体 | **削除できない**（`DELETE .../reviews/<id>` は pending 専用で、submitted 済みには `422` が返る）。本文の編集か、**非表示化**のみ |

レビュー本体を引っ込めるには GraphQL の `minimizeComment` を使う。`PullRequestReview` も対象になっていて、UI 上は「This comment was marked as low quality.」と折り畳まれる。

```bash
# node_id は gh api graphql の reviews(first:20){nodes{id databaseId}} で引く
gh api graphql -f query='mutation { minimizeComment(input: {subjectId: "<node_id>", classifier: LOW_QUALITY}) { minimizedComment { isMinimized minimizedReason } } }'
```

- ID をループで回すときは、**1 行ずつ読む**（`while read -r id` 等）。コマンド置換の結果をそのまま変数展開すると全 ID が 1 つの文字列として渡り、**1 件も処理されないまま「実行した」ように見える**
- 削除・非表示のあとは**残存件数を数えて確かめる**
- **ユーザーが approve 済みの PR にも `COMMENT` レビューは追加できる**。承認の状態は変わらないので、後から指摘を足してよい

**不要になったコメントは残さず削除する。** 投稿後に的外れだったと分かったもの、前提が変わって意味を失ったもの、貼り直しで重複したものが対象。

- **誤検知は放置しない。** 消さずにおくと相手が対応を検討する時間を奪う。指摘の取り下げは、コメントを消したうえで**ユーザーへ口頭で報告**する
- 一方、**相手が既に対応・返信したコメントは消さない**。やりとりの経緯が失われる
- レビュー本体が消せず非表示だけになった場合、その旨をユーザーに伝える。**「消しました」と報告しない**

## 出力の目安

- 報告は重要度順。ブロッカーの有無を先頭 1 行で断定する
- **`must` が無いなら、同じ 1 行で approve の見立てを言い切る**（上記「ユーザーへ伝える見立て」）
- 投稿後は件数の内訳を出す。指摘本文を会話へ再掲しない（GitHub 側にある）
- **URL は PR とインライン 1 件ずつを添える**（`report_formatting.md`）。Step 9 の確認で `html_url` も一緒に拾う
- **良かった点は書かない**（上記「レビューは直す候補だけを出す」）

## やってはいけないこと

- **`APPROVE` / `REQUEST_CHANGES` を投稿すること**。承認のボタンはユーザーが押す（上記「承認は GitHub に書かず、見立てはユーザーへ渡す」）
- **GitHub 上に「LGTM」「マージして問題ない」「良い実装だと思います」と書くこと**。**ユーザーへの報告では逆に、approve の見立てを必ず伝える**
- **指摘がゼロなのにレビューを投稿すること**。中身の無い通知になるので、報告だけで終える
- **CI の状態や approve の話を GitHub へ書くこと**。前者は PR に出ており、後者はユーザーと決めることなので、どちらもレビュアーへ渡す情報ではない（上記「CI と approve は GitHub へ書かない」）
- **良かった点・評価・所感を添えること**。総括・インライン・ユーザーへの報告のいずれも、直す候補だけを出す
- **マージ順・リリース順をユーザーへ報告すること**。PR 本文で問われていても、出した側が把握している（Step 2）
- **ユーザーの GO を得ずに投稿すること**。レビュアーに通知が飛び、取り消せない
- **反証（Step 6）を飛ばして投稿すること**。書けた指摘をそのまま出さない
- **規約の原文を開かずに「規約違反」と書くこと**。引用できないものは指摘にしない
- **`gh pr diff` の行番号をそのまま引用すること**（Step 5）
- **投稿してから形式を直せばよいと考えること**。インラインは消せてもレビュー本体は消えない（下記「投稿し直すとき」）。形式は投稿前に確定する
- 総括だけ、またはインラインだけで済ませること
- **Note ブロックを省くこと**。1 行の `[nits]` でも付ける
- **PR 作成者へのメンションを省くこと**。総括・インラインのすべてに、1 行目として付ける
- **prefix をコードスパンにすること、prefix と同じ行に本文を続けること**（Step 8）
- **総括の件数に prefix を立てること**。`[iaio]` + 「1 件です」は、総括そのものが指摘に見える。地の文で「iaio が 1 件です」と書く
- **`[imo]` と書くこと**。意見の指摘は `[iaio]`（Step 2）
- 自動生成ファイル（`*_mock.go`、`mock/` 配下等）へ指摘すること
- 相手の書き方の好みを規約と偽って指摘すること。**規約に無いものは `[iaio]` 以下**にする
- **件数を揃えるために指摘を水増しすること**。反証で全部落ちたなら**投稿せず**、ユーザーへ「指摘なし」と伝えて終える（上記「指摘がゼロなら投稿しない」）
- **散文を長く積むこと**。同じ観点が 3 件以上なら表、構造・流れなら Mermaid、根拠が長いなら `<details>` に畳む
- **1 コメントに複数の主題を詰めること**。相手がどれに対応済みか管理できなくなる
- **設計判断が絡むものを `suggestion` で渡すこと**。相手が考えずに適用できてしまう
- 相手のコードを長く引用すること。**インラインは既にその行に付いている**

## 例外

- ユーザーが「まとめて 1 コメントで」と指示した場合は、インラインに分けず総括のみで投稿する
- レビュー結果を投稿せず会話に留めたい場合（下読みだけ頼まれた場合）は、Step 7 で終える
