単発版（ `/review-code` ）を **並列実行で高精度化** したものです。**判定表と出力形式は単発版の `references/` を使い、ここには複写しません。**

- `~/.claude/skills/review-code/references/severity.md` — 重要度の判定と裏取り
- `~/.claude/skills/review-code/references/output.md` — 出力フォーマット

**持っているのは Phase 構造と束の分け方だけです。**

## プロジェクト側に同名があれば、そちらを使う

**この名前はリポジトリ側の `.claude/skills/` にも置かれていることがあります。** そのときは**リポジトリ側を優先する**。ディレクトリ構成と規約の対応を知っているのはそちらで、こちらが組み直すと精度が落ちます。

- 判定は**利用可能なスキルの一覧**で行う。`.claude/skills/` と `.claude/commands/` の両方を見る
- **同名でなくてもよい。** 「差分をレビューする」と読めるものがあれば、それを使う
- 本スキルは、**リポジトリ側に無いときの土台**として働く

## 起動時のコスト確認

**サブエージェントを複数並列起動するので、単発版より大きくトークンと時間を使います。**

| 起動経路 | 扱い |
| --- | --- |
| **コマンドで明示的に起動された** | 承知しているとみなし、確認せず Phase 0 へ進む |
| **自然文から自動起動した**（「徹底的に見て」等） | **`AskUserQuestion` で1度確認する** |

確認するときは、軽く済ませる代替として単発版があることも示す。**了承を得るまで起動しない。**

判定に迷ったら**確認する側に倒す**。

## 進め方

### Phase 0: 範囲を確定する

単発版の手順1と2をそのまま踏みます（**diff 範囲の既定・除外・規約の探し方**）。**規約を読まずに並列起動しない。** サブエージェントへ渡すパスは、ここで集めたものを使います。

**対象が3ファイル以下なら並列化せず、単発版へ委譲する。** 起動コストが上回ります。

**追加レビュアーの起動可否**を、ここで測ります。**いずれか一方でも満たせば「大きい差分」**とする（除外分は数えない）。

| 指標 | しきい値 |
| --- | --- |
| 変更ファイル数 | **20以上** |
| 変更行数（追加＋削除） | **1000以上** |

```bash
git diff <範囲> --numstat -- <除外を適用したパス指定> | wc -l | tr -d ' '
git diff <範囲> --numstat -- <除外を適用したパス指定> | awk '{add+=$1; del+=$2} END {print add+del+0}'
```

**言語で絞らない。** リポジトリによって主要言語が違うので、拡張子を決め打ちすると測れません。

### Phase 1: 並列で一斉起動する

#### 束の作り方

**ディレクトリの近さで束ねる。** 言語やフレームワークに依存しない軸なので、どのリポジトリでも成立します。

| 状況 | どうするか |
| --- | --- |
| 1エージェントあたり | **5〜8ファイル** |
| **1つの束が8ファイルを超える** | さらに分ける |
| **1〜2ファイルの束が複数できた** | 近いものをまとめて1体にする |
| **束が1つしかできない**（変更が小さい） | **観点で分ける**（下記） |

**判断基準は「1エージェントが扱う diff が大きすぎてレビューが雑にならないこと」。**

**そのリポジトリが境界を宣言しているなら、その単位を優先する。** ディレクトリの近さより、宣言された責務の区切りのほうが強い軸です。

**複数の束に当たるファイルは、1つにだけ入れる。** 二重に起動すると同じ指摘が2回出ます。**ただし、利用側へ波及する範囲（共有コード・型定義・公開契約）に当たるものは、どの束に入れても波及の観点を併せて見る。** 影響範囲が広いぶん、落とすと最も高くつきます。

**観点で分ける場合**は、差分の性質から選ぶ。全部を並べない。

| 観点 | 選ぶ条件 |
| --- | --- |
| 正確性・境界値 | **常に1体** |
| 規約適合 | Phase 0で規約ドキュメントが見つかっている |
| テストの網羅 | テストファイルが差分にある |
| セキュリティ | 認証・権限・入力値・外部への送信が差分にある |
| 性能 | 繰り返し処理・大量データ・重い再計算の経路が差分にある |

**条件は領域で読み替える。** 同じ「性能」でも、**サーバー側なら繰り返しの中のクエリ、画面側なら不要な再描画やバンドルの肥大**が該当します。表の語をそのまま探すのではなく、**その領域で事故になりやすい形**を選ぶ。

#### フロー整合性レビュアーを必ず1体起動する

**束の大きさや数によらず、常に1体。** ファイル単位に分けると見えなくなるもの（配線漏れ、境界での契約不一致、エラーの伝播切れ）を担当します。

#### 追加レビュアーの併走（大きい差分のみ）

**独立した観点、特に破壊的な失敗シナリオを加えるため**に、別の実装のレビュアーを1体併走させます。**差分全体に対して1回だけ起動**し、束ごとに分割しません。

**起動条件は次の3つをすべて満たすこと。** 1つでも欠ければ併走なしで完結し、サマリに理由を記録します。

1. Phase 0の判定が「大きい差分」である
2. **その追加レビュアーのサブエージェントが利用可能である**
3. コマンド起動である、または「起動時のコスト確認」で併走まで了承されている

**この判定に追加の確認を挟まない。** 併走は任意の補強であり、無くてもレビューは成立します。

**プロンプトには次を必ず含める。**

- **結果を待つ指定**（無いと識別子だけ返り、レビュー本文を回収できない）
- **読み取り専用の明示**（無いと書き込み可能モードで走る）

#### 起動のしかた

**すべて1メッセージの中で、バックグラウンド起動する**（ `run_in_background: true` ）。**完了を待たずに Phase 2へ進む。**

サブエージェントは**会話の文脈を引き継ぎません**。次を漏れなく渡す。

**起動プロンプトへ参照ファイルの本文を複写しない。** パスだけ渡し、**サブエージェント自身に Read させる**（起動プロンプトが短くなり、指示の一貫性も保たれる）。

**参照ファイルは絶対パスへ展開して渡す。** サブエージェントの起動位置は作業中のリポジトリのルートなので、**スキルディレクトリ相対では解決できません**。本スキルの参照ファイルはホームディレクトリ配下にあるため、リポジトリルート相対でも解決できない。

| 渡すもの | 書き方 |
| --- | --- |
| **本スキルと単発版の参照ファイル** | **`~` を展開した絶対パス**（ホームディレクトリ配下にある） |
| **そのリポジトリの規約ファイル** | リポジトリルート相対 |

```markdown
あなたは [担当範囲] を見るコードレビュアーです。

まず次のファイルを Read で全文読み込み、そこに書かれた手順・観点・重要度基準・出力フォーマットに従ってレビューしてください。

- [束担当なら bundle-reviewer.md / フロー担当なら flow-reviewer.md のパス]
- [severity.md のパス]
- [output.md のパス]

## レビュー条件

- diff 範囲: [範囲]
- 担当ファイル:
  - [パス一覧]
- 必ず読む規約（Read で全文。要約・記憶に頼らない）:
  - [Phase 0 で集めたパス]
- 追加の重点観点: [引数の指定。無ければ「なし」]
```

**重要度は「提案」として付けさせる。** 確定は Phase 3で行います。

**フォールバック**: バックグラウンド起動が使えない環境では、同期のまま1メッセージ内で一斉起動してサブエージェント同士の並列性を確保し、Phase 2は起動前または回収直後に実施する。**レビューの内容と出力は変えない。**

### Phase 2: 全体を俯瞰する（並走）

**サブエージェントの完了を待たずに始める。** ここを直列にすると壁時計時間が最も伸びます。

見るのは**個々のファイルに分解すると消えるもの**。

| 観点 | 見るもの |
| --- | --- |
| **境界の歪み** | 宣言された依存方向・責務分担に、変更全体として逆らっていないか |
| **置き場所の誤り** | 「どこに何を足したか」が、その変更の目的と合っているか |
| **束をまたいだ重複・矛盾** | 同じ処理が複数箇所に書かれていないか。共有側へ寄せるべきか |
| **一貫性** | 似た機能を別の方法で実装していないか。理由があるか |

**ここで見つけた指摘も Phase 3のマージ対象。** 重要度はサブエージェントの結果と合わせて確定します。

### Phase 3: 回収してマージする

1. **全サブエージェントの結果を回収する。** 追加レビュアーを起動していたら、その本文も回収する
2. **重複を落とす。** 次の4つを順に適用する
   - 同一箇所への重複指摘は1件にまとめる
   - **レビュアーを跨いだ同種指摘**も1件に集約し、該当箇所を `path:line` で列挙する
   - **複数レビュアーが同じ問題を指摘しているなら1件に統合し、根拠欄に「複数のレビュアーが指摘」と明記する**（一致は確度が高い）
   - 複数の束にまたがる指摘は、**最も根本原因に近い箇所**へ集約する
3. **根拠の無いものを落とす。** 差分から追えない指摘は、この時点で捨てる
4. **失敗したエージェントを補完する。** 空応答・エラーなら、その担当を再起動するか自分で見る
5. **重要度を確定する。** `severity.md` の判定表を当て直し、**must は1件ずつ裏を取る**
6. **観点名を付与する。** `output.md` の観点名から選ぶ。**アルファベットや番号で書かない**
7. **並べ替えて出力する。** `output.md` の形式に従う

**サブエージェントの申告を鵜呑みにしない。** 提案として受け取り、根拠を見て上げ下げします。**追加レビュアーが severity 相当の語を付けていても、この体系へ読み替える。**

## 出力の目安

`output.md` の形式に従います。そのうえで、**どう分けたか**を対象範囲へ足す。

- 起動したエージェントの数と担当範囲
- 大きい差分の判定結果（ファイル数・行数）
- **追加レビュアーの状態**（未起動 / 未導入 / 起動失敗 / 実行し指摘 N 件）
- **回収した指摘のうち、根拠が無くて落とした件数**

## やってはいけないこと

- **判定表と出力形式をここに複写すること**。単発版の `references/` を Read させる
- **規約を読む前に並列起動すること**。サブエージェントへ渡すパスが決まらない
- **変更が3ファイル以下なのに並列化すること**。起動コストが上回る
- **Phase 2をサブエージェントの完了後に始めること**。並走させる
- **起動プロンプトへ参照ファイルの本文を複写すること**
- **参照ファイルをスキルディレクトリ相対で渡すこと**。サブエージェントはルートから解決する
- **サブエージェントが付けた重要度を、そのまま使うこと**
- **フロー整合性レビュアーを省くこと**。束の分け方によらず常に1体
- **同じファイルを複数の束へ入れること**。同じ指摘が2回出る
- **追加レビュアーの有無や失敗でレビュー全体を止めること**。任意の補強です
- **サブエージェントを増やせば精度が上がると考えること**。**同じ差分を重複して見るだけ**なので、束の大きさで決める
- **自動で修正すること**。指摘に留める
- **GitHub へ投稿すること**
