自分が担当している open な PR を**表 1 つ**で見渡せるようにします。「**何を対応していて / 何と紐づいていて / 今どれを動かせるか**」が即座に分かる状態がゴールです。

## 進め方

### 1. 対象 PR を集める（横断が既定）

**カレントリポジトリだけを見ない。** 1 つのプロダクトが FE / BE / インフラに分かれており、**PR は単独で完結しません**。片方だけ見ても、何が何を待っているか分からない。

- 対象はローカルにクローン済みの関連リポジトリ全部（`~/Documents/repositories/github.com/<org>/` 配下を `ls` で列挙）
- **リポジトリごとの取得は独立なので、単一メッセージ内で並列に発行する**

  ```bash
  gh pr list --author "@me" --state open --json number,title,headRefName,isDraft,mergeStateStatus,updatedAt
  ```

- 引数にリポジトリ名があればそれだけに絞る
- **open PR が 0 件のリポジトリは表から省く**（行だけ増えて読みづらい）。全リポジトリで 0 件なら 1 行で返して終了

### 2. 各 PR の状況を取る（並列実行）

**PR ごとの取得は独立なので、単一メッセージ内で並列に実行する。** 直列にすると PR 数だけ待ち時間が積み上がる。

| 取るもの | コマンド |
| --- | --- |
| CI | `gh pr checks <PR>` |
| マージ可否 | `gh pr view <PR> --json mergeStateStatus,reviewDecision` |
| 自分のコメント | `gh api repos/OWNER/REPO/issues/<PR>/comments` から保留メモ等を拾う |

**CI が fail のときは原因まで見る。** `approval required`（レビュー承認待ち）のようにコードと無関係な失敗があり、これを「壊れている」と報告すると誤解を招く。`gh run view <id> --log-failed` で末尾を確認する。

### 3. ブランチとの対応を見る

- カレントブランチがどの PR に対応するかを明示する
- ローカルに未 push のコミットや未コミット変更があれば添える（`git status --porcelain` / `git rev-list --count @{upstream}..HEAD`）
- base ブランチが進んでいれば、その旨も（`git rev-list --count HEAD..origin/<base>`）

### 4. 紐づきを洗い出す

**横断で見る一番の目的がここ。** 各 PR の**本文と自分のコメント**から PR 参照を抽出し（`owner/repo#123` / 同一リポジトリの `#123` / コメントへのアンカー付き URL）、参照先の状態を引く（`gh pr view <ref> --json state,mergedAt,isDraft,reviewDecision`）。**リポジトリをまたぐ参照も対象**。

紐づきが分かったら、**どちらが待たせている側か**まで判定する。

| 関係 | 見分け方 | 報告 |
| --- | --- | --- |
| **相手が律速** | 依存先が open で未 approve | こちらは待ち |
| **こちらが律速** | 依存先が **approve 済み / マージ待ち** | **こちらを進めれば相手が動く**。最優先 |
| マージ順の制約 | 本文に「〜が先」と書いてある | 順序を明記する |

**「依存先が open だからこちらも待ち」と短絡しない。** 契約が固まっていて片側先行が安全な変更では、**遅れている側が相手を止めます**。

#### 参照の鮮度も見る

**片方がマージされると、もう片方の参照が腐る**のが構造的に起きる。よくある腐り方:

| 腐り方 | 例 |
| --- | --- |
| 依存先がマージ済み | 「〜が前提です」と書いた PR が既に入っている。前提ではなく完了事項 |
| 参照先がクローズ | 別 PR に置き換わった。リンクが行き止まりになる |
| 正本が移動した | コメントの内容が別 PR へ移された。アンカー付き URL が古い場所を指す |

参照先の**状態が変わっただけ**（open → merged）なら本文の書き換えが要るとは限らない。**「前提」「〜待ち」と書いてあるのに満たされている**ものを優先して挙げる。

**このスキルは検出だけで、直さない。** 腐った参照を見つけたら、報告に「該当 PR で `/update-pr-description` を打つと本文とコメントを直せる」と添える。修正は 1 PR 単位の作業なので、一覧のついでにやると対象を取り違える。

### 5. 「何待ちか」を判定する

一覧の価値は**次に何をすればいいか**が分かることにあります。各 PR について、以下のどれかに分類する。

| 状態 | 判定材料 |
| --- | --- |
| **動かせる** | ready / CI 緑 / approve 済み → マージできる |
| **レビュー待ち** | ready だが approve 未取得 |
| **こちら待ち** | draft のまま / CI が fail（コード起因）/ 未 push の変更がある |
| **外部待ち** | 他リポジトリの PR やデプロイが前提。**PR 本文やコメントに書かれた保留条件を読み取る** |

外部待ちは本文の「動作要件」節や `[memo]` コメントに書かれていることが多い。**依存先の PR 番号があれば、その状態も併記する**（`owner/repo#123` を `gh pr view` で引く）。

#### draft は「今 ready にしてよいか」まで判定する

**draft をまとめて「こちら待ち」にしない。** 実際には「出せるのに出していないだけ」と「出すべきでない」が混ざっており、前者は放置すると依存先を止めます。

| 判定 | 材料 |
| --- | --- |
| **出せる** | CI が緑（`approval required` の fail は除く）で、依存先がマージされていなくてもレビューは成立する |
| **出さないほうがよい** | 前提が未確定で**レビュー中に設計が変わりうる** / 依存先の契約が固まっていない / 他 PR とマージ順を調整中で先に出すと誤解を招く |

**依存先が未マージ = 出せない、ではありません。** 判定は「**レビュアーが今読んで、指摘が無駄にならないか**」で行う。契約が固まっていて FE 先行が安全な変更（nullable 化・新フィールドの受け入れなど）は、依存先が open でもレビューに出せます。むしろ**こちらが遅れると依存先を止める**ので、その旨を添える。

依存先が approve 済み・マージ待ちなら、**こちらが律速になっている**ことを明記する。

**ready 化そのものは絶対にしない**（`no_auto_ready_pr.md`）。判定を示して、実行はユーザーに委ねる。

### 6. 表で出す

**リポジトリごとに節を分けず、1 つの表に混ぜる。** 分けると紐づいた PR が別の表に散り、横断で見た意味が失われる。

| 列 | 中身 |
| --- | --- |
| PR | `FE v2 #395` のように**通称 + 世代 + 番号**。フルパスは幅を食う。**v1 / v2 を必ず付ける**——番号だけではどちらの世代の話か判別できない |
| 何を | **1 行の説明**。PR タイトルの写しではなく「何が変わるか」（例: 変更履歴にアーカイブ状態を追加） |
| 状態 | draft / ready + CI |
| 紐づき | 依存先を `BE #3002` のように。無ければ `-` |
| 次の一手 | マージできる / ready にできる / 相手待ち / approve 待ち |

**「何を」の列は必ず入れる。** 横断で 10 本を超えると、番号だけでは何の PR か思い出せません。ただし**1 行に収める**——差分の説明は PR 本文の仕事で、ここは思い出すための手がかりです。

表の後に置くのは次の 2 つだけ。

1. **今すぐ動かせるもの**（マージできる / ready にできる）を 1 行。無ければ「すべて待ち」
2. **腐った参照**があれば別立てで（列に入れると幅を食う）

## 出力の目安

- PR 0 件: 1 行
- PR 1 本: 表にせず 3〜4 行
- PR 複数: 表 1 つ + 「動かせるもの」1 行。**PR ごとに節を作らない**（一覧性が落ちる）
- **横断で 10 本を超えても表は 1 つ**。リポジトリで分けたくなったら、代わりに「次の一手」で並べ替える

## してはいけないこと

- **PR ごとに直列でコマンドを打つこと**。取得は並列にする
- CI の fail を、原因を見ずに「失敗」とだけ報告すること。**approve 待ちなのかコード起因なのかで意味が正反対**
- 本文やコメントを読まずに「レビュー待ち」と判定すること。**保留条件が書かれていることがある**
- **「何を」の列を 1 行に収めないこと**。差分の説明は PR 本文の仕事で、ここは思い出すための手がかり
- **リポジトリごとに表を分けること**。紐づいた PR が散り、横断で見た意味が失われる
- **依存先が open なだけで「待ち」と判定すること**。契約が固まっていれば片側先行が正しく、**遅れている側が相手を止めている**
- 参照先の状態が変わっただけで「腐っている」と報告すること。**本文の主張と食い違っているか**で判定する
- 状態を変える操作（ready 化・マージ・close）を勝手に行うこと。**一覧を出すだけ**
- 腐った参照を見つけて**その場で本文を直すこと**。検出に留め、修正は `update-pr-description` に渡す
