自分が担当している open な PR を**表 1 つ**で見渡せるようにします。「今どれが動かせて、どれが何待ちか」が即座に分かる状態がゴールです。

## 進め方

### 1. 対象 PR を集める

- 既定はカレントリポジトリ: `gh pr list --author "@me" --state open --json number,title,headRefName,isDraft,mergeStateStatus,updatedAt`
- 引数にリポジトリ名があればそれを対象にする。`--all` なら、ローカルにクローン済みの関連リポジトリを横断する
- 0 件なら「open な PR なし」と 1 行で返して終了

### 2. 各 PR の状況を取る（並列実行）

**PR ごとの取得は独立なので、単一メッセージ内で並列に実行する。** 直列にすると PR 数だけ待ち時間が積み上がる。

| 取るもの | コマンド |
| --- | --- |
| CI | `gh pr checks <PR>` |
| マージ可否 | `gh pr view <PR> --json mergeStateStatus,reviewDecision` |
| 自分のコメント | `gh api repos/OWNER/REPO/issues/<PR>/comments` から保留メモ等を拾う |

**CI が fail のときは原因まで見る。** `approval required`（レビュー承認待ち）のようにコードと無関係な失敗があり、これを「壊れている」と報告すると誤解を招く。`gh run view <id> --log-failed` で末尾を確認する。

### 3. ブランチとの対応を見る

- カレントブランチがどの PR に対応するかを明示する
- ローカルに未 push のコミットや未コミット変更があれば添える（`git status --porcelain` / `git rev-list --count @{upstream}..HEAD`）
- base ブランチが進んでいれば、その旨も（`git rev-list --count HEAD..origin/<base>`）

### 4. 相互参照の鮮度を見る

**スタックした PR や関連 PR では「片方がマージされると、もう片方の参照が腐る」が構造的に起きる。** 一覧を出すついでに洗い出す。

- 各 PR の**本文と自分のコメント**から PR 参照を抽出する（`owner/repo#123` / 同一リポジトリの `#123` / コメントへのアンカー付き URL）
- 参照先の状態を引く（`gh pr view <ref> --json state,mergedAt`）。**リポジトリをまたぐ参照も対象**
- **merged / closed の PR を参照している open PR** を警告する。よくある腐り方:

| 腐り方 | 例 |
| --- | --- |
| 依存先がマージ済み | 「〜が前提です」と書いた PR が既に入っている。前提ではなく完了事項 |
| 参照先がクローズ | 別 PR に置き換わった。リンクが行き止まりになる |
| 正本が移動した | コメントの内容が別 PR へ移された。アンカー付き URL が古い場所を指す |

参照先の**状態が変わっただけ**（open → merged）なら本文の書き換えが要るとは限らない。**「前提」「〜待ち」と書いてあるのに満たされている**ものを優先して挙げる。

**このスキルは検出だけで、直さない。** 腐った参照を見つけたら、報告に「該当 PR で `/update-pr-description` を打つと本文とコメントを直せる」と添える。修正は 1 PR 単位の作業なので、一覧のついでにやると対象を取り違える。

### 5. 「何待ちか」を判定する

一覧の価値は**次に何をすればいいか**が分かることにあります。各 PR について、以下のどれかに分類する。

| 状態 | 判定材料 |
| --- | --- |
| **動かせる** | ready / CI 緑 / approve 済み → マージできる |
| **レビュー待ち** | ready だが approve 未取得 |
| **こちら待ち** | draft のまま / CI が fail（コード起因）/ 未 push の変更がある |
| **外部待ち** | 他リポジトリの PR やデプロイが前提。**PR 本文やコメントに書かれた保留条件を読み取る** |

外部待ちは本文の「動作要件」節や `[memo]` コメントに書かれていることが多い。**依存先の PR 番号があれば、その状態も併記する**（`owner/repo#123` を `gh pr view` で引く）。

### 6. 表で出す

列は **PR / ブランチ / 状態 / CI / 何待ちか** を基本にする。**腐った参照があれば表の下に別立てで挙げる**（列に入れると幅を食う）。PR が 1 本なら表にせず箇条書きでよい。

表の後に、**今すぐ動かせるものがあれば 1 行**で示す。無ければ「すべて待ち」と書く。

## 出力の目安

- PR 0 件: 1 行
- PR 1 本: 表にせず 3〜4 行
- PR 複数: 表 1 つ + 「動かせるもの」1 行。**PR ごとに節を作らない**（一覧性が落ちる）

## してはいけないこと

- **PR ごとに直列でコマンドを打つこと**。取得は並列にする
- CI の fail を、原因を見ずに「失敗」とだけ報告すること。**approve 待ちなのかコード起因なのかで意味が正反対**
- 本文やコメントを読まずに「レビュー待ち」と判定すること。**保留条件が書かれていることがある**
- PR の内容を要約すること（一覧に要らない。差分の説明は PR 本文の仕事）
- 参照先の状態が変わっただけで「腐っている」と報告すること。**本文の主張と食い違っているか**で判定する
- 状態を変える操作（ready 化・マージ・close）を勝手に行うこと。**一覧を出すだけ**
- 腐った参照を見つけて**その場で本文を直すこと**。検出に留め、修正は `update-pr-description` に渡す
