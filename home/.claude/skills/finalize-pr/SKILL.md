このスキルは「PR を出す直前の総仕上げ」を担うオーケストレーターです。個々のチェック・コミット・PR 説明更新は既存スキルに委譲し、順序と対応要否の判断だけを本スキルが担います。

## 進め方

以下を **上から順に** 実行する。前段で修正が入った場合、後続の判断はその修正後の状態で行う。

1. **点検（並列一斉起動）**: `review-comments`・`review-conventions`・`review-tests` を **単一メッセージ内で 3 個の Skill ツール呼び出しとして同時に発行する**（1 個ずつ別々のメッセージで順番に呼ばない）。3 つは独立観点（コメント品質 / 規約遵守 / テストの過不足）で結果が干渉しないため、直列にすると壁時計時間が伸びる。

   **リポジトリ種別による出し分けは各スキルが内部で判定する**ので、ここでは分岐しない。3 つとも常に呼ぶ。

   全部の結果が揃ってから 2 の修正判断に進む。

   > **フォールバック**: 並列起動が使えない環境では直列で構わないが、その場合も全部の結果を回収してから 2 の判断に進むこと。順序が入れ替わっても最終出力は同じ。
2. **修正の適用**: 1 で「対応必要」と判定された内容を、点検元の報告に従って反映する
   - `[must]` に相当する違反は原則すべて対応する
   - `[imo]` / `[nits]` に相当する示唆は「直した結果が本当に良くなるか」で判断し、非対応なら理由をユーザーへ報告する
   - コメント点検由来と規約点検由来の指摘が同一箇所に重なった場合は 1 件にまとめて対応する
   - 対応後は影響範囲のテスト・lint・format を通す（プロジェクトの `Taskfile` 等で規定されているコマンドを使う）。**テスト一式は `run_in_background: true` で流し、待つ間に残りの修正を進める**
3. **コミット & プッシュ**: `cp` を Skill ツールで呼ぶ
   - `cp` 側の早期離脱判定に任せる (変更なしなら空コミットは作らない)
4. **PR 説明の更新要否判断**: 以下のいずれかに当てはまれば `update-pr-description` を Skill ツールで呼ぶ
   - 2 で本文に反映すべき挙動変化・トレードオフ・レビュー観点が増えた
   - タイトルが差分の核と乖離した
   - 影響範囲・テスト内容の記述が現実と乖離した
   - いずれも該当しなければ呼ばない（同一内容の再送を避ける）

## 出力の目安

- **点検 → 修正なし → cp が「変更なし」で終了 → PR 説明も現状維持**: 「点検クリーン、追加のコミット/PR 説明更新なし」で終了。3〜4 行でよい
- **修正が入った場合**: 対応した内容、非対応にした指摘とその理由、push したコミットハッシュ、PR 説明更新の有無を簡潔に報告

## やってはいけないこと

- 個々のチェックや `cp` / `update-pr-description` の内容をこのスキル本文で再定義すること。各スキルの規約が正で、本スキルは順序のみ管理する
- 点検の結果を待たずに `cp` を先に走らせること（点検 → 修正 → コミット の順を守る）
- 点検スキルを直列に起動すること。3 つは独立観点なので、必ず単一メッセージ内で並列起動する（1 個の完了を待ってから次を起動しない）
- **呼び出し側でリポジトリ種別を判定すること**。各スキルが内部で判定するので、ここでは分岐しない
- 一部の点検結果だけを見て修正判断を先行させること。全部の結果が揃ってから 2 に進む
- `update-pr-description` を無条件に呼ぶこと。差分と本文が既に整合しているなら呼ばない
- `[must]` を根拠なく見送ること

## 前提

- ブランチが PR に紐づいていることを確認するのは各下位スキルの責務。本スキル側では追加確認をしない
- `no_auto_commit` / `karma_commit_style` 等のグローバルルールは `cp` 側が既に見ているため、本スキルで重複して参照しない
