このスキルは「PR を出す直前の総仕上げ」を担うオーケストレーターです。個々のチェック・コミット・PR 説明更新は既存スキルに委譲し、順序と対応要否の判断だけを本スキルが担います。

## 進め方

以下を **上から順に** 実行する。前段で修正が入った場合、後続の判断はその修正後の状態で行う。

1. **ベースとの統合を確かめる（点検と並行して始める）**: **CI はブランチ単体しか見ていない**ので、ベースが進んでいると緑でも壊れていることがある。

   ```bash
   git fetch origin --quiet
   git rev-list --count HEAD..origin/<base>   # ベースからの遅れ
   ```

   **0 なら「ベース最新」と 1 行書いて次へ**。1 以上なら、**作業ツリーを汚さずに** worktree で取り込んで確かめる。

   ```bash
   git worktree add -q --detach <一時パス> HEAD
   cd <一時パス> && git merge --no-edit origin/<base>
   ```

   - **コンフリクトしたら**、衝突ファイルを添えて報告する。**実際の取り込みはユーザーの指示を待つ**（取り込み方は `no_rebase_under_human_review.md`）
   - **通ったらビルドし、続けて変更したパッケージのテストを流す**。ここで落ちたものは 2 で直す
   - 確認が済んだら `git worktree remove --force <一時パス>`

   **遅れが大きいほど CI 緑の意味が薄れる。** ベース側が同じコードを作り変えていても、ブランチ単体のビルドは通ってしまう。

2. **点検の実行**: `review-comments`・`review-conventions`・`review-tests` を**順に** Skill ツールで呼ぶ。3 つとも独立観点（コメント品質 / 規約遵守 / テストの過不足）で、結果は干渉しない。

   **同時に呼んでも並列にはならない。** `Skill` はサブエージェントを起動するのではなく、**手順書を自分の文脈へ読み込ませる**形なので、3 つ同時だと手順が混ざって取り違える。**1 つ呼び、その手順を実行し、結果を得てから次へ進む。**

   **並列化するのは各点検の中。** 依存の無い `Read` / `grep` を 1 メッセージへまとめて発行する。壁時計時間が縮むのはここ。

   **リポジトリ種別による出し分けは各スキルが内部で判定する**ので、ここでは分岐しない。3 つとも常に呼ぶ。

   全部の結果が揃ってから 3 の修正判断に進む。

3. **修正の適用**: 1 の統合検証と 2 の点検で「対応必要」と判定された内容を反映する
   - `[must]` に相当する違反は原則すべて対応する
   - `[imo]` / `[nits]` に相当する示唆は「直した結果が本当に良くなるか」で判断し、非対応なら理由をユーザーへ報告する
   - コメント点検由来と規約点検由来の指摘が同一箇所に重なった場合は 1 件にまとめて対応する
   - 対応後は影響範囲のテスト・lint・format を通す（プロジェクトの `Taskfile` 等で規定されているコマンドを使う）。**テスト一式は `run_in_background: true` で流し、待つ間に残りの修正を進める**
4. **コミット & プッシュ**: `cp` を Skill ツールで呼ぶ
   - `cp` 側の早期離脱判定に任せる (変更なしなら空コミットは作らない)
5. **PR 説明の更新要否判断**: 以下のいずれかに当てはまれば `update-pr-description` を Skill ツールで呼ぶ
   - 3 で本文に反映すべき挙動変化・トレードオフ・レビュー観点が増えた
   - タイトルが差分の核と乖離した
   - 影響範囲・テスト内容の記述が現実と乖離した
   - いずれも該当しなければ呼ばない（同一内容の再送を避ける）

## 出力の目安

- **統合クリーン → 点検 → 修正なし → cp が「変更なし」で終了 → PR 説明も現状維持**: 「ベース最新・点検クリーン、追加のコミット/PR 説明更新なし」で終了。3〜4 行でよい
- **修正が入った場合**: 対応した内容、非対応にした指摘とその理由、push したコミットハッシュ、PR 説明更新の有無を簡潔に報告

## やってはいけないこと

- 個々のチェックや `cp` / `update-pr-description` の内容をこのスキル本文で再定義すること。各スキルの規約が正で、本スキルは順序のみ管理する
- 点検の結果を待たずに `cp` を先に走らせること（点検 → 修正 → コミット の順を守る）
- **点検の中の調査を 1 つずつ直列に発行すること**。依存の無い `Read` / `grep` は 1 メッセージにまとめる
- **呼び出し側でリポジトリ種別を判定すること**。各スキルが内部で判定するので、ここでは分岐しない
- 一部の点検結果だけを見て修正判断を先行させること。全部の結果が揃ってから 3 に進む
- **ベースとの統合検証を飛ばすこと**。CI が緑でも、ベースが進んでいれば統合時に壊れうる
- 検証のために**作業ツリーへ直接ベースを取り込むこと**。worktree を使い、実際の取り込みはユーザーの指示を待つ
- `update-pr-description` を無条件に呼ぶこと。差分と本文が既に整合しているなら呼ばない
- `[must]` を根拠なく見送ること

## 前提

- ブランチが PR に紐づいていることを確認するのは各下位スキルの責務。本スキル側では追加確認をしない
- `no_auto_commit` / `karma_commit_style` 等のグローバルルールは `cp` 側が既に見ているため、本スキルで重複して参照しない
