`~/.claude/rules/` と `~/.claude/skills/` に置く資産の、書き方と整理の手順です。

## プロジェクトルールとの違い

同じ「ルール」でも、置き場所によって性質が変わります。**プロジェクト側の書き方をそのまま持ち込まないでください。**

| | グローバル (`~/.claude/rules/`) | プロジェクト (`.claude/rules/`) |
| --- | --- | --- |
| ロード | **常に全文** | `paths` にマッチしたときだけ |
| 構成 | **1層**（ルールに直接書く） | 2層（ルールは入口、`docs/` が本体） |
| 内容 | 振る舞いの規約（コミット・レビュー・報告の仕方） | コードの規約（命名・配置・実装パターン） |
| 命名 | スネークケース (`no_auto_ready_pr.md`) | ケバブケース (`data-fetching.md`) |

命名の型は3つある。**どれでもよいが、ファイル名だけで何の規約か分かること**を優先する。

| 型 | 使うとき | 例 |
| --- | --- | --- |
| `no_` 始まり | 禁止が主題 | `no_auto_ready_pr` / `no_agent_coordination_in_pr` |
| 動詞始まり | 「〜せよ」が主題 | `verify_before_asserting` / `summarize_after_each_task` |
| 名詞句 | 書式・スタイルそのものが主題 | `karma_commit_style` / `plain_language_explanation` |

**改名は相互参照の追随コストが高い。** `## 関連` で参照し合っているので、型を揃えるためだけの改名は避ける。

`paths` は**プロジェクト内のファイルパス**にしかマッチしません。`~/.claude/skills/**` のようなプロジェクト外のパスは絞り込めないので、グローバルルールに `paths` は使いません。

## 期待する挙動

- **新設する前に `ls ~/.claude/rules/` で近い主題を見る。** 理由は `verify_before_asserting.md` （「無い」を語で判定しない）
- **節を足す前に `grep '^## '` で章立てを出す。** 章順の規約を知っていても、既存の並びを見ないと挿入先を誤る
- **例を書いたら、悪い側と良い側を並べて差分だけを見る。** 節の主張も例の日本語もどちらも正しく、**その差分が主張を示していないことだけが抜ける**形がある。本文を読む動きでは通過する
  - 実際に、外部の記事から引いた例をそのまま貼ったところ、悪い側と良い側で語順が同じだった。節の主張は「長いものから並べる」なのに、**差分は語を2つ足しただけ**だった
  - **引用元が正しくても、例として働くかは別**。並べ替えを説く節なら、例も並べ替えでなければならない
- **1ファイル1主題**にする。複数の主題が混ざったら分割し、`## 関連` で相互に参照する
- **常時ロードされることを意識して量を絞る**。判断に必要な情報（何を守るか・なぜか・例外）は残し、言い換えの反復と前置きを削る
- 章立ては次を基本にする。ただし**内容に即して変えてよい**

  ```
  # タイトル
  <1〜3 行の説明>
  これは全プロジェクト共通の規約です。

  ## 期待する挙動
  ## 禁止する挙動
  ## なぜ
  ## 例外
  ## 関連
  ```

- **見出し名は内容に合わせる**。文体の規約なら `## 期待するスタイル`、PR 説明の規約なら `## 期待する記述` でよい。機械的に `## 期待する挙動` へ揃えない
- **禁止が主題のルール（ `no_` 始まり）は、禁止をタイトルとリード文で明示する**。`## 禁止する挙動` を節として置くなら `## 期待する挙動` より先。ただし1行で言える禁止に節を立てる必要はない
- `## なぜ` は必ず書く。理由が分かると、規約が想定していない場面でも判断できる
- **`## 関連` で相互に繋ぐ**。近い主題のルールが複数あるとき、どれが何を担うかを1行で示すと、読み手が両方を踏まえて判断できる

- 新規作成前に `~/.claude/skills/*/SKILL.md` を Read で確認し、以下のフォーマット要素を既存に揃える
  - frontmatter の有無・キー（ `name` / `description` / etc）
  - 見出し構成（ `## 進め方` / `## 手順` / `## やってはいけないこと` / `## 出力の目安` など、既存で頻出する見出し）
  - 語尾・トーン（体言止め寄り／敬体／命令形の使い分け）
  - 箇条書き / 表の使い方
  - コードブロックのフェンス種別・引用（HEREDOC 等）
- 改修時も同様に、対象 SKILL.md 内および周辺 SKILL.md の慣習を尊重する
- 既存フォーマットが**複数流派に分かれている**場合は、頻度の多い側（正典）に寄せる。判断に迷うときはユーザーに確認する
## 整理の契機

**このディレクトリに手を入れるときが、棚卸しのタイミングです。** 定期的に見直す必要はありません。次のどれかに当たったら、そのつど整理する。次の指示を待たず、提案まで出す。

| 契機 | 見直すこと |
| --- | --- |
| **ルールを追加・変更・削除した** | ディレクトリ全体。手を入れるたびに再編成する |
| **ルールを守れなかった／守らなかったと気づいた** | **そのルール自体**。逸脱はルール側の欠陥を示す信号 |
| **既定の挙動が変わったと分かった** | 埋めていた穴が塞がっていないか |
| **スキルや `CLAUDE.md` に汎用の規定を見つけた** | **ルールへ引き上げられないか**（下記） |
| **auto memory に書いた／書こうとした** | **ルールと重複していないか**、そして**実行時に効く場所へ落ちているか**（下記） |
| **失敗した／指摘を受けた** | その失敗を防ぐ規定が**どこに要るか**。メモリで足りるか、ルールやスキルの手順が要るか |

**1行直しただけでも契機になります。** そのルールを読み返した時点で、隣に同じ主題が無いか・既定と重なっていないかが見えるためです。

守れなかったときに問うのは「次から気をつける」ではなく、**なぜ守られなかったか**。書き方が曖昧なのか、置き場所が悪いのか、そもそも不要なのか。原因に応じて書き直す・移す・消すのいずれかを選ぶ。**同じ逸脱が繰り返されるルールは、内容ではなく形に問題がある。**

### 学んだことを、どこに置くか

**失敗から学んだとき、メモリへ書いて終わりにしない。** メモリは読まれるが、**作業中に辿るのは手順のほう**なので、次に同じスキルを打てば同じ失敗をします。

置き場は「**次に同じ場面へ来たとき、何を見ているか**」で決める。

| 学んだこと | 置き場 |
| --- | --- |
| そのリポジトリ固有の事実（設計の前提・落とし穴） | **メモリ** |
| どのリポジトリでも効く振る舞いの規約 | **ルール** |
| **特定の作業中に必ず踏む判断** | **そのスキルの手順** |

**1つに決めきらなくてよい。** 事実はメモリ、判断の基準はルール、実行時の手順はスキル。同じ学びが3か所に分かれることがあります。ただし**同じ文を3回書かない**。片方だけ古くなります。

**「メモリに書いた」で止まったかを疑う。** 失敗の再発を防げるのは、**その場面で開くもの**に書いたときだけです。

### 置き場をまたぐ整理

**良い規定が1つのスキルにだけ書かれていると、そのスキルを呼んだときしか効きません。** 汎用のものを見つけたらルールへ引き上げる。

| 元の場所 | 引き上げる判断 |
| --- | --- |
| `skills/*/SKILL.md` | **その作業に固有か**を見る。固有でないならルールへ移す |
| `CLAUDE.md` | 「〜せよ」と読めるならルールへ。前提の記述ならそのまま |
| **auto memory** | **どのリポジトリでも効く好みならルールへ。移したら元は消す**（下記） |

引き上げたあとは、**元を消さずに「土台はルール」と参照を張る**。スキル側には固有の事情（ツールのレンダリング挙動、テンプレの構成）が残るので、丸ごと移すと失われる。

**ルールが土台、スキルが上乗せ。** 両方に同じことを書かず、差分だけを持たせる。

#### 逆方向も見る（ルールにあるのに、手順に落ちていない）

**引き上げだけでは片手落ちです。** ルールに書いてあっても、**そのとき呼ぶスキルの手順に無ければ実行時に落ちます**。ルールは読まれても、作業中に辿るのは手順のほうだからです。

| 症状 | 直し方 |
| --- | --- |
| ルールが求める作業が、対応するスキルの**手順に無い** | 手順として節を足す |
| スキルが**「〜してよい」「必要なら」**で書いている | ルールが求めているなら**手順へ格上げする** |
| スキルの `## 例外` に、ルールの本則が入っている | 例外から出す |

**「〜してよい」は最も見つけにくい形です。** 書いてあるので抜けに見えず、実際には毎回やらない理由になります。

**スキルとルールは、どちらを触っても対で見る。** ルールを足したら「これを実行するスキルの手順に入っているか」、スキルを直したら「土台のルールと食い違っていないか」を確かめる。

##### 対応するスキルが無いルールは、自分で手順を持つ

**上の表は「対応するスキルがある」前提です。** ところがルールの多くは、**特定のスキルから呼ばれるわけではありません**。書く場面が作業のあちこちに散っているためです。この場合、手順を落とす先がありません。

**そういうルールは、ルール自身が手順を持つ。** 判断基準だけ書いて手順を書かないと、**「何を書くか」は分かるが「いつ書くか」が決まらない**まま実行時に落ちます。

| ルールが要求すること | 手順が要る合図 |
| --- | --- |
| **2つの操作を対にする**（消したら別の場所へ置く、変えたら追随させる） | **2つが別のタイミングで動く**なら、順序を書く |
| **後から確かめる**（push 後・マージ後・CI 後） | **その時点では別のことを考えている**ので、いつ戻るかを書く |
| **先に控える**（消す前・上書きする前） | **失った後では再現できない** |

実際に「移ろう文脈は PR へ置く」というルールを守れませんでした。判断基準（どれを削るか）は明確でしたが、**削るのは編集中・置くのは push 後**という時間差に触れておらず、削った時点で作業が途切れています。

**「1つの作業にする」と書く。** 分かれていると片方だけで終わります。

##### 守られなかったときは、5つの型で当たる

**逸脱はルール側の欠陥を示す信号です**（上記「整理の契機」）。原因は次の5つに分かれ、**直す場所がそれぞれ違います**。

| 型 | 症状 | 直し方 |
| --- | --- | --- |
| **手順が無い** | 何を書くかは分かるが、**いつ書くか**が決まらない | 順序を書く（上記） |
| **記憶に依存している** | 「〜したとき」「前回〜なら」で条件を書いている | **その場で引ける形へ**（API・ファイル・コマンド） |
| **本則が読まれない位置にある** | 手前で判定手順が完結し、その先へ辿り着かない | **本則を冒頭へ出す**。節タイトルが本則と逆を向いていないか見る |
| **本文だけで効かない** | 規定はあるが、実行時に思い出せない | **`## 禁止する挙動` へも名指しで置く** |
| **数量の単位が書かれていない** | 「1度だけ」「毎回」「N 件まで」の**何につき**が抜けている | **単位を書く**（1 PR につき / 1相手につき / 1セッションにつき） |

**5つ目は、書いた側と読む側で単位が食い違います。** 「総括で1度だけ開く」を「1 PR につき1度」と読み、**同じ相手へ3本連続で出して**ようやく気づいた例があります。書いた側は「1相手につき」の意図でした。

**2つ目が最も見つけにくい。** 「対応後にもう一度呼ばれたとき」のような条件は自然に読めますが、**セッションが変われば前回を覚えていません**。**同じコマンドをいつ打っても同じように動くか**で判定する。

**4つ目は重複に見えます。** ところが本文は説明の流れの中にあり、`## 禁止する挙動` は**逸脱の一覧として引かれる**。役割が違うので、両方に置いてよい。

**判定の問いは「逸脱した瞬間、自分はどの節を開いていたか」。** その節に無ければ、そこへ置く。

**手順を順に辿る形の資産では、前半の節は通り過ぎた後です。** 投稿や実行の直前に開くのは、その段の手順と `## 禁止する挙動` だけ。**規約を読む段に書いてあっても、手を動かす段では視界に入っていません。**

##### 6つ目。文章を直しても止まらないなら、フックへ寄せる

**上の5つはすべて「書き方を直す」型です。** 直しても守られないなら、規約の側ではなく置き場を疑う。

| 見るもの | フックへ寄せる合図 |
| --- | --- |
| **判断が挟まる段があるか** | 「読む」と「守る」の間に「検査を回す」が入る。**そこで落ちる** |
| **出力が取り消せるか** | 外部へ出た後は、消しても記録が残る |
| **形だけで判定できるか** | 文字列やコマンドの形で決まるなら書ける |
| **書いた本人が直後に破ったか** | **手癖のほうが速い。** 思い出せないのではなく、思い出せるのに破る |

**1つ目が本体です。** 規約を読むのに判断は要らず、フックが弾くのにも要らない。**あいだの「検査を回す」だけに判断が挟まり、そこで落ちます。**

**4つ目は、上の5つの型で言う「本文だけで効かない」と対処が同じですが、症状が逆です。** あちらは実行時に思い出せない。こちらは**思い出せるのに破る**。禁止を書いた直後に自分が破ったなら、**文章を足しても止まりません**。

実際に、書式の規約を毎セッション全文読んだうえで投稿した PR 本文30件が、**30件とも違反**していました。同じ日に、投稿前に検査を回した3本は0件。**差は「回すと判断したか」の1段だけ**で、フックにするとその段が消えます。

**寄せる前に、過去の実出力へ当てて測る。** 違反が出ないならフックは要らないし、出た指摘が誤検知なら判定条件のほうが誤っている。

**測るのは「検査を回さなかった出力」だけ。** 回した分を混ぜると、要否そのものが測れません。上の例では、同じ規約・同じ検査条件で**正反対の結論**が出ます。

| 測った範囲 | 違反 | 出る結論 |
| --- | --- | --- |
| 検査を回した3本 | 0/3 | **要らない** |
| 回さなかった30件 | 30/30 | 要る |

**回した分が0件なのは、そのとき回したからです。** フックが埋めるのは「回すと判断しなかったとき」の穴なので、**判断が働いた出力はサンプルに選べません**。分けられないなら、検査の習慣が付く前の期間で切る。

**測る対象が1種類に偏っていないか見る。** 上の30件では PR テンプレートの HTML コメントによる誤検知が0件でしたが、**テンプレが全部英語だっただけ**でした。日本語のコメントで試すと弾きます。**件数が正しくても、探索範囲が覆っていなければ誤検知は出ないまま残ります**（ `verify_the_check_worked.md` ）。

**フックにしても規約は消さない。** deny の理由は結局その規約の文章で、消すと「ブロックされました」しか残りません。**フックが捕まえるのは列挙した形だけ**なので、書いていない形はルールが受け持ちます。

### auto memory との境界

auto memory（ `~/.claude/projects/<project>/memory/` ）は**自分が書く学習ノート**で、ルールは**ユーザーが承認した規約**です。`MEMORY.md` の索引は毎セッション読み込まれるので、**ルールと同じことを書けば同じ規約が2回ロードされます**。

| | ルール | auto memory |
| --- | --- | --- |
| 書き手 | ユーザーの承認を経て自分が書く | **自分が判断して書く** |
| 効く範囲 | **全リポジトリ** | そのリポジトリだけ |
| 内容 | 汎用の振る舞いの規約 | **そのリポジトリ固有の事実**（設計の前提・落とし穴・進行中の作業） |

**汎用の好みをメモリに書かない。** ルールへ引き上げてよいか尋ね、ルールにしたらメモリからは消す。**ここはスキルと違い「元を残して参照を張る」をしない**。どちらも常時ロードされるので、両方に残すと二重に読み込まれたうえ片方だけ古くなる。

**逆に、リポジトリ固有の事実をルールへ書かない。** それはメモリか、そのリポジトリの `.claude/rules/` の担当です。

**残すと判断したら、なぜ残すのかを1行添える。** ルールと主題が近いメモリは、次に整理する人が同じ判定をやり直します。**ルールに無い判定軸を名指しで書く**。「ユーザー指示由来も対象」「理由語で判定する」のように、どこが覆われていないかを示す。

**照合するのは主題ではなく判定軸。** 主題が同じでも、そのメモリだけが持つ判定の手順があれば別物です。原文を開かずに「近いから重複」と決めない。

## 分割・マージ・削除

見るのは次の3つ。

| 操作 | いつ | 何をする |
| --- | --- | --- |
| **分割** | 1ファイルに主題が2つ以上ある | 主題ごとに分け、`## 関連` で繋ぐ |
| **マージ** | 同じ主題が複数ファイルに散っている | 1つに寄せ、残りを消す。**近い主題を新設するより既存へ足す** |
| **削除** | そのルールが無くても挙動が変わらない | 消す。判断に迷うものは残し、**なぜ残すのかを1行添える** |

### 1つへ寄せるとき

**「寄せた」と「届いている」は別です。** 消す前に3つを確かめる。**ルールどうしでも、スキルからルールへでも、スキルどうしでも同じ**。

| 順 | やること | 見落とすと |
| --- | --- | --- |
| 1 | **消す行が寄せた先にあることを1つずつ照合する** | 寄せたつもりの規定が、どこにも無くなる |
| 2 | **元にしか無い規定を、固有として残す** | 場面を限定していた規定が、広い側の規定で上書きされる |
| 3 | **禁止の一覧から消したなら、なぜ書かないかを残す** | 消した跡が空白になり、**次に書き戻される** |

**2は「その規定が寄せた先にあると広すぎないか」で判定する。**

| 固有側に残るもの | 例 |
| --- | --- |
| **適用場面を限定するもの** | 「この経路だけ」「レビュー中は」／承認の範囲を狭める規定 |
| **例外の条件** | `## 例外` に書かれた限定 |
| **次の段の入力になるもの** | 後続の手順が使う値・対象の粒度 |

**部分的に書き直された規定は、どこかが欠けています。** 寄せると、寄せた先にしか無いものが全部に効くようになる。

### 削除の判断

グローバルルールには、**Claude Code の既定の挙動が足りない部分を埋めているもの**があります。アップデートで既定に取り込まれたら、その時点で消す。

既定に入ったかは、ツールの説明文・実際に外して試す・リリースノートで確かめる。**裏を取れないまま「もう既定に入った」と断定しない**（ `verify_before_asserting.md` ）。

既定より**厳しい**運用を求めるルール、既定が不安定で明文化しておくと守られやすいルールは残してよい。その旨を本文に書く。

**実行できないルールも消す。** 従いたくても自分の手で終えられない規定は、書いてあっても効かない（本スキルの「自分が実行できないことは規約にしない」）。

## 固有名は、判定に使う語にも残る

**「プロジェクト固有の事情を書かない」は、主題だけでなく発動条件にも掛かります。** 主題を汎用に書いても、**それが発動する条件が特定領域の語なら、その領域でしか効きません**。

実際に、並列レビューの分割軸は最初から言語非依存にしていたのに、観点を選ぶ条件に `N+1` `ループ内のクエリ` が残っていました。**軸は汎用、条件はサーバー側限定**という状態です。

| 見る場所 | 例 |
| --- | --- |
| 主題・軸 | 気づきやすい。「レイヤー別に分ける」→「ディレクトリの近さで分ける」 |
| **発動条件** | **見落とす。** 「〜が差分にある」「〜を触っているなら」の中身 |
| **例と対比** | **同じく見落とす。** 汎用の規定に、片方の領域の例だけを添えている |

**直し方は2つ。** 語を抽象化するか、**両方の領域を並べる**。

- 抽象化: `ループ内のクエリ・N+1` → `繰り返し処理・重い再計算`
- 並置: 「サーバー側なら N+1、画面側なら不要な再描画」

**並置のほうが実用的なことがあります。** 抽象語だけだと、読んだ側が自分の領域へ翻訳する手間が残るためです。

## どこに置くかの見立て

提案するときは**置き場所まで示す**。ユーザーが「どれにするか」ではなく「やるか否か」を判断できる形にする。

### まず範囲で振り分ける

**内容がグローバルならグローバル設定へ、そのリポジトリ固有ならプロジェクト設定へ置く。**

| 内容 | 置き場 | 例 |
| --- | --- | --- |
| **どのリポジトリでも効かせたい** | `~/.claude/` | コミットメッセージの書式、報告の粒度、レビュー対応の進め方 |
| **そのリポジトリだけで効く** | そのリポジトリの `.claude/` | ディレクトリ構成の規約、使用ライブラリの流儀、そのリポジトリ固有の点検手順 |

**判断は「どこで書いたか」ではなく「どこで効くか」。** プロジェクトの作業中に生まれた規約でも、内容が汎用ならグローバルへ置く。逆に、グローバル資産を整理していて出てきた話でも、特定リポジトリの事情ならプロジェクトへ置く。

迷ったら**プロジェクト側に倒す**。グローバルは毎セッション全文が展開されるので、関係ないリポジトリでも展開されるコストがかかる。後からグローバルへ上げるのは容易。

**プロジェクト固有の資産を促す仕組みは、その資産と同じ側に置く。** グローバルからプロジェクトのスキルやドキュメントを名指しすると、**それが無いリポジトリでは存在しないものを案内する**ことになります。

**「条件付きにすれば他リポジトリでも壊れない」は、置き場所が違うことの証拠です。** 回避策を足したくなったら、その時点で置き場所を疑う。

### 次に種類で振り分ける

| 性質 | 置き場 |
| --- | --- |
| 常に効かせたい振る舞いの規約 | `rules/*.md` |
| 呼ばれたときに踏む複数手順 | `skills/<name>/SKILL.md` |
| ツール実行に反応させたい自動処理 | `settings.json` の `hooks` |
| 知っていれば判断が変わる前提 | `CLAUDE.md` |

**プロジェクトのルールは `paths` で絞れる。** 特定のディレクトリやファイル種別でだけ効かせたいなら frontmatter に書く。グローバルルールに `paths` は効かない（ `rule_conventions.md` ）。

### 重複を見つけたら、効かせたい範囲で寄せる

**同じ規定が2か所にあると、片方だけ古くなります。** どちらを残すかは**いつ効いてほしいか**で決める。

| 効かせたい範囲 | 寄せる先 | 残す側 |
| --- | --- | --- |
| **どの作業でも** | **ルール** | スキルには固有の事情だけ残し、土台への参照を張る |
| **その作業を実行する間だけ** | **スキル** | ルールには置かない。呼ばれない場面で読む価値が無い |
| **必ず走らせたい** | **フック** | 規約は消さない。deny の理由がその文章になる |
| **知っていれば判断が変わる前提** | **`CLAUDE.md`** | 「〜せよ」と読めるならルールへ移す |

**判定は「呼ばれなくても効いてほしいか」。** 効いてほしいならルール、その場だけならスキル。

**フックは置き換えではなく上乗せです。** 判断が挟まる段を消しますが、**列挙した形しか捕まえない**ので、書いていない形はルールが受け持つ（ `rule_conventions.md` の「6つ目」）。

**メモリだけは参照を張らずに消す。** ルールもメモリも常時ロードされるので、両方に残すと同じ規約が2回読まれる（同上「auto memory との境界」）。

### 置き場は仕様を確認してから決める

**Claude Code の資産の種類と置き場は変わる。** 記憶で判断せず、[公式ドキュメント](https://code.claude.com/docs/en/features-overview)で毎回確かめる（ `verify_before_asserting.md` ）。

実際に起きた変更の例。

- **custom commands は skills へ統合された。** `commands/*.md` と `skills/<name>/SKILL.md` はどちらも `/name` を作る。既存は動き続けるが、**新規は skills に置く**
- `/output-style` コマンドは削除されたが、`output-styles/` ディレクトリは現役

確認するのは次の3点。

| 見るもの | なぜ |
| --- | --- |
| **その種類がまだ推奨されているか** | 統合・廃止された置き場に新規で足さないため |
| **より適した種類が増えていないか** | 手で書いていた手順が、機能として入っていることがある |
| **強制が要るなら hooks に寄せられないか** | ルールは読み飛ばされうるが、hooks は必ず走る。「毎回必ず」が要件なら hooks が正解 |

### 自分が実行できないことは規約にしない

**規約は自分が守るためのものです。** 従いたくても実行できない規定を書くと、自分には効かず、**残るのはユーザーの手作業を規約の形で増やしたことだけ**になります。

**「手段が存在する」と「自分が実行できる」は別です。** ここを取り違えると、調べた結果が逆向きの根拠になります。

| 確かめたこと | そこから言えること |
| --- | --- |
| その仕組みがリポジトリにある | **ユーザーが使える** |
| **自分の手元から動かせる** | **自分が使える** |

実際に、画面の変更に Before / After のスクリーンショットを並べる規定を書いて撤回しました。Storybook が入っていることは確かめましたが、**それはユーザーが開けるという意味**で、こちらから撮れるという意味ではありませんでした。

**判定は「その規定に従うとき、最後まで自分の手で終えられるか」。** 途中でユーザーに渡すことになるなら、それは規約ではなく**依頼**です。

**重い / 軽いで判断しない。** 手間の量は、実行できるかどうかとは別の軸です。

## 命名

`動詞-目的語` のケバブケース（ `create-pr` / `resolve-ai-reviews` / `review-tests` ）。**ユーザーがスラッシュコマンドとして打つ名前**なので、名前だけで何をするスキルか分かることを優先する。

| 見るもの | 判断 |
| --- | --- |
| **既存の動詞** | 同じ意味の動詞を新しく持ち込まない。`resolve` があるのに `apply` を足すと、どちらを打つのか毎回迷う |
| **対になるスキル** | 動詞を揃え、**差分だけを変える**（ `resolve-ai-reviews` ↔ `resolve-human-reviews` ）。並べたとき何が違うかが一目で分かる |
| **略語** | 既に定着しているものだけ（ `cp` ）。新しく略さない |

**新設する前に `ls ~/.claude/skills/` で既存の動詞を見る。** 名前を後から変えると、`## 関連` やスキル間の委譲、ユーザーの手の記憶まで追随が要る。

**単数と複数で「1件」と「横断」を書き分ける。** `finalize-pr` は1本、`finalize-prs` は担当する全部。
名前だけで対象の広さが分かるので、打つ前に迷わない。

## 引数の取り方

**同じ種類のスキルは、引数の取り方も揃える。** 揃っていないと、打つたびに順序を思い出すことになる。

| 種類 | 第1引数 |
| --- | --- |
| 特定の PR を扱う | **PR 番号 または URL**（省略時は現在のブランチから特定） |
| 横断で扱う | リポジトリ名（省略時は全部） |
| 差分やファイルを扱う | 対象（省略時はワーキングツリー差分） |

**裸の数値を PR 番号以外の意味で使わない。** 回数・件数・上限は **`--rounds N` のような名前付き**にする。
数値が2つ並ぶと**順序を間違えても通ってしまい**、スキル側では区別できない。

**`argument-hint` を必ず書く。** 引数を取らないスキルにも「引数なし」と書く。
無いと、渡せるのか渡せないのかが打つ側に分からない。**書式は `"[...]"` で揃える**（角括弧は省略可、山括弧は必須の意）。

**frontmatter と本文を食い違わせない。** `argument-hint` を変えたら、本文の引数解釈も同時に直す。
片方だけ直すと、**表示と挙動が食い違って原因が分かりにくい**バグになる。

**グローバルはグローバル間、プロジェクトはプロジェクト間で揃える。** 置き場をまたいで無理に合わせない。
プロジェクト側は扱う対象がリポジトリ固有なので、同じ形にならないことがある。

ルール名（ `rule_conventions.md`、スネークケース）とは別の体系。ルールは**何の規約か**、スキルは**何をするか**を名前にする。

## 新設したら、リンクを張って読めることを確かめる

**`home/.claude/skills/` へ置いただけでは呼べません。** `~/.claude/skills/` は**スキルを1本ずつシンボリックリンクで並べたディレクトリ**なので、新しい1本は張られていません。

```bash
D=$(cd ~/Documents/repositories/github.com/kotahashihama/dotfiles && pwd)
ln -s "$D/home/.claude/skills/<name>" "$HOME/.claude/skills/<name>"
```

**張ったら3つ確かめる。リンクの有無だけでは足りません。**

| 見るもの | なぜ |
| --- | --- |
| `[ -L ~/.claude/skills/<name> ]` | 張り忘れ |
| **`[ -r ~/.claude/skills/<name>/SKILL.md ]`** | **リンク先が壊れていても `-L` は真になる** |
| **存在しない名前で読めないこと** | **検査そのものが空振りしていないか**（陽性しか見ないと、常に真を返す検査に気づけない） |

**一覧に出るかは自分では観測できません。** システムから届く形なので、**別のセッションへ聞く**のが手立てです。

**リストアは通っています。** `scripts/lib.sh` の `PARTIAL_DIRS` に `.claude/skills` があり、新しいマシンでは自動で張られます。**壊れるのは動いているマシンだけ**です。

**常駐から出した規定をスキルへ移したときは、これを飛ばすと再編そのものが失敗します。** 実際に4本を移して張り忘れ、**どこからも読めない状態**を他セッションの指摘まで見逃しました。

## 委譲を書いたら、宛先がその内容を持っているか引く

**`〜が持ちます` と書いた時点では、まだ何も確かめていません。** 参照先が実在することと、そこに答えがあることは別です。

**名指しした語で宛先を引く。** 実際に「描き方は `/format-github-post` が持ちます」と書いたところ、あちらは `Mermaid` を4回出すのに**図の種類を1つも書いていませんでした**（ `sequenceDiagram` も `flowchart` も0件）。**参照切れの検査は通ります**。ファイルは実在するので。

**無ければ、条件を述べている側へ書く。** 宛先の主題がずれるなら足さない（あちらは手段の一覧で、「跨ぐなら」という条件を持っていない）。

**陰性対照も取る。** 存在しない語で0件になることを見ないと、**その語がどのファイルでも当たる**壊れ方を排除できません。**陽性対照は検査が動くかを見て、陰性対照は過剰でないかを見ます。** 委譲では後者が効きます。`sequenceDiagram` のような一般的な語ほど、別の理由で当たりえるためです。

## 手を入れたら全体を整理する

**スキルを追加・変更・削除したときが、棚卸しのタイミングです。** 定期的に見直す必要はありません。次を確かめ、整理まで済ませて1つの作業とする。

| 操作 | いつ | 何をする |
| --- | --- | --- |
| **分割** | 1スキルが複数の責務を抱えている | 責務ごとに分け、片方から他方へ委譲する |
| **マージ** | 同じ手順が複数スキルに重複している | 1つへ寄せ、残りは委譲に置き換える |
| **削除** | 既定の挙動や他スキルで代替でき、呼ばれなくなった | 消す。迷うものは残し、**なぜ残すのかを1行添える** |

**マージの手順は `/organize-rules` の「1つへ寄せるとき」が持つ。** ここには書かない。**照合・固有の残し・跡に理由**の3点は、ルールどうしでもスキルどうしでも同じ形なので、片方に書くと必ず古くなる。

### 削除の判断

グローバルスキルには、**Claude Code の既定の挙動が足りない部分を埋めているもの**があります。アップデートで既定に取り込まれたら、その時点で消す。手順の一部だけが取り込まれた場合は、その節を削って**残りに絞る**。

**該当することは稀です。** スキルは複数手順の組み立てや、そのユーザー固有の運用を束ねたもので、既定がそこまで代替することは多くありません。**「たぶん無い」前提で見て、あれば消す**くらいの重さでよい。

既定に入ったかは、ツールの説明文・実際にスキル無しで試す・リリースノートで確かめる。**裏を取れないまま「もう既定に入った」と断定しない**（ `verify_before_asserting.md` ）。

既定より**厳しい**手順を求めるスキル、既定が不安定で手順を固定しておきたいスキルは残してよい。その旨を本文に書く。

あわせて**委譲の整合**を見る。委譲先の手順を自前で再定義していないか、`## 関連` や本文の相互参照が実態と合っているか。**手順が2箇所に散ると、片方だけ直る事故が起きます。**

`## やってはいけないこと` に「この処理は別スキルの責務」と書いてあるなら、その委譲が実装されているかも確かめる。

## どちら側を触ったかで分かれる

`~/.claude/` の実体は dotfiles リポジトリで、**シンボリックリンク越しに編集しています**。

| 実体の置き場 | git | 編集後 |
| --- | --- | --- |
| `home/.claude/` （rules / skills / hooks / agents / settings.json / CLAUDE.md） | **管理下** | **コミットが要る** |
| `private/.claude/` と `private/.claude-memory/` （メモリ・社内固有名を含むスキル） | `.gitignore` 対象 | 不要 |

**どちら側かの見分け方は `no_internal_names_in_public_assets.md` が持ちます**（スキルは両側にあり、リンク越しでは判別できない）。**`private/` 側なら連絡は要りません。**

**`home/` 配下は公開リポジトリなので、社内固有名を書けません。** 何を書いてよいかは `no_internal_names_in_public_assets.md` が規定します。

**`home/` 側を編集したら、渡す前に固有名を走査する。** `pre-commit` は**ステージ後にしか走らない**ので、コミット担当へ渡す時点では未検査です。

```bash
python3 - <<'EOF'
import re, pathlib, os

# ~/.claude/settings.json はリンクなので、実体から親を遡れば dotfiles の外からでも見つかる
root = pathlib.Path(os.path.realpath(os.path.expanduser("~/.claude/settings.json")))
deny = next(p / "private/.claude/deny-patterns.txt" for p in root.parents
            if (p / "private/.claude/deny-patterns.txt").exists())
pats = [l.strip() for l in deny.read_text(encoding="utf-8").splitlines()
        if l.strip() and not l.startswith("#")]

for f in ["<編集したファイル>"]:
    t = pathlib.Path(os.path.expanduser(f)).read_text(encoding="utf-8")
    for p in pats:
        for m in re.finditer(p, t, re.I):
            print(f"NG {f} : {m.group(0)}")
EOF
```

**相対パスで書かない。** この走査を掛けるのは**他リポジトリで作業しているセッション**なので、dotfiles の作業ツリーにいません。

**0件が返ったら、非公開側のファイルへ同じ走査を掛ける。** 当たらなければ探し方が壊れています（ `verify_the_check_worked.md` ）。

**最も混じるのは例です**（ `no_internal_names_in_public_assets.md` ）。指摘を受けた本文をそのまま例にすると差分が主張を示すので実例が早いのですが、**固有名も一緒に乗ります**。実例を使うこと自体は正しく、**そのあと落とす段が抜ける**。

**それから、dotfiles のセッションが起動していないか `ListAgents` で確認する。**

- 起動していれば `SendMessage` で**何をどう編集したか**を伝えてコミットを促す（ `notify_related_repo_sessions.md` ）。向こうは編集したことを知らない
- 起動していなければ**ユーザーへ1行**添える。「dotfiles に未コミットの変更が N 件」で足りる
- **自分で dotfiles をコミットしない**（ `decide_or_ask.md` ）。作業中のリポジトリと別の履歴を勝手に作らない

**編集のたびに毎回連絡しない。** 一連の作業が一段落した時点でまとめて1回。細切れに送ると、向こうがコミット単位を切れなくなります。

**通達へ返信しても、永続化は終わりません。** 別のセッションから知らせを受けて編集したとき、**返信先がコミット担当とは限りません**。返信で完結した気になりやすいので、**返信先に関わらず dotfiles のセッションへ送る**。
